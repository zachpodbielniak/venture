* Knowledge bases

A knowledge base is a named set of documents the assistant is allowed to
read, searched by meaning rather than by keyword. More than one exists
because the useful question is rarely "what do we know" but "what do the API
docs say" --- and because a base is the unit of scope for retrieval. Asking
one base beats asking all of them the moment two of them disagree, which is
normal: last year's handbook and this year's both describe a real policy.

| Record           | What it is                                            |
|------------------+-------------------------------------------------------|
| =knowledge_base= | a named, slugged set of articles                      |
| =kb_article=     | one document, with its text and where it came from    |
| =kb_chunk=       | one embedded passage of an article                    |
| =kb_link=        | a computed connection to any other record             |

All four are ordinary record types, so they get REST CRUD, the web list and
form, =venturectl= subcommands, MCP tools and audit diffs from the same
registration everything else does. Nothing about them is special-cased.

* Why a passage and not a document

An article is longer than the model's context and, more to the point, longer
than the answer to a question. One vector per document finds the right
handbook and cannot say which paragraph; one per passage finds the paragraph.

The split follows headings first, because a heading is the author's own
statement about where one idea ends. Only a section too long to embed is
broken further, and then at a paragraph boundary, then a sentence, then a
space --- a cut mid-word is the last resort rather than the default.
Consecutive passages overlap by =kb.chunk_overlap= characters so that the one
sentence which answers the question is not the one that fell across a
boundary.

Each passage is embedded with its heading prepended. A paragraph reading
"it must be set before the first run" is unfindable on its own; under "API
tokens" it is not.

Sizes are in characters, not tokens, because the tokeniser belongs to the
model and we do not have it. They are targets rather than limits.

* The embedding model is not the chat model

=kb.embedding_provider= and =kb.embedding_model= are configured separately
from =ai.provider= and =ai.model=, and that separation is deliberate.

The assistant is whichever model writes well. The embedder is whichever model
the corpus was indexed with --- and only one of those can be changed freely.
Every stored vector was made by a particular model, so switching embedders
invalidates the index; switching chat models must not.

It also allows the arrangement most installs want: a hosted model for the
conversation, a local one for the documents, so the corpus never leaves the
machine.

#+begin_src yaml
kb:
  enabled: true
  embedding_provider: ollama          # or openai, for anything compatible
  embedding_url: http://127.0.0.1:11434
  embedding_model: nomic-embed-text:v1.5
  embedding_key_env: ""               # names the variable, never the key
  chunk_chars: 1200
  chunk_overlap: 200
  search_limit: 8
#+end_src

Embedding goes through ai-glib's =AiEmbedder=, implemented there by the
Ollama and OpenAI clients. The OpenAI shape is spoken by every compatible
server --- vLLM, LM Studio, llama.cpp, Together --- so pointing
=embedding_url= at one and naming its model needs no new code here.

** Vectors from two models cannot be compared

This is the trap the whole design is arranged around. The numbers are in
different spaces, and the cosine between them is not a weak match but noise
that reads exactly like one: a number in [-1, 1] that looks entirely
plausible and means nothing.

So the model is recorded in three places, and checked:

- on the *base*, which is claimed by the first model to index it. Indexing
  an article of that base with a different model is refused, naming both.
- on the *article*, so a reindex can skip what is already current.
- on the *chunk*, so a search skips any passage the configured model did not
  write rather than scoring it.

Changing =kb.embedding_model= therefore requires a forced reindex. That is
not a limitation to work around; it is the only correct response.

* Storage

A vector is base64 of little-endian float32 in a text column. Neither backend
has a vector type: SQLite has none, and the PostgreSQL one lives in an
extension this deployment does not install. JSON would have been the obvious
alternative and is four times the size for the same numbers.

Little-endian is named rather than native so a database moved between
architectures still reads back what it stored.

Search is brute-force cosine over the chunks of the bases asked for. At a few
thousand passages the arithmetic is microseconds and the query that reads
them costs more, so the index nobody can build is not yet missed --- and when
it is, this column is what an ANN index would be built from anyway.

* Indexing is synchronous, and bulk work is a command

Coding runs hold the only background thread in VENTURE and are forbidden from
touching the database: writing a record emits =entity-saved=, whose handler
enters podomation's nested main loop on the default context, and driving that
from a second thread is a context-ownership failure rather than merely a data
race.

So an article is embedded on the request that saved it, and anything larger
is an explicit command. There is no sweep that happens on its own.

Re-indexing an article *replaces* its passages inside one transaction. An
article that shrank would otherwise stay findable by text it no longer
contains, citing a document that has since been corrected. A failure part-way
leaves the previous index rather than none.

Chunks are purged rather than soft deleted. A chunk is derived from its
article and carries no history of its own --- the article's audit trail is
the one that matters --- and a soft-deleted chunk would still be read back by
the search that walks the table.

* What is searched

Only *published* articles. A draft is knowledge somebody is still deciding
about, and an assistant citing one is quoting a document its author has not
stood behind. Drafts are still embedded, so promoting one costs nothing.

Only bases marked *auto-retrieve*, when the caller names none. A base of
drafts, or one kept only for export, should not silently answer every
question, so participation is a property of the base rather than a default.
Naming a base explicitly searches it either way.

An unknown base slug is an error naming it, not a silent omission: somebody
who typed =#handbok= and got answers from everywhere else would reasonably
believe the handbook had been searched and had nothing to say.

* Getting documents in

Four kinds of input, and the differences matter:

| Input                     | What happens                                    |
|---------------------------+-------------------------------------------------|
| =.org= =.md= =.txt= =.html= | the file is the article, verbatim             |
| =.pdf= =.docx=            | text is extracted; the article holds the text   |
| =.zip= =.tar.gz= =.tgz=   | unpacked, and each file inside follows these rules |
| anything else             | skipped, with a note saying why                 |

The last is deliberate. A binary read as text produces a body of mojibake
that embeds to a vector, and a vector nobody can tell is meaningless is worse
than a missing one: it competes with real answers.

Text is *validated* as UTF-8, not repaired. Substituting replacement
characters silently changes what the document says, and the change is
invisible until somebody reads the passage it landed in.

An archive is recognised by its bytes rather than its name, so one uploaded
without an extension still unpacks and a =.zip= that is not one is stored
instead of fed to the unpacker. A =.docx= is also a zip and is deliberately
excluded: it is a document with a known extractor, and unpacking it would
file its XML parts as articles. Nesting is capped at three deep and the
entry count at =kb.max_archive_entries=, because a zip inside a zip inside a
zip is a zip bomb whether or not anybody meant it that way.

** Syncing a directory

Give a base a =source-path= and it can be brought into line with a directory
on the server:

#+begin_src sh
venturectl kb sync handbook
#+end_src

Change is detected by hashing the file's *bytes*, not its extracted text. A
PDF re-saved with identical text is therefore seen as changed, which is the
cheap direction to be wrong in --- the alternative pays the extraction cost
for every file on every sync just to decide it had nothing to do. An
unchanged file costs a hash and nothing else, which is what makes syncing a
large tree cheap enough to run often.

Dotfiles are skipped, so a checkout's =.git= does not become several thousand
articles.

An article whose file has gone is *archived*, not deleted. A file removed
from a checkout is usually a move, and destroying the article would take its
cross-references with it. Archived articles are not searched, so the
observable behaviour is the same and the mistake is recoverable --- and if
the file comes back, the article is published again.

** Exporting

#+begin_src sh
venturectl kb export handbook --format tar.gz > handbook.tar.gz
#+end_src

One file per article under =articles/=, named by slug and given the extension
its format exports as. A PDF exports as =.txt=, because what the article
holds is the extracted text and writing that under a =.pdf= name produces a
file nothing can open.

=manifest.json= carries what a plain file has nowhere to hold: the base's
description, and each article's status, tags, origin and source path. Without
it an export is a pile of text files that cannot be imported back into the
same shape.

The export is itself importable, which is the property worth having: an
export nobody can import is a backup that does not restore.

* Reaching it

Knowledge bases are ordinary record types, so =list kb_article=,
=get knowledge_base 1= and =create kb_article ...= work everywhere records
work --- REST, =venturectl=, the MCP tool surface. What follows is only the
part that is not CRUD.

** From the assistant

Two tools: =venture_kb_search=, which searches by meaning and returns
passages with the article and base they came from, and =venture_kb_list=,
which says what bases exist and what each is for.

The assistant is told to quote what it uses and name the article, and to say
when the passages do not answer the question rather than filling the gap from
memory.

** The =#= key, in the chat

Naming a base is an instruction rather than a hint:

#+begin_example
#venture_docs how do I add an API token?
#+end_example

The token is resolved and the retrieval happens *before* the model sees the
turn, so the passages arrive with the question instead of costing a tool call
to rediscover. Several bases can be named at once.

A =#= that is not a base is left alone: =#1=, =#tax2026= and a C preprocessor
line all appear in real questions, and refusing a message over one would be
absurd. It is only read as a base reference at a word boundary, so =C#= and
=issue#3= are not. But a token that *looks* like an attempt and matches
nothing is reported to the model, because silently searching nothing after
somebody typed =#handbok= reads as "the handbook has nothing to say".

** REST

| Method | Path                            | Role   |
|--------+---------------------------------+--------|
| =GET=  | =/api/v1/kb/search?q=&kb=&limit== | viewer |
| =POST= | =/api/v1/kb/:id/sync=           | editor |
| =POST= | =/api/v1/kb/:id/reindex?force== | editor |
| =GET=  | =/api/v1/kb/:id/export?format== | viewer |

=kb= is comma separated, so one request can scope to several bases the way
the chat's =#= tokens do.

Sync and reindex need the *editor* role rather than a session: a sync reads a
directory on the server and rewrites articles from it, which is a change to
what the assistant will tell everybody.

** venturectl

#+begin_src sh
venturectl kb search "how do I add an API token?" --kb venture_docs
venturectl kb sync 3
venturectl kb reindex           # every base; --force after a model change
venturectl kb export 3 --format tar.gz > docs.tar.gz
#+end_src

=kb search= finds meaning; =list kb_article search=...= matches characters
and will miss a passage that answers the question in different words. Both
are useful, for different questions.

* Cross-referencing

The point of the whole feature: an idea's page saying which passages of which
handbook bear on it, without anybody having filed the connection.

A record's text is embedded and compared against the corpus, and links above
=kb.crossref_min_score= are recorded as =kb_link= rows. Below that threshold
nothing is recorded at all --- a weak match is not a weak signal here.
With a corpus of any size everything matches everything a little, and a page
listing its ten least-irrelevant passages is worse than one listing none.

** Which records participate

Derived from the field table, not listed anywhere. A type declaring at least
one long text field has something to compare; one with only short strings ---
a ledger line, a tax category --- does not. That is the same declaration the
web form reads to choose a textarea over a one-line box, so a record type a
plugin registers next week is covered without a line changing here.

Four exclusions, each for its own reason:

- the knowledge-base types themselves, because cross-referencing an article
  against the corpus it belongs to finds itself
- users and API tokens, which carry credentials and nothing worth matching
- the audit log, which is a record of changes rather than a thing knowledge
  bears on
- chat threads and messages, which are per-user and not shared knowledge

A record's *short* string fields are left out of the comparison text as well.
Tags and an assignee say what a record is filed under rather than what it is
about, and including them pulls every record with the same assignee towards
the same passages.

Fields flagged =VENTURE_COLUMN_FLAG_SENSITIVE= are skipped even when they are
text. An embedding request is the AI, and the vector would outlive the
redaction --- nothing about a stored vector says what it was made from.

** When it runs

Never on its own. Each record costs an embedding request, so a sweep of a
populated install is minutes of them, and coding runs hold the only
background thread in VENTURE and may not touch the database --- there is
nowhere to hide the work. Making it a command means the operator chooses when
to pay:

#+begin_src sh
venturectl kb crossref idea 12
#+end_src

or the *Find related* button on the record's own page. Re-running replaces
that record's links rather than adding to them: a record whose description
was rewritten is about something else now, and keeping the old links would
cite passages for text that has gone.

Pages read the stored links rather than recomputing, so rendering costs a
query instead of an embedding request. The consequence is that links are as
old as the last cross-reference, which is why each one records when it was
computed.

* Writing an article from a record

#+begin_src sh
venturectl kb article research_note 7 --kb 2
#+end_src

For turning a research note, a resolved ticket or a closed deal into
something the assistant can find later. The article is built from the
record's own text --- its display name as the title, its long text fields as
the body --- rather than by asking a model to summarise it. A summary is a
second version of the truth, and this one is meant to be citable.

=origin-type= and =origin-id= record where it came from, so a second call
updates that article rather than making another. Generating twice from a
ticket that has since been resolved should correct the article, not leave two
versions for the assistant to choose between.

* In the browser

*Knowledge* in the sidebar (=/kb=) lists the bases and carries one search box
across them. It is a page of its own rather than only the generic
=/e/knowledge_base= list because searching by meaning is the one thing the
generic machinery cannot do: its list filter matches characters.

Each base row offers the three things its record form cannot express ---
sync, reindex and export. Everything else about a base or an article is the
ordinary generated form, because it is an ordinary record type.

Every eligible record's page grows a *Related knowledge* panel showing the
passages that bear on it, each with its score as a percentage. The score is
shown rather than hidden: a reader deciding whether to follow a link wants to
know whether it is a strong match or the weakest one that got past the
threshold.

That panel is hand-written rather than derived. =kb_link= names its subject by
type and id, so the generic related-records walk --- which keys on reference
fields --- would never find it. =kb_chunk= is excluded from that walk too,
for a different reason: it *does* reference =kb_article=, and an article's
page listing its own passages as "kb_chunk #1 … #47" is a wall of links that
say nothing.
