* Automation

VENTURE embeds [[https://gitlab.com/podomation][podomation]] as its automation engine. Rules are pods in
podomation's DSL, living in one file — =automations.pod= under the state
directory by default, =automation.pods_file= to move it — and the =venture=
module makes record changes into events and record operations into handlers.

* The Automations page

=/automations= is the whole loop in one place:

- *Status and pods.* Whether the engine runs and which pods loaded, from the
  engine's own accounting.
- *The rules editor.* Edits the live file with line numbers and diagnostics
  as you type. The diagnostics come from the same parser that loads the
  file — an error shown in the editor is exactly the error that would have
  broken the reload, with the offending line marked.
- *Save and reload.* Saving validates first and is refused if the source
  does not parse, so the running rules are never replaced with something
  broken. A successful save rebuilds the engine immediately.
- *The module reference.* Every loaded pod module, from live introspection
  rather than a list that drifts.

Viewing requires the admin role. Saving and reloading require owner: rules
execute code on the server — inline crispy and bash included — and that is
beyond data entry.

** Reload is a rebuild

A reload tears the engine down and rebuilds it from the file. Pods hold
timers, counters and circuit-breaker state, and parsing new rules into a
running engine would stack them beside the old ones — the bug that doubles
every automation side effect. Rebuilding from nothing is the only path where
what runs afterwards is exactly what the file says.

* Modules

The rules' vocabulary comes from podomation's modules -- =cron=, =timer=,
=log=, =http=, =ntfy= and around a hundred more -- plus VENTURE's own
=venture= module. They are installed alongside the server, and the
Automations page lists what is actually loaded rather than what the
documentation claims.

Check that list before writing a rule against a module name from
elsewhere: podomation's own documentation calls the cron module
=cron_event=, but the module registers itself as =cron=, and a rule using
the documented name parses cleanly and then refuses to load with "unknown
source module".

* The venture module

- *Events:* =on_created=, =on_updated= and =on_deleted= fire for every
  record change from every surface — web, API, CLI, AI. Plugins may register
  more, and raise them with =venture_automation_emit()=.
- *Handlers:* the built-ins below, plus whatever plugins registered — the
  same repository everything else uses.
- *Audit:* everything an automation writes is audited as the automation
  actor, so the trail always distinguishes a rule's change from a person's
  or the AI's.
- Audit entries never raise events, and neither does anything an
  automation does from inside a handler — a write or a plugin's event —
  which is what stops a rule that writes from triggering itself forever.

| Handler             | What it does                                    |
|---------------------+-------------------------------------------------|
| =query=, =count=    | Count the records of a type matching a filter   |
| =report=            | Run a report for a period and hand on its text  |
| =create=            | Create a record from =field=value= pairs        |
| =low_stock=         | Inventory items at or below their reorder point |
| =assets_run_period= | Post a period's depreciation                    |
| =mail_deliver=      | Deliver the mail that is due                    |
| =mail_sync=         | Fetch new mail from the mailboxes               |
| =recurring_run=     | Raise the recurring documents that are due      |
| =collections_run=   | Collect the payments that are due               |
| =bankfeed_sync=     | Fetch new bank transactions                     |
| =commerce_import=   | Import orders from the connected shops          |
| =report_packs_run=  | Deliver the report packs that are due           |
| =dunning_sweep=     | Send the overdue-invoice reminders              |
| =backups_run=       | Take the backups that are due                   |

** One registry, built-ins first

The handlers and events are not a list inside the module: they are the
context's =VentureAutomationHandlerRegistry=
(=venture_context_get_automation_handlers()=), which the module asks every
time a rule calls it. The built-ins above and the three record events are
registered first, when the context first hands the registry out; a plugin
registers after, and a name already held — a built-in's or another
plugin's — is refused, so what a rule does never depends on which plugin
loaded first. An unknown handler is still refused: from a pod with a
warning, from =venture_automation_invoke()= with an error naming every
handler that exists.

The registry lives on the context, not on the engine, for two reasons:
plugins load before the engine is built, and a reload rebuilds the engine —
a rebuild must not forget what a plugin added.

A plugin adds a handler or an event in C (see [[file:extending.org][Extending VENTURE]]), or, as an
exec plugin, names a handler in its manifest with the =automation_handler=
provides kind, which runs its program (see [[file:plugins.org][Plugins]]).

** Handlers stay synchronous

Every handler — built-in, a plugin's in C, an exec plugin's program — runs
on the main thread, inside the pod or invocation that called it. The engine
sets podomation's handler timeout to zero for this; a non-zero timeout
would run handlers on a worker thread while the main loop spins underneath,
and VENTURE's handlers write to the database and read a non-atomic cascade
guard. An exec handler therefore blocks the server for as long as its
program runs, bounded by its manifest's =timeout=.

** A plugin's events

#+begin_src
pod feeds = venture->new();
feeds->feed_finished => log->write_info("{event->source}: {event->rows} rows");
#+end_src

A plugin registers =feed_finished= and raises it with
=venture_automation_emit(context, "feed_finished", data, &error)=, where
=data= is an =a{sv}= a rule reads as =\{event->member\}=. An unregistered
event is refused, automation on or off, so a typo surfaces the first time;
the record events are refused, because only the database may say a record
was written. With automation off the emit succeeds and nothing happens.

* Worked examples

=data/examples/automations.pod= in the source tree, including the one that
matters for a business: the recurring expense.
=data/examples/clawtilla-triggers.pod= is the other shape: telling an outside
AI agent that a record changed, which needs no code in either project.
=tests/test-automation.c= parses every =.pod= in that directory with the real
parser, so a shipped example that does not load is a test failure rather than
a bug report from whoever copied it.

#+begin_src
pod monthly_hosting = cron->new("0 9 1 * *");
monthly_hosting->on_schedule => venture->create("expense",
        "description=VPS hosting", "vendor=Hosting Co", "amount=12.00",
        "category=software");
#+end_src

Hosting bills on the 1st whether you remember it or not; this makes the
books agree. The same shape covers subscriptions, retainers invoiced
monthly, and any other transaction that recurs on a clock rather than an
event.

* From the command line

The file is ordinary text; the page is a convenience, not a gatekeeper.
Edit it in cmacs, then either restart or press Reload on the page — the
reload button exists precisely for the file edited outside the browser.
