* VENTURE

An ERP and CRM in one, written in C on GLib/GObject, for running a portfolio of small business ventures rather than one company.

** The shape of the thing in one page

Everything derives from GObject properties. A record type is a field table; from that VENTURE builds the database table, the REST resource, the JSON and YAML serialisation, the web form, the AI tool schema, the audit diff and the CLI subcommands. Adding a field is a line; adding a record type is a registration.

Money is never a double. =VentureMoney= is an exact integer count of minor units plus a currency and its exponent. Every operation checks for overflow, rounding is half to even, splitting preserves the total exactly, and arithmetic across currencies is refused rather than guessed.

Nothing is deleted. Deletion stamps a time; the row stays, so a report over a past period still reconstructs and an accidental deletion is recoverable.

Everything is a module, and every module is a switch. The CRM, invoicing, the knowledge bases, the software factory: each is a named group of record types, reports, pages and services that a configuration turns off as one thing, and a module whose requirement is off is refused at startup rather than run half-working.

Any record links to any other. A =record_link= names both ends by type and id and carries a kind with an inverse, so a release points at the tickets it shipped and an incident at the deployment that caused it, on every record's page, through the API, the CLI and the AI.

Something outside can be told too. A webhook is a URL, a set of events and a signing secret; every audited change matching it is POSTed with an HMAC-SHA256 over the body, asynchronously so no write waits on somebody else's server, and every attempt is kept. Ten refusals in a row switch a dead endpoint off and say so.

You are told what matters, and only that. Every record's page has a Watch button and a timeline; a comment naming =@you=, a ticket handed to you, a change to something you follow, a service level about to be missed, a budget crossed or a run finishing lands in your inbox, fed by the audit trail so every door tells the same people the same things. Saved views keep a filtered list under a name; a service-level policy puts clocks on a ticket; a macro answers in one press; sprints burn down; forty records change in one transaction; and the coding runs have one screen, a cost, and a budget that refuses them before the money is gone.

Any page you want, you build. A dashboard is a grid of widgets — a count, a list, a report's figure, a breakdown, a note, a row of buttons — each a declarative question answered from any module's records or reports, rendered the same for the browser, the API and the assistant. There can be as many as you like; one can be home; a personal one is yours alone; and a dashboard exports as JSON that imports anywhere.

Outside prices come in, and stay. A data source names a provider -- built in, or added by a plugin in any runtime, a program included -- and a worker thread fetches it on a schedule it learns from the far end, through an origin allowlist, a budget and byte caps, into a SQLite file of its own outside the main database: every snapshot reduced as it lands to the latest price, a regional median and a deal price, hourly and daily history, odds and estimated sales. The Trading pages browse it, alert rules watch it, recipes and goals can price from it, and the arbitrage scan finds the flips, crafts and surebets in it -- net of each venue's fees -- and records the attempt as a trade whose legs post to the ledger and close into gains per currency. None of that thread touches the database; its results cross back to the main thread as plain data.

The AI reads freely and cannot write unsupervised. A tool call that would change a record stages a diff for approval instead; only approval applies it, and the applied write is audited with the prompt that caused it. Any REST write can do the same with =?stage=1=, so an outside agent proposes into the same queue and a person answers both from one page.

Two binaries, both statically linked against every vendored dependency: =venture= is the server, =venturectl= is the client. Either builds alone.
