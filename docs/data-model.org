* Data model

Every record derives from =VentureEntity= and carries the same spine:

| Field             | Purpose                                              |
|-------------------+------------------------------------------------------|
| =id=              | surrogate primary key; zero until first saved        |
| =uuid=            | stable external identifier, safe to expose           |
| =organization_id= | owning entity; scopes every query                    |
| =created_at=      | when the record first existed                        |
| =updated_at=      | when it last changed                                 |
| =version=         | optimistic concurrency counter                       |
| =deleted_at=      | soft deletion; the row is never removed              |
| =attributes=      | free-form JSON for one-off information               |

* The types

** Structure

- *organization* — a business or personal entity. Legal form drives tax
  treatment; personal bookkeeping lives alongside the businesses without
  mixing into their reports.
- *venture* — one thing you are doing. Its kind is a registry key, not an
  enum, so a new kind needs no rebuild.

** Catalogue

- *product* — with both =category= and =genre=, because a book's category on
  a store is rarely the genre you actually think in.
- *inventory_item* — reorder point, lead time, carrying cost.
- *inventory_txn* — a signed movement. Quantity on hand is their sum, never a
  stored field.

** Revenue

- *sale* — gross, discount, shipping in and out, fees, tax collected and
  remitted, refunds. =external_id= is indexed so re-importing a marketplace
  export cannot duplicate sales.

** Money

- *expense* — with a deductibility and a business-use percentage.
- *account* — a chart of accounts; five classes.
- *ledger_entry* — double-entry lines grouped by =transaction_id=.
- *tax_category* — default deductibility per category.

** Relations

- *contact*, *interaction*, *deal* — the CRM. A deal's weighted value is its
  value times probability, with a closed outcome overriding the stored
  probability.

** Growth

- *campaign*, *newsletter*, *subscriber*, *post*.

** Thinking

- *idea* — scored as opportunity × confidence ÷ effort, so a cheap idea of
  moderate promise outranks an expensive one of high promise. That is usually
  the right answer when the binding constraint is your own time.
- *research_note*, *document*.

** Work

- *ticket*, *ticket_comment* — internal tasks and external support requests,
  one shape. See the ticket section below.

** Billing

- *invoice*, *invoice_line* — money owed, distinct from money arrived. A
  line's amount is quantity × unit price, computed as an exact rational and
  rounded half to even — never stored, so it cannot disagree with its
  factors. The lifecycle is draft → sent → paid (void from anywhere
  unpaid; paid is terminal), and marking paid creates the sale with the
  invoice total as gross — the wiring that keeps invoicing and the books
  from quietly disagreeing about revenue. =/invoices/:id/print= renders the
  printable document.

** Conversations

- *chat_thread*, *chat_message* — AI conversations, stored as ordinary
  records so a thread survives restarts and resumes anywhere. Scoped to the
  account that had them: the chat routes serve only the caller's own
  threads, and the generic record surfaces for these two types are
  owner-only.

** Access

- *user*, *api_token*, *audit_entry*.

** Forge

- *forge*, *forge_repo*, *forge_rule*, *ticket_link*, *forge_run*.

A =forge= is a server you have an account on; it holds the access token and the webhook secret, and is owner-only everywhere for that reason. A =forge_repo= is one repository on it, named =owner/repo=. A =forge_rule= says what may happen automatically for a given repository and issue type. A =ticket_link= joins a ticket to a repository and carries the issue number, the branch and the pull request — one record rather than three fields on the ticket, because a ticket can be worked in two repositories at once. A =forge_run= is one attempt by a runner, and like the audit log it cannot be edited through the generic surfaces.

Tickets gained two fields: =issue-type= (epic, story, task, subtask, research, bug) and =repo-id=. The issue type is a different question from the existing =kind=: kind says whose problem it is and decides who may read the replies, the issue type says what shape the work is. An external bug is both. See [[file:forge.org][Git forges]].

* Adding a record type

In a header:

#+begin_src C
VENTURE_DECLARE_ENTITY(VentureWidget, venture_widget, WIDGET)
#+end_src

In a source file:

#+begin_src C
static const VentureFieldDecl venture_widget_fields[] = {
	VENTURE_FIELD_NAME("name", "Name", "What it is called"),
	VENTURE_FIELD_REF("venture-id", "Venture", NULL, "venture",
	                  VENTURE_COLUMN_FLAG_NOT_NULL),
	VENTURE_FIELD_MONEY("price", "Price", "What it sells for"),
	VENTURE_FIELD_ENUM("status", "Status", NULL,
	                   venture_task_status_get_type,
	                   VENTURE_COLUMN_FLAG_INDEXED)
};

VENTURE_DEFINE_ENTITY(VentureWidget, venture_widget, venture_widget_fields)
#+end_src

Then register it. That is the entire type: table, REST resource, JSON and
YAML, web list view, AI tools, audit diffs and CLI subcommands all follow.

** Field kinds

=string= =text= =integer= =double= =money= =boolean= =date= =datetime= =enum=
=reference= =json=

** Column flags

| Flag           | Effect                                                 |
|----------------+--------------------------------------------------------|
| =NOT_NULL=     | required; an empty string does not satisfy it          |
| =UNIQUE=       | uniqueness constraint                                  |
| =INDEXED=      | an index                                               |
| =IMMUTABLE=    | settable on insert, never on update                    |
| =SENSITIVE=    | never serialised to an API response, log, export or AI |
| =SEARCHABLE=   | included in free-text search                           |
| =TRANSIENT=    | computed; never persisted                              |

* Schema evolution

Adding a field is a non-event: the column appears on next startup, existing
rows get NULL, nothing is migrated by hand.

Removing or retyping a field is deliberately *not* automatic. Both destroy
data, and doing either silently on startup because someone renamed a field
would be indefensible. Those stay a deliberate migration.

* CRM: companies, contacts, deals

*Companies* are the outside businesses you deal with — customers, prospects,
suppliers, the marketplaces you sell on, partners. Distinct from *entities*,
which are the businesses you *are*. That distinction is easy to blur and
expensive to blur: one of them appears on your tax return.

A contact belongs to a company by reference rather than by name. The
free-text version could not answer "everything to do with this account",
which is the question a CRM exists for, and it spelled the same company three
ways across three records.

Deals and interactions carry a company as well as a contact, because people
move and accounts persist, and the pipeline is usually read by account.

** Every record has a detail page

=/e/<type>/<id>= shows a record's fields and, beneath them, *every record
that points at it* — a company's contacts, deals, tickets and interactions;
a contact's deals and tickets; a ticket's comments.

Those sections are derived from the reference metadata, not written out per
type. A company page grows a Tickets section the moment a ticket gains a
company field, and a record type that arrives from a plugin appears here for
free. Each section is labelled by the field that points back, because a type
can reference the same target twice — a ticket has both a parent and
children.

References render as links, so following a relationship is a click rather
than a search.

* Tickets

One record covers internal work and external support, because the work is
the same shape: something to do, in a state, assigned to somebody, with a
thread of comments. What differs is who raised it and who may read the
replies, and those are a field and a flag rather than two systems to keep in
step — which matters on the day a support request turns out to be a bug, and
the bug is the work.

| Field       | For                                                     |
|-------------+---------------------------------------------------------|
| =kind=      | =internal= (your work) or =external= (somebody's request) |
| =contact_id= | who raised it, for an external ticket                   |
| =company_id= | the account it came from                               |
| =parent_id= | a ticket this one is part of, so epics and split-out bugs stay connected |
| =resolution= | what was actually done about it                        |

Comments are their own records with an =internal= flag: a reply to the
customer and a note to yourself live in one ordered thread and stay tellable
apart.

** The board

=/tickets= is a kanban board grouped by status. Drag a card to move it;
column counts update as you go, and the position is remembered so a column
stays in the order you left it.

Cancelled is deliberately not a column — it is an outcome rather than a
stage, and a column nobody drags into only takes up room. Cancelled tickets
are still in the list view.

Every card also carries a status select and a *Move* button. That is not a
duplicate implementation: it is what a browser with scripting disabled uses,
and it posts the same endpoint the drag handler does, so the two cannot
disagree about what moving means.

Moving into =done= or =cancelled= stamps the resolution time, so "how long
did that take" is answerable without reading the audit log. Moving back out
clears it — a ticket that was reopened was not resolved.

Priority reads off the left edge of each card, so the urgent ones are
findable without reading a word.

** Views and filters

=/tickets?view=board= and =?view=list=, filtered by =kind=, =assignee= and
=venture_id=. The filters are links rather than a form, so any view you want
to keep is a URL you can bookmark.

Everything is scoped to the selected entity, like the rest of the UI.

* Entities

An entity is a business or a personal sphere you keep books for: "my side
business", "my personal stuff", an LLC, a trust. Every record belongs to
exactly one, and the entity picker at the top of the sidebar decides what you
are looking at.

Create one from the picker's *+ New entity*, or at =/e/organization/new=.
The legal form drives which tax treatment applies, so a personal entity and
an LLC are not the same thing to the tax report.

** Everything is scoped to the selected entity

Lists, the dashboard and reports all follow the picker. *All entities* shows
the portfolio at once, which is what you want for a net position and not what
you want when filing anything.

Every form carries an *Entity* select, defaulted to whichever entity is
selected. It is the field most likely to be wrong and least likely to be
noticed: a sale filed against the wrong business is a tax problem discovered
months later.

** Entities nest

An entity can name a parent, so "my side business" can hold the LLC that
trades under it. Selecting the parent rolls up everything beneath it, to any
depth; selecting the child shows only its own.

The picker indents children under their parent. A record still belongs to
exactly one entity — the hierarchy decides what is *shown* together, never
what a record is filed against, so a roll-up can never quietly move anything.

An entity whose parent has been deleted still appears at the top level rather
than vanishing, because the list is the only place you could fix it from.

** Managing them

=/entities= is the dedicated page: every entity with its legal form, its
parent, how many records it holds and which one is the default. Add one, make
another the default, or delete one. Admin or owner.

Deleting is refused, with a reason, when it would leave something broken:

| Refused when            | Because                                            |
|-------------------------+----------------------------------------------------|
| it is the only entity   | everything has to belong to something              |
| it is the default       | the default is where unattributed records land     |
| it holds other entities | they would be left pointing at something gone      |

When the entity still holds records, the delete form asks where they should
go rather than refusing outright — "fold my personal things into the
business" is the actual reason people delete an entity. The move and the
deletion happen in one transaction, and each moved record is audited
individually, so the log shows what moved rather than records quietly
changing hands.

The deletion is soft, like every other one here: the entity is hidden and
kept, because last year's figures still refer to it.

If you delete the entity you were looking at, the picker falls back to *All
entities* — otherwise the browser would keep asking for a scope that no
longer exists and show nothing, with no clue why.

* Adding and editing records

Every record type has a working form, reachable from *New* on its list page
and *Edit* on each row. Fields, their controls, their order and which are
required all come from the type's field table — the same metadata the
database schema, the REST API and the AI tools are built from.

That is what makes it worth the indirection: a record type gains a full form
the moment it is registered, including one that arrives from a plugin, with
nobody writing HTML for it.

| Field kind  | Control                                          |
|-------------+--------------------------------------------------|
| string      | a text box                                       |
| text        | a text area                                      |
| money       | a text box taking =12.34= or =12.34 USD=         |
| integer     | a number box                                     |
| boolean     | a checkbox                                       |
| date        | a date picker                                    |
| enum        | a select of the declared values                  |
| reference   | a select of the records it can point at          |

The control follows the kind the field table *declared*, not one recomputed
from its C type. That distinction is load-bearing: a long text field and a
short string field are both =G_TYPE_STRING=, so a recomputed kind turns every
Notes field into a one-line box. Field order is carried the same way, because
GObject returns properties in its own order rather than the declared one —
without it a list's first columns are whichever fields sort early, which in
practice meant seven empty ones.

A reference picker lists every candidate rather than a page of them: a picker
that silently omits the record you are looking for is worse than a long list,
and these tables are small by nature.

Sensitive fields — a tax identifier, a password hash — are never rendered
into a form. That is what the flag means, and a form is exactly where a
value would otherwise be echoed back to the browser.

Deleting is soft and says so: the record is hidden and kept, because a
deleted sale is still part of last quarter's figures.
