#+title: Planned activities and call history
#+description: The next action as a record, and a daily worklist

* Planned work and history

The =activities= module requires =crm=. An =activity= is something planned;
an =interaction= is what happened. Tasks, calls, meetings, email and followups
share the same field table, generated forms, REST resource, CLI and audit trail.
An =activity_type= names a reusable kind with a default duration in minutes
and an active flag. The duration is descriptive; selecting a type does not
currently stamp meeting times.

An activity belongs to one organization. It carries a subject, body, owner
(username), due time, optional meeting start and end, priority, status,
completion time and outcome. Contact, company and deal references create the
ordinary reverse panels on their pages. Each panel lists planned activities,
including an empty panel with a *New activity* link that prefills its relation.

=related_type= and =related_id= also accept an enabled registered company,
contact, deal, lead, ticket or invoice. Both must be supplied together, the
record must exist in the same organization, and a CRM relation fills its
ordinary reference. Lead registration belongs to the leads module; this
module neither declares nor creates leads. Optional CRM references must also
belong to the activity's organization.

* Completing and moving the next action

=VentureActivityService= owns completion. It saves =done= and =completed_at=,
records the outcome in an interaction when a contact, company, deal or lead
is related, and creates the next occurrence when recurrence is enabled. All
records and audit entries share one transaction. A refused interaction or
next occurrence leaves the original planned and writes no partial history.
=VentureActivityService::completing= is a =G_SIGNAL_RUN_LAST= veto signal,
emitted inside the transaction after version/status validation and before
writing. Its detached snapshot cannot change the action; the first returned
=GError= aborts it. Reentrant actions are refused.

Company-only, deal-only and lead-only interactions are permitted without
inventing a contact. The service preserves its caller's object and checks its version.

Generic writes setting =status=done= are refused, naming the service.
Completed activities cannot be edited to rewrite their completion. Deletion
is the normal soft deletion: retained history is not erased.

Snooze moves the due time and reminder to =until=, and moves a meeting's
start while preserving its duration. It rearms the reminder. Reassign changes
the owner; cancel keeps the row with =cancelled= status. These actions require
a planned activity. Owner strings follow the ticket assignee convention: an
unknown username can own work but has no inbox to notify.

| Surface | Completion |
|---------+------------|
| Web | *Done* on =/worklist= |
| REST | =POST /api/v1/activities/:id/complete= with ={"outcome":"Agreed next step"}= |
| CLI | =venturectl activity complete ID outcome=...= |
| Assistant | =venture_activity_complete=, staged unless autonomous |

REST completion accepts =?stage=1=. It stages an outcome and status change
without writing anything; approval calls the service against the original
version. A stale approval fails. A generic staged =status=done= update does
not gain completion authority. Snooze, reassign and cancel use the same REST
route with their verb, taking =until=, =owner=, or an empty object. These
three action endpoints refuse staging; ordinary editable fields can be
proposed with the generic staged record API.

Recurrence is =none=, =daily=, =weekly= or =monthly=. Completion advances
all supplied scheduling fields from their previous dates, once, rather than
from the completion time. It creates one planned successor with the same
owner and relations and no completion or reminder-delivery stamps. Monthly
advancement uses the start time, or the due time when no start is supplied,
as its anchor. Other timestamps retain their offsets so meeting duration
and reminder lead time survive month-end clipping. Calendar months clip
a day that does not exist in the next month; later occurrences advance from that clipped date. A recurring
activity needs a due or start time.

* My day and dashboards

=/worklist= shows the signed-in username's overdue, today and upcoming work
within the selected organization (the default organization when none is
selected). Queues use UTC calendar days: overdue is before today's midnight,
today ends at tomorrow's midnight, and upcoming includes undated work.

#+begin_src sh
venturectl activity list mine
venturectl activity list overdue
venturectl activity list today
venturectl list activity owner=alice status=planned
venturectl report worklist organization_id=1
#+end_src

The existing =venturectl activity TYPE ID= timeline command retains its
meaning. The =worklist= report is a current-week operational report, with
one row per owner: overdue, due today, due this week and done this week.
Weeks begin Monday in UTC. It exposes =activities_overdue= and
=activities_today= metrics. It uses the default organization unless
=organization_id= is supplied; it does not combine legal entities.

Dashboards can use the ordinary =count=, =list= and =upcoming= kinds with
=entity_type=activity=, =field=due_at= and
=filter=status=planned&owner={me}=. A =metric= widget can read the worklist
report's =activities_overdue= or =activities_today=. No special widget
renderer or alternate query engine is involved.

* Reminders and calendars

A due =remind_at= produces one inbox notification for the active user whose
username matches the owner in that organization. Delivery and =reminded_at=
are saved together, so repeating the sweep does not repeat the notification.
No matching active user leaves it pending. Snoozing explicitly rearms it.
A reentrant sweep from a notification callback is refused before it can
redeliver an in-flight reminder.
The bounded sweep runs on the worklist, inbox and ticket board and can be called explicitly:

=POST /api/v1/activities/sweep?organization_id=1=.

There is no background database thread and no mail delivery.

=GET /api/v1/activities.ics?owner=alice&organization_id=1= exports calls
and meetings with a start or due time. The authenticated export uses stable
UUID-based UIDs, UTC timestamps, CRLF lines, escaped text and UTF-8-safe
75-octet line folding. Each stored occurrence is a separate event; recurrence
is advanced by completion, so the export does not promise uncreated events.
This is an export, not a calendar synchronization protocol. Two-way
synchronization over CalDAV — the same UUID-based UIDs, pushed and pulled
— and the public scheduling link that books a meeting into this table are
the =calendar= module; see [[file:calendar.org][calendar sync]].

* Upgrade and verification

Field metadata adds activity tables when the module is enabled. The paired
migration adds an organization-scoped lookup index to the core notification
table, including when activities is disabled. It preserves existing CRM
history and creates no activities from old interactions.

=test-activities= exercises metadata, completion and recurring history,
generic completion refusal, transaction rollback after the first write,
snooze/reassign/cancel, two reminder sweeps, staged approval, calendar text,
the worklist report, related panels, CLI completion and route authentication.
PostgreSQL is supported by the shared repository; the default suite runs
SQLite and does not constitute a live PostgreSQL integration run.

An explicit CRM reference must continue to match the related subject when edited; changing only the explicit reference is refused so completion history cannot attach to a different customer.

Email is recorded as history here as well: the =mail_sync= module writes an
=interaction= of kind =email= on each matched contact for inbound mail, and
the outbox writes one with =outbound= set when a message is sent, so a
contact's timeline shows both directions. See [[file:mail.org][mail]],
section Inbound.

* Logging calls

*Log a call* appears among the generated actions on company, contact and
lead pages and on an activity of kind =call=. The same =log_call= action
is available through the ordinary REST action route, =venturectl act= and
the assistant's generic action tool. There is no telephony connection,
recording download, transcription request or provisioning side effect.

A planned call must name a verified lead, company, contact or deal before
=log_call= can record its CRM history. Legacy completion without a CRM
relation retains its previous behavior and creates no interaction.

The service creates a completed call activity for a CRM subject, or
completes the selected planned call. It writes exactly one linked
=interaction= of kind =call= and an optional planned followup in the same
transaction. The ordinary =completing= veto signal and recurrence machinery
are reused. A history, followup, validation or veto failure rolls back all
business rows and audit entries. The caller's input record stays unchanged.

#+begin_src sh
venturectl act company 1 log_call subject='Discovery call' owner=alice \
  call_direction=inbound call_duration=120 \
  call_occurred_at=2026-09-01T10:00:00Z call_outcome=callback \
  outcome='Send the estimate' call_followup_due_at=2026-09-02T10:00:00Z
#+end_src

=POST /api/v1/company/1/actions/log_call= accepts the same names in a JSON
object, with =call_duration= a JSON integer. Append =?stage=1= to use the
existing confirmation queue. Staging writes no history or followup;
approval rechecks the target version, current access and service rules.
A changed activity or CRM target makes the approval stale. Read-only roles
cannot log calls, and disabling activities removes the action's availability.
There is no public unauthenticated logging endpoint.

| Input | Meaning and defaults |
|-------+----------------------|
| =subject= | Required call title |
| =owner= | Username credited for this event; defaults to the existing activity owner, then the actor, then Unassigned |
| =call_direction= | Required =inbound= or =outbound= |
| =call_duration= | Required actual duration in seconds, from 0 through 86400 |
| =call_occurred_at= | Required actual timestamp, not in the future; independent of planned dates and the completion stamp |
| =call_outcome= | Required =reached=, =voicemail=, =no_answer= or =callback= |
| =outcome= | Optional narrative notes, distinct from the structured result, at most 4096 characters |
| =call_recording_url= | Optional stable HTTPS URL; no credentials, query string or fragment |
| =call_transcript= | Optional supplied transcript, at most 65536 characters |
| =call_followup_due_at= | Optional; creates one followup due no earlier than the call |
| =call_followup_owner= | Defaults to the call owner |
| =call_followup_subject= | Defaults to Follow up plus the call title |
| =call_followup_remind_at= | Defaults to due; must be between occurrence and due |
| =call_external_source= and =call_external_id= | Optional pair: authenticated adapter namespace/version and stable provider call identity |

Call inputs and generated forms share the record field metadata. Other
string inputs are bounded to 1024 characters. Recording addresses are
validated before entering a staged confirmation, with errors that disclose
no submitted credentials. A signed download URL with credential-bearing
query parameters is deliberately unsupported; store a stable authenticated
recording page instead. The server never fetches this address.

If a planned call recurs, its ordinary next occurrence is created too.
That recurrence and an explicitly requested followup are separate planned
items. Neither inherits the completed call's transcript, recording, replay
identity or linked historical evidence. Followups use the existing reminder
sweep and username ownership convention, including unknown usernames with
no inbox delivery.

** Replay, ownership and history

External identities are scoped by the activity's verified organization and
source namespace. The identity is an idempotency key, not authorization.
Future voice adapters must authenticate using an ordinary authorized
organization credential and keep the source/version and provider call ID
stable. No provider-specific webhook or telephony client is implemented.

An exact replay returns the original completed activity and creates no
second interaction, followup or recurrence. Reusing an identity with a
different normalized call payload returns a conflict. Without the external
pair, the service derives a =manual-v1= identity from the subject and
normalized call details, including the actual occurrence time. Submitting
those same details again therefore reuses history; two otherwise identical
calls need distinct actual timestamps or explicit external identities.
Deleted call identities remain reserved and cannot resurrect history.
A database uniqueness constraint enforces the organization-scoped identity;
the same external ID in another organization is independent.

Call evidence is service-owned. Generic CRUD cannot manufacture it or
rewrite a completed call, so owner attribution, duration and outcome remain
historical facts. Planned activity status and dates remain separate. Old
completed calls retain their original completion time and an =unknown=
structured outcome; the migration does not infer old durations or fabricate
interactions. Ordinary completion of a call records occurrence at completion
and preserves the historical outbound default; use *Log a call* to supply
actual occurrence, direction and result.

** Timelines, reporting and retention

Company, contact, lead and deal timelines include one summary for each
linked completed call. A lead-only call needs no invented contact. Timeline
summaries contain the title and narrative outcome, not recording addresses
or transcripts. Call content remains on its activity page under normal
organization and record access. Text is escaped when rendered. A related
record ID or caller-supplied organization cannot grant access to another
organization's content.

The =calls= report groups completed call activities by the owner frozen at
logging. It counts activity rows once, not both the activity and its linked
interaction or followup. It uses actual occurrence in the requested period,
with an inclusive start and exclusive end; historical calls without the new
occurrence field fall back to their completion stamp. It reports call count,
inbound/outbound counts, duration seconds and counts for each structured
outcome. Raw imported interactions without completed activities are not
silently treated as structured call logs. Organizations are never combined.

The existing =activity_churn= headline is a customer/cash-receipt churn
metric, not an interaction counter. Logging a phone call does not create a
cash receipt or alter that accounting definition. The =calls= report is the
call-activity evidence; this distinction prevents communication events from
changing financial churn arithmetic.

Recording links and transcripts are optional, retained CRM history with the
same access, audit and backup lifecycle as the completed activity. The
supported default is no automatic expiry. Soft deletion hides the active
record but retains evidence; it is not erasure of the database, audit or
backups. There is no claim of consent capture, automatic content retention
purging or provider-side recording deletion. Operators should store only
content their agreed retention policy permits and account for retained
audit/backup copies in that policy.

** Migration and verification

Paired migration =000490_call_history= checks the additive metadata-owned
fields when activities exists and tolerates a disabled module. The scoped
replay index comes from =VENTURE_COLUMN_FLAG_UNIQUE_ORGANIZATION= on the
service's identity digest. Migration preserves existing activities and
interactions, and backfills no invented call history.

The call tests in =test-activities= cover lead-only history and exact replay,
changed-payload conflict, bounded inputs and credential-address refusal,
transaction rollback after a failed followup, staged completion and stale
approval, occurrence-based counts, exactly one timeline event per call,
escaped transcript rendering and module switching. Run after building the
DEBUG server and CLI, because the suite executes the real CLI:

#+begin_src sh
make DEBUG=1
make DEBUG=1 test-one T=test-activities
#+end_src
