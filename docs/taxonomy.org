* Grouping things without writing C

Until this release a product's grouping was two free-text columns
(=category= and =subcategory=) and an inventory item's place was one
(=location=). Text cannot nest, cannot be renamed once for every row that
uses it, and cannot say that "Herbs" in one shop is not "Herbs" in another.
Four pieces replace it, all of them generic:

- =category= (core) :: one node of a tree any record type can be grouped
  by. A tree may be tied to one record type with =applies_to=: product
  groups, expense heads, a game economy's herbs and ore.
- =location= (sales) :: one node of a tree of places stock can be: a
  warehouse and its bins, a van, a character and the bank it keeps.
- =tags= :: a comma-separated, searchable string on =product=,
  =inventory_item= and =sale=, the same shape a ticket's tags have.
- Two more custom field kinds, =double= and =reference=, so any type --
  including a plugin's -- can carry a number that is not money and a link
  to a category (or anything else) with no C at all.

The old text columns stay. Imports, the =categories= report and older API
clients still write them, and nothing that reads them changes. Upgrading
built the trees from what they held (see [[*Upgrading][Upgrading]]); new work should set
the references.

* Categories

A category is a name and an optional parent. The path a person reads is
computed from the parents every time it is shown and is never stored:

#+begin_example
Materials                 (applies_to product)
├── Herbs                 path: "Materials / Herbs"
│   └── Rare              path: "Materials / Herbs / Rare"
└── Ore
Crafted
└── Potions
#+end_example

Renaming "Materials" to "Reagents" changes every path beneath it at once,
with no cascade and nothing rewritten -- which is the whole reason the path
is not a column.

** Fields

| Field         | Kind      | For                                                                      |
|---------------+-----------+--------------------------------------------------------------------------|
| =name=        | string    | this level's name: Herbs; required                                       |
| =parent_id=   | reference | the category this one sits under; 0 or blank is a top level              |
| =applies_to=  | string    | optional registered type name the tree groups, e.g. =product=; blank is any |
| =position=    | integer   | order among its siblings, lowest first                                   |
| =color=       | string    | accent used in the UI                                                    |
| =description= | text      | what belongs here                                                        |

=category= is a core type: it is always on, because any module's records
-- and any plugin's -- may be grouped by one.

** What the save refuses

Every writer passes through the same validators
(=src/core/venture-category.c=): the form, the API, an approved staged
change, the assistant and a plugin.

- *A loop.* A category cannot be its own parent, and cannot be moved under
  anything beneath it: "A under C" when C is under B under A is refused
  with "would close a loop". The schema has no foreign keys (by design), so
  this is the only thing that stops one.
- *A parent in another organization.* A tree spanning two organizations
  would show one's names on the other's pages.
- *Too deep.* At most =VENTURE_CATEGORY_MAX_DEPTH= (32) levels. Every walk
  up or down the tree stops there too, so a loop written behind the
  validator's back (hand-written SQL) ends a walk instead of hanging it.
- *An =applies_to= that is not a record type.* It is checked against every
  type ever registered (=venture_entity_registry_lookup_any()=), so a tree
  for a module that is switched off today can still be edited, and a
  plugin's type is valid the day it registers. It is stored lowercase and
  trimmed, the way the registry spells it.
- *A parent that groups a different type.* A child's =applies_to= must
  equal its parent's; blank ("any type") is not the same as =product=.
- *Changing =applies_to= under sub-categories.* The children would then
  disagree with their parent; move or change them first.

A parent that the category already had is left alone even if it has since
been deleted -- the rule every reference follows -- so a category under a
deleted parent can still be renamed.

** Records that point at a category

=product.category_id= is the one built-in reference today. A save that
*writes* a category reference is held to the tree's =applies_to=: a product
cannot be filed under a category whose tree groups expenses. This is found
from the field table, not from a list -- any reference field declared
against =category=, on any type including a plugin's, is checked the same
way. A category with a blank =applies_to= fits anything. A record keeping
the category it already had is not re-checked, so it stays editable after
its tree changes.

The category must also be in the record's own organization, and so must a
location any record points at (=inventory_item.location_id=, an
observation's, a session's -- again every reference declared against
=location=). The generic reference check only asks whether the target
exists for the writer, and somebody in two organizations sees both: a
product of one filed under the other's category would put the other's
names on this one's reports, and make a category report that a member of
only one organization cannot read at all.

The ordinary reference rules apply first: a category that does not exist
or is soft-deleted cannot be written into =category_id=.

** Paths, ancestors and subtrees

Three functions in =src/core/venture-category.h= read a tree. They take the
type, so the same code serves locations:

| Function                              | Answers                                                             |
|---------------------------------------+---------------------------------------------------------------------|
| =venture_category_path()=             | "Materials / Herbs / Rare", joined by =VENTURE_CATEGORY_PATH_SEPARATOR= |
| =venture_category_ancestor_at_depth()= | the ancestor at depth N (0 is the top); a shallower node is its own answer |
| =venture_category_descendants()=      | every live node beneath one, breadth first, optionally itself first |

=ancestor_at_depth= is what grouping "by category, two levels deep" needs:
"Materials / Herbs / Rare" at depth 1 is "Herbs", and a product filed
directly under "Materials" lands in the "Materials" group rather than
nowhere. =descendants= is what "in Materials, at any depth" needs: one
query per level, never one per node, and a deleted node is not in it.

** Where the path is shown, and where it is not

Pickers and list pages show a category's own =name=, not its path. A
record's display name comes from the entity class's =get_display_name=
virtual method, which has no database to walk parents with, and adding a
per-type presentation table is exactly what this codebase refuses. So two
categories called "Herbs" under different parents read the same in a
picker; give the level a distinguishing name, or use =position= to keep
siblings together. The path is available to any page, report or plugin
that has the database, through =venture_category_path()=.

* Locations

A location is a place stock can be, and places nest:

#+begin_example
Warehouse                (kind warehouse)
└── Aisle 3              (kind aisle)
    └── Bin 12           (kind bin)
Alt 1                    (kind character)
└── Bag                  (kind bag)
Guild bank               (kind bank)
#+end_example

** Fields

| Field         | Kind      | For                                                            |
|---------------+-----------+----------------------------------------------------------------|
| =name=        | string    | what you call the place; required                              |
| =parent_id=   | reference | the location this one is inside                                |
| =kind=        | string    | free text: warehouse, bin, shelf, van, character, bank         |
| =description= | text      |                                                                |
| =active=      | boolean   | still in use; an inactive place keeps its history              |

=kind= is free text on purpose: the set of kinds is whatever the
operator's world has, and an enum would need a rebuild to add "van".

=active= has no default a form can supply; a location made in a form is
inactive until the box is ticked, like a product's =active=. The ones the
upgrade made are active.

=location= belongs to the =sales= module with the inventory it describes.
The same validator as a category's refuses a loop, a parent in another
organization and a tree deeper than 32 levels; a location has no
=applies_to=.

** Inventory items

=inventory_item.location_id= points at a location, checked like any other
reference. =inventory_item.location= (now labelled "Location (text)") is
kept for the writers that still fill it. Two items of the same product in
two places are still two items -- that is how transfers between locations
work (see [[file:inventory.org][Inventory]]).

* Tags

=product=, =inventory_item= and =sale= carry =tags=: one string, comma
separated, marked searchable, so a free-text search on the list page or
=search= on the API finds a record by any of its tags. It is the same shape
as a ticket's or a contact's tags. Tags are for the ad-hoc grouping a tree
is too heavy for -- "farmable", "gift", "clearance".

#+begin_src sh
venturectl update product 12 tags=herb,farmable
venturectl list product search=farmable
#+end_src

* Custom fields that reference a record, and decimals

[[file:custom-fields.org][Custom fields]] gain two kinds:

- =double= :: a finite decimal ("12.5", "1e-3"). Not money: money has a
  currency and is never a double. Refused: text, and anything that
  overflows.
- =reference= :: a link to a record of the type named in the definition's
  options, ={"target":"category"}=. The target must be a registered type
  when the field is defined (any module, on or off).

A reference value is checked exactly as a built-in reference field is:

- it must be a positive record id;
- when *written*, the target must exist and not be soft-deleted; a target
  whose module is switched off is refused with the switch named;
- a value the record already held is left alone, so a record pointing at a
  since-deleted row stays editable;
- a =category= target is also held to its tree's =applies_to=.

The form draws a reference field as the ordinary picker (every live record
of the target type in the organization), and a double as a decimal input,
from the same renderer every built-in field uses.

#+begin_src sh
venturectl fields define record_type=product name=shelf kind=reference options='{"target":"location"}'
venturectl fields define record_type=product name=weight_kg kind=double
venturectl fields value record_type=product record_id=12 name=shelf value=3
#+end_src

This is how a type with no =category_id= of its own -- a plugin's record, a
=sale=, an =expense= -- is put in a category tree today: a custom
reference field targeting =category=.

* The sidebar

Categories and Locations are filed under a new *Operations* heading,
between Support and Build: the structure the rest of the pages hang their
records from, rather than money or people. Operations is the heading later
phases add sessions, goals and recipes to. See [[file:navigation.org][Navigation]].

* API and CLI

Both types are ordinary records: =/api/v1/category=, =/api/v1/location=,
=/e/category=, =/e/location=, and every generic =venturectl= verb.

#+begin_src sh
venturectl describe category
venturectl create category name=Materials applies_to=product
venturectl create category name=Herbs parent_id=1 applies_to=product
venturectl create product venture_id=1 name=Peacebloom category_id=2 tags=herb
venturectl create location name="Alt 1" kind=character active=true
venturectl create location name=Bag kind=bag parent_id=1 active=true
venturectl update inventory_item 7 location_id=2
#+end_src

A refusal is a validation error (=venturectl= exits 8) naming the rule: "would close a loop", "must group the same
records", "groups expense records, not product", "belongs to another
organization".

* Upgrading

Two migrations, paired for SQLite and PostgreSQL, run after the new
columns exist:

- =000695_inventory_locations= :: one top-level, active location per
  distinct (organization, trimmed =inventory_item.location=) -- deleted
  items included, so a restored item finds its place -- and each item's
  =location_id= set to it. Blank and NULL text are left unlinked.
- =000700_product_categories= :: one top-level category (=applies_to=
  =product=) per distinct (organization, trimmed =category=), one child
  per distinct =subcategory= seen with it, and each product's
  =category_id= set to its subcategory's row, or its category's when it
  has none. A subcategory with no category names no parent and stays text.

Neither touches the text columns. Both are guarded by =-- requires-table:=
on the table they read (=inventory_items=, =products=), which is absent
only when sales was never on and so held nothing to migrate. Sales switched
off after use still has those tables -- startup reconciles a disabled
module's existing tables -- but never gets a =locations= table, because
reconciliation does not create a hidden type's table; =000695= therefore
creates it with the columns the field table declares, and the backfill runs
now instead of being recorded as done and never run.
=/migrations/taxonomy-backfill= and =/migrations/taxonomy-sales-off= in
=tests/test-migrations.c= cover both paths, a restart, and the rows being
whole records the ORM reads back.

* Traps

- *The path is computed, never stored.* Do not add a =path= column or cache
  one on a record: renaming a parent would then need a cascade, and the
  one that is missed is the one a report shows. Call
  =venture_category_path()=.
- *=applies_to= is a string checked against the registry, not an enum.* An
  enum would need a rebuild for every new type and would refuse a plugin's.
- *The category-reference check is found from the field table.* Do not add
  a list of "types with a category"; declare a =VENTURE_FIELD_REF= to
  =category= and the check follows.
- *Walks are bounded and remember what they saw.* Anything new that walks
  a tree must do the same, or one hand-written loop in the table hangs a
  request.
- *The validator reads parents under a trusted scope.* A loop is a loop
  whoever is saving; a check the caller's access could blind would let one
  through.
