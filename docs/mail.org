#+title: Transactional mail

* Delivery semantics

The =mail= module requires =core=. =mail_message= is a durable outbox and
=mail_template= stores organization templates. Both use the generated record
surfaces. A nonempty =idempotency_key= is unique within its organization,
including soft-deleted history. Enqueueing the same key returns the same row.

The delivery contract is "at-least-once submission, at-most-once automatic
retry, operator-resolved uncertainty". This does not promise duplicate-free
SMTP delivery. A successful send means relay acceptance, not inbox delivery.

A sweep commits =sending= with a lease before attempting submission. A
definite failure before submission becomes =failed= with exponential backoff
(60 seconds, 120 seconds, and so on), then =dead= at the attempt limit.
A lost submission reply becomes =uncertain= and is never automatically
retried. An expired =sending= lease also becomes =uncertain=: a process crash
may have happened after the relay accepted the message. Deliberate retry
reuses the same row and Message-ID; receiving MTAs may deduplicate it.

* Enqueueing from another feature

=venture_mail_outbox_enqueue()= accepts an unsaved =VentureMailMessage= with
an exact organization, recipient, subject, text/HTML bodies and an
idempotency key. Call it inside the transaction that writes the source
record. It performs no network I/O. A delivery sweep must run after commit.

=VentureMailer= is a GInterface with synchronous and async send/finish
methods. =VentureLogMailer= records independent message snapshots in memory
and supports injected errors for tests. No test should send real mail.

The =sequence_delivery=, =billing_notice=, =quote_delivery= and =collection_notice= adapters each
read one source row, construct the message, use a source-type/id-derived
idempotency key and call enqueue. The source lane owns eligibility and
content; the outbox owns submission. Those source-row adapters remain a
cross-lane integration function, not additional SMTP implementations.

Service-generated invitations use the sensitive =private_text_body= field for their bearer link. Only the outbox enqueue service may create this content; stored messages remain immutable. Public record serialization, forms and audit omit it. SMTP sends this private text in place of both public body alternatives, so an HTML mail client cannot hide the access link. The protected content remains in the database for durable retries and must be treated as a credential in database backups.

* Templates

Templates substitute ={field}= values from a record's public JSON fields
into subject, text and HTML. HTML values are escaped. Unknown and sensitive
fields are refused, and a template cannot render a different organization's
record.

* SMTP configuration

#+begin_src yaml
mail:
  host: smtp.example.net
  port: 587
  security: starttls                 # starttls | tls | none
  username: accounts@example.net     # empty means no authentication
  password_env: VENTURE_SMTP_PASSWORD # NAME only; never a password
  from_address: accounts@example.net
  from_name: Accounts
  reply_to: support@example.net
#+end_src

Set the named variable in the server's environment. Authentication over
=none= is refused by mail-glib. TLS certificates are verified. The adapter
uses mail-glib's one-attempt delivery interface; GMime composes the MIME and
sets the durable Message-ID on the snapshot. Venture never implements SMTP.
SMTP errors are recorded as fixed, credential-free outcome descriptions.

The mailer reads a configuration snapshot when first requested. Restart the
server after changing SMTP settings. =venture_context_get_mailer()= and
=venture_context_get_mail_outbox()= return NULL when =modules.mail: false=.

* Operator commands

#+begin_src sh
venturectl mail test to=operator@example.net
venturectl mail send to=customer@example.net subject='Your receipt' body='Thank you.'
venturectl mail send to=customer@example.net subject='Your invoice' --html invoice.html
venturectl mail deliver --limit 100
venturectl mail list state=uncertain
venturectl mail retry 42
#+end_src

Supply =organization_id=N= for a legal entity other than the default.
=mail test= performs one immediate submission through the configured mailer.
=mail send= only enqueues. A =failed= row has a scheduled retry; an
=uncertain= row needs a deliberate operator decision. Retry restarts its
attempt budget, retaining its Message-ID and audit history. Mail rows cannot
be deleted, restored or purged, preserving their idempotency keys.

The generated web list is =/e/mail_message?state=uncertain=. The invoice
page's Send button issues a draft through the settlement service and queues
its HTML invoice, together with a nonfinancial =invoice_event= of kind
=mail_queued=. Repeated Send presses return the same message. SMTP failure
does not unissue the accounting document. The organization's =invoice=
mail template supplies the subject and introductory text/HTML; the invoice
line table and total follow it. The default template is saved on first use.

User creation with an email queues a welcome notice. A subsequent password
hash change queues a password-reset notification, with both writes in one
transaction. No password is mailed. This uses the existing authenticated
password-change/reset workflow; it does not add a public reset-token flow.
Users without an email are skipped.

* Scheduling

Run a bounded sweep for each organization every minute. This podomation rule
uses the same outbox service as REST and the CLI, on the main thread:

#+begin_src text
pod mail_minute = cron->new("* * * * *");
mail_minute->on_schedule => venture->mail_deliver("1", "100");
#+end_src

The arguments are organization ID and attempt limit. Add a rule for each
organization. Use a scheduled rule, after business transactions commit.

* Attachments and durable snapshots

=attachments= is a JSON field containing document references, for example
=[{"type":"document","id":42}]=. Each document must exist, be live and
belong to the message's organization. Its file must be under the server's
=state-dir/attachments/= directory. At enqueue time the outbox copies the
bytes and metadata into its retained message attributes. Later file edits or
removal cannot change a retry. The combined attachment limit is 20 MiB.
GMime encodes the attachment bytes; Bcc addresses stay envelope-only.

* API

- =POST /api/v1/mail/send=: message fields; returns the queued row (202).
- =POST /api/v1/mail/test=: =to=; one immediate test submission.
- =POST /api/v1/mail/deliver=: =organization_id= and =limit= (1–1000).
- =POST /api/v1/mail_messages/:id/retry=: deliberate retry, optional organization.
- =POST /api/v1/invoices/:id/send=: atomic issue/enqueue/event, returns the message.

Actions require editor access; generated lists require ordinary read access.
Mail actions refuse CLI =--stage=; use =--stage create mail_message= to stage
an enqueue through the generic record machinery. Delivery must run outside
any open database transaction, after all source writes commit.

* Upgrades and verification

The field tables add the mail tables and per-organization unique index.
The paired =000160_mail_outbox.sql= scripts verify that the uniqueness index
exists when its table exists, including upgrades with mail disabled. They do
not infer or send historical mail. Existing business rows are unchanged.

=test-mail= covers outbox states, retry exhaustion, retained keys, lease
expiry, template escaping, SMTP uncertainty and Message-ID/Bcc behavior over
a local socket, invoice/user consumers, atomic invoice/user rollback and attachment
snapshots. =test-mail-surfaces= exercises the real CLI against a private HTTP

=VentureMailerRegistry= owns named transport implementations. The context uses
its =smtp= slot; =venture_context_set_mailer()= replaces it for tests or plugins.
Async send completes on the initiating main context and never accesses the database.

SMTP tests enforce organization write authority and policy-plugin vetoes before invoking the mail transport, just as an outbox enqueue does.

* Inbound

The =mail_sync= module requires =mail=, =crm= and =leads= and suggests
=capture=. It owns =mail_account=, =mail_inbound= and
=mail_unmatched_sender=. =mail_account= is owner-only: the row names the
IMAP host and which environment variable holds the password, so an editor
who could change either could point the next sweep at a host they control
or name a different secret in the process environment. =mail_inbound= is
written by the sweep and refuses generic writes, like a webhook delivery.
=mail_unmatched_sender= stays ordinary CRM data.

An account names a mailbox address, IMAP host, port and security (=tls= or
=starttls=), username, the folders to watch, an optional capture address and
capture folder, and =secret_env=: the NAME of a =VENTURE_IMAP_*= environment
variable holding the password or app token. The row never holds the secret.
A name that is not =VENTURE_IMAP_= followed by letters, digits or underscores
is refused before any connection, so a row cannot exfiltrate
=VENTURE_SMTP_PASSWORD= or the session secret. A sync whose variable is unset
fails with a =VENTURE_ERROR_CONFIG= error naming that variable and never
opens a connection. Authentication over =none= is refused even when the
username is empty: this client always sends =LOGIN=.

=VentureMailSyncService= is the one service behind every surface. For each
watched folder it reads the stored high-water UID from =cursors=, asks the
transport for the UIDs above it, fetches each message and processes it in
its own transaction: the raw RFC 5322 bytes are filed as a =document= of kind
=email= under =state-dir/attachments/=, a =mail_inbound= row records the
folder, UID, Message-ID, thread root and what was created, and the cursor
advances. The =(account, folder, uid)= key is unique within the organization,
so a rerun against the same mailbox creates nothing even if a cursor write
was lost. A failure stops the sweep at that message and is recorded on the
account's =last_error=; the messages before it stay committed.

** Matching and threading

Every From, To and Cc address is normalised the way lead deduplication does
(=venture_lead_normalize_email()=: lower case, trimmed, +tag removed) and
compared with each contact's email. Each matched contact receives an
=interaction= of kind =email= carrying the contact's company, the subject,
the text body, the message date and =outbound= when the message came from
the account's own address. Threads are resolved by In-Reply-To and
References: a reply inherits the =thread_id= of the earliest known ancestor,
otherwise the oldest reference or its own Message-ID becomes the root, so
=/e/mail_inbound?thread_id=...= lists a conversation.

Addresses that match no contact create nothing on the CRM side. They are
upserted into =mail_unmatched_sender= with a count, the last subject and the
display name, listed at =/e/mail_unmatched_sender=. =POST
/api/v1/mail_unmatched_senders/:id/create_contact= creates the contact from
that row and removes it in the same transaction. The account's own address
is never a match nor an unmatched sender.

** Capture

A message addressed to the capture address, or sitting in the capture
folder, does not touch the timeline. Each attachment is filed as a
=document= of kind =receipt= with its SHA-256 =hash=, =extracted_text= for
textual attachments, and handed to
=venture_capture_service_ingest_for_organization()= with source =email=, the
subject as title, the sender as vendor, the message date and the body as
notes — the same path an upload takes, so conversion, period guards and
approvals are unchanged. A message with no attachment files its text body as
the receipt. An attachment whose content hash already backs a capture item in
the organization is skipped, so a receipt uploaded by hand and forwarded by
mail is one inbox row.

** Outbound on the timeline

When the outbox's delivery sweep records a message as =sent=, the same
transaction records an =email= interaction with =outbound= set on every
contact whose email matches a To or Cc recipient. The private text body is
never copied. Unknown recipients record nothing.

** Running it

#+begin_src sh
venturectl mail sync                     # every active account in the default organization
venturectl mail sync organization_id=2 limit=10
curl -X POST .../api/v1/mail/sync?organization_id=1
#+end_src

The sweep is bounded and synchronous, like the activities sweep: it runs on
the main thread, one account after another, and returns
={"accounts", "messages", "errors": [{"account", "error"}]}=. There is no
background thread; schedule it the way =mail deliver= is scheduled. The
action requires editor access and refuses =--stage=.

** Transport

=VentureImapClient= is a GInterface (connect, select, uids_after, fetch,
disconnect). =deps/mail-glib= is sending-only, so =VentureSocketImapClient=
in =src/mail/= is a minimal IMAP4rev1 client over GIO sockets: implicit TLS
or STARTTLS through GTlsClientConnection, =LOGIN=, =EXAMINE= (read-only;
nothing is flagged or moved), =UID SEARCH UID n:*= and =UID FETCH
(BODY.PEEK[])=. Literals larger than 20 MiB and control lines longer than
8 KiB are refused; a truncated =guint= size would otherwise overflow the
fetch buffer. Usernames, secrets and folder names containing CR or LF are
refused so they cannot inject a second IMAP command. Server response text is
never surfaced in errors, because a rejected LOGIN line carries the
credential. =VentureFakeImapClient= is an in-memory mailbox for tests; the
suite opens no sockets. GMime, already a server dependency through
mail-glib, parses the fetched bytes.

OAuth (XOAUTH2 for Google and Microsoft) would attach in
=VentureSocketImapClient= as a second authentication step selected by a
=secret_kind= on the account, with the token refresh living in a separate
service that writes the access token to the same secret source; nothing in
the sync service would change. Calendar synchronisation would be a sibling
=VentureCalendarClient= interface feeding the activities module the way this
one feeds interactions.
