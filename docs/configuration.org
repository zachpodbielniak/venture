* Configuration

#+begin_src sh
venture --generate-config > ~/.config/venture/config.yaml
#+end_src

* Layering

Applied in order, each overriding the last field by field:

1. defaults compiled into the binary
2. =/etc/venture/config.yaml=
3. =$XDG_CONFIG_HOME/venture/config.yaml=
4. the file named by =--config=
5. a compiled =config.c= beside whichever file was loaded last
6. =VENTURE_*= environment variables
7. command-line options

An unknown key is a warning, not an error — it is usually a setting from
another version, and refusing to start over one would be worse than carrying
on without it.

* Secrets

Secrets never live in the configuration. Every secret setting names an
environment variable instead, so a config file can be committed to a dotfiles
repository without thinking about it.

| Setting                        | Reads                     |
|--------------------------------+---------------------------|
| =security.session_secret_env=  | the session signing secret |
| =database.password_env=        | the database password      |
| =ai.api_key_env=               | the provider API key       |

Without a session secret one is generated at startup — secure, but sessions
end at every restart. The server says so rather than leaving you to guess.

** The database password

The connection URI is written without one:

#+begin_src yaml
database:
  uri: "postgres://venture@db.internal/venture"
  password_env: "VENTURE_DB_PASSWORD"
#+end_src

At startup VENTURE reads that variable and splices the value into the URI's
authority, URI-escaping it first — =openssl rand -base64= produces =/= and
=+= routinely, and both are structural in a URI.

This keeps the password out of the configuration file, out of =podman
inspect= output, and out of anything you might paste into a bug report. A
password already spelled out in the URI wins, so an explicit choice is never
overridden by a stray variable in the environment. SQLite URIs are left
alone: there is no authority to rewrite and mangling the path would break a
working default.

* Users, roles and passwords

There is no default password. On first start VENTURE creates the =owner=
account with a random one and prints it once:

#+begin_src bash
podman logs venture-dev | grep -A3 'owner account'
#+end_src

It is stored hashed, so it cannot be recovered afterwards. Lost it before
saving it? Delete the state directory and start again, or pass
=--owner-password= on a first run.

** Changing your own password

=/account=. It asks for the current password as well as the new one, even
though the session already proves who you are — that is what stops somebody
who walked up to an unlocked browser from locking you out of your own books.

** Signing out

The *Sign out* button is at the bottom of the sidebar, under the name of
whoever is signed in.

It ends the session on the server, not just in the browser. Session cookies
are signed rather than stored, so clearing the browser's copy is all a logout
can do on its own — anyone still holding a copy would stay signed in until it
expired. Signing out records a cut-off on the account and every session
issued before it is refused, which is what makes signing out on a shared
machine mean something.

That covers every session the account has open, not only the one that asked.
When the reason for signing out is that somebody else may have the cookie,
that is the useful behaviour.

** Managing users

=/users=, owner only. Add an account with a username, role and password;
change a role; deactivate somebody; reset a password without knowing the old
one, which is the point of a reset.

A deactivated account fails authentication before the password is even
compared, so deactivating is the way to remove access without deleting the
history that references the account.

** Roles

| Role      | May                                                        |
|-----------+------------------------------------------------------------|
| =owner=   | everything, including managing users and reading settings   |
| =admin=   | all data and settings; not user management                  |
| =editor=  | read and write business data                               |
| =viewer=  | read only                                                  |
| =service= | a non-human integration account                            |

Accounts and API tokens are administered by owners only, everywhere: the
=/users= page, =/e/user=, =/e/api_token= and their API equivalents all
require it. An editor able to add a user with =role: owner= — even one with
no password yet — would be a way to grant themselves access.

Only an owner may set a password, whether creating an account or changing an
existing one.

** The last owner

VENTURE refuses to demote or deactivate the only active owner. There is no
recovery from an install nobody can administer short of editing the database
by hand, and the mistake is one click. Promote somebody else first.

** Password policy

Length only, from =security.password_min_length=, eight by default. Set it
to =1= to turn the check off entirely.

Eight suits what this normally is: one operator, bound to loopback, behind
whatever already guards the machine. Raise it if you ever expose the port —
at that point the password is the only thing between a stranger and your
books, and the configuration validator's refusal to run without
authentication on a non-loopback address is the other half of that.

Length only, because composition rules — a digit, a symbol, mixed case — push
people towards short passwords they mangle to satisfy a checker. Length is
measured in characters rather than bytes, so a passphrase of accented
characters is not let through early for being non-ASCII.

** From the command line

A password is not an ordinary field: it is marked sensitive, so it never
appears in a response. It is accepted on write, and applied:

#+begin_src bash
venturectl create user username=alice display_name=Alice role=editor password='a long enough one'
#+end_src

Without this, that command would report success and produce an account that
could never log in. A new account is active unless =active=false= is given,
for the same reason.

* Environment variables

Any setting can be overridden. The name is the property uppercased with
underscores: =VENTURE_SERVER_PORT=, =VENTURE_AI_MODEL=,
=VENTURE_DATABASE_URI=. List settings take a comma-separated value.

* Validation

Checked before anything is opened, so a mistake is reported in a second
rather than after a database has been created in the wrong place.

The one hard rule: =security.require_auth: false= with a non-loopback
=server.bind_address= is refused. This API reads and rewrites financial
records and drives an AI that can do the same; serving it to a network with
no authentication is not a configuration choice.

Also refused: half-configured TLS (which would silently serve plain HTTP), a
port out of range, an unrecognised database scheme, a =postgres://= URI in a
build without libpq, a malformed currency, a fiscal month outside 1–12.

* Compiled C configuration

Some configuration is a decision, not a value. Put a =config.c= beside your
=config.yaml= and it is compiled with crispy at startup — cached by content
hash, so it costs a compile only after an edit — and its =venture_configure()=
runs last among the files:

#+begin_src C
#include <venture/venture.h>

gboolean
venture_configure(VentureConfig *config, GError **error)
{
	/* The production database on the server, a scratch one everywhere
	 * else, so one configuration works on every machine. */
	if (0 == g_strcmp0(g_get_host_name(), "workshop"))
		venture_config_set_database_uri(config,
			"postgres://venture@localhost/venture");

	/* An unattended run has nobody to approve a staged write. */
	if (NULL != g_getenv("VENTURE_UNATTENDED"))
		venture_config_set_ai_policy(config, VENTURE_AI_POLICY_AUTONOMOUS);

	return TRUE;
}
#+end_src

Return =FALSE= with =error= set to abort startup.

#+begin_src sh
venture --generate-c-config > ~/.config/venture/config.c
#+end_src

* Sections

- *server* — bind address, port, TLS, request limits
- *database* — URI, pool size, automatic migration
- *security* — authentication, sessions, password iterations, rate limit
- *locale* — currency, timezone, fiscal year start
- *ai* — provider, model, policy, auto-approved tools, prompt extras, and
  the confirmation queue (see below)
- *automation* — the pods file, module paths, shutdown timeout
- *plugins* — paths, crispy, declarative venture types
- *ui* — look (=classic= or =industrial=, the two designs; the default
  until a person picks one with the switch in the sidebar), theme
  (=system=, =light=, =dark= or =mocha=, the Catppuccin palette; the
  default until a person picks one with the toggle), accent,
  page size, the AI panel (=ui.chat_dock= gates the
  launcher and panel entirely; =ui.chat_dock_expanded= starts the panel open)
- *logging* — level, file, format
- *modules* — which modules are on; see below and [[file:modules.org][Modules]]
- *federation* — opt-in object sharing; see [[file:federation.org][Federation]]
- *mail* — the transactional SMTP relay and the operator allowlist for
  organization-bound SMTP accounts; see below
- *kb* — knowledge base chunking, search and import limits; the
  =embedding_*= keys are legacy hints, organizations bind providers
  explicitly
- *backup* — where scheduled backups go and how many are kept; see below
- *stripe*, *payroll*, *bankfeed*, *commerce*, *group* — one =enabled=
  switch each, off by default, equivalent to the =modules= entry
- *ocr* — the local OCR engine; see [[file:ocr.org][OCR]]
- *oidc* — organization sign-in, its issuer allowlist and loopback
  exception; see [[file:oidc.org][OIDC]]
- *imap*, *calendar*, *connectors* — operator allowlists for private
  mailbox and calendar connectors, deny by default; see
  [[file:connectors.org][Connectors]]
- *hosted* — the workspace binding and HTTP admission limits a hosted
  tenant process runs with; see [[file:hosted-workspaces.org][Hosted workspaces]]
- *docs* — where the rendered documentation site is read from; see below

Every setting is documented inline in the generated file; sections that
are off by default (=ocr=, =oidc=, =imap=, =calendar=, =connectors=,
=hosted=, =docs= and the opt-in module switches) appear there commented
out with their defaults, so uncommenting a key changes nothing until you
edit its value. The allowlists (=mail.allowed_endpoints=,
=imap.allowed_endpoints=, =calendar.allowed_origins= and
=oidc.allowed_issuers=) are deny by default: empty denies every endpoint
or issuer, so an organization-bound account cannot connect until its host
is listed.

** Modules

#+begin_src yaml
modules:
  crm: false
  factory:
    enabled: true
#+end_src

Each key is a module name; the value is a boolean or a mapping with =enabled=. A module nobody mentions is on. =VENTURE_MODULE_<NAME>=false= does the same from the environment, =--disable-module NAME= for one run, and =venture_config_set_module_enabled()= from a compiled C configuration.

Validation refuses a module whose requirement is off, naming both, before the database is opened. A name that is no module is refused once plugins have loaded, because a plugin can add one. =venture --list-modules= prints the resolved table without starting anything.

The older =ai.enabled=, =kb.enabled=, =automation.enabled=, =forge.enabled= and =plugins.enabled= keep working; both they and the module switch must be true. Prefer the =modules= section.

** The =ai.confirmation_*= settings are not only about AI

=ai.confirmation_ttl= (3600) is how long a proposed change waits for a
decision before it is dropped, and =ai.confirmation_limit= (200) is how many
may wait at once. Both govern the whole confirmation queue, which is also
where a REST write staged with =?stage=1= lands — the prefix is from when the
in-process assistant was the only thing that staged anything.

They are left named that way on purpose. Renaming a configuration key to tidy
up a prefix silently reverts every install that set the old one, and a queue
that quietly went back to an hour is exactly the sort of change nobody
notices until a card has vanished.

An install with =ai.enabled: false= still has a working queue and still
honours both settings. See [[file:api.org][Staging a write]].

** =ui.look=: the two designs

VENTURE ships two complete stylesheets and draws every page in one of them. =classic= is the editorial look it had first: serif titles, white cards on a bone canvas, hairline rules. =industrial= is the instrument panel: heavy uppercase headlines, monospace labels, hard one-pixel compartments, one red. Both carry all four themes, and every page, widget and plugin surface exists in both. See [[file:interface.org][The interface]].

The setting is the default. The switch at the bottom of the sidebar — labelled with the look it changes /to/ — sets a plain cookie for a year, and the server reads that cookie before it draws anything, so the choice survives sign-out and applies to the sign-in page too. The value is a closed set; a cookie edited by hand falls back to the configuration.

** What =ui.accent= actually controls

Less than the name suggests, and deliberately. Empty — the default — means each look keeps the accent it was drawn with: the classic look's blue (=#1f6c9f=) and the industrial look's hazard red (=#e61919=), which in that design has one meaning: look here. Set a hex colour and it applies in both looks. See [[file:interface.org][The interface]].

So the accent tints links, the focus ring, the active sidebar rail, the unread mark, the keyboard cursor and the landing ghost on a dashboard canvas. It does *not* fill primary buttons — those are ink on the ground, near-white in the dark theme and carbon in the light one, which is what keeps a page with a Save and a Cancel on it down to one solid rectangle.

The value reaches the page as =--accent-config=, and every other accent value is mixed from it: the hover shade, the soft wash behind an active row, and the brightened form the dark themes need against a dark ground. Set one hex colour and all three themes follow. Setting =--accent= directly would not work — the dark palette's own rule is more specific than the one the server emits, so a configured colour would apply in light mode and silently vanish in dark.

An operator may set another hue. In the industrial look negative readings — an overdue clock, a failed delivery — are drawn in the accent, so a configured blue makes "overdue" blue too. That is the trade the setting makes.

Status colours are not configurable. Positive, warning and informational each have a fixed colour and a matching wash, chosen per substrate, because they have to stay distinguishable from one another and from whatever accent an operator picks.

** Transactional mail

The =mail= section configures =host=, =port=, =security= (=starttls=, =tls= or
=none=), =username=, =password_env=, =from_address=, =from_name= and
=reply_to=. =password_env= is an environment variable name, never a literal
password. Empty username disables authentication. Disable the whole outbox
with =modules.mail: false=. Organization-bound SMTP accounts additionally
need their =host:port= listed in =allowed_endpoints= (empty denies all) and
may trust an operator-owned CA bundle through =tls_ca_file= (empty uses
system trust). See [[file:mail.org][transactional mail]].

** Scheduled backups

The =backup= section has two keys. =directory= (=backups=) is where a
=backup_schedule= that names no =destination= writes its files; a relative
path is under the state directory. =retention= (=7=) is how many successful
backups a schedule keeps when its own =retention= is zero. Both are
defaults a schedule overrides per row; neither turns scheduling on -- a
schedule is a record, and a sweep has to be called. See
[[file:backup.org][scheduled backups]].
** The documentation site

The =docs= section has one setting, =site_dir= (=VENTURE_DOCS_SITE_DIR=,
=docs-site-dir= on the object): the directory whose top-level files
=/docs= serves. It defaults to =$(VENTUREDATADIR)/docs-site=, where =make
install= puts the rendered site; =make run=, =just start= and the demo
point it at the tree's =build/docs-site=. Render the site with =make
docs-site= or =venturectl docs build=; the server reads it and never
writes it. =modules.docs: false= switches =/docs= off. See
[[file:docs-site.org][The documentation site]].

* HTTP receive and connection limits

These startup settings apply to every route before application dispatch, including
new plugin routes, generic record writes and anonymous endpoints. They do not
change health authentication or the hosted Host/origin/lifecycle checks for
accepted requests. Changes require a restart; runtime configuration notifications
do not alter the transport budget of existing connections.

| Server setting | Default | Accepted range and meaning |
| =max_request_size_mb= | 32 | 1..1024 MiB per received body |
| =max_buffered_request_mb= | 64 | At least one maximum body, up to 4096 MiB within the platform address space; aggregate bodies awaiting dispatch |
| =max_connections= | 128 | 1..4096 accepted connections on this workspace listener |
| =request_timeout= | 60 | 1..3600 seconds; absolute receive deadline and keep-alive idle deadline |

Invalid limits fail before the server executable opens its database or creates a
workspace binding. Embedded server construction validates before initializing its
workspace as well. The receive clock starts when a connection is accepted,
including a stalled TLS handshake, and again when a keep-alive request begins.
Receiving a byte does not reset that deadline. An idle connection gets a fresh
idle deadline after its response finishes.

A declared oversized length is refused early; malformed negative lengths receive HTTP 400. Chunked and ordinary bodies share
the same count of actual received bytes; Content-Length is not a substitute for
that count. VENTURE disables libsoup's automatic accumulation, retains checked
chunks only, and restores the completed body for its ordinary metadata-driven
handlers. Body overflow returns HTTP 413. Aggregate receive-budget exhaustion
returns HTTP 503 with Retry-After; partial bodies never reach a handler. Credits
are released on dispatch, disconnect, abort or timeout. A parsed slow request
receives HTTP 408. Error writes and TLS close-notify share a further one-second
bound. Rejected connections close and cannot be reused for pipelined writes.

Before a complete header or TLS handshake exists, or when connection slots are
full, the transport closes without promising an HTTP response. TCP resets are
possible when a rejected peer continues sending unread data. Normal HTTPS errors
are written through the retained TLS stream, never as plaintext on a TLS socket.
The supported upstream protocol is HTTP/1; experimental =SOUP_SERVER_HTTP2=
causes startup refusal. Terminate HTTP/2 at the gateway.

The aggregate budget covers bodies waiting to enter application dispatch. It is
not a total process-memory ceiling: libsoup headers/framing, body flattening,
active handlers, response buffers and provider work consume additional memory.
The inspected libsoup 3.6.6 implementation also bounds a received HTTP/1 header block at
100 KiB. The connection cap includes idle connections and incomplete handshakes;
it is independent for each workspace server. Use the platform memory/CPU limits
and lower budgets when sizing a workspace.

The receive deadline does not preempt a synchronous handler, cancel committed
business work, bound an SSE response lifetime, or replace provider-specific
timeouts. A blocked main context can delay timer delivery. Keep gateway limits
for total connections, TLS/HTTP parsing, rate/fairness, request and response time,
and process supervision; keep the application's separate dispatch admission
control and bounded service operations. No gateway performance or hostile-load
capacity claim follows from these transport regression tests.

Implementation uses the public libsoup [[https://libsoup.gnome.org/libsoup-3.0/signal.Server.request-started.html][request-started]] and
[[https://libsoup.gnome.org/libsoup-3.0/signal.ServerMessage.got-chunk.html][got-chunk]] signals, preserving the one application router.
See [[file:http-limits-demonstration.org][the built-server demonstration]] for observable rejection,
ordinary writes, TLS, timeout and neighboring-listener behavior.
