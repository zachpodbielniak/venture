#+title: Organization access
#+description: Organization membership and record ownership

* Access records

The =orgaccess= module requires =core= and is on by default. It declares
=organization_membership=, =team= and =team_membership= as ordinary records.
An organization membership names a user and a role and can be deactivated.
There is one membership per user and organization, including inactive and
soft-deleted rows. Reactivate the existing membership when access resumes.
A team belongs to one organization; a user can belong to several teams.

Companies, contacts, deals, tickets and ventures carry =owner_user_id= and
an optional =team_id=. These are references, so generated forms, REST and
=venturectl describe= expose the same fields.

* Upgrade

The paired =000180_orgaccess.sql= migrations preserve each existing owner's
access by adding owner memberships in all existing, live organizations.
Other global roles receive no implicit memberships. The migration retains
its access tables even when the module is disabled during upgrade, so an
owner backfill is not lost by switching the module on later. Migration
history prevents a subsequent restart from granting revoked access again.

=test-orgaccess= covers generated fields, membership uniqueness, the module
switch, and upgrading populated user and organization tables and restarting.

* Request boundary

=VentureAccessPolicy= is shared by the repository. A synchronous request
scope carries a copy of its principal, restores the previous scope on exit,
and never remains active while an asynchronous response waits. The repository
checks individual reads and both the stored and proposed versions of writes.
Queries filter before pagination, and counts ignore pagination. These checks
also constrain records loaded by reports, widgets and reference pickers.

Global owners and admins retain their data authority. Other users require an
active membership in the record's exact organization; a parent organization
is a presentation hierarchy and never grants a child's membership. Finance
modules mark their types as financial class metadata; modules transitively requiring =finance= inherit this restriction, including plugin modules. Those types require
organization finance, admin or owner authority. Sales, support and viewer
members read assigned records or records attached to their assigned venture;
team ownership requires a team and active team membership in the same
organization. A viewer cannot apply writes.

The =decide= signal runs after built-in checks, with =G_SIGNAL_RUN_LAST=.
Handlers return an owned =GError= to veto; the first veto stops emission.
Returning NULL cannot override a built-in refusal.

Token membership snapshots are captured on creation and intersected with
current membership authority. A later grant or promotion cannot expand an
existing token. Legacy non-admin tokens with no snapshot need rotation.
The initial owner and their memberships are created in one transaction.

* Role matrix

Global owner/admin retain their existing bypass. All other global roles
still face the existing type and action restrictions, in addition to this
matrix for their exact organization membership. "Assigned" means direct
owner, active team member, or a child of an assigned venture.

| Organization role | Business read/export | Business write/delete | Financial read/export/write/delete | Access administration |
|-------------------+----------------------+-----------------------+------------------------------------+-----------------------|
| owner             | all                  | all                   | all                                | write/delete          |
| admin             | all                  | all                   | all                                | write/delete          |
| editor            | all                  | all                   | denied; may propose journal post   | read only             |
| finance           | all                  | all                   | all                                | read only             |
| sales             | assigned             | assigned              | denied                             | read only             |
| support           | assigned             | assigned              | denied                             | read only             |
| viewer            | assigned             | propose creation only | denied; proposals need approval    | read only             |
| accountant        | empty/404            | 404                   | read/export only; writes refused naming the role | empty/404 |
| no membership     | empty/404            | 404                   | empty/404                          | empty/404             |

Members can read their organization's row for the picker. Membership does
not inherit through =parent_id=. Personal chat, watch and notification
records declare a personal owner reference in their field table and keep
that user's boundary. This describes access to whole records; it does not
introduce field permissions.

Organization membership, including organization owner or admin, cannot grant access to another user's personal record. Global administrator authority remains unchanged.

Watch and notification rows also require current read access to their referenced business record, so retained labels and excerpts do not expose revoked access through the inbox.

A type-level action performed at ID 0 with no declared subject record --
the dunning sweep, a recurring or collections run, a batch create -- is
checked as a new record of its type in the organization its
=organization_id= parameter names. =venture_action_prepare_target()= places
the placeholder there on every path that checks an action (direct, staged,
approved) and the action runs in that organization. A member who is not a
global owner or admin and names none is refused with a validation error on
=organization_id= (=venture_action_require_organization()=) rather than the
policy's "No such record"; global administrators and internal jobs keep the
default organization. =/orgaccess/type-level-actions= pins the matrix: the
organization's finance member may, a member of another organization gets
404, an organization editor on a financial type gets 403.

Filters supplied by callers only narrow access. The current implementation
filters candidate records before applying offset and limit; its cost grows
with the candidate set. Reports and plugins must use the repository's typed
read methods, not raw SQL, for user-requested data. Internal jobs without a
request principal retain their service authority; a new user-facing tool must
enter a policy scope with its caller, as the built-in assistant tools do.

Database audit, save, delete and transaction notifications invoke trusted service consumers independently of the triggering request's read scope, preserving notifications to other users and configured automation. Delayed webhook delivery and coding-progress callbacks likewise restore service authority before updating their records.

* The accountant role

An outside accountant is invited the way any user is: the global owner
creates the =user= (global role =viewer=, so nothing outside an organisation
opens to them) and an organisation owner or admin creates an
=organization_membership= with role =accountant=, from the generated form,
=POST /api/v1/organization_membership= or =venturectl create
organization_membership=. A CPA with several clients holds one accountant
membership per client organisation; the entity picker lists exactly those,
switching narrows every read to the chosen client, and deactivating one
membership removes that client alone. Tokens minted while the user was an
accountant keep that snapshot: a later promotion cannot widen what the
token can do. The global role check still runs first, as for every member:
a global viewer's write over REST falls at "needs the editor role" before
the membership is consulted, and promoting the accountant to global
=editor= only changes which refusal they read — the membership then
refuses the same write naming the accountant role, and CRM stays not
found.

The books, as this role sees them, are every record type owned by a module
that requires =finance= — ledger accounts, journals and lines, invoices and
receivables, bills and payables, bank accounts and statements, tax codes,
filings and 1099 packs, fixed assets, saved reports and scheduled packs,
fiscal years and periods — except payroll, plus the organisation row for
the picker, =company= rows because aging and 1099 summaries name customers
and vendors, and =document= rows attached to an expense. Reads and exports
of those succeed; every =write= and =delete= is refused with a
=VENTURE_ERROR_PERMISSION_DENIED= whose message names the accountant role,
before any row is touched, and the role never proposes a change for
approval. Everything else — leads, deals, activities, tickets, mail,
sequences, contacts, sales, dashboards, saved views, webhooks, plugin
settings, teams, memberships and other users — does not exist: reads and
writes alike answer =VENTURE_ERROR_NOT_FOUND=, the same as for a stranger,
so a 403 never confirms a record. The accountant's own =user= row stays
readable for the account page and sign-out.

On the web an accountant-only user lands on =/books= from =/= and the
sidebar offers Books alone (see [[file:reporting.org][the year-end pack]]).
=test-accountant= proves each of these rules, refusals included.

* Proposals and posting

An organization viewer can propose a new record through the form or REST;
these requests return 202 and enter the shared confirmation queue. Existing
global role checks still apply. A viewer cannot update an existing record.
The same authority check constrains assistant tools, including autonomous
mode. Confirmations are visible only to authorized readers or their still
authorized proposer. Approval rechecks current authority.

=POST /api/v1/journals/:id/post=, =venturectl journal post ID= and the
assistant tool =venture_journal_post= share the journal action. An organization editor
proposes it; finance, organization admin/owner, or global administrators can
apply it. REST =?stage=1=, CLI =--stage= and assistant =confirm_writes=
always stage, even for finance. The proposal preserves the draft header version and a fingerprint
of its lines. Changed lines cause a conflict, rather than approval of different
amounts. Approval calls the existing posting service, which retains balance,
currency, source, period and immutable-history checks. Generic writes to a
journal's posted state remain refused.

A user with no memberships is directed to their account page, which explains
that an organization owner must grant access. Password changes and sign-out
remain available. Business reads return no records.

Public lead capture at =POST /f/:token= uses its form token authority even when the browser also carries a local session. That exact route receives an independent protocol scope; its token, active-form, field allowlist, body-size and rate-limit checks remain owned by the lead capture handler. Other =/f/= paths and methods receive ordinary request authority.

Public quote viewing (=GET /q/:token=) and acceptance (=POST /q/:token= or =POST /q/:token/accept=) likewise use the quote capability independently of an incidental session. Other quote paths or methods retain local request authority; quote token validation, allowed states, revision checks and the public field allowlist still apply.

Assignment fields marked =VENTURE_COLUMN_FLAG_ASSIGNED_USERNAME= grant record ownership to that account within its current organization membership: lead/activity/deal =owner= and ticket =assignee=. Username resolution uses the authenticated user id, including API tokens whose display name is a token label. Assignment, explicit =owner_user_id=, team membership and venture ownership are additive grants; reassignment does not revoke a separate explicit owner/team/venture grant. Assignment never grants organization membership or bypasses financial or viewer write restrictions.

* Accounting second-actor rules

Only organization owners/admins or global administrators may change or delete a second-actor rule. Authenticated proposals identify the account by user ID, so two API tokens belonging to the same person do not satisfy the second-person requirement. Token labels remain audit descriptions. An active request scope retains this identity even when an internal caller omits its audit actor.

** Whole-operation consent

A post/pay rule applies to one complete business operation before its first write. The pending proposal includes the command name, organization, full input arguments and proposed record/ordered details, plus a conservative snapshot of all persistent business records in the organization and shared organization-zero records, including configuration. Changing an amount, line, account mapping, date, allocation, batch payload or source record requires a fresh proposal. Even an unrelated business or configuration edit can invalidate a pending proposal; retry the intended operation to propose its current state. Automatically generated identities on unsaved records do not change the meaning of an otherwise identical retry.

The first actor receives a permission-denied response after the pending proposal is saved; generated documents, allocations, journals and ledger entries have not been written. A different authorized account repeats the same operation with the same inputs. Nested posting and settlement steps share the outer operation's consent, so a multi-document batch or multi-vendor payment run requires one matching approval rather than a separate approval for each intermediate row. Consent is consumed once inside the same transaction as the business effects. A failed write or failed approval save rolls everything back and leaves no applied consent behind.

Service entry points establish this scope themselves, including direct C callers, rather than depending on a particular page or REST route. Recurring sweeps, financial batches, billing requests, capture conversions, commerce imports and Stripe fee postings and chargebacks bind their complete inputs before generating financial rows. Commerce consent also includes the fetched provider order contents; a changed remote order must be proposed again. A service invoked inside an unrecognized caller-owned transaction refuses a protected operation because it cannot durably save a new proposal independently of that caller's rollback.

Pending consent expires after 24 hours from its creation time; future-dated evidence is also refused. Repeating an expired operation creates a fresh proposal that a second authorized account must approve. Old proposals remain as evidence and cannot be replayed. Authentication traffic, audit records, approval evidence, notifications and delivery queues are excluded from the business snapshot so ordinary login and proposal activity do not invalidate consent.

The rule protects posting and payment effects, including generic saves that trigger those effects. Ordinary draft creation, draft editing and financial configuration changes remain available to a single authorized account; non-posting deletion and restoration do not require post/pay consent. Those changes still invalidate pending snapshots, so the approving account must repeat the intended posting or payment against the current books. Invoice batches with posting disabled, trial setup, subscription term/state changes, draft bill capture and read-only billing/recurring previews do not request accounting consent. A mixed batch or sweep retains one whole-operation gate when any member can post or pay.

** Dry runs and trusted events

A dry run that executes financial writes before rolling them back still requires consent, because save signals run during execution. A rolled-back batch dry run leaves the proposal pending rather than consuming it. Read-only previews remain read-only.

Internal derived work without an authenticated request principal or explicit user actor retains the existing trusted-service policy. This includes signature-verified Stripe webhooks recording provider receipts; they are provider evidence, not a second local person. An internal call made under an authenticated request retains that account identity even when the audit actor argument is omitted. Dropping the audit actor must never bypass a user rule. Human approval scopes do not authorize unrelated signal-triggered operations.

** Implementation boundaries

Consent snapshots run in the same serializable transaction as the protected command. Pending proposals expire after 24 hours, and a process restart or posting-rule registry replacement requires a fresh proposal. A final policy-revision check precedes consumption. Opaque exchange-policy callbacks are refused under second-actor rules; the supported exchange policy is the same organization's persisted rate table.

The transaction binding, server-side enforcement, expiry and single-use consumption follow the principles in [[https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html][OWASP Transaction Authorization]]. Operators authorize the significant inputs by repeating the exact business command under their own account; approval records store the fingerprint rather than a second copy of sensitive input data.
