#+title: Recurring documents, collections and batch entry
#+description: Reusable schedules, overdue reminders and all-or-nothing financial imports

* Recurring invoices, bills, expenses and journals

The =recurring= module requires =invoicing=, =payables=, =ledger=, =periods=,
=receivables= and =mail=. Its records are field tables: =recurring_schedule=,
=recurring_occurrence=, =collection_policy=, =collection_step=,
=collection_case=, =collection_notice= and =financial_batch=.

A schedule names a document kind, frequency, IANA timezone, start and optional
end, whether to auto-issue/approve/post, and a JSON template. Pause and resume
are service actions. =next_run_at= is a preview of the next calendar day,
computed from =start_at= plus =cycle_index= so January 31 stays the 31st after
February, including 29 February in a leap year.

Generation uses the live services: invoices go through
=VentureSettlementService=, bills through =VenturePayablesService=, expenses
through ordinary save (and therefore autojournal), journals through
=VenturePostingService=. Invoices and bills are never written as raw journals.

Each occurrence has a durable =occurrence_key= of =schedule-id:YYYY-MM-DD=.
Repeating a sweep creates nothing. A closed fiscal period records
=skipped_closed= and continues. A failed attempt is retained on the occurrence
and the schedule. Template edits apply only to later occurrences.

#+begin_src sh
venturectl create recurring_schedule name=Hosting kind=invoice frequency=monthly \
  timezone=UTC auto_post=true start_at=2026-01-15 \
  'template={"company_id":1,"lines":[{"description":"Hosting","quantity":1,"unit_price":"40 USD"}]}'
venturectl recurring run --as-of 2026-03-15 --dry-run
venturectl recurring run --as-of 2026-03-15
venturectl act recurring_schedule ID pause
#+end_src

Schedule the CLI or the =recurring_run= automation handler. There is no extra
database worker.

* Invoice collections and statements

A =collection_policy= holds reminder steps at day offsets (negative is before
due) and an optional monthly =statement_day=. The sweep measures overdue days
from the frozen due date, skips paid, void, credited, disputed and held cases,
and enqueues durable =mail_message= rows with an occurrence key so a restart or
a concurrent settlement cannot send the same notice twice. Delivery failures
stay on the notice. Customer statements use the existing =customer_statement=
report for content.

=collections_worklist= lists overdue invoices with owner, promised payment date
and dispute notes. Follow-up is the generated case action plus another notice
key for that day.

#+begin_src sh
venturectl create collection_policy name=Standard active=true statement_day=1
venturectl create collection_step policy_id=1 day_offset=7 action=reminder active=true
venturectl collections run --as-of 2026-01-17
venturectl report collections_worklist
#+end_src

* Batch financial documents

=venture_recurring_service_batch= parses CSV or JSON, validates every document,
then creates invoices or expenses in one transaction. Any refusal rolls the
batch back. =post=true issues invoices only after every draft validates.
Duplicate invoice numbers and expense =external_id= values, in the payload or
already stored, are refused. Dry-run runs the same transaction and rolls it
back.

CSV invoice rows that share =number= become one document with several lines.
JSON uses a =documents= array.

#+begin_src sh
venturectl batch invoice --dry-run
venturectl act invoice 0 batch_create format=json post=true 'payload={...}'
#+end_src

A =financial_batch= record stores a reusable payload. Its =apply= action runs
the same service.
