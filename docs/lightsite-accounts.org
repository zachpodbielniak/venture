#+TITLE: Lightsite account validation

* Purpose and boundary

[[https://git.mcgoaty.com/lightsite/daemon/issues/20][Lightsite daemon #20]] needs a verified identity before an operator provisions
an owning account. =GET /api/v1/account-identity/:id= returns that identity;
=:id= is a positive organization ID in this hosted workspace.

This endpoint uses ordinary bearer-token authentication. It does not expose
the =tenant_workspace= administrative record to tokens or create a second
identity/credential store. That generic administrative API still requires an
interactive tenant administrator.

* Contract

A successful response is JSON with HTTP 200 and =Cache-Control: no-store=:

#+begin_src json
{"origin":"https://business.example","workspace_id":"8f062b79-1d2b-4d7f-99e5-bd3bf588e05a","organization_id":42,"state":"active"}
#+end_src

Use the canonical =hosted.origin=, including its port when configured. The
ordinary hosted Host/Origin boundary applies. The route is classified tenant
work, with no support-capability or platform bypass.

The current authenticated principal must be an active hosted member and
have organization owner/admin authority. For a token, both its captured
membership snapshot and current membership must allow that organization.
A later grant cannot enlarge an existing token. Use a token attached to the
provisioning member, minted after the organization's authority has been
granted; no new token type is needed. The member mints it themselves with
=POST /api/v1/tokens= while signed in to Venture with a browser session: any
signed-in user may mint a token for their own account, owned by them and
carrying their own global role and current membership snapshot. A bearer
token cannot mint one unless it carries the global admin role, and the
=/account/tokens= page stays administrator-only. See [[file:api.org][the API's
Authentication section]].
An interactive tenant administrator retains the existing organization-policy
semantics. Ordinary token calls do not inherit tenant-administrator authority.

The core =venture_tenant_service_account_identity()= reads the principal from
the database access scope. Its caller must authenticate credentials first.
It reuses the tenant service and organization access policy and reads the
organization through the repository. HTTP calls do this through the usual
authentication layer, so revoked/expired tokens, inactive users/memberships,
inactive or deleted organizations and token snapshot limits all apply.

Provisioning requires an initialized, active workspace. Read-only, suspended,
unknown, changed-identity and uninitialized workspaces refuse it. This read
endpoint checks the write/side-effect lifecycle gate because its response
permits provisioning elsewhere. It changes no Venture records.

| Result | Meaning |
|--------+---------|
| 200 | Exact account reference validated; state is active |
| 401 | Missing, expired or invalid credentials |
| 403 | Hosted identity, lifecycle or organization authority refused |
| 404 | Requested organization unavailable through repository lookup |
| 422 | Organization ID is not a positive signed 64-bit integer |

A hosted preflight may return 403 before the handler runs. Clients treat
all non-200 responses as refusal; response wording is not an API contract.

* Consumer requirements

Lightsite selects a trusted connection from private operator configuration.
It compares the returned origin, workspace UUID and organization ID against
the complete requested reference, and requires =state: active=. A bare
organization ID, owner email or submitted workspace UUID is insufficient.
Redirects must not forward credentials. Bound response size and request time;
network errors must not create an account.

Validation is a provisioning assertion, not a session or permission grant.
Consumers must separately authorize each management action. Suspending an
account does not delete its sites or public files.

* Verification

=tests/test-account-identity.c= starts a real hosted server and uses a minted
bearer token. Before implementation the first valid request failed with
404 instead of 200. The test covers the returned identity, anonymous and bad
credentials, incorrect Host, another organization, later membership grants,
malformed and overflowing IDs, token expiry, read-only/suspended/unknown
lifecycle, changed workspace identity, inactive users, deleted organizations,
membership revocation, token revocation, and continued token refusal on
workspace administration. Role demotion revokes an existing admin token;
promotion does not enlarge a token minted with a viewer membership. Successful
responses are checked for exactly the four documented fields; successful and
refused responses both prohibit caching. =tests/test-auth.c= includes the new
route in anonymous checks.

The same file's =/account-identity/member-mints-own-token= signs in a hosted
member (global editor, tenant =member=, admin of one organization) with a
browser session and mints a token at =POST /api/v1/tokens=. Before the change
that was refused with 403. The minted token reports the organization with
=can_manage_sites= true, omits an organization the member is not in, cannot
mint another token, and a read-only workspace refuses the session's mint.

#+begin_src sh
make DEBUG=1 test-one T=test-account-identity
make DEBUG=1 test-one T=test-tenant
make DEBUG=1 test-one T=test-auth
#+end_src

The end-to-end Lightsite demonstration is linked from the prerequisite PR
and Lightsite PR #23. It uses the actual provisioning command and this built
server; fixture responses alone do not establish interoperability.

Refusals produced by the account-identity handler emit one server diagnostic
with the stable error category and domain/code. Credentials, token names,
organization input and response bodies are excluded. HTTP responses remain
uncacheable; this diagnostic does not grant or weaken provisioning authority.

* Signed-in account authority for site management

=GET /api/v1/account-authority= authenticates the requesting Venture user
(session or that user's normal bearer token). It accepts no target user and
never infers identity from email, a domain, a site or a shared provisioning
token. Lightsite must forward/use a credential belonging to the signed-in
principal; this endpoint does not turn a Lightsite cookie into Venture identity.

#+begin_src json
{"origin":"https://venture.example","workspace_id":"8f062b79-1d2b-4d7f-99e5-bd3bf588e05a","state":"active","user_id":7,"organizations":[{"organization_id":42,"role":"admin","can_manage_sites":true}]}
#+end_src

Match the complete configured origin/workspace and the account's organization.
The =user_id= is local to that workspace. =role= describes current membership;
**authorize site management only when =can_manage_sites= is true**. That decision
requires a write-capable credential and owner/admin membership both now and in the bearer token's captured
snapshot. A viewer token promoted later can report the new current role but
still has =can_manage_sites: false=. A later demotion immediately removes
management authority. Tokens omit organizations absent from their snapshot.
Other roles receive no site-management permission from this API.

Only explicit active memberships in active, non-deleted organizations appear.
Workspace/platform administration does not fabricate organization membership.
Inactive users, revoked/expired credentials, non-active workspace lifecycle,
identity mismatch and support sessions fail closed. Storage failure returns an
error, never a successful empty authority list. There is no permission cache:
responses use =Cache-Control: no-store=. Lightsite must validate current authority
on management operations, refuse redirects and bound the complete request and
body as described in its =docs/venture-accounts.org= (five seconds, 4096 bytes).

The response is bounded to twenty explicit memberships; more refuses the whole
request rather than returning a partial permission list. This is a management
authority endpoint, not a membership directory or an arbitrary-user lookup.
Public hosting remains independent of authority-service availability.
Provisioning still uses the unchanged =/api/v1/account-identity/:id= contract.
