* Version 4 snapshots

=VentureBackupService= exports version 4 JSON snapshots from a consistent
read transaction. Record fields and references come from GObject metadata.
The archive includes financial records from sales, invoicing, receivables,
payables, ledger, periods, banking, goods, setup, cutover, statements, tax filing,
budgets, equity, consolidation, claims, payroll, projects, billing and close, plus companies,
contacts, ventures, custom-field definitions and layouts. It retains drafts,
soft-deleted records, account classifications, control mappings, journals and
ledger projections, invoices, bills, frozen tax, allocations, credits, refunds
and document events. CSV remains a type/count summary and cannot be restored.

Restore requires a newly created, empty destination organization, including
an empty chart; it does not combine two sets of books. It copies book currency
and fiscal-year settings while retaining the destination organization's name
and identity. All records receive new IDs and UUIDs. Ordinary and supported
polymorphic references are remapped, and globally unique account codes and
operational keys are scoped to the destination. Historical dates, versions,
statuses and money values are retained.

The importer inserts historical state directly through the existing database
binder. It does not issue invoices, apply receipts, run shipment commands or
post journals again. This avoids duplicating income and stock movements.
Custom-value indexes are rebuilt from the owning records' public attributes.
The final =accounting_backup= record has state =restored= and contains the
source-to-destination ID/UUID mapping. The entire restore, including that
receipt and organization settings, commits together or rolls back together.

The exporter and importer must support compatible record schemas. Unknown or
missing persistent fields are rejected rather than silently defaulted.

Missing references, duplicate identities, incomplete fields, unbalanced posted
journals and missing or inconsistent ledger projections fail the transaction.
Tests compare every archived public field after identity remapping, exact row
counts, ledger balances and invoice/bill balances, including refunds, credits,
foreign currency and frozen tax.

* Scope and compatibility

An accounting snapshot is not an installation backup. It excludes credentials,
users, sessions, provider configuration, attachments and unrelated operational
modules. References to access-management records or other organizations are
recorded as external UUID identities. Those identities must already exist at
the destination; numeric IDs are never assumed to identify the same person or
organization across databases. Retain a full database and file backup for
whole-installation disaster recovery.

Version 3 remains supported only for manual opening-ledger imports. Its account and journal fields are validated before any write; malformed dates, line arrays and debit/credit sides are rejected without changing the destination.
Its document packs lack the relationships needed for historical restoration and
remain refused, as do versions 1 and 2. Export a fresh version 4 snapshot from
the source database to restore document history; missing evidence cannot be
recovered by upgrading the JSON version number.

* Scheduled backups

A =backup_schedule= is an ordinary record of the =backup= module, edited
through the generic record surfaces (REST, CLI, the record form). It names a
=scope=, =organization= for a version 4 accounting snapshot of the schedule's
own organization or =installation= for a copy of the whole database; a
=schedule= in the grammar scheduled report packs use (=daily=, or five
numeric/=*= cron fields evaluated in UTC, empty for manual-only); a
=retention= count; a =destination= directory; and a =verify= flag. Zero
retention and an empty destination fall back to =backup.retention= and
=backup.directory= from the [[file:configuration.org][configuration]], which
default to seven copies under the state directory's =backups=. Saving a
schedule with an unparseable expression, an unknown scope or a negative
retention is refused. Both tables come from the field tables; migration
=000372_backup_schedules= verifies they are present together, or absent
when the module is off, and backfills nothing.

=VentureBackupScheduleService= (=src/backup/venture-backup-schedule-service.c=)
is the one place a scheduled backup is written, verified and pruned. Its
sweep, =venture_backup_schedule_service_run_due=, dispatches every due
schedule the way report packs are dispatched, catching up once on the
scheduled day and stamping =last-run-at=. Automation reaches it as
=venture->backups_run("ORG")= (=0= for every organization); there is no
background thread, so something must call the sweep -- a pod automation, or
=venturectl backup run= from cron.

Every attempt records a =backup_run=: =started-at=, =finished-at=, =path=,
=size=, =sha256=, =status= (=running=, =succeeded=, =failed= or =pruned=)
and a =message= when it failed. Runs are evidence and are written only by
the service; generic writes and deletes of a =backup_run= are refused by
name. An organization run writes the snapshot as
=organization-<org>-<stamp>-<run>.json=; an installation run writes
=installation-<org>-<stamp>-<run>.sqlite= using SQLite's =VACUUM INTO=, a
consistent copy taken in-process. On PostgreSQL an installation schedule
records a =failed= run saying so: =pg_dump= is the tool there, and the
schedule's destination directory is where its output belongs.

After a successful run the schedule's successful backups beyond =retention=
are pruned oldest-first: the file is removed and the run keeps its record
with status =pruned=. Pruning only ever follows a success. A failed run
records its status and deletes nothing, however many files there are.

Off-site transport is not implemented. The destination directory is the
hand-off: point rsync, restic or an S3 sync at it, and keep the =backup_run=
row as the inventory of what should be there and what it should hash to.

* Series stores

Market data lives outside the database, in one SQLite file per data source under =<state_dir>/series/<data-source-uuid>/store.db= (see [[file:market-data.org][Market data]]). Those files hold history no source will serve again -- an auction house answers with what is listed now, never with what was listed last month -- so an installation backup copies them too. =series.include_in_backup= (true by default) turns this off for an operator who keeps the stores some other way; with the =feeds= module off, or no store on disk, nothing happens.

After an installation run succeeds, the backup service calls the companions registered with =venture_backup_schedule_service_add_companion()=; the feeds module registers one. It records one =backup_run= per store -- every data source's store, deleted sources included, since soft deletion leaves the file and its history -- with scope =series=, kind =backup=, status =running=, =parent-run-id= naming the installation run it was taken with and =store-uuid= naming the data source. The copy itself is queued to the feeds worker thread, never taken on the main thread: a store can be gigabytes, and the server keeps serving while it is read. The installation run returns at once; =venturectl backup run= answers with the database copy, and the store copies finish behind it (=venturectl list backup_run scope=series= shows them).

On the worker the copy is SQLite's online backup API on a connection of its own, inside one read transaction: the copy is the store as of one moment, however many commits the writer makes while it runs (WAL lets it go on), and the pinned read is also what lets the copy finish at all while a busy source keeps writing -- without it SQLite restarts a copy at every commit. It is written to =series-<uuid>-<stamp>-<run>.sqlite.partial= in the installation copy's directory and renamed into place only when complete, switched to a rollback journal so the file stands alone, and its SHA-256 and size are computed on the worker. The answer comes back to the main thread as plain data and is recorded on the run (=succeeded= with path, size and digest, or =failed= with SQLite's reason), waiting for any open transaction to close first. A failed store copy never fails the installation run or another store's copy; it is visible on its own row.

Retention follows the schedule's =retention=, counted per store: a schedule keeping seven copies keeps seven of the database and seven of each store, oldest-first pruning removes the file and marks the run =pruned=, and pruning only ever follows that store's own success. A store copy still running when the next backup comes is left to finish; the new one is recorded as =failed= with "skipped" rather than starting a second copy of the same file. A copy recorded as running that will never be answered -- the server stopped, or feeds were switched off, before the worker finished -- is marked =failed= ("interrupted") by the next installation backup of that schedule. Turning =include_in_backup= off stops new copies; the files already written are kept until removed by hand.

On PostgreSQL an installation schedule records a failed run (=pg_dump= is the tool there), and store copies only follow a successful installation copy, so none are made. Copy the stores with the state directory instead; SQLite's own =.backup= command (=sqlite3 store.db ".backup /backups/store-copy.db"=) is safe while the server runs, and a plain file copy is safe only with the server stopped.

The restore drill restores books and never picks a store copy: the latest run it drills is the newest database copy or snapshot.

** Restoring a store

There is no automated restore of a live store, as there is none of a live database. To put a store back by hand:

1. Stop the server (or switch =feeds= off), so nothing holds the store's writer.
2. Find the run: =venturectl list backup_run scope=series store_uuid=<uuid>=; its =path= is the file and =sha256= what it should hash to (=sha256sum=).
3. Copy the file to =<state_dir>/series/<uuid>/store.db=, replacing what is there, and delete =store.db-wal= and =store.db-shm= beside it: they belong to the file being replaced.
4. Start the server. The writer reopens the store, switches it back to WAL and, if the copy is from an older release, upgrades its schema.

History after the copy's moment is gone from the restored store; the next sync carries on from there. A store copy holds market data only, so it may be restored independently of the database copy it was taken with.

* Verification

=venturectl backup verify RUN= -- =POST /api/v1/backup_run/:id/actions/verify=,
or the Verify button on the Backups page -- proves a backup restores. The
file's SHA-256 is recomputed and must match the run; a changed file is a
refusal, not a verdict. An organization snapshot is then restored through
=venture_backup_service_restore= into a fresh, empty, in-memory SQLite
database and compared with the live organization: every account's balance
per currency from each side's own posting service (the trial balance), the
debit and credit totals those balances add up to (the ledger totals), and
the row count of every record type the archive carries, soft-deleted rows
included (the document counts). An installation copy is verified by opening
a scratch copy of the file -- opening SQLite rewrites its header, and the
retained artefact is never touched -- and running the same comparison for
every organization, leaving out the backup module's own records and the
audit trail, which the act of backing up writes after the copy is taken.

A series store copy cannot be tied to anything live -- the store has moved on since -- so verifying one recomputes its digest and then opens the file immutable (no lock, no journal, not one byte written, so the digest still matches afterwards) and runs SQLite's =integrity_check=. It ties when the file is whole and at a schema this build reads; the report carries =store_uuid=, =schema_version=, =integrity= and the =venues=, =instruments= and =current_rows= it holds. Verifying reads the whole file on the request that asked, as verifying an installation copy does.

The verdict, =tie= or =mismatch=, is recorded on the run with =verified-at=
and a JSON =report= holding each comparison and a =mismatches= list in plain
words ("account 4000 USD: live -75.00 USD, restored -50.00 USD"). A mismatch
is a statement about the live books having moved since the snapshot as much
as about the snapshot; verifying immediately after a run ties, and a
schedule with =verify= set does exactly that inside the sweep. A run that
never succeeded or whose file is gone cannot be verified. The live database
is never written by a verification.

* The restore drill

=venturectl backup restore-drill [run_id=N] [organization_id=N] [name=...]=
-- =POST /api/v1/backup_run/0/actions/restore_drill= -- is the same restore
and tie-out kept as its own record: a =backup_run= of kind =drill= naming
its =source-run-id=, with the verdict and the full report retained the way a
scheduled report pack keeps its last output. Without =run_id= the latest
succeeded backup of the organization is drilled. Drills never count toward
retention and are never pruned, so the evidence that a restore worked
outlives the file it restored.

* The Backups page

=/settings/backups=, linked from Settings, lists the active organization's
schedules and runs with their sizes, digests and verification verdicts.
Anyone signed in may read it. Run now, Verify and Restore drill are shown
to, and accepted from, owners and admins only; the actions behind the REST
routes carry the same =admin= gate, so an accountant (editor) or a read-only
viewer cannot trigger a backup from any surface.

The schedule and run ids arrive in a form, so each is checked against the
active organization before anything runs: the service reads the organization
off the record it is handed, and without that check an admin of one
organization could have snapshotted, verified or drilled another's by posting
its number. A record from elsewhere is reported as not found.

* Whole-workspace recovery

An accounting pack is not an operational tenant backup. It omits credentials,
attachments and application state needed to restore a workspace. The separate
[[file:tenant-recovery.org][tenant recovery utility]] snapshots a stopped application and its PostgreSQL
database into an encrypted archive, verifies workspace identity, and restores
only into an empty destination. Keep the recovery key outside that archive.

A hosted workspace runs on PostgreSQL, so its installation schedules make no copies and no store copies; its series stores are in the state directory, which the tenant recovery archive already carries whole (=state.tar=, taken with the application stopped, so every store is consistent). Restoring the archive restores the stores with everything else.
