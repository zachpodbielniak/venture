* The interface

VENTURE's web UI is drawn from one stylesheet at a time, embedded into the server binary at build time; there is no build step, no framework and no web font. This page is what the stylesheet is made of, so that a page added to the server, a widget added to a dashboard, or a plugin's own markup lands in the same design instead of beside it.

** Principles

The interface is built for somebody running a business between other things, not for the person who designed the schema. Six rules decide every page, borrowed from the tools people find calm to use -- Apple's clarity and deference, Stripe's summary-first records, Linear's quiet density, and Nielsen's recognition over recall -- and each is enforced in code rather than hoped for:

- *Say it in their words.* A type is "Form submission", a status is "In progress", a field is "Email permission". Internal names, raw ids and UUIDs never reach a page by default. (=venture_entity_type_dup_label()=, the choice labels, the caption register.)
- *Lead with what they came for.* A record page is a title, a status, the content somebody wrote and the type's own block; its details sit beside it, not in front of it. A form submission shows who wrote in and what they wrote. (=docs/record-view.org=)
- *Show what is set; fold the rest.* Empty fields are not rows. Machinery -- replay keys, digests, revisions -- and the full field list are one click away, never on the page. Forms keep the essentials in view and fold the rest. Progressive disclosure is =<details>=, so it needs no script.
- *One primary action per page.* Edit on a record, New on a list, Save on a form. Actions that ask for input stay folded behind their name until chosen.
- *Know where you are.* Every record, list and form carries a trail -- "Customers / Contacts" -- read from the same map as the sidebar, and the sidebar opens the group you are in and folds the others.
- *Derive, never hand-write.* All of the above comes from the field table through one classification (=venture_field_spec_get_role()=). A new record type, or a plugin's, reads this way the day it registers; no page is written per type.

** Two looks

There are two designs, and every page exists in both. The switch at the bottom of the sidebar (a form, so it works without scripting) sets a cookie; =ui.look= in the configuration is the default until a browser has chosen.

- *industrial* — the instrument panel this page describes. =data/static/venture-industrial.css=. The default.
- *classic* — the editorial design VENTURE shipped with: serif page titles against a sans interface, white cards with rounded corners on a warm bone canvas, hairline grey rules, a configurable accent on links. =data/static/venture-classic.css=. It carries the same four themes and the same class names; it is a second reading of the same markup, not a second interface.

The rest of this page is about the industrial look. The class inventory at the end applies to both, which is what lets a plugin or a widget be written once.

** The substrates

There are three themes and one design. The theme toggle in the sidebar footer (and the =t= key) cycles them; =ui.theme= in the configuration sets the default until a person picks one, and the choice is remembered in the browser.

- *dark* — tactical telemetry. A deactivated CRT ground (=#0A0A0A=, never pure black), white phosphor text (=#EAEAEA=), scanlines and a film of grain over everything. This is the primary substrate and the one the design was drawn on.
- *light* — Swiss industrial print. The same drawing on unbleached documentation paper (=#F4F4F0=) in carbon ink (=#111111=), with grain and no scanlines.
- *mocha* — Catppuccin Mocha's palette on the telemetry substrate: a skin, not a second design.

Every rule in the stylesheet is written once against custom properties; a theme is a block of property values. That is what keeps the three looking like one panel seen under different light, and it is the contract a plugin should rely on: use the tokens, never a literal colour.

** Two registers of type

The hierarchy is done by type alone. Nothing is boxed, tinted or iconed to say what it is.

- *Macro* — headlines. The heavy grotesque, uppercase, tight (=letter-spacing: -0.035em=), leading under one, sized with =clamp()= so a page title scales with the viewport without ever wrapping badly. Only =h1=, =h2=, stat values and the dashboard's big figures are set this way.
- *Micro* — readings. Small monospace, uppercase, tracked out (=10.5px=, =letter-spacing: 0.1em=). The chrome is this: table headers, card heads, the navigation, badges, buttons, stat labels, timestamps, coordinates.
- *Captions* — the name of a field beside its value or above its input, in a record's Details and in a form. Sentence case, small, muted, in the sans. A caption like "Email permission outcome" is read rather than scanned, and four tracked-out words in capitals made every record page shout; the micro register stays on the chrome.
- *Prose* — sentences. Plain sans at =13–14px= in sentence case: a ticket body, a comment, a description, a subtitle, a form's help text. An operator reads these, so they are never shouted.

The rule for a new element is to ask which of these it is. A thing that labels the interface is micro; a thing that names a field is a caption. A thing a person reads is prose. A thing that names the page is macro.

The machine-readable HTML elements are set in the mono automatically: =<code>=, =<samp>=, =<kbd>=, =<data>=, =<output>= and =<time>=. Use them for what they mean — a keystroke in =<kbd>=, a value the program produced in =<samp>=, a figure with a machine value in =<data>= — and the type follows.

** Geometry

Ticket cards contain their absolutely positioned screen-reader captions.
They must not rely on a reveal animation's transform to do so: reduced motion
removes that transform, and off-screen board columns would otherwise widen
the whole page. The board itself owns horizontal scrolling.

Corners are ninety degrees. There is no =border-radius= anywhere, no gradient, no soft shadow; the =--radius-*= and =--shadow-*= tokens still exist for anything written against them and resolve to zero and none.

Zones are compartments. A card is one rule around a surface with registration marks in its top corners. A grid of cards shares its rules: the cells sit one pixel apart and each carries a one-pixel outline, so neighbours have exactly one line between them and a short last row leaves the ground showing rather than a painted block. The same device draws the stat row, the service-level clocks and a record's definition list.

A floating surface — the palette, a modal, a toast, the assistant's launcher — is separated from the page by a hard ring (=--ring=: one pixel of the ground, then one of the strong rule) rather than a blur.

** One accent

Hazard red is the only accent, and it means "look here": links, the focus ring, the active navigation rail, the unread mark, the keyboard cursor, the landing ghost on the dashboard canvas, the required marker on a field. Nothing large is ever filled with it. The primary button is ink on the ground, so a page with a Save and a Cancel still has exactly one solid rectangle.

Green and amber are readings, not decoration: a positive figure, an overdue clock, a warning notice. They appear on a status and nowhere else.

The operator may still set =ui.accent=, which then applies to both looks; left empty, each look keeps its own — red here, blue in classic. See [[file:configuration.org][Configuration]].

** Framing

ASCII does the framing that boxes used to. A section heading in the sidebar is =/// SECTION=. The page eyebrow is =>>> RECORD TYPE=. A card head is =[ TITLE ]=. The brand is =[ ▣ NAME ]=. A tag is =#tag=. These are drawn by the stylesheet from pseudo-elements, so the markup carries none of it and a test that inspects the HTML sees plain text.

The sidebar footer carries the data plate: =REV 0.6.0= and an online mark, in =<samp>= because it is the program's own output.

** Post-processing

Two fixed, non-interactive layers sit over everything. On the dark substrates a =repeating-linear-gradient= draws the electron beam's sweep at low opacity; on every substrate an SVG turbulence tile, generated inline rather than downloaded, lays a film of grain. Both are felt rather than seen. They are above the palette and the assistant, because those are on the same tube as the rest, and they do not print.

Motion is short and mechanical: a press moves a button one pixel down and right, a spinner is a square turning in eight steps, a card lifts by lighting its rule red. =prefers-reduced-motion= removes all of it.

** Charts

Charts are drawn by the server as inline SVG (=src/web/venture-web-chart.c=): a line of up to four series (=VENTURE_WEB_CHART_MAX_SERIES=), those marked secondary on a right-hand axis of their own, bars, a word-sized sparkline and a weekday-by-hour heat map. The series on one side of a line chart share that side's scale: two prices are one unit and must be read against one axis, or the gap between a price and its region's median would mean nothing; a quantity beside them is another unit and gets the other side. They need no script and they print. The markup never carries a colour: every mark is stroked or filled with =currentColor= and carries a class, and both stylesheets colour the classes from the tokens, in one block written once against the tokens and appended to each.

| =.chart-line-4= | the fourth series, dotted (the price history's comparison: the region's median or another venue) | =--text= |

Red is not used: a chart is something to read, and red means "look here". A heat map of prices shades the cheapest cell darkest, because cheap is what a buyer looks for; a map of quantities shades the most darkest. No radius, no gradient, no shadow, as everywhere.

Every chart has a =<title>=, a =<desc>= when it has a sentence to say, =role="img"= with an =aria-label=, and a table of every figure -- a picture of numbers is not the numbers. Every label is escaped; the coordinates are written in the C locale, because a decimal comma would split one SVG number into two.

An axis steps in round figures -- 1, 2, 2.5 or 5 times a power of ten, whole when every value is (a count, or minor units) -- and its margin is as wide as its widest label, so a gold price axis reads 2,600g, 2,800g and is never cut off at the card's edge. The drawing is a fixed 640 by 220 scaled to its box, capped at 360px high so its text stays near its size without script.

*** Interactive charts (venture.js)

A line or bar chart also carries its raw numbers as JSON in =<script type="application/json" data-plot>= beside its table: ={kind, sec, axis, v}= -- each series' side, how its axis reads (={kind: "money", exp, pre, suf}= from the series' =currency=, or =percent=, or =number= with =int=), and its values with =null= for a gap. The names, the labels and every figure shown come from the table, as the server formatted them; =<=, =>=, =&= and ='= in the JSON are =\u= escapes. =wirePlots()= in venture.js redraws the chart from them at the width it is shown (=.plot-on= on the figure hides the server's drawing and legend) and adds:

- a readout under the pointer -- a rule, a ring on each line, and every series' figure at that point, snapped to the nearest point with data -- or under the arrow keys when the chart has focus (Home and End too; the arrows skip the hours nothing was seen in);
- the legend as buttons (=aria-pressed=) that switch a series off and rescale its axis; one always stays;
- drag across the chart, or + and -, to zoom into a range; Reset zoom, a double-click or 0 shows it all;
- the low, high, latest and change of the first series shown, over the range in view;
- Table, which shows the chart's table, and CSV, which downloads it.

Its classes are =plot-*= (=.plot=, =.plot-svg=, =.plot-s1= … =.plot-s4= with =.plot-line=, =.plot-area=, =.plot-bridge=, =.plot-dot=, =.plot-ring=, =.plot-col=, =.plot-tip=, =.plot-key-1= … =.plot-key-4=, =.plot-controls=, =.plot-stats=, =.plot-tools=), in both stylesheets after the =chart-*= rules, and never a =chart-*= class: venture.js is inlined into every page, and a test that greps a page for =chart-line= would find the script. A chart wired once is marked, and the page's MutationObserver ignores changes inside a =.plot=, so the readout redrawing on every pointer move does not rescan the page's tables.

The Trading pages add =.market-filters= (a filter form), =.market-action-row= and =.form-inline= (a row of small forms), =.market-stats= (a hook on the shared =.stat-row=, which styles it) and =.market-figure= (stat rows), =.market-heat= (two heat maps stacked), =.market-ranges= and =.market-range= (the price history's row of range links in the micro register, the one drawn =aria-current="page"= and in ink, never the accent), =.market-trend= (a table cell holding a row's seven-day sparkline, kept on one line), =.market-table= (a data table that scrolls inside its card on a phone), =.market-widget= and =.market-hits= (the market dashboard cards). They are the block /Market data: the charts and the Trading pages/ in each stylesheet.

The arbitrage pages (=/arbitrage=, =/arbitrage/crafting=, =/arbitrage/recipe-lists=, =/arbitrage/plan=, =/arbitrage/calc=) add the block /Arbitrage: the scan, the presets and the calculators/:

** The Accounts pages

The /accounts pages add one block to each stylesheet ("Accounts: the operator's characters, banks, inventory and ledger"), written against the tokens like the market block before it. The attention list (=.accounts-attention=, =.attention-row=) is one compartment per place to log in to, with a three-pixel rule down its left edge in the status colour of its most urgent reason: =.is-overdue= takes the accent -- red, because an expired listing or a mail about to be lost is exactly where to look -- =.is-soon= the warning colour, =.is-waiting= the info colour, a stale row the faint rule. Deadlines in tables are =<time class="expiry expiry-expired|soon|later|none">=, the first two in the same two colours and bold; nothing else on these pages is coloured. Row heads that are names (a character, an item) are =td.row-head= in the prose register, never a =th=, which the labels' micro register would set in capitals. Money on these pages is drawn in whole units once it passes a thousand of them (=1,214,277g=, not =1214276g 97s 68c=), its leading figure grouped -- display only; every answer keeps the exact minor units. The filters fold into a =<details class="card accounts-controls">=, open when a filter is in force, so the table is what greets a person. =.accounts-places= is the grid of place tiles on an account's page, =.share-bar= the small bar beside an item's share of the inventory (its width an inline style, which is a length, not a colour), and =.account-sub= the muted line under a name (level and class, a category); =.account-professions= is the one listing a character's professions as links into Crafting, each profession's ranks by expansion folded in a =<details class="account-tiers">=. Under 640 pixels the attention rows stack and the wide tables scroll inside their card.

** The discussion

Every record page that takes comments draws a *Discussion* card ([[file:comments.org][Comments]]). It is a transcript, and both looks read it as one:

- *Who* is two letters in a square -- ink on the ground in the industrial look, the reader's own comment drawn in outline; a circle washed in the accent in the classic look -- and a name in the prose register. A badge in the micro register says "You", "Owner" or "Admin"; "via API token #N" says a token wrote it.
- *When* is a reading: the micro register, "3 hours ago", with the exact time in the configured zone on hover. It is the permalink.
- *What* is prose at reading size, drawn by the markdown renderer: headings at h3 and below, lists, quotes ruled on the left, code on the sunken ground, tables with micro-register headers, a mention as a ruled chip in the mono (a pill in the accent wash in classic), a record reference as a link marked with a faint =#=.
- *Replies* hang one step smaller from a single rule dropped from the avatar of the comment they answer, each tied to it with a short tick.
- *Actions* -- Reply, Copy link, Edit, Delete -- are micro-register text that brightens to the accent under the pointer; on a pointer that hovers they rest dimmed until the comment is looked at, and on a phone or from the keyboard they are always there.
- *The comment a link lands on* (=:target=, or one just posted) is the one accent outline on the page, with a brief wash that fades.
- *The composer* is one ruled field: a bar of Write and Preview tabs and the formatting tools above the text (shown only with scripting), the hint and the button below. It takes the accent ring on focus as a whole. The @ menu is a floating list on the hard ring.

Its classes: =.discussion= (the card), =.discussion-threads=, =.discussion-thread=, =.discussion-replies=, =.discussion-comment= (=.is-reply=, =.is-own=, =.is-deleted=), =.discussion-avatar=, =.discussion-main=, =.discussion-head=, =.discussion-author=, =.discussion-badge=, =.discussion-via=, =.discussion-when=, =.discussion-edited=, =.discussion-body=, =.discussion-gone=, =.discussion-actions=, =.discussion-action= (=.is-danger=), =.discussion-edit=, =.discussion-delete=, =.discussion-reply=, =.discussion-new=, =.discussion-empty=, =.discussion-composer=, =.discussion-bar=, =.discussion-tabs=, =.discussion-tab=, =.discussion-tools=, =.discussion-tool=, =.discussion-field=, =.discussion-preview=, =.discussion-menu=, =.discussion-foot=, =.discussion-hint=, =.discussion-buttons=; =.markdown= for rendered prose with =.md-table=, =.md-left=, =.md-center=, =.md-right=; =.mention=; =.record-ref=; and =.timeline-link= for the activity's link to a comment. They are the block /Discussion: comments on every record/ at the end of each stylesheet, written once against the tokens; =/comments/both-looks= in =tests/test-comments.c= checks a sample in both. The script's hooks are =data-discussion-*= attributes, never these classes.

** Pickers

A native =<select>= draws its popup with the operating system, and no stylesheet reaches it: on a dark theme it opens as a grey slab in somebody else's font, and with sixty record types in it there is nothing to type into.

So the select stays — hidden, and still what the form posts and what every existing handler reads — and a button and a panel drawn from these tokens go in front of it. Past seven options the panel gets a filter box. Arrows move, =Enter= picks, =Escape= closes, and a click outside dismisses it. With scripting off the native control is simply still there, which is the point of enhancing rather than replacing.

The panel is positioned against the viewport rather than its container. A card clips its contents — it has to, or a table's corners escape it — so a panel laid out inside one is cut off at the card's edge.

Where a form wants a record's id, the same idea applies twice over: a search box in front of the number input finds the record by name through =/ui/records/search=, and the id it fills in came from a record that exists. Asking for a number meant opening the list in another tab to read one off it, and a mistyped digit links to a different record silently.

** Tables

Every table with a heading row sorts and filters in the browser. A click on a heading reorders the rows on the page; a second click turns it round; =aria-sort= marks the column and draws the arrow. A heading that is not already a link becomes a button, so the keyboard reaches it. Tables of eight rows or more get a box that hides the rows not matching what is typed, with a count of what is left. This is the default rather than something a table opts into, because the tables nobody had marked were exactly the ones found not sorting: =wireSortableTables()= in =venture.js= takes every =table= on the page, and a =MutationObserver= takes the ones that arrive later -- an htmx swap, a streamed chat answer, a modal.

What a cell sorts by, in order: its =data-sort-value=; the =datetime= of a =<time>= when the time is what the cell says (a price's age, "3h", with or without its "stale" flag), so it sorts by the moment -- a venue's name with an age beside it sorts by the name; its text read as a figure -- gold ("9,999g 98s" in copper), money in any currency ("$1,234.56", "1,234.56 USD", "USD 1,234.56", "-$5.00", the accountant's "(5.00)"), a percent, a date ("2026-10-08", "2026-10-08 12:30 UTC", "8 Oct 2026", "2026-W41"), an age ("12 min ago", "in 3 h", "just now"), a plain figure with its unit -- and otherwise as a name, numbers in names in numeric order. A column is numeric when four values in five read as figures, so one "n/a" does not turn it alphabetical; whatever does not read sorts last, with the empty cells ("—"), either way round. A numeric column sorts largest (or newest) first on the first click.

Rows that are not data keep their place:

- a row that is one cell across the table -- "Nothing matches.", or a group's heading such as a realm or a login (=<th scope="rowgroup">=) -- stays put, and the rows under it sort among themselves;
- a total belongs in =<tfoot>=, where no sort reaches it; one left in the body (=class="total"=, =subtotal=, =summary=, =data-sort-pin=, or a first cell spanning columns with figures after it) stays at the foot of its group. A report row marked with =venture_report_result_mark_summary()= is drawn in the foot.

Some tables must not sort, and are left alone:

| Left alone | Because |
|-------------------------------------------------------------+-------------------------------------------------------------------|
| =data-no-sort= on the table or an ancestor | the server knows the order is the content |
| a statement report (=venture_report_result_set_ordered()=) | sections, accounts and totals: another order is a wrong statement |
| the money calendar's month and week grids | rows are weeks, columns are days |
| a line editor (=tbody[data-lines]=, or a field posted by a form outside its own row) | its rows post in order, and its script numbers them |
| a cell spanning rows (=rowspan=) | the rows it spans belong together |
| no =<thead>=, or more than one heading row | nothing to click, or no single column under a heading |
| =.chart-data= / =.visually-hidden= | a chart's table for a screen reader, in the chart's order |

A tick box or a form inside its own row does not count as an editor: it goes with its row. =data-no-filter= keeps the filter box off a table whose page has a finder of its own (the report index). A single heading opts out with =data-no-sort= on its =th=. A column of sparklines does (there is nothing to sort by), and so does a column of a table paged on the server that the server cannot sort by: Browse's /vs 7-day median/ is a figure of the rows on screen only, and sorting those fifty would pass for an order of every page. On Deals, which is not paged, the same column sorts in the browser like any other.

A table paged on the server says =data-server-sort= -- Browse, the inventory, every record list (=/e/TYPE=) -- because a heading must sort every page, not the fifty on screen. Its headings stay links the server sorts by, and with script a click on one, or on its pager, fetches that address and swaps only the table's card (=[data-sort-region]=, else the =.card=, else the =.table-wrap=) for the one in the answer: the filters, the search box and the scroll position stay where they were. The address goes into the history, so back and forward step through the orders, and the hidden =sort=/=dir= fields of a filter form beside the table are brought up to date, so the next "Show" asks for the order on screen. Anything unexpected -- an error, a redirect to the login page, an answer without the table -- becomes the ordinary page load it replaced. Without script the links load the page.

The documentation site does not load =venture.js=; =venture-docs.js= sorts its tables the plain way (figures, dates and names), which is all a page of reference tables needs.

** Home and the ticket board

*Home answers the morning's questions on one screen.* The =today= dashboard template -- the demo's home -- is four rows: money in and out this month, invoices and bills past due, what needs you (your tickets, the triage queue, promises missed, bills to approve), then the late invoices, the bills falling due, the urgent tickets, what awaits your approval and the things you do next. Every figure links to the records behind it. The home page's head is one line: the page's name, today's date and *Edit this page*; the other dashboards are in the sidebar. A metric's period reads as words ("September 2026", "All time"), never as the parameter it was asked with. The widgets are the dashboard kinds, rendered in the core like any other page's -- the web layer draws only the frame.

*A ticket card answers the questions you would open it for.* The number, the priority in words when it is urgent or high, and the service-level clock across the top; the title; whose it is (the company, else the person who raised it, else "Internal") and who has it ("Unassigned" when nobody does); how long ago it was opened, its due date, its points; at most three tags. The head of the board says how the queue stands -- open, waiting to triage, past a promise -- and the controls are one labelled toolbar: whose tickets, a *Type* menu in words, board or list, and *Save view*. Columns are headings with human names and scroll sideways, snapping to a column; on a phone each column is most of the screen wide.

** A keyboard, a screen reader, a phone

- *A way past the sidebar.* The first thing Tab reaches is *Skip to content*, visible only while focused; =<main id="main">= takes the focus. The sidebar is a =<nav aria-label="Main">= and its search box is labelled.
- *Every control is named.* A button that shows only an arrow, a bin or a cross carries an =aria-label=; a table column of such buttons has a heading only a screen reader sees (=.visually-hidden=, clipped rather than hidden, so it is still read). =tests/test-record-view.c= checks every button on the main pages for a name.
- *Focus is always visible*, in both looks and every theme, with the accent ring -- including on ghost buttons and summaries that once turned it off.
- *Refusals are announced.* An error notice (=notice negative=) and the error page carry =role="alert"=; toasts appear in a polite live region that is on the page from the start, because a region added with its first message is often not read out, and a failure toast is an alert of its own.
- *On a phone* the sidebar is one line -- the name, the entity, search, New, Inbox -- and a *Menu* button (=aria-expanded=, =aria-controls=) that opens the same list a desk shows, folded groups and all. It is drawn open and folded by script only on a narrow screen, so with scripting off every link is still there. Dashboard figures sit two to a row and everything else takes the full width; a document's lines become small blocks with their own captions; a table of records scrolls inside its card instead of pushing the page sideways.

Rules for these are appended to both stylesheets as one block, written against the tokens, so the two looks stay in step.

** Why this and not the usual

A business tool is looked at for hours. The generic interface — rounded white cards, blue buttons, a drop shadow under everything — is designed to be glanced at, and it goes soft under sustained attention: nothing is aligned to anything, every element is lifted the same amount, and colour is spent on decoration so there is none left for meaning. A panel drawn with one pixel rules, two registers of type and one red is the opposite: everything sits on a line, the hierarchy is scale, and when something is red it is because you should look at it.

* Organization access

The organization picker lists only the caller's memberships, unless their
global owner/admin role permits all organizations. Selecting a parent does
not grant its children's data. Lists, search results, reference choices,
reports, exports and dashboard widgets share the same record policy.

A user without memberships lands on their account page with a message asking
an organization owner to grant access. They can change their own password and
sign out. Hidden records answer 404; the interface never distinguishes an
unknown record from a record outside the caller's organizations.

The generated access-record forms manage memberships and teams. Company,
contact, deal, ticket and venture forms expose owner and team references.
An organization viewer's new-record submission becomes a confirmation;
applying it still requires an authorized approver. See
[[file:orgaccess.org][Organization access]] for the full role matrix.

* Form submission feedback

Validation refusals stay above the form with its entered values intact. A
request in flight blocks a second submit; when it completes, controls regain
their previous disabled state. A lost or unreadable response is an /unknown
outcome/, since the write may already have committed. The notice asks the
person to check the record before retrying; it never promises nothing was
saved based on a network error.
