#+title: Leads
#+description: Capture, qualification, assignment and conversion before the opportunity

* An inquiry has its own lifecycle

The =leads= module requires =crm=. It owns =lead=, =lead_form=,
=lead_assignment_rule=, =lead_routing_rule=, =lead_scoring_rule= and
=lead_score_history=. Their tables, forms, REST resources, CLI commands,
CSV import and audit records derive from the field tables. Switching the
module off hides its records and reports and refuses its actions. A deal's
existing stage remains the opportunity's stage; leads add no pipeline.

A lead belongs to one organization and may name a venture and a campaign.
It carries name, company name, email, phone, website, source, integer score,
owner, qualification state, notes, first-seen and last-activity timestamps,
the =score_manual= mark and =routing_rule_id=, the rule that last placed it.
The score is the sum of the organization's scoring rules unless an operator
types one; see [[*Scoring formula][Scoring formula]]. Campaign references
require outreach to be enabled when written, but leads otherwise work
without outreach.

| State | Meaning |
|-------+---------|
| =new= | Awaiting work |
| =working= | Being worked |
| =qualified= | Ready for conversion |
| =unqualified= | Unsuitable, with =unqualified_reason= |
| =recycled= | Return to nurturing, with =unqualified_reason= and =recycle_until= |
| =converted= | Company/contact and optional deal linked by the service |

Change qualification through the ordinary lead editor or generic API/CLI.
State and owner changes append interactions. New dated lead interactions
advance =last_activity_at= in the same transaction, without moving it
backward for older events; reload a lead after logging an interaction. An interaction may now name a
lead before there is a contact, or a company; existing contact interactions
keep working. The lead's related-record section shows these interactions.

* Public capture

Create a form through the ordinary record editor. Set its organization,
optional venture, =active=true= and =on_duplicate= (=merge= by default).
=fields= is an optional JSON array of accepted field names; the permitted
public inputs are =name=, =company_name=, =email=, =phone=, =website=,
=source= and =notes=. Public callers cannot choose organization, venture,
owner, qualification or conversion references. The form's name supplies the
source when the submission does not provide one.

A blank =public_token= generates a random UUID. Tokens are globally unique
capabilities because the public URL has no organization component. Business
matching and assignment remain scoped to the form's organization.

#+begin_src sh
venturectl create lead_form name='Website inquiry' organization_id=1 \
  active=true on_duplicate=merge honeypot=fax \
  'fields=["name","company_name","email","phone","notes"]'
#+end_src

Copy the returned =public_token= into an ordinary HTML form:

#+begin_src html
<form method="post" action="https://venture.example/f/PUBLIC_TOKEN">
  <label>Name <input name="name" required></label>
  <label>Company <input name="company_name"></label>
  <label>Email <input name="email" type="email"></label>
  <label>Phone <input name="phone" type="tel"></label>
  <label>Message <textarea name="notes"></textarea></label>
  <label hidden>Fax <input name="fax" tabindex="-1" autocomplete="off"></label>
  <button type="submit">Send inquiry</button>
</form>
#+end_src

=POST /f/:token= accepts form encoding and JSON without local credentials.
The existing =security.login_rate_limit= budget supplies an independent
per-peer-IP capture limiter; =server.max_request_size_mb= caps the body.
A filled honeypot returns an empty 200 response and creates nothing. Other
accepted captures return 200; form submissions redirect with 302 when the
form has an HTTP(S) or local-path =redirect_url=. JSON submissions stay 200.
Inactive, missing or disabled forms answer 404; rate exhaustion answers 429.

* Duplicate handling and assignment

=VentureLeadService= normalizes email to lowercase and removes the local
part's =+tag=, phone to digits, and website to a lowercase host without
=www.=. No country-code inference, provider-specific dot removal or fuzzy
company-name matching is performed. Empty identifiers never match.

Any equal normalized email, phone or website matches a live lead, contact
or company in the same organization. Leads are considered first, then
contacts, then companies, with the lowest id breaking ties.

- =reject=: refuse with 409 and leave the transaction unchanged.
- =merge=: retain the existing record and append a capture interaction
  containing the new source. Existing customer details are not overwritten.
- =create=: deliberately retain another inquiry.

Generic REST, CLI and CSV creation use =reject=. A CSV import therefore
rolls back as a whole when an inquiry duplicates existing data. Form capture
uses the form's selected policy. Two submissions to a merging form create
one lead and a second-source interaction.

Routing rules run first (see [[*Routing rules][Routing rules]]). When no
routing rule matches, the older assignment rules still apply: active
assignment rules filter by source and venture within the lead's
organization. The rule with more filters wins; equal specificity uses the
lowest id. =round_robin= advances a persisted cursor in the creation
transaction; =least_busy= counts new, working and qualified leads; =first=
uses the first nonempty username. An explicit owner is preserved. No
matching rule leaves the lead unassigned; a matching empty rota is refused.
Reassignment uses the same service from REST and CLI; editing Owner in the
web form also records its history.

* Routing rules

A =lead_routing_rule= belongs to one organization and carries =position=,
=conditions=, =action=, =assign_to=, =team_id=, =venture_id=, a persisted
round-robin =cursor= and =active=. Create and edit rules through the
ordinary record editor, REST or =venturectl create lead_routing_rule=.

=conditions= is text with one condition per line or semicolon. Each is
=field=value= (case-insensitive equality) or =field~pattern= (case-insensitive
regular expression). A field is any lead column in its wire spelling
(=source=, =company_name=, =status=, =campaign_id=), a reference by its
target's name (=campaign=Spring=, =venture=Rockets=) or a custom field or
attribute (=country=US=, =company_size~^[0-9]{3,}=). Every condition must
hold; an empty text matches every lead. A rule whose conditions do not
parse, whose pattern does not compile, or whose action lacks its target is
refused when written, not discovered when a lead arrives.

| Action | Effect |
|--------+--------|
| =assign_user= | Sets =owner= to =assign_to= |
| =round_robin= | Rotates =owner= over the active members of =team_id= |
| =assign_venture= | Sets the lead's venture to =venture_id=; the owner is untouched |

Rules are evaluated in ascending =position= (ties by id) when a lead is
created without an explicit owner and on an explicit re-route. The first
active match acts and is recorded on the lead as =routing_rule_id= with a
"Lead routed" interaction. When the organization has active routing rules
and none matches, the lead stays unassigned and a "No rule matched"
interaction is appended; an organization with no routing rules writes no
routing history. Generic writes cannot set =routing_rule_id=.

Round-robin state is the rule's own =cursor=, advanced in the same
transaction as the lead. The rota is the team's members, by user id, whose
team membership, organization membership in the lead's organization and
account are all active; a member who leaves or is deactivated is skipped and
the cursor continues fairly over the rest. A rota with nobody left refuses
the write. Round-robin needs =orgaccess= for teams and memberships; the
team must belong to the rule's organization.

#+begin_src sh
venturectl create lead_routing_rule organization_id=1 name='Web to sales rota' \
  position=10 'conditions=source=web' action=round_robin team_id=3 active=true
venturectl create lead_routing_rule organization_id=1 name='Enterprise US' \
  position=20 $'conditions=country=US\ncompany_size~^[0-9]{3,}$' \
  action=assign_user assign_to=alice active=true
venturectl leads reroute 42
#+end_src

=POST /api/v1/leads/:id/reroute= and =venturectl leads reroute ID= (also
=lead reroute=) clear the owner and run the rules again, recording the
verdict either way. Converted leads are read-only and cannot be re-routed.
Staging (=?stage=1=) is not offered for re-routing.

* Scoring formula

A =lead_scoring_rule= carries =conditions= in the same syntax, integer
=points= (negative allowed) and =active=. A lead's =score= is the sum of the
points of every active rule in its organization whose conditions hold. The
lead service recomputes it on every save it handles -- creation, capture,
qualification, reassignment, routing -- so there is no generic write that
leaves a stale score. Each change appends a =lead_score_history= row with
the previous score, the new score, the comma-separated ids of the rules
that fired, the =manual= mark and =scored_at=. History rows are written only
by the service; a generic write to =lead_score_history= is refused.

An operator may still type a score. A saved score that differs from the
stored one without =score_manual= set takes the mark automatically, as does
a nonzero score on a new lead; a marked lead keeps its score while rules and
fields change. Clear =score_manual= through the ordinary editor, or run
=POST /api/v1/leads/:id/rescore= / =venturectl leads rescore ID=, which
clears the mark and applies the formula. Both write history when the score
changes. Scoring rules in another organization never count.

#+begin_src sh
venturectl create lead_scoring_rule organization_id=1 name='Web inquiry' \
  'conditions=source=web' points=30 active=true
venturectl create lead_scoring_rule organization_id=1 name='Large company' \
  'conditions=company_size~^[0-9]{3,}$' points=20 active=true
venturectl update lead 42 score=80            # marks score_manual
venturectl leads rescore 42                   # clears it and recomputes
#+end_src

The formula is rule-based only; there is no model training, behavioural
tracking or external enrichment.

* Conversion is one transaction

Qualify first, then use the web Convert action, the REST action or:

#+begin_src sh
venturectl lead convert 42 deal=yes
venturectl lead convert 42 deal=no company_id=7 contact_id=12
venturectl --stage lead convert 42 deal=no
venturectl lead reassign 42 owner=alex
venturectl lead reassign 42
venturectl update lead 42 status=recycled \
  unqualified_reason='Budget next quarter' recycle_until=2026-12-01
#+end_src

=venture_lead_service_convert()= creates or links a company and contact and
optionally creates a deal. New records inherit organization, venture,
source and campaign. A missing company name uses the lead's name. Linked
records must belong to the same organization; an existing contact cannot
belong to another company. Existing linked records retain their attribution.
Generic writes cannot forge conversion references or converted status.
Converted leads are read-only; append interactions to continue their history.

Company, contact, deal, lead state, conversion ids, interaction and audit
writes share one transaction. A deal failure leaves no partial company or
contact behind. A second conversion or stale lead version is a conflict.
The input lead object remains unchanged by conversion; use its returned
record or reload it. The new deal uses the existing default stage.

The service emits =converting= inside the transaction before writes. Its
=G_SIGNAL_RUN_LAST= handlers receive a detached snapshot and may return an
owned =GError= to veto. =converted= is emitted only after the outermost
commit; rollback drops queued notices. Keep external effects on that signal.

The assistant's =venture_lead_convert= stages through the same confirmation
queue as REST =?stage=1=; autonomous policy applies through the same service.
Approval rechecks the stored version and eligibility. CLI =--stage= works
for conversion. Staged reassignment is refused; ordinary reassignment is
immediate. This module sends no mail and schedules no nurturing work.

* Reports and dashboards

=lead_sources= groups leads created in the requested period by source and
campaign, showing count, current converted count and percentage converted.
It measures a creation cohort, not a historical snapshot of qualification.

=lead_response_time= measures creation to the earliest dated outbound
interaction carrying =lead_id=. Inbound interactions do not count; unanswered
leads are counted separately. It reports seconds and average seconds.

=leads_recycled_due= exposes the =leads_recycled_due= count for recycled
leads whose return date has arrived. It is a live queue, independent of the
report period. Use the ordinary report metric dashboard widget with report
=leads_recycled_due= and field =leads_recycled_due=.

=routing= groups leads created in the period by the routing rule and owner
that placed them, one row per pair with the count, and reports =routed=
and =unrouted= metrics; a lead with neither a rule nor an owner is unrouted.

=scoring= bands scores in steps of =band_size= (default 25; negative scores
share a =<0= band) and reports, per band, the count, converted count and
conversion rate, with =leads= and =average_score= metrics.

All five reports accept =organization_id= and default to the installation's
default organization. They do not combine organizations. Interaction writers
should retain =lead_id= for response-time attribution, including after
conversion. A nurturing lane may consume recycled leads and their dates;
this lane does not create enrollments or activities.

* Upgrades and verification

Paired migration =000140_leads.sql= verifies the additive lead and interaction
schema after metadata reconciliation. It preserves existing CRM rows and
accepts installations where leads are disabled and their table is absent;
it does not infer historical inquiries or conversion history from deals.
The SQLite upgrade test exercises old columns, repeated migration,
preservation of contacts, invalid-schema refusal and a disabled-table path.
The PostgreSQL script is shipped but has not been run against a live server.

=test-leads= covers normalization, scoped matching, form policies, public
capture, rate limiting, assignment, qualification history, recycling,
conversion and injected rollback, lifecycle signals, REST staging and actual
CLI execution, report values, module hiding and upgrades. =test-auth= checks
that lead business actions refuse anonymous callers. =test-lead-routing=
covers position order and first match, the no-match timeline note, the
legacy fallback, condition syntax over columns, references and attributes,
refusal of malformed rules, fair round-robin rotation with persisted cursor
and skipped members, venture placement, re-route, the scoring sum and its
history, manual override and rescore, refusal of generic history and
routing-reference writes, both reports and the real CLI verbs.

Paired migration =000371_lead_routing.sql= verifies that the three routing
and scoring tables are present together, or all absent when the module is
disabled; the lead's =score_manual= and =routing_rule_id= columns come from
additive metadata reconciliation.

Conversion refuses recursive conversion calls from its callbacks, and archived leads cannot be converted. Interaction history may reference a deal alone, including activity completion history.

A reply linked to both a lead and an enrolled contact updates lead activity history and exits matching sequences atomically. Neither service repeats the other service's already-authorized write.
