* Extending VENTURE

Four mechanisms, in ascending order of effort, plus a fifth for code that
is not C at all.

All of them are loaded by =VenturePluginManager= at startup, from the
directories named by =plugins.paths= and =plugins.venture_type_paths=, plus
the compiled-in =VENTURE_PLUGINDIR=. Each file goes to a /runtime/: =.so=
to =native=, =.c= to =crispy=, =.yaml= to =declarative=. A directory holding
a =*.plugin.yaml= manifest is a plugin of its own, and a manifest is how an
=exec= plugin -- a program in any language -- is loaded. A plugin can add a
runtime, and a file nothing claims yet waits for one. The loader's rules,
the manifest format, exec plugins and the protocol they speak are in
[[file:plugins.org][Plugins: runtimes, manifests and exec]].

A plugin that fails to load is skipped with a warning rather than stopping
the server, because one broken extension should not cost you access to your
data. The exception is anything named in =plugins.required=: that list exists
precisely to say "this install is wrong without it", and a failure there is
fatal.

For development, =VENTURE_PLUGIN_PATH= and =VENTURE_VENTURE_TYPE_PATH= add
directories without editing the configuration; =make run= sets both to the
build tree.

* 1. A declarative venture type

A new kind of venture — its fields, metrics and report columns — is a YAML
file in a directory named by =plugins.venture_type_paths=. No code, no
rebuild, no restart beyond the next one.

#+begin_src yaml
name: etsy
label: Etsy shop
description: A print-on-demand or handmade storefront

fields:
  shop_name:     string
  listing_fee:   money
  section:
    type: string
    label: Shop section
    indexed: true
  material:
    type: enum
    choices: [wood, acrylic, paper, metal]

metrics:
  - listings_active
  - revenue_per_listing
#+end_src

Five ship in =data/venture-types/=: =books=, =etsy=, =newsletter=,
=virtual_economy= (trading, crafting or farming inside a game world or a
platform's own economy: the world, the server or region, the currency code,
the faction, the account handle, the main marketplace) and =general=
(anything that is not a business: a household, a hobby, a club, a project).
[[file:examples/game-economy.org][The game-economy walkthrough]] uses
=virtual_economy= from end to end.

** The declarations are enforced at the save

A venture names its type in =venture_type=, and the fields the type
declares live in the venture's attribute bag. A =venture= save validator
(=src/core/venture-venture-type-check.c=) holds every writer -- the form,
the REST API, =venturectl=, an approved staged change, the assistant -- to
what the YAML says:

- =required= fields must be present and non-empty;
- an =enum= value must be one of its =choices=;
- an =integer= or =double= field's text must parse as a number (a whole one
  for an integer) and fall within =min= and =max=;
- =max_length= and =pattern= apply as they do to a compiled field.

When the rules apply follows the reference rule: *what a save writes is
checked, what it keeps is left alone*.

- A venture created with a type, or moved to another, is checked against
  every field the type declares.
- A venture keeping its type has only the declared attributes whose value
  this save changes checked. A venture stored before a field became
  required, or before a choice was withdrawn, stays editable; the rule
  bites when somebody writes that field.
- A =venture_type= that is written and not registered is refused, naming
  the registered ones. With plugins switched off nothing is loaded and
  nothing can be judged, so any name is accepted; and a venture keeping a
  type whose file has since been removed stays editable.

Attributes are written in the same request as the rest of the record, so a
type with a required field can be created in one step:

#+begin_src sh
venturectl create venture name="Silverfen auction house" \
    venture_type=virtual_economy attributes.world="Evermoor Online" \
    attributes.marketplace=auction_house
#+end_src

Over the REST API they are the nested =attributes= object:
={"name": "...", "venture_type": "virtual_economy", "attributes": {"world":
"Evermoor Online"}}=. A =PATCH= merges into the bag; a =null= value
removes an attribute.

* 2. A crispy script

Drop a =.c= file into a plugin directory. crispy compiles it on demand and
caches the result by content hash, so it costs a compile only after an edit.
The compiled object resolves =venture_*= against the running executable, so
the full API is available with no link line to get right.

#+begin_src C
#include <venture/venture.h>

gboolean venture_plugin_register(VentureContext *context, GError **error);

gboolean
venture_plugin_register(VentureContext *context, GError **error)
{
	venture_report_registry_add(
		venture_context_get_report_registry(context),
		VENTURE_REPORT(venture_func_report_new(
			"royalties", "Royalty statement",
			"Per-title royalties for the period", my_royalty_report)));

	return TRUE;
}
#+end_src

A complete, working one is in [[file:../plugins/scripts/royalties.c][=plugins/scripts/royalties.c=]] — royalties by genre,
around 250 lines with the comments. Copy it into a plugin directory to see
the mechanism work:

#+begin_src bash
cp plugins/scripts/royalties.c ~/.local/share/venture/plugins/
#+end_src

Declare the entry points as well as defining them. The tree builds with
=-Wmissing-declarations=, and so should you; a plugin is one translation unit
with no header of its own, so nothing else declares them.

The compiled object is cached by content hash under =<state_dir>/crispy-cache=.
An unchanged source costs a lookup on the next start rather than a compile —
in the region of 50ms against 250ms here. Editing the file produces a new
hash and a new object; touching it without changing it does not.

Compile errors are reported as plugin load failures, naming the file, so a
typo shows up as a skipped plugin with gcc's message rather than a mystery.

Set =plugins.allow_crispy: false= to turn this off. It runs a compiler over
files in the plugin directories, so enable it only where you trust what is in
them — which, for a personal install, you do.

* 3. A native plugin

A compiled =.so= in =plugins.paths=, loaded with GModule. Same entry point,
same API; use it when you want a build step and a Makefile of your own.

Plugins are never unloaded. A loaded object may have registered a GType, and
pulling the code out from under a live type crashes on next use.

A plugin should declare itself as a module, in one call:

#+begin_src C
static GType (*const types[]) (void) = { venture_subscription_get_type, NULL };
static const gchar *const requires[] = { "finance", NULL };
static const gchar *const reports[] = { "subscriptions", NULL };
static const VentureModuleInfo module = {
	"example", "Example plugin", "Recurring subscriptions.",
	requires, NULL, types, reports, NULL, FALSE
};

venture_context_register_module(context, &module, error);
#+end_src

That registers the types, resolves the module against the running configuration and applies the result, so =modules.example.enabled: false= switches the plugin off exactly as it switches a built-in module -- types hidden, reports hidden, pages gone. See [[file:modules.org][Modules]].

A record type whose invariants span rows -- "both ends of this must exist" -- registers a /save validator/ with =venture_database_add_save_validator()=. It runs inside the database lock before every write of that type, from every writer, and may fill derived fields. =record_link= is the worked example.

A record type whose saves are accounting events -- a payment, a trade leg, a fee -- registers a /posting source/ with =venture_ledger_register_source_type()=: the type, the name of a posting rule it added to =venture_posting_service_get_rules()=, a function saying whether a version is postable, and the date property its journals carry. From then on every save of the type, through every door, posts in the record's own transaction exactly as a sale does: an unchanged save posts nothing, a changed one reverses and reposts, and a version that stops being postable (cancelled, say) has its journals reversed and its memo holding movements cleared. The rule is built for both the stored and the new version on every save, so it must be pure. Register once per database at install time; a type registered twice is refused. Never add a =VENTURE_IS_*= check to the ledger instead. See [[file:ledger.org::*Posting on save: the source registry][Posting on save]] for the whole contract and an example.

* 4. An exec plugin

A program in its own directory, beside a manifest:

#+begin_src yaml
name: supplier-csv
runtime: exec
protocol: 1
entry: fetch.sh
exec:
  timeout: 30
#+end_src

It reads one JSON request on standard input and answers in JSON lines on
standard output; settings and secrets arrive on stdin only. Off unless
=plugins.allow_exec= is on, and run with an argv array, a cleared
environment, a deadline and byte caps -- but as the server's user, so it
is not a sandbox. What it can be used for comes from its manifest's
=provides= list; see [[file:plugins.org][Plugins]] for all of it.

* 5. A record type in C

The most powerful and still small. See [[file:data-model.org][the data model]] — a field table and a
registration is the whole type, and it becomes a database table, a REST
resource, a web view, an AI tool and a set of CLI subcommands at once.

* Automations

Scheduled work is described in podomation's DSL, in the file named by
=automation.pods_file=:

#+begin_src
pod nightly = cron->new("0 2 * * *");
nightly->on_tick => venture->report("pnl", "yesterday")
    | log->write_info("Yesterday: {pipe->summary}");

pod restock = timer->new(3600000);
restock->on_tick => venture->low_stock()
    | ntfy->send("Restock needed: {pipe->count} items\n{pipe->detail}");

pod watch = venture->new();
watch->on_created => venture->count("sale");
#+end_src

The engine is embedded in the server process, so an automation sees the same
database and the same validation as everything else. =VentureDatabase= emits
=entity-saved= and =entity-deleted=, which is how "when a sale is recorded, do
X" works without the write path knowing automations exist.

** The =venture= pod module

Registered in-process rather than loaded as a =.so=, because it needs the
=VentureContext= and an out-of-process module could not be handed one.

Events, raised on any record change: =on_created=, =on_updated=,
=on_deleted=. A plugin may register more (below).

*An automation's own writes do not raise events.* Otherwise the obvious rule

#+begin_src
watch->on_created => venture->create("research_note", "title=seen");
#+end_src

creates a record, which raises =on_created=, which creates a record, until
the disk is full. There is no useful depth limit to pick instead — one level
of cascade is as arbitrary as ten — and a rule that genuinely needs to chain
can call the next step in its own pipeline, where the author can see it.
Audit entries never raise events either, for the same reason.

Handlers -- the built-ins, registered first; the modules' sweeps
(=dunning_sweep=, =recurring_run=, =mail_sync=, =backups_run= and the rest)
are listed in [[file:automation.org][Automating VENTURE]]:

| Handler      | Arguments                       | What it answers                       |
|--------------+---------------------------------+---------------------------------------|
| =query=      | type, then =field=value= pairs  | how many records match                |
| =count=      | type, then =field=value= pairs  | the same, read as a count             |
| =report=     | report name, period             | a rendered report                     |
| =create=     | type, then =field=value= pairs  | writes a record                       |
| =low_stock=  | —                               | items at or below their reorder point |

Fields are written as =field=value=, the same syntax =venturectl= and the
REST API take, with the same =field__operator=value= filters:

#+begin_src
venture->create("idea", "title=A pop-up shop", "status=researching");
venture->query("sale", "channel=etsy", "gross__gte=50");
#+end_src

*Not JSON*, even though the API takes JSON here. podomation's DSL
interpolates =\{...\}= inside string literals, so every brace in a JSON
argument reads as a variable reference and the rule fails to interpolate
rather than doing anything. A JSON argument is still accepted if it starts
with a brace — for callers that are not the DSL — but from a rule, use pairs.

Every handler answers in the same shape — =count=, =summary=, =detail= — so a
downstream pipe stage can read =\{pipe->count\}= without knowing which
handler produced it. Writes are audited as =VENTURE_ACTOR_KIND_AUTOMATION=,
so reviewing the log later answers "did I do this, or did a rule?".

=venture_automation_invoke()= runs a handler immediately, as though an event
had triggered it. It exists because the alternative way to find out what a
rule will do is to wait for its trigger and read the log afterwards.

** A plugin's own handlers and events

What the =venture= module answers to is a registry, not a list in the
module: =venture_context_get_automation_handlers()= holds every handler a
rule may call and every event a pod may bind. It lives on the context
because plugins load before the engine is built, and a reload rebuilds the
engine without forgetting what a plugin added. The built-ins are registered
first, when the context first hands the registry out, and a name is never
registered twice -- so no plugin can replace =report= or =count=, and an
unknown name is still refused, naming the handlers that exist.

A handler, from =venture_plugin_register()=:

#+begin_src C
static gboolean
subscription_costs(VentureContext *context, const gchar *name,
                   GVariant *params, GVariant **result,
                   gpointer user_data, GError **error)
{
	const gchar *window = venture_automation_argument(params, 0);
	/* ... work out count, summary, detail ... */
	if (NULL != result)
		*result = venture_automation_result_new(count, summary, detail);
	return TRUE;
}

venture_automation_handler_registry_add(
	venture_context_get_automation_handlers(context),
	"subscription_costs", "Active subscriptions and their annual cost",
	subscription_costs, NULL, NULL, error);
#+end_src

and a rule calls it like any built-in: =venture->subscription_costs()=.
Names are a lower-case letter, then lower-case letters, digits and =_=, up
to 64 bytes -- what the DSL can spell. A handler:

- runs synchronously on the main thread, inside the pod or the invocation
  that called it, and may read and write the database; a write should be
  made as the automation actor;
- reads its arguments with =venture_automation_argument()= (positional
  strings, as the DSL passes them) and answers with
  =venture_automation_result_new()=, the =count= / =summary= / =detail=
  shape every handler shares;
- fails by setting its =GError=. A handler that returns =FALSE= without one
  is taken to have logged its own reason (every built-in does, with
  =g_warning()=): the caller reports =VENTURE_ERROR_AUTOMATION= ("see the
  log") and a pod does not log it twice. So keep that code for "already
  reported" and raise your own errors with another.

An event:

#+begin_src C
venture_automation_handler_registry_add_event(
	venture_context_get_automation_handlers(context),
	"feed_finished", "A market-data feed finished a run", error);

/* later, when it happens: */
venture_automation_emit(context, "feed_finished",
	g_variant_new_parsed("{'source': <%s>, 'rows': <%x>}", name, rows),
	&error);
#+end_src

#+begin_src
pod feeds = venture->new();
feeds->feed_finished => log->write_info("{event->source}: {event->rows} rows");
#+end_src

=venture_automation_emit()= refuses an event nobody registered -- whether
or not automation is on, so a typo is found the first time -- and refuses
=on_created=, =on_updated= and =on_deleted=, which only the database
raises: a plugin forging a record change would set off every rule that
trusts one. The data is an =a{sv}= dictionary, read in a rule as
=\{event->member\}=. With automation off or not started the emit succeeds
and nothing happens. The cascade guard holds for events as for writes: an
event raised from inside a handler goes nowhere.

An exec plugin provides a handler from its manifest instead, with the
=automation_handler= provides kind; see [[file:plugins.org][Plugins]].

The event above is an illustration; the feeds module registers its two real ones the same way, =feed_synced= and =feed_failed=, raised after every data source run with the source, the run, the organization, the status, the rows and the error in the event's data -- see [[file:automation.org::*Market data events][Automating VENTURE]] for the members and [[file:market-data.org::*Runs][Market data: runs]] for what a run is.

* Pages and sidebar rows

A plugin can add pages of its own. The server does not exist when plugins
load, so a plugin leaves a /web extension/ on the context, and every web
server built over it runs the extension after registering its own routes:

#+begin_src C
static HtmxResponse *
costs_page(HtmxRequest *request, GHashTable *params, gpointer user_data)
{
	VentureWebServer *server = user_data;
	HtmxResponse *refusal;

	refusal = venture_web_server_require_module(server, request, "example");
	if (NULL != refusal)
		return refusal;
	refusal = venture_web_server_require_page(server, request,
	                                          VENTURE_USER_ROLE_VIEWER);
	if (NULL != refusal)
		return refusal;

	return venture_web_server_render_page(server, request,
		"/example/subscriptions", "Subscription costs", body_html);
}

static gboolean
example_web(VentureWebServer *server, gpointer user_data, GError **error)
{
	venture_web_server_add_classified_route(server, HTMX_METHOD_GET,
		"/example/subscriptions", VENTURE_DATA_CLASS_TENANT,
		VENTURE_HOSTED_ROUTE_NONE, costs_page, server);

	return venture_web_server_add_nav_link(server, "/example/subscriptions",
		"Subscription costs", "calendar", "example", error);
}

/* in venture_plugin_register(): */
venture_context_add_web_extension(context, example_web, NULL, NULL);
#+end_src

The rules:

- *Routes through =venture_web_server_add_classified_route()=*, never the
  raw router: hosted mode refuses unclassified routes, and the class is
  what tenant isolation reads.
- *Every route carries its own guard.* =venture_web_server_require_page()=
  sends an anonymous visitor to the login page and refuses a role short of
  the page's with a 403; =venture_web_server_require_api()= answers 401 and
  403 as JSON; =venture_web_server_require_module()= answers a switched-off
  module the way a built-in page does. A route with no guard looks exactly
  like one with, which is why =tests/test-auth.c= checks an extension's.
- *Built-in routes win.* Extensions run after every built-in route and the
  router takes the first match, so an extension can neither shadow a page
  nor take over =/api/v1/:type=. A path a built-in already matches is
  simply unreachable; give a plugin's pages a prefix of their own.
- *=content= is HTML as given.* =venture_web_server_render_page()= wraps it
  in the shell every page uses -- sidebar, assistant, both looks -- and
  writes it unchanged, so escape what a person typed with
  =venture_html_escape_append()=, and use the theme's classes and tokens,
  never a literal colour.
- *A sidebar row is checked.* =venture_web_server_add_nav_link()= is only
  callable from an extension (built-in pages belong in the static table);
  its path must be plain and absolute and already served by a GET route;
  its label is escaped; its icon is a name from the built-in set
  (=venture_web_server_nav_icon_names()=), never markup; its module, if
  given, must exist and hides the row while off. Rows appear under a
  "Plugins" heading drawn only when there is one; see
  [[file:navigation.org][Navigation]].
- *A failing extension is skipped with a warning*, like a failing plugin;
  the routes it added before failing stay, because a router cannot take
  one back.

=plugins/example/venture-example-plugin.c= does all of this: a handler, a
page and its row.

* Plugin configuration at runtime

A plugin gets settings without inventing storage: the =/plugins= page shows
every loaded plugin with a YAML editor, and what it saves lands on a
=plugin_config= record — audited like any other write, admin-gated, and
validated as YAML before anything is stored.

The plugin's side is two calls:

#+begin_src C
static void
on_config_changed(VenturePluginManager *manager, const gchar *name,
                  gpointer user_data)
{
	g_autoptr(JsonNode) config = NULL;

	if (0 != g_strcmp0(name, "myplugin.c"))
		return;

	config = venture_plugin_manager_get_config(manager, "myplugin.c");
	rate = venture_plugin_config_get_double(config, "rate_percent", 70.0);
}

/* in venture_plugin_register(): */
manager = venture_context_get_plugin_manager(context);
on_config_changed(manager, "myplugin.c", NULL);   /* initial read */
g_signal_connect(manager, "config-changed",
                 G_CALLBACK(on_config_changed), NULL);
#+end_src

The manager is on the context before any plugin loads, so the lookup in
=venture_plugin_register()= finds it. (Before plugin runtimes it was set
only after loading, and this lookup quietly returned =NULL= at startup.)
An exec plugin gets the same configuration as the =settings= member of its
request, read at each run.

The signal fires the moment the page saves, so the plugin follows its
settings live — no restart, no polling. =plugins/scripts/royalties.c= is the
worked example: set =rate_percent: 65= on the /plugins page and the very
next royalties report uses it.

Secrets do not belong in plugin configuration, for the same reason they do
not belong in =config.yaml=: name an environment variable there instead.

* Market data: data source providers

Where a data source's prices come from is a /provider/, and the providers are a registry on the context: =venture_context_get_data_source_providers()=, added to with =venture_data_source_provider_registry_add(registry, provider, error)=. Three ship -- =http_json=, =csv= and =file_jsonl= -- and they are registered whether or not the feeds module is on, so a plugin may add its own unconditionally; a name already held is refused (=VENTURE_ERROR_ALREADY_EXISTS=), never replaced.

A provider is either a GObject implementing the =VentureDataSourceProvider= interface (=get_name=, =get_label=, =dup_settings_schema=, an optional =freeze= and =list_units=, =fetch_async=) or, with no GObject to write, one blocking function wrapped by =venture_func_data_source_provider_new(name, label, schema_json, fetch, user_data, destroy)=:

#+begin_src C
static VentureFeedBatch *
price_list_fetch(VentureFeedRequest *request, gpointer user_data, GError **error)
{
	g_autoptr(VentureFeedBatch) batch = venture_feed_batch_new();

	/* venture_feed_request_http_get() or venture_feed_request_read_file(),
	 * then venture_feed_batch_add_venue() / _begin_snapshot() /
	 * _add_listing() ... */
	return g_steal_pointer(&batch);
}

/* in venture_plugin_register(): */
g_autoptr(VentureDataSourceProvider) provider = venture_func_data_source_provider_new(
	"price_list", "Supplier price list",
	"{\"type\": \"object\", \"properties\": {\"url\": {\"type\": \"string\"}}}",
	price_list_fetch, NULL, NULL);

if (!venture_data_source_provider_registry_add(
		venture_context_get_data_source_providers(context), provider, error))
	return FALSE;
#+end_src

The rules that matter, all of them because a fetch runs on another thread:

- *A fetch touches nothing but its =VentureFeedRequest=.* The function form runs on a GTask thread, the interface's =fetch_async= on the feeds worker; neither may read the database, the configuration or a plugin's settings. Anything a fetch needs from the main thread is taken by =freeze=, which runs there when a source is loaded and returns data that never changes afterwards.
- *Network and files go through the request.* =venture_feed_request_http_get()= / =venture_feed_request_http_send()= enforce =feeds.allowed_origins=, the body cap, the deadline, the request budget, and refuse redirects; =venture_feed_request_read_file()= enforces =feeds.file_roots=. A provider with its own socket would step around every one of those.
- *Credentials are schema-marked, never settings.* A property marked =x-sensitive= in the settings schema is refused in a source's settings and sealed on the source's credentials page instead; a fetch reads it with =venture_feed_request_get_secret()=.
- *The feeds code is built only with SQLite*, so a native plugin guards its provider with =#ifdef VENTURE_HAVE_SQLITE= as =plugins/blizzard-auctions/blizzard-plugin.c= does.

An exec plugin provides one from its manifest instead, with the =data_source_provider= provides kind ([[file:plugins.org::*Data source providers from an exec plugin][Plugins]]). The batch, the threading contract and the transport are in [[file:market-data.org::*Providers][Market data: providers]]; the three reference plugins -- Blizzard's auction houses as a GObject provider, the-odds-api as one crispy function, a supplier's CSV as an exec program -- are in [[file:plugins.org::*The reference plugins][Plugins: the reference plugins]].

A module that wants to ride every feed run rather than supply one -- alerts do -- adds a hook with =venture_feeds_add_hook()=; see [[file:market-data.org::*Hooks][Market data: hooks]].

* Arbitrage: fee models, strategies and export formats

The arbitrage engine finds opportunities through three registries on the context, each holding its built-ins first and each open to a plugin's =venture_plugin_register()= with plain functions:

| Registry       | Getter                                        | Add                                          | Built-ins                                        |
|----------------+-----------------------------------------------+----------------------------------------------+--------------------------------------------------|
| fee models     | =venture_context_get_fee_models()=            | =venture_fee_model_registry_add()=           | =percent=, =commission=, =none=                  |
| strategies     | =venture_context_get_arbitrage_strategies()=  | =venture_arbitrage_strategy_registry_add()=  | =spread=, =transform=, =deal=, =cover=, =back_lay= |
| export formats | =venture_context_get_export_formats()=        | =venture_export_format_registry_add()=       | =csv=, =shopping_list=                           |

A fee model is a compute function (what a side of a trade costs at a venue, from the venue's =fee_params= and -- since the Blizzard plugin needed a vendor price for its deposit -- the instrument's stored =attrs=) and an optional validator, which a venue's save calls when its model or parameters are written. A strategy is a scan function -- it reads the stores through the =VentureArbitrageScan= it is handed and adds opportunities, usually with =venture_arbitrage_scan_add_flip()=, which does every venue's fees, the transfer, the currency conversion and the figures in one call -- and an optional plan, which turns an opportunity into the =record= action's request. An export format turns a scan's rows into bytes, served by =/arbitrage/export?format=NAME=. A plugin's strategy is a tab on =/arbitrage=, a value of =strategy= at every door (the =arbitrage_scan= report, presets, the widget), and its rows are filtered, sorted, exported and recorded exactly like the built-ins'. The contract and a worked crispy strategy are in [[file:arbitrage.org::*Plugins: strategies, fee models and export formats][Arbitrage]].

* Every extension point

Everything a plugin can add, in one place. Each is a registry the running program already consults for its own built-ins, which is why an addition is indistinguishable from one: there is no list of "plugin things" anywhere to fall out of step. A native or crispy plugin calls these from =venture_plugin_register()= with the =VentureContext= it is handed; an exec plugin reaches only the two rows marked as provides kinds, because what the others take is a C function, not a program to run.

Three rules hold across the table, and each exists because the alternative went wrong somewhere:

- *A name is held once.* Every registry here that is keyed by a name refuses a second registration of it, so a plugin cannot quietly replace =report=, =percent= or =csv=; built-ins are registered first, when the registry is first handed out. The report registry is the exception -- =venture_report_registry_add()= replaces a report of the same name -- so pick a report name nothing ships. Save validators and web extensions have no name and simply accumulate.
- *Registries on the context survive a rebuild of what reads them.* The automation engine is rebuilt on every reload and a web server is built after plugins load; both read the context's registries afresh, which is why a plugin registers into the context and not into the engine or the server.
- *A kind whose module can be switched off stays registered.* A provides kind, a provider or a widget kind belonging to a module that is off is kept and says so (or skips) while off, so turning the module back on needs nothing re-registered -- the same reason reports are hidden rather than removed.

The Blizzard plugin is the worked example of several at once: a data source provider, the =wow_auction= fee model, the =tsm= export format and the =import_recipes= record action from one =venture_plugin_register()= ([[file:plugins.org::*Blizzard: a provider as a GObject, and four registries from one plugin][Plugins: Blizzard]]). Where the market-data and arbitrage pieces fit together is in [[file:market-data.org][Market data]] and [[file:arbitrage.org][Arbitrage]].

* What extensions get for free

Anything registered through these mechanisms is indistinguishable from a
built-in to every consumer:

- record types get a table, REST CRUD, serialisation, a list view, AI tools,
  audit diffs and CLI subcommands
- reports appear in the CLI, the web UI, the API and the AI's report tool
- both are covered by the same validation, concurrency and audit guarantees
- a module is switched, listed and masked exactly as a built-in one, and its
  types link to and from every other record through =record_link=
- a record type registered as a posting source posts on every save, from
  every door, exactly as a sale does
- automation handlers and events sit in the registry the built-ins do, so
  a rule cannot tell a plugin's step from a built-in one
- pages are drawn in the same shell, guarded the same way, and listed in
  the sidebar by the same renderer
- fee models, arbitrage strategies and export formats sit in the
  registries the built-ins do, so a venue, a scan and an export cannot
  tell a plugin's from a built-in one
- a data source provider is named by a data source's =provider= like a
  built-in one, synced by the same worker under the same origin, file and budget limits, and its
  rows reach the Trading pages, the oracle, alerts and the scan exactly as
  =http_json='s do
- a widget kind is offered by the dashboard editor and answers through
  the page, the API and the assistant from its one function

That is the point of deriving everything from property metadata rather than
writing it out: there is no second path for extensions to fall short on.
