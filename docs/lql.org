* LQL in VENTURE

[[file:../deps/libre-query-language/README.org][LQL]] (libre-query-language) is a pipeline query language: =fetch ticket | filter status not in ["done", "cancelled"] and assignee == me() | summarize n = count(), by: priority=. VENTURE embeds its library so that one language can filter every list page, drive charts and answer the API, the CLI and MCP (the LQL epic). This page covers the foundation -- the dependency, the record source and its guarantees -- and what is built on it: the filter bar over the ticket board and list, the same bar over every generic list page (=/e/<type>=), and the =?q== parameter of every list (see [[*Filter bars][Filter bars]]). =POST /api/v1/query=, =venturectl query=, the MCP tool =venture_query= and the dashboard's query widget run on it too ([[*Running a query][Running a query]]).

The whole of what a query can name is built by =venture_lql_environment_new()= (=src/lql/=), once per caller:

- LQL's built-in commands and functions, which compute on rows and never touch a file, a program or the network;
- one source per record type the caller may read (=fetch ticket=, =fetch invoice=, ...);
- VENTURE's functions: =me()=, =my_id()=, =my_teams()=, =today()=, =period()=, =organization()=, and the aggregate =sum_money()=.

Nothing else. See [[*What is deliberately not registered][What is deliberately not registered]].

* The dependency

=deps/libre-query-language= is a git submodule pinned to a tag (v0.16.0, the first with =LQL_LIMIT_MAX_BYTES=). VENTURE builds only its library archive, =make -C deps/libre-query-language static=, into =deps/libre-query-language/build/<type>/liblql-1.0.a=, and links it into the server, the shared library and the tests like every other vendored archive (=LQL_DIR=, =LQL_LIB=, =dep-lql= in =config.mk= and =rules.mk=). =venturectl= never sees it.

The library needs GLib alone (=glib-2.0=, =gobject-2.0=, =gio-2.0= and =libm=), which VENTURE already requires, so it adds *no Fedora build package*: =glib2-devel= is already in =make list-deps=. LQL's command line program needs json-glib, libyaml, libxml2, zstd, xz and bzip2, and its own vendored yaml-glib; none of that is built here, and the nested =deps/yaml-glib= submodule is never initialised.

=src/lql/venture-lql.h= is outside =<venture.h>= and outside the GIR: its API speaks LQL's own types, and only server code links the archive. =make clean-deps= removes LQL's build tree with the others.

* The record source

=VentureLqlSource= reads one record type the way =GET /api/v1/<type>= does.

** Which types are sources

A type is a source when its module is on (=venture_entity_registry_list_names()= hides the types of a module that is off) and the caller passes the type gate. The web layer's gate is the list API's own role check, =venture_web_require_for_type()=, so the owner-only types (=user=, =api_token=, chat, notifications, comments, webhooks, ...) and the tenant data-class rules hold: a type =GET /api/v1/<type>= refuses the caller is not a source at all, and =fetch user= is "no source named 'user'". The source is named as the type is, in the singular.

** Which rows

Every fetch builds a =VentureQuery= and calls =venture_database_find()= inside =venture_access_policy_enter_snapshot()= with the caller's reader, captured when the environment was built (=venture_access_policy_snapshot()=). That is exactly how a read worker answers =GET /api/v1/<type>=, so the access policy decides every row the same way: organization membership, role-scoped visibility (sales, support and viewer members see assigned records only: assigned to them, owned by them, or on their team), personal records.

An unqualified fetch is scoped to the business selected in the browser and every business beneath it, as =venture_web_scope_to_active_organization()= scopes a list; =organization_id == N= replaces that scope, as =?organization_id=N= does. Businesses themselves and workspace administration records are never scoped.

Soft-deleted rows are left out; =fetch ticket, include_deleted: TRUE= reads them too, as =?include_deleted=true= does. Any other argument or parameter is an error.

The web layer's door is =venture_web_server_new_lql_environment(server, request, &error)=: it authenticates the request, admits it as the list API admits a reader, scopes it to the selected business and gates every type. =tests/test-lql.c= holds a viewer's =fetch ticket= to their =GET /api/v1/ticket=, row for row and field for field.

** Which fields

The fields of a row are the members of the list API's own JSON for the record, =venture_serializable_to_json(record, FALSE)=, and the schema LQL sees (=get_columns=, which completion and hover read) is built from the same persistent properties. A sensitive field is not merely empty: it is not a field.

| VENTURE field          | LQL value                                                                     |
|------------------------+-------------------------------------------------------------------------------|
| string, text, enum     | String (an enum is its name: ="in_progress"=)                                 |
| integer, reference     | Int                                                                           |
| double                 | Double                                                                        |
| boolean                | Boolean                                                                       |
| date, date and time    | Timestamp (a date is midnight UTC of that day, as VENTURE stores it)          |
| money                  | Record ={amount, currency, exponent, formatted}=, =amount= an Int in minor units |
| JSON                   | String, as the API sends it                                                    |
| =display_name=         | String: the record's name as lists show it                                    |
| =attributes=           | Record of custom attributes; NULL when there are none                          |

Money is never a Double: =value.amount= is =10000= for 100.00 USD, and =value.formatted= is the text. Compare amounts within one currency (=value.currency == "USD" and value.amount > 10000=).

Every reference is an id and also =<ref>_label=, the display name of what it points at (=company_id= and =company_label=). Labels are read through the same reader, a batch of ids at a time; a record the caller may not read, or of a type they may not open, leaves its label NULL, so a label never names more than the record would.

* What reaches the database

LQL offers the source each conjunct (each term joined by =and=) of the =filter= stages right after the =fetch=. Those that mean exactly what a VENTURE filter means become filters of the query, and LQL does not evaluate them again (EXACT); the text matches narrow the read and LQL still checks every row (HINT); everything else is LQL's. One table decides both the plan and the read (=venture_lql_source_map()=), and =lql_query_explain()= shows the query that runs.

| LQL                                               | VENTURE filter                    | How      |
|---------------------------------------------------+-----------------------------------+----------|
| =f == c=, =!=, =<=, =<==, =>=, =>==                 | =eq= =ne= =lt= =lte= =gt= =gte=   | EXACT    |
| =f in [c, ...]=, =f not in [c, ...]=              | =in=, =not_in=                    | EXACT    |
| =is_null(f)=, =is_not_null(f)=                    | =is_null=, =not_null=             | EXACT    |
| =between(f, lo, hi)=                              | =between=                         | EXACT    |
| =m.amount OP c=, =m.currency == "X"=               | the money amount; its currency    | EXACT    |
| =organization_id == N=                            | =eq=, replacing the business scope | EXACT   |
| =contains=, =starts_with=, =ends_with=, =like= (case-sensitive) | =like=              | HINT     |
| =or=, =not=, other functions, labels, =display_name= | none                           | LQL      |

=f= is a stored field and =c= any expression without a field: a literal, a =$parameter=, =now() - 7d=, =me()=, =my_teams()=, =period("this_month").start=. The value has to be of the field's own type, because LQL answers ~==~ between types FALSE and ~!=~ TRUE, which no SQL comparison reproduces. Within that:

- A string or enum compares with ~==~ and ~!=~ only (PostgreSQL orders text by collation, LQL by bytes), and never with the empty string, which a VENTURE filter reads as "NULL or empty".
- A Timestamp compares with =<= =<== =>= =>== and =between= only: stored times omit a zero fraction, and only the range operators compare them by instant.
- A boolean compares with ~==~ and ~!=~.
- A NULL anywhere in an =in= list keeps the conjunct LQL's.
- The text matches are HINT, not EXACT: SQL =LIKE= is case-insensitive for ASCII on SQLite and reads =%= and =_= in the text as wildcards, so it can only keep more rows. A pattern with a backslash, or a case-insensitive match (=contains(f, "x", TRUE)=), stays LQL's entirely. The =ilike= filter is never used: SQL and LQL fold case differently outside ASCII, and pushing it could drop rows.

NULL is three-valued on both paths: =due_at < X= and =not (due_at < X)= both leave out a ticket with no due date, as SQL does; =filter_out= keeps it.

A conjunct the plan took as EXACT is applied when the query runs; if it no longer maps then (an operand of another type at run time), the source checks it row by row itself rather than return a row LQL was promised it would not.

A =limit= that follows only EXACT filters is given to the database.

=tests/test-lql.c= runs every form above both right after the fetch and after a =sort= (where LQL alone evaluates it) and holds the rows equal.

** Columns that are NULL but read as a value

A column a later migration added holds SQL NULL in every row older than it, but the record does not always read NULL there: an unset enum reads its zero member (=ticket.priority= reads ="low"=), an integer 0, a boolean FALSE. The row LQL sees and the list API's JSON both show that value, so every filter the source pushes compares the value as read, not the stored column (=venture_query_add_filter_as_read()=, VENTURE #45):

| On a field whose NULL reads as =D=      | The database is asked                         |
|-----------------------------------------+-----------------------------------------------|
| =is_null(f)=                            | nothing matches (=1 = 0=)                     |
| =is_not_null(f)=                        | everything matches (=1 = 1=)                  |
| a comparison =D= passes (=f == D=, =f != X=, =f in [D, ...]=, =f >= 0= with =D= = 0, ...) | =(f OP c OR f IS NULL)= |
| a comparison =D= fails                  | =f OP c=, which leaves NULL out already       |
| =m.currency == "X"=                     | =m= not NULL and its currency =X=; for the default currency also a NULL or empty currency column, which reads as the default |

What a NULL column reads as is taken from one source: a record of the type freshly constructed, nothing loaded into it, read through =g_object_get_property()=. That is exactly what loading a row leaves when the column is NULL (=venture_schema_populate_property()= skips it). It is not taken from the =GParamSpec= default (an unset declared field reads its GType's zero value, whatever the default says) nor from a field spec's =default=, which only seeds new forms. Plugin types are covered the same way, and so is any column added later, with nothing to declare.

The identity spine every record has (=id=, =uuid=, =organization_id=, =created_at=, =updated_at=, =deleted_at=, =version=) is compared as stored: it has been in every table since the table was made and every save writes it, so it never holds a legacy NULL. (=created_at= and =updated_at= on a fresh record are the time it was made, which no filter could match; without this every "Created this week" chip would stay LQL's.)

Two cases stay LQL's (NONE) rather than be answered wrongly: a value that is not fixed (two fresh records disagree, or it is a time other than =created_at= and =updated_at=, which every table has had since it was created and every save writes, so they compare as stored), and a text match (=contains= and the rest) on a text field that reads a value, since SQL =LIKE= of it cannot be decided here. Rows VENTURE writes hold no such NULL; nothing here changes for them.

The =?field== URL filters still compare the stored column until their own VENTURE ticket lands: =GET /api/v1/ticket?priority=low= leaves out a row whose priority column is NULL, though that row reads ="low"=.

Not covered: stored text that the reader rewrites. An enum column holding text that is not a canonical nick (hand-edited SQL; VENTURE always writes the nick) reads as the matching member, case- and dash-insensitively, or as the zero member when nothing matches; a currency stored in lower case reads in upper case. The filter compares the stored text there.

* VENTURE's functions

| Function                          | Gives                                                                                              |
|-----------------------------------+----------------------------------------------------------------------------------------------------|
| =me() -> String=                  | your username: what =assignee= holds. =assignee == me()=                                           |
| =my_id() -> Int=                  | your user id: what =owner_user_id= holds. =owner_user_id == my_id()=; NULL with sign-in off        |
| =my_teams() -> Array=             | the ids of the teams you are an active member of. =team_id in my_teams()=                          |
| =today() -> Timestamp=            | the start of today on the business calendar (=locale.timezone=), as dates are stored              |
| =period(name: String) -> Record=  | ={start, end, label}= of a report period; =end= is exclusive; ="all"= has NULL ends                |
| =organization() -> Int=           | the business selected in the sidebar; NULL when all are                                            |

=period()= takes the report period names (=venture_context_parse_period()=): =today=, =yesterday=, =this_week=, =last_week=, =this_month=, =last_month=, =this_quarter=, =last_quarter=, =this_year=, =last_year=, =ytd=, =mtd=, =qtd=, =fy=, =fy_2026=, =last_7_days=, =last_30_days=, =last_90_days=, =last_365_days=, =2026=, =2026-03=, =2026-Q2=, =2026-01-01..2026-03-31=, =all=. It reads them on the business calendar and fiscal year at the query's =now()=, so every row of one query, and every period in it, sees the same instant:

#+begin_src lql
fetch ticket
| filter updated_at >= period("this_week").start and updated_at < period("this_week").end
| summarize n = count(), by: status
#+end_src

All six scalar functions are evaluated without a row, so a comparison with them reaches the database.

** Money: one total per currency

=sum(total.amount)= would add dollars to gold. =sum_money(field)= is the aggregate that does not: it is the reports' accumulator (=venture_money_totals_add()=, what the =sum= widget and the =aggregate= report keep currencies apart with), and it answers an =Array= of money records, one per currency, sorted by code:

#+begin_src lql
fetch invoice_line
| lookup (fetch invoice), on: invoice_id == id, prefix: "invoice_"
| filter invoice_issued_at >= period("this_quarter").start and invoice_issued_at < period("this_quarter").end
| summarize invoices = count_distinct(invoice_id), total = sum_money(income_amount), by: {status = invoice_status}
#+end_src

A sent quarter of 1500.00 USD and 300.00 EUR is =total: [{amount: 30000, currency: "EUR", ...}, {amount: 150000, currency: "USD", ...}]=: two figures, never 1800 of nothing. NULL is skipped, no money at all is an empty array, and a value that is not money (=sum_money(id)=) is refused. An invoice has no stored total; its amounts are frozen on its lines (=income_amount=, =tax_amount=) when it is issued, so the query reads the lines, and a draft, which has no =issued_at=, is in no quarter. Everything that shows a query -- the CSV, the table, every chart -- keeps the array's figures apart in turn.

* Bounds

| Setting            | Default | Range       | Means                                                                                    |
|--------------------+---------+-------------+------------------------------------------------------------------------------------------|
| =query.max_rows=   |  10000  | 1..1000000  | the most rows one =fetch= may read, after the access policy and the pushed filters; also the most rows any later stage may hold |
| =query.timeout_ms= |   5000  | 1..600000   | the longest one query may run                                                            |
| =query.max_bytes=  | 67108864 | 1048576..1073741824 | the most string and array bytes one query may create (64 MiB) |

A =fetch= that would read more than =query.max_rows= fails with an error that names the bound; it never answers with a silently shorter list. The source reads one row past the bound to tell the two apart. Filter on stored fields right after the =fetch=, so the database narrows the read, or add =| limit N=. Neither bound can be switched off: zero means "none" to LQL, so the configuration refuses it.

The timeout is LQL's own =timeout_ms=: it bounds evaluation between stages and cannot interrupt a database read in progress, which =query.max_rows= bounds instead.

=query.max_bytes= is the memory budget of one query: a query that concatenates large strings, nested, would otherwise allocate without bound and take the whole process with it (VENTURE #44). =venture_lql_environment_new()= sets it on every environment as LQL's =LQL_LIMIT_MAX_BYTES= (libre-query-language v0.16.0): the bytes of every string and array the query creates while LQL evaluates it count against it, and freeing one does not give its bytes back. Rows a =fetch= reads are not charged -- they are read on the main thread, outside the evaluation, and =query.max_rows= bounds them instead. LQL also caps any one result of =concat=, =replace=, =replace_regex=, =split=, =pad=, =repeat=, =array_concat= and =array_join= at 16 MiB and 1048576 values, whatever the budget. Over the budget or a cap the query is refused with =validation= (422) and LQL's message -- "the query allocated more than N bytes (max_bytes): over query.max_bytes", or "the result would exceed 16 MiB" -- and the server, and the next query, carry on. Like the other bounds it cannot be switched off. =/lql/query/bounds/max-bytes-refuses= pins it, on the read workers and in hosted mode; a filter bar is held to the same budget (=/lql-bar/bounds/max-bytes=, see [[*Problems][Problems]]).

* Filter bars

A filter bar holds one LQL filter over one record type: the part of a query after =fetch TYPE | filter=. The ticket board and list have one (=/tickets=), every generic list page has one (=/e/<type>=, see [[*Generic lists][Generic lists]]), and every list takes the same filter as =?q== (=GET /api/v1/ticket?q=...=, =/e/ticket?q=...=).

** What the bar takes

The text is a filter expression, or a =filter= or =filter_out= stage of its own:

#+begin_src lql
status not in ["done", "cancelled"]
assignee == me() or team_id in my_teams()
issue_type == "bug" and priority in ["high", "urgent"] and updated_at > ago(7d)
not (issue_type == "bug")
filter_out due_at < now()
#+end_src

It becomes =fetch ticket\n| filter TEXT= (or =| TEXT=), run as the caller in the environment of =venture_web_server_new_lql_environment()=, so it sees exactly the rows and fields the list API would. Nothing else can ride along: a =|= in the text is refused (the bar holds one filter, not a pipeline -- a =summarize= has no cards), and the environment has no source but the records. A =$parameter= is refused too, since nothing supplies one.

A field the record does not have is refused with "did you mean" (=lql_assist_lint()=). LQL itself would run =staus == "todo"= and match nothing -- a missing field is NULL -- which in a bar is always a typo, and an empty board is the worst way to say so.

=assignee in my_teams()= is valid LQL that never matches: =assignee= is a username and =my_teams()= gives team ids. Mine-or-my-team's is =assignee == me() or team_id in my_teams()=.

** How a list applies it

=venture_lql_filter_find_ids()= runs the filter with =| fields id= and gives the ids it kept; the list adds =id in [...]= to its own query, which then reads, orders, pages and counts as it always did. Only the selection is LQL's, so a list's JSON, its =total= and its sorting are unchanged, and the database still narrows the read where the filter allows (see [[*What reaches the database][What reaches the database]]). The read is bounded by =query.max_rows= and =query.timeout_ms=, and one filter may keep at most =VENTURE_LQL_FILTER_MAX_IDS= (30000) records, below what SQLite and PostgreSQL bind in one statement. A filter that keeps nothing selects nothing (an =id IS NULL= no row passes), never everything.

** Where it runs

A person's query never runs on the main loop. Every route that runs one -- =/tickets= with =q=, a list or export with =q=, =GET /api/v1/<type>?q==, and =GET /lql/assist= (preparing evaluates what was typed, and completion fetches repositories) -- answers from a fiber (=venture_web_answer_later()=, as the Stripe routes do). The fiber builds the environment first, under the request's own access and tenant scopes, so the reader it captures -- the one every read is judged by -- is the request's, hosted per-workspace restriction included.

It then runs the LQL work through the same helper =POST /api/v1/query= uses, =venture_web_query_off_loop()= (see [[*Where a query runs][Where a query runs]]): evaluated on a query worker with a =GCancellable=, cancelled at =query.timeout_ms= and a second's grace or when the client goes, while every fetch the filter needs is read back in the fiber, on the main thread, inside the request's scopes. Before handing it over, the route builds the schema of the one source the work names -- the list's type, and for =/lql/assist= also =forge_repo=, which repository completion fetches (=venture_lql_environment_prepare_source()=) -- since the worker touches no registry. That is the same with read workers and without them: a hosted install, which keeps every request on the main thread for its per-workspace scopes, and an in-memory database evaluate the filter off the main loop too. =tests/test-lql-bar.c= runs every test both ways, and =/lql-bar/runs/main-loop-stays-responsive= answers the list API and a second filtered page while a slow filter is evaluated, in both.

** Problems

=venture_lql_filter_check()= prepares the query without reading anything and places what is wrong in the text the person typed, not in the query it became: an offset and length, the unknown name and the suggestions (=VentureLqlProblem=). The board draws it on the server, so it works with scripting off: the message, the text highlighted with the faulty part in a =<mark class="lql-mark">=, a caret line under it, and a "did you mean" link per suggestion that writes it in. It draws no board, and answers 400. The list API answers 400 =invalid_argument= with "q, column N: MESSAGE". A problem of the query as a whole has no place and is shown as a message; the list API classes it as =POST /api/v1/query= does (=venture_lql_query_set_error()=, =VentureLqlProblem.code=): a bound -- =query.max_rows=, =query.max_bytes=, the records one list may show -- is 422 =validation=, the time limit or a cancelled run 504 =timeout=. A filter over the memory budget is therefore the bar's problem on the page and a 422 naming =query.max_bytes= on the list API, and the server carries on.

** The board's URL filters

The board always read =kind=, =issue_type=, =assignee=, =venture_id= and =sprint_id= (blank, and for kind and type =all=, meaning "any"). It now reads any other =field__op=value= on a ticket field as the list API does, so =/tickets?status__not_in=done,cancelled= -- what dashboards link to -- filters the board too; parameters that name no ticket field are still ignored. All of them go through =venture_query_apply_query_string()=, one route.

The bar shows them as the LQL they mean (=venture_lql_filter_from_query_string()=), joined with the bar's own =q=: =status__not_in=done,cancelled= is =status not in ["done", "cancelled"]=, =assignee== is =(is_null(assignee) or assignee == "")= (blank means "null or empty" to a URL filter), a date is =timestamp("2026-01-01")=, =like= and =ilike= are =like(f, "%x%", TRUE)=. Submitting the bar carries the lot on as =q= alone, which is how an old link becomes a query. While they are URL filters they are applied as URL filters; =tests/test-lql-bar.c= holds the translation to the same tickets.

** Generic lists

Every list page generated from a field table, =/e/<type>= -- companies, contacts, deals, leads, invoices, bills, expenses, products, inventory, forge repositories, releases and every other registered type, a plugin's included -- draws the same bar above its table, with the chips its field table gives (see [[*Quick chips][Quick chips]]). Nothing is written per page: =venture_web_ui_list()= draws it for whichever type it lists.

The bar narrows what the page already shows. Every other parameter of the page -- the Filters panel's field filters, a named view's tab (=customer=true=), the search, the sort -- stays in the URL and is carried along by the bar's form and by every chip and "did you mean" link; paging is dropped, so a new filter starts on page one. The Filters panel carries =q= along the same way. =?q== filters the page, its CSV export and the list API alike, and sorting and paging links keep it.

A filter that cannot run draws its problem in the bar, as on the board -- message, marked text, caret, "did you mean" -- and the page answers 400 with no table, so a typo never reads as "no such records". The page builds a query environment only when it has a filter to run; an unfiltered page's chips are worked out from their own text.

** Pages with a layout of their own

A page with its own layout is in only where it already draws a generic list; the rest keep their own controls, and their records are all reachable, with the bar, at =/e/<type>=.

** Quick chips

Each chip is a link that adds its term to the bar with =and=, or takes it off when it is already one of the bar's top-level terms (=venture_lql_filter_toggle()=); a bar whose text has a top-level =or= is bracketed first. A person never has to learn the syntax for these.

The ticket board's chips are its own:

| Chip              | Term                                         |
|-------------------+----------------------------------------------|
| Not done          | =status not in ["done", "cancelled"]=        |
| Mine              | =assignee == me()=                           |
| Unassigned        | =(is_null(assignee) or assignee == "")=      |
| Bugs              | =issue_type == "bug"=                        |
| Updated this week | =updated_at >= period("this_week").start=    |

"This week" is the calendar week on the business calendar (=locale.timezone=), not the last seven days; =updated_at > ago(7d)= is that.

A generic list's chips are worked out from its field table (=venture_lql_filter_chips()=), so a new type, or a plugin's, gets them with no code:

| Chip                       | When                                                                                       | Term                                                    |
|----------------------------+--------------------------------------------------------------------------------------------+---------------------------------------------------------|
| Open, Closed               | the type's lifecycle field (=status=, =stage=, =state=) is an enumeration with both final and unfinished states | =status not in [...]=, =status in [...]=        |
| Mine                       | a string field the access policy reads as "assigned to" (=VENTURE_COLUMN_FLAG_ASSIGNED_USERNAME=) | =assignee == me()=, =owner == me()=       |
| Mine                       | else a reference to the owning user, =owner_user_id= or =owner_id=                          | =owner_user_id == my_id()=                              |
| /Date/ this week, this month | the first date the table declares that says when the record happened, else =created_at=  | =(issued_at >= period("this_week").start and issued_at < period("this_week").end)= |

A state is final when its name is one of the words a life ends in -- =done=, =cancelled=, =closed=, =completed=, =resolved=, =won=, =lost=, =paid=, =void=, =accepted=, =declined=, =expired=, =converted=, =archived=, =released=, =failed=, ... (=venture_lql_closed_states= in =venture-lql-filter.c=) -- words rather than a table per type, as the status badge's tones are. =sent=, =active=, =published= and =posted= are deliberately not final: an invoice sent is still owed. An invoice's Open is =status not in ["paid", "void"]=, a deal's =stage not in ["won", "lost"]=, a quote's =status not in ["accepted", "declined", "expired", "superseded"]=. A type whose lifecycle is a plain string (a bill's, a purchase order's) or that has none (an expense) has no Open and Closed.

The primary date skips a schedule's machinery -- a pause or lease (=-until=), an expiry, =last-= and =next-= runs, reminders -- so a company, whose first dates are a dunning pause and a late-fee pause, gets =created_at=. An invoice gets =issued_at=, an expense =occurred_at=, a bill =bill_date=, a deal =expected_close_at=, a ticket =due_at=. A window is one bracketed term, so it toggles as one, and both bounds push down.

Every chip of every registered type checks, runs, and is taken by the source in full (EXACT): =tests/test-lql-lists.c= goes through them all, so a chip is never a table scan.

** Editor help

With scripting on, =venture.js= asks =GET /lql/assist?type=ticket&q=TEXT&at=N[&base=URL]= as you type (150 ms after the last key, only the latest answer drawn). =N= is the cursor in UTF-16 units, as a browser counts, and every offset in the answer is too:

#+begin_src json
{
  "status": "<the line under the bar, as the page would draw it>",
  "problem": null,
  "completions": [
    {"label": "in_progress", "kind": "value", "detail": "VentureTicketStatus",
     "insert": "\"in_progress\"", "start": 10, "end": 10}
  ]
}
#+end_src

Completion (=venture_lql_filter_complete()=) offers LQL's own candidates -- field names, functions, keywords, constants -- and first, where a field is being compared (=status == =, =priority == "hi=, =issue_type == bu=, =status not in ["done", =), the values that field takes: an enumeration's names (=status=, =priority=, =issue_type=, =kind=, ...), or for a reference to a forge repository its ids (=repo_id=, the name as detail) or names (=repo_label=), read as the caller, so a repository they cannot read is never offered. The list is a listbox under the input: arrows move, Enter or Tab takes one, Escape closes, Ctrl+Space asks. Enter with nothing chosen submits the form as it would without the list.

** Highlighting

=venture_lql_filter_highlight()= draws the text as =<span class="lql-KIND">= per token (LQL's highlight kinds), escaped. Both looks' stylesheets carry the rules, and point each =--lql-*= variable at a role of the look's palette (=--lql-string: var(--positive)=, =--lql-keyword: var(--accent)=, =--lql-error: var(--negative)=, ...) rather than at a colour, so light and dark and an organisation's accent apply to a query for free. =lql_highlight_get_css()= is not used: the rules are in the stylesheets, served once.

** Saved views

A view saved from a filtered list keeps =q= in =saved_view.lql= and the rest of the query string in =saved_view.query=, and opens at =<list>?<query>&q=<lql>=. A view without =lql= (every view saved before) opens as it always did. Migration =001083_saved_view_lql= checks the column, which reconciliation adds from the field table. Every generic list has the *Save view* control, so a view can be of any type.

A view is saved and offered only for a type the caller may open: =POST /views= refuses a type whose module is off (404, the module named) or that the list's role check refuses (403, =user=, =api_token=, ...), and the sidebar and =/views= leave such views out -- one kept from before its module was turned off included -- so a link never leads to a refusal.

** The module gate

A type whose module is off is no source at all (=venture_entity_registry_list_names()= hides it), so it is not fetchable from its list page, from =?q== on its list API, from =/lql/assist=, or from a saved view; those answer 404. Nor can another list's filter reach it, or any second type: a sub-pipeline is only ever a command's argument (=append=, =lookup=), and a command needs the =|= the bar refuses, so the one source a bar's filter reads is its own list's type.

A financial type (one of the finance module's, or of a module requiring it) stays the finance roles' to read: the source reads through the access policy, so a member who is not owner, admin or finance filters invoices to nothing, on the page and the list API alike, exactly as the unfiltered list shows them nothing. =tests/test-lql-lists.c= holds both, with expense claims (module =claims= off) and invoices.

** At scale

The filter is only as cheap as what the database narrows. =tests/test-lql-lists.c= fills a company table with fifty thousand rows, ten times a =query.max_rows= of 5000: the Mine chip, a date window, an equality and a conjunction of them read only what they keep and answer in milliseconds, as the filter alone, as =/e/company?q== and as the list API; =lower(name) == "..."=, which the source cannot take, passes the bound and is refused with the bound's message rather than scanning.

* Running a query

=venture_lql_query_run()= (=src/lql/venture-lql-query.c=) runs one query in a caller's environment and answers the =venture.query/1= document: =columns= (name and LQL type), =rows= (one object per row in column order), =row_count=, =explain= and =elapsed_ms=, the shape [[file:api.org::*Queries: POST /api/v1/query][POST /api/v1/query]] documents. Every surface goes through it:

| Surface                      | Who it runs as                     | Reads the document by                       |
|------------------------------+------------------------------------+---------------------------------------------|
| =POST /api/v1/query=         | the request's token or session     | writing it, or its rows as CSV              |
| =venturectl query 'LQL'=     | =VENTURE_TOKEN=                    | posting to the API and printing the answer  |
| MCP =venture_query=          | the MCP session's caller           | posting to the API, answer untouched        |
| the dashboard =query= widget | whoever is looking at the page     | drawing it ([[file:dashboards.org::*The query kind][The query kind]]) |

So the API, the CLI and the MCP tool answer with the same rows by construction, and =tests/test-lql-query.c= holds them equal for "open tickets by assignee" and "invoices this quarter by status", CSV included.

Before a query runs, every =fetch= in it -- the main pipeline and every sub-pipeline of a =lookup= or =append= -- is checked against the types the gate refused when the environment was built (=venture_lql_environment_get_refusal()=); one of them fails with the gate's own error, which is what =GET /api/v1/<type>= says to the same caller (=This needs the admin role or higher=, a 403). A type of a module that is off, or a name that is no type, stays LQL's =no source named= (400).

Then LQL's errors become VENTURE's, keeping LQL's =LINE:COLUMN:= prefix: a query that does not parse, check or evaluate is =invalid_argument= (400), a bound -- =query.max_rows=, LQL's stage and depth limits -- is =validation= (422), and the time limit is =timeout= (504) with a message naming =query.timeout_ms=.

=venture_lql_query_to_csv()= writes the document's rows as CSV. Both are declared in =venture-lql.h=, outside the GIR like the rest of it.

* Where a query runs

A query is the one request a caller can make arbitrarily expensive without writing anything, so no query is evaluated on the main loop. The pieces, in =src/web/venture-web-query.inc=:

- *A fiber per request.* =POST /api/v1/query=, =GET /api/v1/dashboards/:slug=, =/dashboards/:slug/widgets/:id= and every page that draws a dashboard grid (=/=, =/dashboards/:slug=, =/dashboards/:slug/edit=) answer from a fiber of the main loop (=venture_web_answer_later()=, as the Stripe routes do). The fiber keeps the request's own access snapshot, its hosted admission, its tenant request scope and the hosted finish check. All of those routes are =VENTURE_HOSTED_ROUTE_NONE=, so no support capability is admitted, and the fiber's plain tenant scope is the one the pipeline would give them.
- *Prepared in the request's scope.* The caller's environment is built inside that fiber, in the request's access scope -- the viewer's policy and, in hosted mode, the workspace -- and the query is prepared there (=venture_lql_query_prepare()=): parsed within LQL's limits, every =fetch= checked against the caller's refusals, the schema of every source it names built from the entity registry, and the functions' inputs captured (=my_teams()=, the calendar of =today()= and =period()=).
- *Evaluated on a worker.* =venture_lql_query_execute()= runs on a query worker -- a bounded pool of four threads (=VENTURE_WEB_QUERY_THREADS=); more queries wait in its queue -- with a =GCancellable=, while the fiber yields and the main loop serves everybody else.
- *Read on the main thread.* No worker touches the database (AGENTS.md, the thread list). Each fetch the evaluation needs is handed back to the fiber (=venture_lql_set_read_dispatch()=), which wakes, reads it on the main thread inside the request's own scopes as the caller's snapshot (=venture_lql_read_perform()=), hands the rows to the worker and yields again.
- *Cancelled.* The query's deadline -- =query.timeout_ms= plus a second's grace; LQL's own =timeout_ms= normally answers first -- and a client that goes away both cancel it. The evaluation stops at its next step, and a fetch handed back but not yet read is never read. A cancelled query answers =timeout= (504).

What this does not do: one fetch is still one main-thread read of up to =query.max_rows= + 1 rows, what one page of a record list costs, and the main loop runs only between two of them. A query of sixty-four fetches is sixty-four such reads with other requests served in between, not one long block. The client's going away is a hint: libsoup does not watch a paused connection, so it may be noticed only when the answer is written, and then the deadline is what stops the query.

The helper is one and generic: =venture_web_query_off_loop(server, request, environment, work, data, cancellable, error)= runs any LQL work -- a query, the ids a filter keeps, checking or completing a person's text -- on a worker, with its fetches read back in the fiber. Given the environment, it first builds the schema of every source in it (=venture_lql_environment_prepare_sources()=), so work that asks any source for its columns stays off the registry; the work itself may touch LQL and nothing else. =POST /api/v1/query= and the query widget call it through =venture_web_query_run()=, which prepares the query first and so builds only the sources it names. The filter bars, =?q== on every list and =GET /lql/assist= call it directly (see [[*Where it runs][Where it runs]]). There is no other: every LQL caller goes through this one.

Off a fiber -- a stack that cannot yield, a nested main loop, an open transaction -- the worker still evaluates and the calling stack waits for it, reading its fetches meanwhile: the main loop is blocked for as long as the query takes, bounded by the same deadline. No query route takes that path.

A host can add pure functions to every environment with =venture_lql_set_environment_hook()=; they are evaluated on a worker, so they must not touch the database, a registry, the configuration or the context. The tests use it to add a =nap()= that takes time.

=tests/test-lql-query.c= pins the worker (=/lql/query/runs/main-loop-stays-responsive=: a second query and a record list are answered while the first is evaluated), the deadline (=/lql/query/runs/deadline-stops-the-query=) and the cancellation (=/lql/query/runs/cancel-mid-query=, including the fetch that is never read). =tests/test-lql-query-hosted.c= runs two hosted workspaces in one process and holds each one's queries -- through the API and through a query widget, two at once on workers -- to its own rows.

The web layer has two doors. =venture_web_server_new_lql_environment()= scopes to the business picked in the browser; =POST /api/v1/query= also takes =?organization_id=N=. A query widget's environment is built from the very request that asked for the page, scoped to the page's organizations, the first time a query widget on the page runs, and kept for the rest of that page.

* What is deliberately not registered

LQL can read files (=read=), run programs (=exec= and command definitions), talk SQL (=sql=, =sqlite=, =postgres=), read git history, the systemd journal and Kubernetes. Each is a provider a host has to add; VENTURE adds none. Every one of them would read around the one reader path and its access policy: a =sql= source would answer any question about any table, whatever the caller may see. =tests/test-lql.c= holds =read "/etc/passwd"=, =sql ...=, =sqlite=, =postgres=, =exec=, =git_log=, =k8s= and =journal= to "unknown command", and checks that every =fetch= name is a record source. =tests/test-lql-query.c= holds the same commands to a 400 through =POST /api/v1/query=, as an administrator, so no door reaches them either.

LQL scripts (=.include= of other files) are a host API (=lql_script_load()=) that no query can reach, and VENTURE does not use it.

LQL here is read-only. Writes from a query result are a later story, through the existing bulk route and its validators.
