* LQL in VENTURE

[[file:../deps/libre-query-language/README.org][LQL]] (libre-query-language) is a pipeline query language: =fetch ticket | filter status not in ["done", "cancelled"] and assignee == me() | summarize n = count(), by: priority=. VENTURE embeds its library so that one language can filter every list page, drive charts and answer the API, the CLI and MCP (the LQL epic). This page covers the foundation -- the dependency, the record source and its guarantees -- and the first thing built on it, the filter bar over the ticket board and list and the =?q== parameter of every list (see [[*Filter bars][Filter bars]]). The generic list pages and =/api/v1/query= build on the same.

The whole of what a query can name is built by =venture_lql_environment_new()= (=src/lql/=), once per caller:

- LQL's built-in commands and functions, which compute on rows and never touch a file, a program or the network;
- one source per record type the caller may read (=fetch ticket=, =fetch invoice=, ...);
- VENTURE's functions: =me()=, =my_teams()=, =today()=, =period()=, =organization()=.

Nothing else. See [[*What is deliberately not registered][What is deliberately not registered]].

* The dependency

=deps/libre-query-language= is a git submodule pinned to a tag (v0.15.0). VENTURE builds only its library archive, =make -C deps/libre-query-language static=, into =deps/libre-query-language/build/<type>/liblql-1.0.a=, and links it into the server, the shared library and the tests like every other vendored archive (=LQL_DIR=, =LQL_LIB=, =dep-lql= in =config.mk= and =rules.mk=). =venturectl= never sees it.

The library needs GLib alone (=glib-2.0=, =gobject-2.0=, =gio-2.0= and =libm=), which VENTURE already requires, so it adds *no Fedora build package*: =glib2-devel= is already in =make list-deps=. LQL's command line program needs json-glib, libyaml, libxml2, zstd, xz and bzip2, and its own vendored yaml-glib; none of that is built here, and the nested =deps/yaml-glib= submodule is never initialised.

=src/lql/venture-lql.h= is outside =<venture.h>= and outside the GIR: its API speaks LQL's own types, and only server code links the archive. =make clean-deps= removes LQL's build tree with the others.

* The record source

=VentureLqlSource= reads one record type the way =GET /api/v1/<type>= does.

** Which types are sources

A type is a source when its module is on (=venture_entity_registry_list_names()= hides the types of a module that is off) and the caller passes the type gate. The web layer's gate is the list API's own role check, =venture_web_require_for_type()=, so the owner-only types (=user=, =api_token=, chat, notifications, comments, webhooks, ...) and the tenant data-class rules hold: a type =GET /api/v1/<type>= refuses the caller is not a source at all, and =fetch user= is "no source named 'user'". The source is named as the type is, in the singular.

** Which rows

Every fetch builds a =VentureQuery= and calls =venture_database_find()= inside =venture_access_policy_enter_snapshot()= with the caller's reader, captured when the environment was built (=venture_access_policy_snapshot()=). That is exactly how a read worker answers =GET /api/v1/<type>=, so the access policy decides every row the same way: organization membership, role-scoped visibility (sales, support and viewer members see assigned records only: assigned to them, owned by them, or on their team), personal records.

An unqualified fetch is scoped to the business selected in the browser and every business beneath it, as =venture_web_scope_to_active_organization()= scopes a list; =organization_id == N= replaces that scope, as =?organization_id=N= does. Businesses themselves and workspace administration records are never scoped.

Soft-deleted rows are left out; =fetch ticket, include_deleted: TRUE= reads them too, as =?include_deleted=true= does. Any other argument or parameter is an error.

The web layer's door is =venture_web_server_new_lql_environment(server, request, &error)=: it authenticates the request, admits it as the list API admits a reader, scopes it to the selected business and gates every type. =tests/test-lql.c= holds a viewer's =fetch ticket= to their =GET /api/v1/ticket=, row for row and field for field.

** Which fields

The fields of a row are the members of the list API's own JSON for the record, =venture_serializable_to_json(record, FALSE)=, and the schema LQL sees (=get_columns=, which completion and hover read) is built from the same persistent properties. A sensitive field is not merely empty: it is not a field.

| VENTURE field          | LQL value                                                                     |
|------------------------+-------------------------------------------------------------------------------|
| string, text, enum     | String (an enum is its name: ="in_progress"=)                                 |
| integer, reference     | Int                                                                           |
| double                 | Double                                                                        |
| boolean                | Boolean                                                                       |
| date, date and time    | Timestamp (a date is midnight UTC of that day, as VENTURE stores it)          |
| money                  | Record ={amount, currency, exponent, formatted}=, =amount= an Int in minor units |
| JSON                   | String, as the API sends it                                                    |
| =display_name=         | String: the record's name as lists show it                                    |
| =attributes=           | Record of custom attributes; NULL when there are none                          |

Money is never a Double: =value.amount= is =10000= for 100.00 USD, and =value.formatted= is the text. Compare amounts within one currency (=value.currency == "USD" and value.amount > 10000=).

Every reference is an id and also =<ref>_label=, the display name of what it points at (=company_id= and =company_label=). Labels are read through the same reader, a batch of ids at a time; a record the caller may not read, or of a type they may not open, leaves its label NULL, so a label never names more than the record would.

* What reaches the database

LQL offers the source each conjunct (each term joined by =and=) of the =filter= stages right after the =fetch=. Those that mean exactly what a VENTURE filter means become filters of the query, and LQL does not evaluate them again (EXACT); the text matches narrow the read and LQL still checks every row (HINT); everything else is LQL's. One table decides both the plan and the read (=venture_lql_source_map()=), and =lql_query_explain()= shows the query that runs.

| LQL                                               | VENTURE filter                    | How      |
|---------------------------------------------------+-----------------------------------+----------|
| =f == c=, =!=, =<=, =<==, =>=, =>==                 | =eq= =ne= =lt= =lte= =gt= =gte=   | EXACT    |
| =f in [c, ...]=, =f not in [c, ...]=              | =in=, =not_in=                    | EXACT    |
| =is_null(f)=, =is_not_null(f)=                    | =is_null=, =not_null=             | EXACT    |
| =between(f, lo, hi)=                              | =between=                         | EXACT    |
| =m.amount OP c=, =m.currency == "X"=               | the money amount; its currency    | EXACT    |
| =organization_id == N=                            | =eq=, replacing the business scope | EXACT   |
| =contains=, =starts_with=, =ends_with=, =like= (case-sensitive) | =like=              | HINT     |
| =or=, =not=, other functions, labels, =display_name= | none                           | LQL      |

=f= is a stored field and =c= any expression without a field: a literal, a =$parameter=, =now() - 7d=, =me()=, =my_teams()=, =period("this_month").start=. The value has to be of the field's own type, because LQL answers ~==~ between types FALSE and ~!=~ TRUE, which no SQL comparison reproduces. Within that:

- A string or enum compares with ~==~ and ~!=~ only (PostgreSQL orders text by collation, LQL by bytes), and never with the empty string, which a VENTURE filter reads as "NULL or empty".
- A Timestamp compares with =<= =<== =>= =>== and =between= only: stored times omit a zero fraction, and only the range operators compare them by instant.
- A boolean compares with ~==~ and ~!=~.
- A NULL anywhere in an =in= list keeps the conjunct LQL's.
- The text matches are HINT, not EXACT: SQL =LIKE= is case-insensitive for ASCII on SQLite and reads =%= and =_= in the text as wildcards, so it can only keep more rows. A pattern with a backslash, or a case-insensitive match (=contains(f, "x", TRUE)=), stays LQL's entirely. The =ilike= filter is never used: SQL and LQL fold case differently outside ASCII, and pushing it could drop rows.

NULL is three-valued on both paths: =due_at < X= and =not (due_at < X)= both leave out a ticket with no due date, as SQL does; =filter_out= keeps it.

A conjunct the plan took as EXACT is applied when the query runs; if it no longer maps then (an operand of another type at run time), the source checks it row by row itself rather than return a row LQL was promised it would not.

A =limit= that follows only EXACT filters is given to the database.

=tests/test-lql.c= runs every form above both right after the fetch and after a =sort= (where LQL alone evaluates it) and holds the rows equal.

One caveat no pushdown can repair: a column holding SQL NULL where the record reads a default (an integer or enum column added by a migration, on rows older than it) reads as the default in the row and the list API alike, while the filter compares the stored NULL. Rows VENTURE writes never hold such a NULL.

* VENTURE's functions

| Function                          | Gives                                                                                              |
|-----------------------------------+----------------------------------------------------------------------------------------------------|
| =me() -> String=                  | your username: what =assignee= holds. =assignee == me()=                                           |
| =my_teams() -> Array=             | the ids of the teams you are an active member of. =team_id in my_teams()=                          |
| =today() -> Timestamp=            | the start of today on the business calendar (=locale.timezone=), as dates are stored              |
| =period(name: String) -> Record=  | ={start, end, label}= of a report period; =end= is exclusive; ="all"= has NULL ends                |
| =organization() -> Int=           | the business selected in the sidebar; NULL when all are                                            |

=period()= takes the report period names (=venture_context_parse_period()=): =today=, =yesterday=, =this_week=, =last_week=, =this_month=, =last_month=, =this_quarter=, =last_quarter=, =this_year=, =last_year=, =ytd=, =mtd=, =qtd=, =fy=, =fy_2026=, =last_7_days=, =last_30_days=, =last_90_days=, =last_365_days=, =2026=, =2026-03=, =2026-Q2=, =2026-01-01..2026-03-31=, =all=. It reads them on the business calendar and fiscal year at the query's =now()=, so every row of one query, and every period in it, sees the same instant:

#+begin_src lql
fetch ticket
| filter updated_at >= period("this_week").start and updated_at < period("this_week").end
| summarize n = count(), by: status
#+end_src

All five functions are evaluated without a row, so a comparison with them reaches the database.

* Bounds

| Setting            | Default | Range       | Means                                                                                    |
|--------------------+---------+-------------+------------------------------------------------------------------------------------------|
| =query.max_rows=   |  10000  | 1..1000000  | the most rows one =fetch= may read, after the access policy and the pushed filters; also the most rows any later stage may hold |
| =query.timeout_ms= |   5000  | 1..600000   | the longest one query may run                                                            |

A =fetch= that would read more than =query.max_rows= fails with an error that names the bound; it never answers with a silently shorter list. The source reads one row past the bound to tell the two apart. Filter on stored fields right after the =fetch=, so the database narrows the read, or add =| limit N=. Neither bound can be switched off: zero means "none" to LQL, so the configuration refuses it.

The timeout is LQL's own =timeout_ms=: it bounds evaluation between stages and cannot interrupt a database read in progress, which =query.max_rows= bounds instead.

* Filter bars

A filter bar holds one LQL filter over one record type: the part of a query after =fetch TYPE | filter=. The ticket board and list have one (=/tickets=), and every list takes the same filter as =?q== (=GET /api/v1/ticket?q=...=, =/e/ticket?q=...=).

** What the bar takes

The text is a filter expression, or a =filter= or =filter_out= stage of its own:

#+begin_src lql
status not in ["done", "cancelled"]
assignee == me() or team_id in my_teams()
issue_type == "bug" and priority in ["high", "urgent"] and updated_at > ago(7d)
not (issue_type == "bug")
filter_out due_at < now()
#+end_src

It becomes =fetch ticket\n| filter TEXT= (or =| TEXT=), run as the caller in the environment of =venture_web_server_new_lql_environment()=, so it sees exactly the rows and fields the list API would. Nothing else can ride along: a =|= in the text is refused (the bar holds one filter, not a pipeline -- a =summarize= has no cards), and the environment has no source but the records. A =$parameter= is refused too, since nothing supplies one.

A field the record does not have is refused with "did you mean" (=lql_assist_lint()=). LQL itself would run =staus == "todo"= and match nothing -- a missing field is NULL -- which in a bar is always a typo, and an empty board is the worst way to say so.

=assignee in my_teams()= is valid LQL that never matches: =assignee= is a username and =my_teams()= gives team ids. Mine-or-my-team's is =assignee == me() or team_id in my_teams()=.

** How a list applies it

=venture_lql_filter_find_ids()= runs the filter with =| fields id= and gives the ids it kept; the list adds =id in [...]= to its own query, which then reads, orders, pages and counts as it always did. Only the selection is LQL's, so a list's JSON, its =total= and its sorting are unchanged, and the database still narrows the read where the filter allows (see [[*What reaches the database][What reaches the database]]). The read is bounded by =query.max_rows= and =query.timeout_ms=, and one filter may keep at most =VENTURE_LQL_FILTER_MAX_IDS= (30000) records, below what SQLite and PostgreSQL bind in one statement. A filter that keeps nothing selects nothing (an =id IS NULL= no row passes), never everything.

** Where it runs

A person's query never runs on the main loop. Every route that runs one -- =/tickets= with =q=, a list or export with =q=, =GET /api/v1/<type>?q==, and =GET /lql/assist= (preparing evaluates what was typed, and completion reads repositories) -- answers from a fiber (=venture_web_answer_later()=, as the Stripe routes do). The fiber builds the environment first, under the request's own access and tenant scopes, so the reader it captures -- the one every read is judged by -- is the request's, hosted per-workspace restriction included. It then hands the LQL work to a read worker (=venture_parallel_submit()=, with a read lease and that reader) and yields; the listener and every other request go on meanwhile, and the fiber is woken when the work is done (not inside somebody else's transaction). The run carries a =GCancellable=, cancelled a second past =query.timeout_ms= in case it outlasts LQL's own limit, which is only looked at between stages.

Where the server has no read workers -- a hosted install keeps every request on the main thread for its per-workspace scopes, and an in-memory database has no read connections -- the work runs in the fiber itself. =tests/test-lql-bar.c= runs every test both ways.

The byte budget (VENTURE #44) is not there yet: a query's memory is bounded only by the row bound and the time limit until the libre-query-language pin carries =LQL_LIMIT_MAX_BYTES=. =venture_lql_environment_new()= marks where =query.max_bytes= is set.

** Problems

=venture_lql_filter_check()= prepares the query without reading anything and places what is wrong in the text the person typed, not in the query it became: an offset and length, the unknown name and the suggestions (=VentureLqlProblem=). The board draws it on the server, so it works with scripting off: the message, the text highlighted with the faulty part in a =<mark class="lql-mark">=, a caret line under it, and a "did you mean" link per suggestion that writes it in. It draws no board, and answers 400. The list API answers 400 =invalid_argument= with "q, column N: MESSAGE". A problem of the query as a whole (the row bound, the time limit) has no place and is shown as a message.

** The board's URL filters

The board always read =kind=, =issue_type=, =assignee=, =venture_id= and =sprint_id= (blank, and for kind and type =all=, meaning "any"). It now reads any other =field__op=value= on a ticket field as the list API does, so =/tickets?status__not_in=done,cancelled= -- what dashboards link to -- filters the board too; parameters that name no ticket field are still ignored. All of them go through =venture_query_apply_query_string()=, one route.

The bar shows them as the LQL they mean (=venture_lql_filter_from_query_string()=), joined with the bar's own =q=: =status__not_in=done,cancelled= is =status not in ["done", "cancelled"]=, =assignee== is =(is_null(assignee) or assignee == "")= (blank means "null or empty" to a URL filter), a date is =timestamp("2026-01-01")=, =like= and =ilike= are =like(f, "%x%", TRUE)=. Submitting the bar carries the lot on as =q= alone, which is how an old link becomes a query. While they are URL filters they are applied as URL filters; =tests/test-lql-bar.c= holds the translation to the same tickets.

** Quick chips

Each chip is a link that adds its term to the bar with =and=, or takes it off when it is already one of the bar's top-level terms (=venture_lql_filter_toggle()=); a bar whose text has a top-level =or= is bracketed first. A person never has to learn the syntax for these.

| Chip              | Term                                         |
|-------------------+----------------------------------------------|
| Not done          | =status not in ["done", "cancelled"]=        |
| Mine              | =assignee == me()=                           |
| Unassigned        | =(is_null(assignee) or assignee == "")=      |
| Bugs              | =issue_type == "bug"=                        |
| Updated this week | =updated_at >= period("this_week").start=    |

"This week" is the calendar week on the business calendar (=locale.timezone=), not the last seven days; =updated_at > ago(7d)= is that.

** Editor help

With scripting on, =venture.js= asks =GET /lql/assist?type=ticket&q=TEXT&at=N[&base=URL]= as you type (150 ms after the last key, only the latest answer drawn). =N= is the cursor in UTF-16 units, as a browser counts, and every offset in the answer is too:

#+begin_src json
{
  "status": "<the line under the bar, as the page would draw it>",
  "problem": null,
  "completions": [
    {"label": "in_progress", "kind": "value", "detail": "VentureTicketStatus",
     "insert": "\"in_progress\"", "start": 10, "end": 10}
  ]
}
#+end_src

Completion (=venture_lql_filter_complete()=) offers LQL's own candidates -- field names, functions, keywords, constants -- and first, where a field is being compared (=status == =, =priority == "hi=, =issue_type == bu=, =status not in ["done", =), the values that field takes: an enumeration's names (=status=, =priority=, =issue_type=, =kind=, ...), or for a reference to a forge repository its ids (=repo_id=, the name as detail) or names (=repo_label=), read as the caller, so a repository they cannot read is never offered. The list is a listbox under the input: arrows move, Enter or Tab takes one, Escape closes, Ctrl+Space asks. Enter with nothing chosen submits the form as it would without the list.

** Highlighting

=venture_lql_filter_highlight()= draws the text as =<span class="lql-KIND">= per token (LQL's highlight kinds), escaped. Both looks' stylesheets carry the rules, and point each =--lql-*= variable at a role of the look's palette (=--lql-string: var(--positive)=, =--lql-keyword: var(--accent)=, =--lql-error: var(--negative)=, ...) rather than at a colour, so light and dark and an organisation's accent apply to a query for free. =lql_highlight_get_css()= is not used: the rules are in the stylesheets, served once.

** Saved views

A view saved from a filtered list keeps =q= in =saved_view.lql= and the rest of the query string in =saved_view.query=, and opens at =<list>?<query>&q=<lql>=. A view without =lql= (every view saved before) opens as it always did. Migration =001083_saved_view_lql= checks the column, which reconciliation adds from the field table.

* What is deliberately not registered

LQL can read files (=read=), run programs (=exec= and command definitions), talk SQL (=sql=, =sqlite=, =postgres=), read git history, the systemd journal and Kubernetes. Each is a provider a host has to add; VENTURE adds none. Every one of them would read around the one reader path and its access policy: a =sql= source would answer any question about any table, whatever the caller may see. =tests/test-lql.c= holds =read "/etc/passwd"=, =sql ...=, =sqlite=, =postgres=, =exec=, =git_log=, =k8s= and =journal= to "unknown command", and checks that every =fetch= name is a record source.

LQL scripts (=.include= of other files) are a host API (=lql_script_load()=) that no query can reach, and VENTURE does not use it.

LQL here is read-only. Writes from a query result are a later story, through the existing bulk route and its validators.
