* What this is

VENTURE has always accepted webhooks from a git forge. This is the other direction: a record changed here, and something outside wants to know. A =webhook= is a URL, a list of events and a signing secret; every audited change matching one is POSTed to it, signed the way VENTURE signs nothing else and verifies everything it receives, and what happened is kept as a =webhook_delivery=.

The module is =webhooks= and it requires only =core=. Turning it off stops every delivery without deleting anything, which is the switch to reach for when an endpoint is melting.

* Events

An event is the record type and what happened to it: =ticket.created=, =invoice.updated=, =sale.deleted=. Nothing writes that list down — it is the types crossed with three actions, so a plugin's record type is publishable the day it registers, for the same reason the REST API and the CLI cover it with no routing to add.

A webhook subscribes with a comma-separated list of patterns:

| Pattern                       | Matches                                     |
|-------------------------------+---------------------------------------------|
| =*=                           | everything                                  |
| =ticket.*=                    | every action on a ticket                    |
| =ticket.created=              | exactly that                                |
| =ticket.created, invoice.*=   | either                                      |
| (blank)                       | everything — a webhook nobody has narrowed yet |

A prefix is not a type: =ticket.*= does not match =ticket_link.created=.

A market data alert firing is one of these too: it writes an =alert_hit= as the system, so =alert_hit.created= is the alert event, with the hit's message as the body's =label= (cut to 120 characters, as the hit's display name is) and =record.url= the hit's page. There is no separate alert event to subscribe to (see [[file:market-data.org::*Alerts][Market data: alerts]]). The system's own creations are published like anybody's. A hit is written outside any transaction and outside any automation handler, so the delivery leaves as the hit is saved, at most =VENTURE_ALERTS_MAX_HITS_PER_RUN= (100) per feed run and never more often per rule and subject than the rule's cooldown.

The feeds module's records are published the same way, which is worth knowing before subscribing to =*=: every recorded feed run is a =data_source_run.created=, written as the system -- one per source per =feeds.run_window_minutes= at most for a scheduled source, one per manual sync. Subscribe to =alert_hit.created= (or =data_source_run.*= on purpose) rather than everything when a source polls often. A recorded arbitrage trade is =arbitrage_trade.created= and each leg =arbitrage_leg.created=, and executing or closing them are =.updated= events, like any record.

** What is never published

Some types are quiet, whatever a webhook subscribes to: =webhook= and =webhook_delivery= (a delivery about a delivery is the obvious loop), =notification= and =watch= (bookkeeping), =audit_entry=, =chat_thread= and =chat_message= (private), =kb_chunk= and =kb_link= (derived, and a reindex would post a thousand times), =federation_replica=, =federation_peer= and =federation_grant= (federation's own bookkeeping, which names peers and what is shared with them), =api_token= and =user= (access management). Market data added nothing to it: an alert hit is exactly what an outside system wants to hear about, and a feed run is ordinary business activity of the organization that owns the source. The list is in =src/core/venture-webhook.c= beside the one the inbox uses, and for the same reasons.

* The body

#+begin_src json
{
  "event": "ticket.created",
  "delivery": "0f0a9f5e-...",
  "occurred_at": "2026-09-12T09:14:02Z",
  "actor": "zach",
  "webhook": { "id": 1, "name": "Ops chat" },
  "record": {
    "type": "ticket",
    "id": 7,
    "label": "Checkout returns 500 on Apple Pay",
    "url": "/e/ticket/7"
  },
  "data": null
}
#+end_src

The envelope is always this shape, so a receiver routes on it without knowing VENTURE's types, and =delivery= is a fresh id it can deduplicate on. =data= is =null= unless the webhook has *Send the record* set, in which case it carries the whole record — never its sensitive fields, which are withheld from a body posted to somebody else's server for exactly the reason they are withheld from a response.

* Signing

Every delivery carries three headers:

| Header                 | What it is                                            |
|------------------------+-------------------------------------------------------|
| =X-Venture-Event=      | the event name                                        |
| =X-Venture-Delivery=   | a fresh id for this delivery                          |
| =X-Venture-Signature=  | =sha256=< hex >=, an HMAC-SHA256 of the exact body bytes keyed by the secret |

Compute the HMAC over the raw body and compare in constant time. This is the same shape VENTURE verifies on the way in from a forge, so an operator who has wired one up already knows how to check the other.

A webhook with no secret sends no signature, and the page says *unsigned* in yellow. Generate one with the *New secret* button, =venturectl webhook secret ID= or =POST /api/v1/webhooks/:id/secret=; it is shown exactly once, like an API token, because only its holder needs it and a secret shown twice is a secret in two logs.

* Deliveries

Sending is asynchronous, on the main loop. A write does not wait for somebody else's server — and no background thread in this program may touch the database (the coding runs' thread, the feeds worker and the transport tasks of the bank feed, the mailer and the feed providers; =AGENTS.md= lists every one), so this is a queued request rather than a thread, and the result is recorded when it arrives.

Every attempt becomes a =webhook_delivery=: the event, the record, the state, the status code, how long it took, the body that went out and the beginning of what came back. Delivery records are evidence, like a coding run and the audit log: the generic routes refuse to edit them, and reading stays open.

** When the far end stops answering

Consecutive failures are counted on the webhook. A success resets the count; ten in a row switches the webhook off and tells the owners and admins in their inbox. An endpoint that has refused ten deliveries is gone, and posting to it on every write for the rest of the week costs a request per change and tells nobody anything. Switch it back on from the webhook's page once it is fixed.

There is no retry. A retry that is not idempotent on the far end is worse than a gap, and a delivery id is exactly what a receiver needs to make its own decision; the delivery log is how you find what was missed.

* Pushes to a phone: gotify and ntfy

A webhook's =format= says what the far end expects. =venture= (the zero value, what every webhook made before the formats existed reads back as) is the signed envelope above. =gotify= and =ntfy= turn the same event into a push notification, which is how a price alert reaches a phone:

| Format   | Request                                                                                         | Token                              |
|----------+-------------------------------------------------------------------------------------------------+------------------------------------|
| =gotify= | =POST {url}/message= (the URL is the server's, e.g. =http://host.containers.internal:8280=), JSON ={"title", "message", "priority"}= | =X-Gotify-Key=: an application token; required |
| =ntfy=   | =POST {url}= (the URL is the topic's, e.g. =https://ntfy.example.com/trading=), the message as a plain-text body, =Title= and =Priority= headers | =Authorization: Bearer=: an access token; optional, a public topic needs none |

The title is what happened, in words: the record type's name ("Alert hit", "Ticket"), with "updated" or "deleted" when it was not a creation, or "VENTURE" for *Test*. The message is the record's label -- for an alert hit, its sentence, cut to 120 characters ("Star Ruby: buy at Silver Hand for 41.2000 GOLD, sell at Area 52 for 58.0000 GOLD, 13.9000 GOLD profit (33.7%)"). With =server.base_url= set the message ends with the record's address, and the push opens it when tapped (gotify's =client::notification= extra, ntfy's =Click= header). =priority= on the webhook is 1 to 10 on gotify's scale (ntfy gets half of it, rounded up, 1 to 5); 0 leaves each service its default (5 and 3). =events= works as for any webhook: =alert_hit.created= for market alerts and nothing else. =include_record= and the signing secret mean nothing to a push.

Three rules keep the token where it belongs:

- *The token is never a field.* It is sealed in the credential store, under =webhook-<uuid>=, with the installation's =VENTURE_INTEGRATION_KEY= (without the key it cannot be set at all). Set it on the Webhooks page (a write-only box beside each push webhook), with =POST /api/v1/webhooks/:id/token= ={"token": "..."}= or with =venturectl webhook token ID < token-file= -- standard input, never an argument, because argv is readable by every process on the host. Nothing shows it again: the page and =GET /api/v1/webhooks= say =token_set=, and a far end that echoes the header back in an error has it masked in the delivery's excerpt.
- *A push goes only to an origin the operator allowed.* =webhooks.allowed_origins= (=VENTURE_WEBHOOKS_ALLOWED_ORIGINS=) is a comma-separated list of exact origins -- scheme, host and a port other than the scheme's own, no path -- deny by default. Plain =http= is accepted, because a gotify on the same host or LAN is the usual case, and it means the token crosses that network in the clear: list an =http= origin only for a network you trust. A push to any other origin is refused before anything is sent and recorded as a failed delivery naming the setting. The signed =venture= envelope carries no credential and is not held to the list.
- *A token goes only where it was sent when it was set.* Sealing it records the webhook's origin then; a delivery after the URL moves -- even to another allowed origin -- is refused with "set the token again". Redirects are never followed, so a 302 cannot carry the token to a host the response chose.

A push that cannot be built (no token on a gotify webhook, an origin not on the list) is a failed delivery like a refusal from the far end, and counts towards the ten that switch a webhook off. *Test* sends a push saying so ("A test from VENTURE: this webhook reaches you.") and waits for the answer.

For the gotify on this deployment:

#+begin_src sh
# the server's environment (compose env file), then restart it
VENTURE_INTEGRATION_KEY=<base64 of 32 random bytes>   # already set if any credential is sealed
VENTURE_WEBHOOKS_ALLOWED_ORIGINS=http://host.containers.internal:8280

venturectl create webhook name="Phone" url=http://host.containers.internal:8280 \
    format=gotify events=alert_hit.created priority=8 active=true organization_id=N
venturectl webhook token ID < gotify-app-token.txt   # an application token made in gotify's UI
venturectl webhook test ID
#+end_src

* Testing one

*Test* on the Webhooks page sends a =webhook.test= delivery and waits for the answer, so pressing it tells you whether the far end is there rather than promising to find out. The same thing is =venturectl webhook test ID= and =POST /api/v1/webhooks/:id/test=.

Pointing a webhook at your own install to see what a body looks like works, which is worth saying because it did not at first: the test waits in a nested main loop rather than blocking, so the server can answer itself.

* Over the API and the CLI

| Question              | API                                    | venturectl               |
|-----------------------+----------------------------------------+--------------------------|
| what is listening     | =GET /api/v1/webhooks=                 | =webhooks=               |
| is the far end there  | =POST /api/v1/webhooks/:id/test=       | =webhook test ID=        |
| a fresh secret        | =POST /api/v1/webhooks/:id/secret=     | =webhook secret ID=      |
| a push's token        | =POST /api/v1/webhooks/:id/token=      | =webhook token ID < file= |
| make or change one    | the generic routes on =webhook=        | =create/update webhook=  |

Webhooks are owner-only everywhere — the page, the generic routes, the API — for the same reason a forge is: the row names the host this install's business data is posted to and holds the secret that signs it, and an editor who could change the URL could point every change in the books at a server they control, with the staged diff showing nothing but a URL moving.

The assistant is not given webhooks at all. It has no tool that lists, makes or changes one, exactly as it has no way to read a forge's token.
