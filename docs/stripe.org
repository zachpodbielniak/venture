#+title: Stripe payments
#+description: Hosted Checkout for issued invoices and verified settlement

* Configure an organization account

Stripe is opt-in: set =stripe.enabled: true=. It requires =receivables=,
=integrations= and its organization-access prerequisite. The module table
places Stripe after these dependencies so the bottom-up registry stays acyclic.
An unconfigured organization does not prevent startup; its Checkout operation
fails closed until an organization owner/admin connects it.

Set the installation encryption key as documented in [[file:integrations.org][Organization integrations]].
Open Stripe settings from the organization record, or visit
=/organizations/<id>/settings/stripe= as that organization's owner/admin.
Supply all seven fields: =secret_key=, =publishable_key=, =webhook_secret=,
=api_version=, =success_url=, =cancel_url= and =environment= (=test= or =live=).
Return URLs require HTTPS without embedded credentials. Account verification
calls Stripe's authenticated =GET /v1/account= before saving. The account ID
comes from Stripe; keys must match the selected environment. Connect accounts
and restricted API keys are outside this adapter's current contract.

The page shows only account identity, environment and the exact webhook path.
Every credential input starts blank, including after a failed submission.
Settings are encrypted with authenticated organization/account/environment
binding; generic records, CLI, AI tools and audit never return clear credentials.
Test connection verifies current credentials still identify the bound account.
Connect or rotate requires all values and the displayed connection identity
and optimistic version. Stale forms cannot change a replacement connection.
A same-account rotation takes effect on the next operation, including cached
services. The previous webhook secret stops working immediately: coordinate
rotation with Stripe's endpoint configuration; no overlap window is implied.

Disconnect retains the historical binding and its encrypted credentials for
outstanding signed callbacks. A different account or environment requires
disconnect followed by connect. New invoices select the current connection;
old pending Checkouts remain with their original account. A pending Checkout
from any earlier account, including an unbound legacy row, refuses creation
of another payment link until reconciled. Disconnecting never moves payment
evidence or settles an invoice. Return-page navigation never records cash.

Production reads no =VENTURE_STRIPE_*= credential fallback, including the
default organization. The legacy environment constructor exists only when an
explicit offline transport is injected in a C test. Existing installation
credentials must be deliberately connected to each intended organization.
The legacy =/webhooks/stripe= endpoint is unavailable in production; configure
the connection-specific path shown on the settings page.

* Dashboard and catalog setup

Checkout refuses deleted invoices and customers before creating provider objects, including historical references that remain on an issued invoice.

Ordinary sent invoices with a positive open balance qualify. Checkout
charges that remaining amount with Stripe =price_data= (currency, unit
amount in Stripe charge units, and a product name). A =stripe_price_link=
is optional catalog evidence; it is not required to open a session, and
it cannot replace the invoice remaining. Subscription catalog mapping
and payment-driven recovery are not implemented.
Billing invoice lines copy =plan_price.product_id=, so a subscription invoice
qualifies for Checkout when a =stripe_price_link= exists for that product.
=billing collect= records an operator-confirmed receipt through an authorized =manual= customer payment method and recovers =past_due=. Processor mandates alone cannot record cash. Do not rewrite issued invoice evidence to
pass eligibility.

1. Configure the HTTPS webhook endpoint at =/webhooks/stripe/<connection-id>= for
   =checkout.session.completed=. Select the same explicit API version used
   in that organization’s settings, and save its signing secret there.
2. Issue the Venture invoice through the normal settlement lifecycle.
   Use *Pay with Stripe* on its page, or =venturectl invoice checkout ID=.

A stored expired session may be replaced. The existing receivables
lifecycle requires a bill-to company. Unexpected webhook totals are
recorded as mismatches.

* What is stored

| Record | Purpose |
|--------+---------|
| =stripe_price_link= | Organization's product-to-price mapping |
| =stripe_customer_link= | Company or contact's Stripe customer identifier |
| =stripe_checkout= | Invoice, globally unique session ID, URL, status, expected exact money and settled payment |
| =stripe_event= | Globally unique event ID, type, receipt/processing times, sensitive verified payload and result |

Customer creation sends the Venture company UUID as supported customer
metadata. The service reuses an existing customer link. Customer creation
has a stable UUID-derived idempotency key; Checkout's key uses the invoice
UUID and version. Repeating Checkout returns its existing stored row.

Checkout sends no metadata: the pinned library does not support it for that
operation. The stored session ID maps back to the invoice. An authenticated
event naming an unknown session is stored with result =ignored= and changes
no payment. This endpoint never accepts an invoice ID from webhook metadata.

* Verification and settlement

=VentureStripeService= is the provider boundary. Generic writes cannot create
or edit Checkout or event evidence, and cannot delete, restore or purge it.
The service sends requests synchronously through =StripeClient= and forwards
its detailed, redacted =event::stripe.*= observations into the audit log.

Every delivery is signature-verified over the original bytes. A fresh verifier
uses the same immutable configuration for each delivery; durable event IDs
provide replay protection so an identical valid retry can receive HTTP 200.
An invalid signature receives 400 and leaves a redacted rejection audit. A duplicate event changes no rows, including
audits. Unknown authenticated event types are recorded and ignored.

A completion must report paid status, a payment-intent identifier, and an
amount and currency equal to the expected VentureMoney. Comparison uses the
Stripe's charge units and checked rescaling; overflow is a mismatch,
not equality. There is no universal two-decimal assumption.
Mismatches are recorded, refused, and need operator reconciliation.

The event, receipt, allocations, postings and completed Checkout row share
one database transaction. The receipt is applied through
=venture_settlement_service_apply_payment()= with method =stripe= and the
payment-intent ID as both reference and external ID. Settlement invokes the
existing fiscal-period and journal guards. Failure rolls everything back;
Stripe can retry the delivery. No invoice status or journal is written by
provider code. A second event for an already settled session cannot create
another payment.

* Boundaries and verification

=processor_payout= records a payout batch's gross, fees and net bank amount.
Fees post to platform fees (6000), never income. =processor_payout_item= names
the receipts in the batch so a grouped deposit can be matched without
double-posting cash. =processor_dispute= holds AR by moving the invoice to the
built-in =disputed= workflow state. A lost dispute reverses the receipt through
=VentureSettlementService= as a refund. =processor_exception= is the retry
queue for mismatches, closed periods and out-of-order events.

There are no Billing Portal, Stripe Invoice creation,
Connect accounts or generic provider interface. A future provider should own
its transport and verified external-event mapping, then call the same
settlement service. A future provider interface would sit in front of
=VentureStripeService='s Checkout and webhook actions. SaaS billing must create
and issue its Venture invoice first, then call this service; it must not set
financial invoice state itself.

There is no automatic expiration/replacement workflow for stored Checkout
sessions in this version. Once a session expires at Stripe, an operator must
reconcile it before requesting a replacement; repeating the action preserves
the original session and idempotency identity.

=test-stripe= uses a fake =StripeTransport= and locally signed webhook bytes;
no network requests to Stripe and no stripe-mock are involved. It exercises
eligibility, exact amounts, session linkage, duplicate delivery, rollback,
immutable evidence, configuration and HTTP/CLI/web actions. The full suite
runs with =GSETTINGS_BACKEND=memory make DEBUG=1 -j8 test=.

Checkout enforces invoice write authority, including organization roles and policy-plugin vetoes, before any customer or session request reaches Stripe.

A product link identifies a remote Price, not its value. Before creating a customer or Checkout session, Venture retrieves the Price and requires an active one-time per-unit integer amount with no quantity transformation. Its amount times the integral quantity must exactly equal the invoice's open balance in the same currency. Recurring, tiered and fractional-minor-unit prices are refused. Discounts, taxes and partial payments are not reconstructed in Checkout; any difference from the linked Price is refused before external writes.

Both Price validation and signed webhook settlement use Stripe's charge currency units: the documented zero-decimal currencies (including MGA) use exponent zero, while ISK and UGX retain Stripe's two-decimal API representation and must be multiples of 100. See [[https://docs.stripe.com/currencies][Stripe supported currency rules]]. Checked integer arithmetic reconciles these units with an invoice's stored exponent; overflow is refusal, never equality.

Only =POST /webhooks/stripe= uses independent signature authority; an incidental local browser session does not restrict or widen that capability. Signature, payload size and module guards still apply. Neighboring paths and other methods retain local authentication and organization policy.

A lost chargeback requires an open dispute. Repeating the loss action is refused, including partial disputes, so the same dispute cannot reverse a second portion of its receipt.

* Historical identity and upgrades

Migration =000500_stripe_account_bindings= verifies the metadata upgrade.
Customer mappings, price mappings, Checkouts, events, payouts and disputes
reference the immutable integration connection. Identifiers are unique within
=(organization, connection, identifier)=, so equal provider IDs in different
accounts or environments do not collide. Payment external references and
provider idempotency keys include the connection UUID. Payout and dispute
operations refuse receipts recorded under another connection, including an
earlier connection belonging to the same organization. Generic writers cannot
rewrite customer mappings or payment evidence; catalog references are checked
at save for the same organization and immutable binding.

Old rows remain connection zero/NULL (one legacy partition); no migration
infers their historical account from today's credentials. The shared scoped
uniqueness migrator removes obsolete global/organization-only indexes while
preserving other schema objects and rows. It refuses duplicates transactionally.
Signed callbacks require the exact retained connection, matching event
=livemode=, and a matching =account= when present. An unknown event is durably
ignored only after these checks. Replacement accounts cannot claim old sessions.

This adapter covers hosted invoice Checkout and verified receipts. It does not
provision Lightsite, ACH mandates, automatic subscription charges, Stripe
Connect delegation or account discovery across arbitrary credentials.
