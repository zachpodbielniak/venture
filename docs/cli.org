* For an AI agent

=skills/venture/= is the agent skill for VENTURE, invoked as =/venture=:
=SKILL.md= orients an agent (what VENTURE is, the probes to run first,
critical rules, where things live, the command surface and a table of
common requests), and =references/= holds one guide per subsystem -- the
system as a whole, the data model module by module, the raw REST API,
every =venturectl= verb, reports, dashboards, the books, billing, the CRM,
the desk, the factory, market data and arbitrage -- plus a symptom-first
troubleshooting index. It is maintained alongside the code rather than as
documentation about it. It was called =venturectl= until it grew past the
command line; =make install-skill= removes a link it left under that name.

Install it for whichever agents you use:

#+begin_src bash
make install-skill
#+end_src

That symlinks it into =~/.claude/skills=, =~/.grok/skills= and
=~/.agents/skills= — Claude Code, grok-build and opencode respectively.
Symlinked rather than copied, so editing the working tree is immediately
what every agent reads; a copy would drift the first time one was edited in
place. Override =SKILL_DESTS= for a different set, and =make
uninstall-skill= removes the links. Neither target will touch a real
directory that happens to share the name.

The habit it exists to instil is =venturectl describe TYPE= before writing
anything. That prints every field in the spelling you must type, what each
reference points at, and what each enum accepts — all generated from the
source, so unlike prose it cannot drift.

* venturectl

Drives the server over its REST API. It deliberately does not open the
database: one writer, one set of validation rules, one audit trail.

It links only =libventure-core.a= and yaml-glib, so =make venturectl= works on
a machine that cannot build the server at all.

* Setup

#+begin_src sh
export VENTURE_SERVER=http://127.0.0.1:8747   # the default
export VENTURE_TOKEN=vk_...                    # from POST /api/v1/tokens
#+end_src

The token is read from the environment rather than a flag because a flag is
visible in the process list. Keep it in =~/.bashrc-secrets=.

* Periods

Ledger reports accept =basis=cash= or =basis=accrual= and =dimension=VALUE= alongside the period; these options pass through to the same report implementation used by the web page.
The leads =lead_scoring= report accepts =band_size=N= for the width of its score bands (default 25).
The =aggregate= report takes =type=, =measure=, =aggregate=, =group_by=, =category_depth=, =date_field=, =bucket=, =filter= and =per= after the period --- =venturectl report aggregate 2026 type=sale measure=gross group_by=channel date_field=occurred_at bucket=month=; quote a =filter= holding =&=. See [[file:reporting.org][Reporting]].

The market reports take =product_id= and =source= (=price_history=) and =group_by=, =category_depth= and =venture_id= (=listing_performance=) the same way --- =venturectl report price_history last_30_days product_id=12 source="market value" bucket=week=. See [[file:market.org][Market]]. =recipe_margin= takes =price_source=, =category_id= and =venture_id= --- =venturectl report recipe_margin all price_source="market value"= --- and a recipe is crafted with the generic action verb, =venturectl act recipe 3 craft times=5 location_id=2=, which types each argument from the action's schema. See [[file:production.org][Production]]. =session_performance= takes =group_by= (=activity=, =category=, =location=, =venture=), =category_depth=, =price_source= and =venture_id= --- =venturectl report session_performance this_month group_by=activity price_source="market value"= --- and a session's goods go into stock with =venturectl act session 8 post=, which takes no arguments and posts only what is new. See [[file:sessions.org][Sessions]]. =goal_progress= takes =status= (one nick, or several comma separated), =category_id= and =venture_id=, and =goal_materials= takes =goal_id=, =price_source=, =include_on_hand= (=true= or =false=) and =venture_id= --- =venturectl report goal_materials all goal_id=3 price_source="market value"=. See [[file:goals.org][Goals]].

Anywhere a period is accepted — a =report= argument, a =period== filter on a
list — the full grammar is:

| Form                     | Examples                                     |
|--------------------------+----------------------------------------------|
| named                    | =today=, =yesterday=, =this_week=, =last_week=, =this_month=, =last_month=, =this_quarter=, =last_quarter=, =this_year=, =last_year= |
| to date                  | =ytd=, =qtd=, =mtd=                          |
| fiscal year              | =fy= (current), =fy_2026=                    |
| rolling                  | =last_30_days=, =last_90_days=               |
| calendar                 | =2026=, =2026-03=, =2026-Q2=, =2026-03-14=   |
| explicit range           | =2026-01-01..2026-03-31=                     |
| everything               | =all=                                        |

* Output

A terminal gets an aligned table; a pipe gets JSON, so this works with no
flag:

#+begin_src sh
venturectl list sale | jq '.records[].gross.formatted'
venturectl -f yaml get venture 1 >> ~/Documents/notes/00_inbox/venture.org
venturectl -f csv list expense period=fy > expenses.csv
#+end_src

=--format= takes =table=, =json=, =yaml= or =csv=. =--quiet= drops the totals
line.

The table truncates and selects columns for the eye; CSV does neither — every
field appears, in the wire spelling =describe= documents, with money printed
as its formatted form. =-f csv report NAME= returns the server's own CSV
rendering, byte-identical to the web export. Cells are escaped and a leading
=​== is defused, so an export opens in a spreadsheet without executing
anything.

* Exit codes

Distinct so a script can branch:

| Code | Meaning              |
|------+----------------------|
|    0 | success              |
|    1 | general failure      |
|    2 | usage                |
|    3 | not found            |
|    4 | conflict             |
|    5 | authentication       |
|    6 | unsupported          |
|    7 | network or timeout   |
|    8 | validation           |

#+begin_src sh
if ! venturectl get venture "$id" >/dev/null 2>&1; then
	case $? in
		3) echo "no such venture" ;;
		5) echo "check VENTURE_TOKEN" ;;
		7) echo "server unreachable" ;;
	esac
fi
#+end_src

* Using it with an AI

The interface is deliberately machine-friendly: =venturectl types= enumerates
what exists, =venturectl types TYPE= describes a type's fields, and JSON is
the default when output is piped. An agent can discover the whole data model
without documentation.

For an agent that speaks the Model Context Protocol rather than a shell,
=venturectl mcp= is the same API as a stdio MCP server: nine tools whose
record-type enumerations are generated from =/api/v1/schema= at startup, so a
plugin's type is offered with no change anywhere. Writes are staged rather
than applied unless =--apply-writes= is given: the change is queued on the
server for somebody to approve, not merely described. =venturectl --stage=
does the same for =create=, =update=, =delete= and =act= from the shell. It takes its credential from
=VENTURE_TOKEN= and refuses =--token= outright, since an MCP server is spawned
from a config file. See [[file:mcp.org][venturectl mcp]].

* Reconciliation suggestions

=venturectl reconcile suggest TYPE ID [--matcher NAME] [--threshold N]=
prints ranked book-record matches for a saved bank line. Without =--matcher=
it merges every registered matcher. The default threshold is 80; scores
strictly above it stage the banking =match= action when that module
is available. With no banking records installed it returns suggestions
only. It never applies a match. Use =-f json= to include the full confirmation
objects, then review them in the ordinary confirmation queue. See
[[file:reconciliation.org][reconciliation suggestions]] for matcher plugins
and the banking seam.
* Stripe checkout

=invoice checkout ID= calls the Stripe service and returns the stored Checkout record, including =url=. It requires the Stripe module and a sent invoice with one configured product line. See [[file:stripe.org][Stripe payments]].
* Asset actions

=venturectl asset place ID=, =asset dispose ID proceeds=AMOUNT= and
=asset write-off ID= call the asset service. Optional =in_service_at= or
=disposed_at= selects an effective date.

=venturectl assets run-period YYYY-MM [organization_id=ID] [--dry-run]=
posts the organization's scheduled depreciation and deferral releases in
one transaction. The default organization is used when omitted. A retry
posts only remaining scheduled entries; a closed period is refused.

The ordinary record commands manage draft =fixed_asset= and new =deferral=
records. Lifecycle status and schedule history are service-owned. See
[[file:assets.org][fixed assets and deferrals]] for profiles and examples.
* Organization access and journal posting

The ordinary =list/get/create/update/delete/describe= commands also manage
=organization_membership=, =team= and =team_membership=. Inviting an outside
accountant is the same two records — no new verb:

#+begin_src sh
venturectl create user username=cpa role=viewer password=...      # global owner
venturectl create organization_membership user_id=7 organization_id=1 role=accountant active=true
venturectl create organization_membership user_id=7 organization_id=2 role=accountant active=true
#+end_src

Signed in as that user, =venturectl= reads and exports the books of each
client organisation and nothing else; a write is refused with a message
naming the accountant role. See [[file:orgaccess.org][the role matrix]]. Tokens constrain all
responses to their mint-time memberships intersected with current authority.
Selecting =organization_id= only narrows that scope. Global owners keep the
existing output formats and data authority.

=venturectl journal post ID= calls the shared posting service. An organization
editor receives a pending confirmation; finance and organization admin/owner
can post directly. =venturectl --stage journal post ID= always proposes.
A pending confirmation is not a posted journal. Generic =update journal=
cannot advance state. See [[file:orgaccess.org][Organization access]].
=venturectl user mfa reset USER= (an id or a username) is the owner-only
break-glass path for a lost phone and lost recovery codes: it calls the
=mfa_reset= action on =user=, turns the account's second factor off, spends
its recovery codes and writes an =mfa_reset= audit row naming the token or
person that ran it. The ordinary commands manage =mfa_policy=, the
per-organization =require_mfa_for_admins= setting. See
[[file:security.org][Security: the second factor]].

Customer health is a report too, with =band=, =owner= and =sort= as
options; the only verb is the sweep, which is a business action rather
than a record write.

#+begin_src sh
venturectl report customer_health this_month band=red sort=-overdue_days
venturectl customers health-sweep as_of=2026-06-01 limit=50   # {"created": N}
venturectl update headline_setting 1 health_touch_days=45 health_overdue_days=30 health_open_tickets=5

=renew= without an ID sweeps all due subscriptions in the selected
organization; =renew ID= renews one. =--as-of= sets the effective action
or sweep date. =--dry-run= previews sweeps without writing anything.
The generated =plan= and =plan_price= records configure the catalogue.
Direct subscription state writes are refused. The assistant can stage
=billing_request= through its generated create tool; all CLI billing
actions also honor =--stage=. See [[file:billing.org][SaaS billing]] for prices,
trial activation, proration, historical report definitions and limitations.

* The money calendar

=money calendar= prints the agenda of every dated money event between two
inclusive days, through the =money_calendar= report:

#+begin_src sh
venturectl money calendar --from 2026-03-01 --to 2026-03-31
venturectl money calendar --from 2026-03-01 --to 2026-03-31 --kind bill --as-of 2026-03-02
venturectl -f json money calendar --from 2026-03-01 --to 2026-03-31
#+end_src

=--from= and =--to= are required. =--kind= keeps one of =recurring=,
=bill=, =invoice=, =dunning=, =payroll= or =tax=; an unknown kind is
refused. =--as-of= is the day overdue items are carried to. Each day prints
with its ISO week and per-currency net, then one line per event. =-f json=
prints the report unchanged. See [[file:money-calendar.org][the money calendar]].
* Transactional mail

=venturectl mail send to=... subject=... body=...= enqueues; =--html FILE=
adds HTML. =mail test to=...= tests the configured SMTP transport immediately.
=mail deliver [--limit N]= sweeps due messages, =mail list state=uncertain=
shows outcomes needing an operator, and =mail retry ID= deliberately reuses
that row and Message-ID. All accept =organization_id=N= where relevant.
See [[file:mail.org][mail]] for uncertainty and scheduling. Actions reject
=--stage=; =--stage create mail_message= proposes an enqueue instead.

=venturectl mail sync [organization_id=N] [limit=N]= runs the bounded
inbound sweep over every active =mail_account= in the organization that is
not backing off and prints the accounts and messages processed, the accounts
skipped, whether a budget deferred the rest, and any per-account error.
=venturectl mail sync account_id=N= syncs one account now, ignoring its
backoff (owner only). =venturectl mail contact ID= turns an unmatched sender
into a contact and backfills its earlier mail onto the timeline;
=venturectl mail dismiss ID= keeps the address as an ignore-list entry. The
raw messages, interactions, unmatched senders and capture items the sync
creates are ordinary records: =venturectl list mail_inbound=, =venturectl
list mail_unmatched_sender dismissed=false=. See [[file:mail.org][mail]],
section Inbound.

* Calendar sync

=venturectl calendar sync [organization_id=N] [limit=N]= runs the bounded
two-way CalDAV sweep over every active =calendar_account= in the
organization and prints the accounts and changes processed with any
per-account error. It requires an editor, refuses =--stage=, and never
deletes: a removal on either side cancels the other. The accounts and
scheduling links are ordinary records — =venturectl create calendar_account
url=... owner=ben username=... secret_env=VENTURE_CALDAV_BEN
calendar_path=/calendars/ben/default/ active=true= (owner-only) and
=venturectl create booking_page slug=intro owner=ben duration_minutes=30
timezone=America/Chicago availability='{"mon":"09:00-17:00"}' active=true=;
=venturectl list calendar_event= shows what the sync linked. See
[[file:calendar.org][calendar sync]].

* Quote actions

=venturectl quote send ID= freezes and queues a proposal.
=venturectl quote accept ID 'by=Full Name'= accepts it and issues its invoice.
=venturectl quote decline ID 'reason=Explanation'= records a refusal;
=venturectl quote revise ID= clones the proposal and supersedes its source.
For approval, use =--stage create quote_action quote_id=ID action=accept
expected_version=N accepted_by=NAME=. See [[file:quotes.org][quotes]].
* Leads

=venturectl lead convert ID [deal=yes|no] [company_id=ID] [contact_id=ID]=
converts a qualified inquiry atomically. =--stage= queues conversion for
approval. =venturectl lead reassign ID [owner=NAME]= assigns explicitly or
runs matching rules again. Generic =create/update lead= supports capture and
qualification; converted state and references belong to the service.
Recycle with =status=recycled unqualified_reason=... recycle_until=YYYY-MM-DD=.

=venturectl leads reroute ID= clears the owner and evaluates the routing
rules again in position order, recording "Lead routed" or "No rule matched"
on the timeline. =venturectl leads rescore ID= clears a manual score mark
and applies the scoring formula. Both take no other arguments, refuse
converted leads, do not accept =--stage=, and are also spelled =lead reroute=
/ =lead rescore=. Rules themselves are ordinary records:
=venturectl create lead_routing_rule ...= and
=venturectl create lead_scoring_rule ...=.
See [[file:leads.org][leads]] for capture forms, duplicate policies,
routing, scoring and reports.
See [[file:leads.org][leads]] for capture forms, duplicate policies and reports.

=venturectl crm preview MANIFEST= reads a migration manifest, inlines the
CSV files its =files= member names (relative to the manifest) and creates a
=crm_import= batch in the preview state. =venturectl crm import MANIFEST=
does the same and imports it; =crm import ID= imports a previewed batch,
=crm activate ID= accepts it and =crm rollback ID= removes what the batch
created. See [[file:crm-import.org][CRM migration]] for the manifest, the
built-in HubSpot, Zoho CRM and Salesforce column maps and the refusals.
* Planned activities

=venturectl activity complete ID outcome=...= completes planned work through
the activity service, records history and advances recurrence atomically.
=venturectl activity list mine|overdue|today= reads the signed-in user's worklist.
The existing =activity TYPE ID= still reads a record's timeline.
Create and edit planned work with generic =create activity= and =update activity=;
setting =status=done= through generic writes is refused. See [[file:activities.org][activities]].
* Vendor bills

=venturectl bill approve ID [date=DATE]= approves a draft supplier bill.
=bill pay ID [amount=MONEY] [date=DATE] [method=METHOD]= pays the outstanding
amount or the supplied partial amount; excess cash remains vendor credit.
=bill void ID [date=DATE]= reverses an unpaid approved bill. These call the
same =VenturePayablesService= as the web and REST actions. Generic writes
setting a bill's financial status are refused.

=report payables PERIOD= reconstructs historical aging;
=report vendor_statement PERIOD vendor_id=ID= reads the supplier's dated
statement. Both accept =organization_id=, =currency= and =as_of=.
See [[file:payables.org][vendor payables]] for credits and cash-report projections.

=bill pay-bulk 1,2,3 adapter=transfer= pays selected approved bills through
the payables adapters. =close open|run|sign|complete|reopen|pack= is the
accountant close workspace. =capture ingest|convert|reject= files receipts
and supplier invoices. =accounting= lists the daily books next actions.
See [[file:close.org][close]], [[file:capture.org][capture]] and
[[file:accounting.org][accounting home]].

=venturectl cutover template SECTION= prints a cutover CSV template;
=venturectl cutover csv source=S cutoff=DATE [currency=C] SECTION=@FILE ...=
sends CSV files to preview a new cutover batch (=build_only=true= returns the
payload JSON instead). Batch actions are ordinary record actions:
=act accounting_cutover ID import|reconcile|rollback_preflight|activate|rollback=.
See [[file:cutover.org][accounting cutover]].

=venturectl tax-filing prepare|review|submit|acknowledge|amend= prepares a
jurisdiction return pack. =contractor-tax prepare|review|approve|export=
builds a 1099-NEC pack from paid bills. See [[file:tax-filing.org][tax
filing]] and [[file:contractor-tax.org][contractor 1099]].

=venturectl sales-tax export period=PERIOD [jurisdiction=CODE]
[organization_id=N] [as_of=DATE]= writes the =sales_tax_return= report as
the CSV a filer keeps: one quoted row per jurisdiction with gross, exempt
and taxable sales, tax collected, tax credited and net due. =report
sales_tax_return PERIOD= is the same figures through the generic report
surface. See [[file:sales-tax.org][sales tax by jurisdiction]].
* Banking actions

=venturectl bank ACTION ID [JSON|@FILE]= calls the banking service over REST.
=import= takes a bank account ID; =auto= and =reconcile= take a statement ID;
=match=, =unmatch=, =exclude= and =create= take a transaction ID.

* Market data, arbitrage and plugins

Five verb groups reach what is not a record: =accounts= reads the /accounts pages' answers (the operator's characters, inventory and ledger), =feeds= queues a market data source's sync and reads its schedule, =market= asks the price oracle and the Trading pages' questions, =arbitrage= scans for opportunities, records them as trades and runs the calculators, and =plugins= lists what the server loaded. Each is a thin client of a JSON route (=/api/v1/feeds=, =/api/v1/market=, =/api/v1/arbitrage=, =/api/v1/plugins=) or of a record action, asking exactly the question the matching page asks, so the terminal and the page cannot answer differently. The records themselves -- =data_source=, =venue=, =instrument=, =watchlist=, =alert_rule=, =arbitrage_trade=, =arbitrage_strategy= and the rest -- need no verb of their own: =list=, =create=, =update= and =act= cover them like any other type. What the verbs ask about is described in [[file:market-data.org][Market data]] (the series stores, feeds, the price oracle, alerts and the Trading pages), [[file:arbitrage.org][Arbitrage]] (trades and legs, the scan, presets and calculators) and [[file:plugins.org][Plugins]] (runtimes, exec plugins and what a manifest provides).

** Feeds

=feeds sync ID= queues a sync of the =data_source= and answers at once with ={"status": "queued", "data_source_id": ID}= (202): the server never waits on an outside host inside a request. =--wait= is the CLI waiting instead. It reads the source's newest run before queueing, then asks for the newest run once a second until one newer than that appears and prints it; after five minutes (=VENTURE_CLI_FEEDS_WAIT_SECONDS=) it gives up with exit 7 and names the =feeds runs= command that will show the run later -- the sync is still queued, only the waiting stopped. A run it waited for that *failed* is printed and exits 1 with the run's error; partial and deferred runs exit 0. =--wait= belongs to =feeds sync= and =feeds push= and is refused on =feeds runs=, =feeds due= and every other verb, because a flag that is quietly ignored teaches that it did something.

=feeds push ID FILE|-= sends a file, or standard input for =-=, as the body of =POST /api/v1/feeds/ID/push= under =Content-Type: application/x-ndjson=, unparsed: the server reads it as a =file_jsonl= source reads a file, so a malformed line is the run's failure, with its line number, not the command's. It answers ={"status": "queued", "push_id": ...}= (202). With =--wait= the server holds the request until the push's run is written -- at most two minutes, so the CLI raises its own socket timeout for this one request -- and the run is printed as =feeds sync --wait= prints one, and exits as it does: a failed run (a malformed line, with its line number) exits 1 with the run's error. When the server answers without the run -- it took longer than two minutes, or two other requests were already waiting on pushes -- the queued answer is printed (it carries the =push_id=) and the command exits 7, as =feeds sync --wait= does when it gives up; the push is still queued. A source whose provider is not =push=, that is switched off, or that already has four pushes not yet stored is refused with exit 4 (conflict) -- push again when those finish; a body past =feeds.max_push_mb= is refused by the server. =--wait= belongs to =feeds sync= and =feeds push=. See [[file:market-data.org::*The push provider][Market data: the push provider]].

=feeds runs ID= prints the source's =data_source_run= records newest first (status, trigger, units, rows, error and the rest of the run's counters), and =feeds due= every unit of every source in the organization with when the worker checks it next, soonest first; a unit that never runs on its own (a =manual= schedule) has a null =next_check= and sorts last. With the feeds module off (=feeds.enabled=, off by default) every =/api/v1/feeds= route is NOT_FOUND, so all three exit 3. Testing a source, purging its history and the Blizzard plugin's recipe import are record actions: =venturectl act data_source ID test unit=...=, =act data_source ID purge_history=, =act data_source ID import_recipes ...=.

** Which organization

The =feeds= and =market= verbs and =arbitrage scan=, =record= and =export= answer for the organization =organization_id=N= names; without it, for the caller's active organization, which for a token is always the default one -- so the parameter is how a second organization's market data is reached from the command line at all. The server judges it before reading anything: a member of the organization is answered, anybody else is told NOT_FOUND (exit 3), exactly what reading one of its records would say, and a value that is not a positive whole number is refused (exit 2, by the CLI before anything is sent). A source, rule, list or scan row of another organization than the one asked about is NOT_FOUND too, which is why a second organization's source asked about without the parameter reads like a missing one ("No such data source in organization 1").

Where a verb takes =name=value= options -- =market browse=, =deals=, =venues=, =instrument=, =alerts=, =quote= and the arbitrage scan verbs -- =organization_id= is one of them. Verbs with positional words take it as a trailing word after them, and refuse anything else there (exit 2): =feeds sync ID [--wait] organization_id=N=, =feeds push ID FILE [--wait] organization_id=N=, =feeds runs ID organization_id=N=, =feeds due organization_id=N=, =market promote SOURCE instrument|venue|account KEY organization_id=N=, =market watchlist [ID] organization_id=N=, =market alerts evaluate RULE_ID organization_id=N=. =arbitrage record name=... legs=...= passes it to the =record= action, whose own parameter it is. =arbitrage calc= and =registries= read no organization, and =arbitrage close=, =reopen=, =abandon= and =execute= act on a record that already belongs to one, so =organization_id== there is refused as an unknown action parameter (exit 2).

** Market

The =market= verbs are the Trading pages' JSON twins (=/api/v1/market/...=) asked under the pages' own query names (=source=, =group=, =category=); the report spellings =data_source_id=, =group_key= and =category_path= are accepted too, so an option that worked on =report market_deals= works here. Each option is typed before anything is sent: =page=two=, =stock=maybe= or =dir=sideways= is refused by name (exit 2), and so is a name the verb does not take (=limit=5=), because a page reads an unknown =dir= as ascending and a false =stock= as unset rather than refusing it. =browse= sorts only by the columns =venture_marketdata_browse_sorts()= lists (=min_price=, =quantity=, =market_value=, =region_median=, =pct_vs_region=, =sale_rate=, =sold_per_day=, =deal_price=, =listings=, =name=, =updated=, =venue=); anything else is refused by the server (exit 2). =market watchlists= is the same verb as =market watchlist=.

=market instrument SOURCE_ID KEY= takes the store's key, not an instrument record's id, and sends it as one path segment however many slashes it holds. =market quote= takes an instrument id (or =product=ID=) and passes =basis=, =venue= (a venue key, else a group), =venue_id=, =at=, =currency=, =prefer_currency=, =fallback= and =source= to the price oracle; it prints the oracle's answer as it is. =market promote= prints the record it made, found or restored.

=market alerts evaluate RULE_ID= *writes* the hits it finds, under the rule's cooldown and as a feed run would -- a webhook and the inbox fire -- and =--dry-run= (=?record=false=) only says what would fire. That is the opposite default from the record action =act alert_rule ID evaluate=, which only looks unless given =record=true=. Neither can be staged, and =--dry-run= is refused on every other =market= verb.

The answers draw as a table on a terminal (named columns, money with its currency, a blank -- never a zero -- for a figure that is not there, then the answer's notes, which =-q= drops), the rows as CSV with =-f csv=, and the whole answer -- notes, echoes of the question and all -- with =-f json= or =-f yaml=, so a script never loses what the table leaves out.

** Accounts

The =accounts= verbs are the /accounts pages' JSON twins (=/api/v1/accounts/...=), asked under the pages' own query names and typed before anything is sent, like =market='s:

#+begin_src sh
venturectl accounts                                   # the summary, then every account (accounts list)
venturectl accounts attention                         # where to log in next, each place with its reasons
venturectl accounts attention expiring_hours=4 mail_days=1
venturectl accounts attention login=ZAKMANN             # one login's places (tsmctl: its WTF account folder)
venturectl accounts list by_login=true                # grouped by login, then realm; the logins' table after
venturectl accounts list sort=gold dir=desc basis=market
venturectl accounts show 4 "Drgold-Thorium Brotherhood"     # listings, mail, holdings, ledger
venturectl accounts inventory place=bank min_value="500.00 GOLD" sort=value
venturectl accounts inventory dead=true dead_days=45  # nothing sold for 45 days
venturectl accounts pnl period=last_90_days group_by=week
venturectl accounts pnl group_by=instrument account="Drgold-Thorium Brotherhood"
venturectl accounts pnl group_by=login period=last_90_days
venturectl accounts inventory group_by=login          # what each login holds, after the items
venturectl accounts post 4 dry_run=true                # what the books would take, a day at a time
venturectl accounts post 4 until=2026-10-01           # post every day before 1 October
venturectl accounts record-flips 4 min_profit="5.0000 GOLD" limit=200
#+end_src

=list= and =attention= take =source=, =group= (a realm), =login= (a login's key), =by_login= (=true=: grouped by login, then realm), =basis= (=conservative=, =market=, =min=, =historical=, =region_market=, =region_sale_avg=), =expiring_hours=, =mail_days=, =stale_days=, =sort= and =dir=; =show SOURCE_ID KEY= takes the account's key in the store, sent as one path segment whatever it holds, and =basis=, =expiring_hours= and =ledger=; =inventory= takes =source=, =account= (or =account_key=), =login=, =group_by= (=login=), =place=, =category= (or =category_path=), =search=, =min_value= (with its currency), =dead= (=true=/=false=), =dead_days=, =basis=, =sort=, =dir=, =page= and =per_page=; =pnl= takes =source=, =period=, =group_by= (=login= among the groupings), =account=, =login=, =venue=, =instrument=, =label= (the source's own label, =Auction=) and =top=. Every verb takes =organization_id=N=. A table prints on a terminal; =-f json= prints the whole answer, notes and all. See [[file:market-data.org][Market data]], "The Accounts pages".

=accounts post SOURCE_ID= and =accounts record-flips SOURCE_ID= are the books' two type-level actions (=act external_posting 0 post_ledger= and =act arbitrage_trade 0 record_flips=) under friendlier names: the source becomes =data_source_id=, and each option is typed before it is sent -- =limit= and =organization_id= as whole numbers, =dry_run= as a boolean -- because the action framework refuses a string where it declared a number. =post= takes =from=, =until=, =account= (or =account_key=) and =dry_run=; =record-flips= takes =from=, =until=, =instrument=, =min_profit= (with its currency) =limit= and =dry_run=. Both honour =--stage=. The answer is the data source with the pass in its =result=: the table prints what the pass did and the days (or trades), =-f json= prints the pass whole. A source books one way (its =books= setting: =daily= for =post=, =trades= for =record-flips=); the other is refused (exit 1, CONFIG), a dry run is answered in any mode. See [[file:market-data.org][Market data]], "The external ledger in the books", and [[file:arbitrage.org][Arbitrage]], "Flips from an external ledger".

** Arbitrage

=arbitrage scan= takes the strategy as its first word (=spread= when there is none) and the scan's options after it (see [[file:arbitrage.org][Arbitrage]], "The question"). Money names its currency (="10.00 GOLD"=; a bare bound is refused by the server rather than read as dollars), percents are plain numbers ("15" is 15%), and the options that are whole numbers -- =preset_id=, =data_source_id=, =recipe_id=, =units=, =buy_sources=, =max_age_hours=, =top=, =organization_id= -- are typed by the CLI. Every other option travels as text for the server to read, and it refuses by name one that neither the scan nor the chosen strategy declares -- the CLI keeps no list of its own, which is how a plugin strategy's own options get through. Options a scan route would quietly ignore or drop are refused instead (exit 2): =venture_id=, =as_of=, =key=, =format= and =calc=. =cover= and =back_lay= leave out an event whose =commence_time= has passed, and say so in a note.

The table numbers its rows, and =arbitrage record N= with the same options records row /N/: the CLI asks the same question, takes that row's key and what narrows the plan to it, and posts them to =/api/v1/arbitrage/record=, which re-runs the scan and performs the =record= action with the plan -- a row the prices have moved away is refused (exit 3, "That opportunity is no longer there"), never recorded from what the terminal showed, and a row past the end is exit 3 too. Pass exactly the options the scan had, or row /N/ is a different row. =arbitrage record KEY= does the same with a key from a JSON scan.

=arbitrage record name=... legs=...=, =close=, =reopen=, =abandon= and =execute= are the =act= verb on =arbitrage_trade= and =arbitrage_leg= under a friendlier name: every argument is typed from the action's own schema, an unknown parameter is refused (exit 2), and =legs=@FILE= (or =expected=@FILE=) reads the value from a file. All five honour =--stage=, as does recording a scan row (=POST /api/v1/arbitrage/record?stage=1=); planning a staged row still promotes the venues and instruments its legs name, because legs must name records, but the trade and its legs wait for approval. =--stage= is refused on =scan=, =calc=, =export= and =registries=, which write nothing.

=arbitrage calc= runs the calculators on the server (=/api/v1/arbitrage/calc=): =surebet= takes every outcome's odds as bare words (or =odds="+150 -120"=; a bare negative American price would read as an option), =back-lay= (or =back_lay=) the back and lay odds, =flip= the buy and sell prices. =--stake= (or =stake==, not both) is the total or back stake; a flip takes none, its capital being the buy price. Unlike a scan's bounds, a calculator reads an amount that names no currency -- =--stake 100=, =fixed==, =transfer==, a flip's prices -- in the install's default currency, so name it. =format= picks the odds format (=auto=, =decimal=, =american=, =fractional=). Stakes are rounded to the currency's minor unit and the answer keeps both readings: a surebet's =payout= is the least of the rounded payouts -- what any result is sure to pay -- and =profit= that less the stakes, while =payout_ideal= and =profit_ideal= are the unrounded figures; a back-lay's =worst= rounds against you and =ideal= does not. Quote the sure figures as what a person gets.

=arbitrage export FORMAT= writes what a registered export format (=csv=, =shopping_list=, or a plugin's, such as the Blizzard plugin's =tsm=) makes of the scan, raw, to stdout or to =-o FILE=; an unknown format is NOT_FOUND (exit 3). =arbitrage registries= lists the strategies, fee models, export formats and scan option names this server has. =--stake= belongs to =arbitrage calc= and =-o= to =arbitrage export= alone; both are refused on every other verb.

** Plugins

=venturectl plugins= (or =plugins list=) prints every plugin the server loaded -- its name, kind, runtime (=native=, =crispy=, =exec= or =declarative=) and what its manifest provides (=data_source_provider=, =automation_handler=). It is owner only, because the answer names paths on the server. "No plugins are loaded." is an answer, not an error. An exec plugin loads only when the operator sets =plugins.allow_exec=; nothing from the command line turns it on. Strategies, fee models and export formats a plugin registers appear in =arbitrage registries=, not here.

** Reports

The market and arbitrage reports run through =report= like every other, with their options after the period: =accounts= (=data_source_id=, =group_key=, =login=, =group_by= (=login=), =basis=, =expiring_hours=, =mail_days=, =stale_days=, =sort=), =account_holdings= (=data_source_id=, =account_key=, =login=, =group_by= (=login=), =place=, =category_path=, =basis=, =min_value=, =dead_days=, =sort=, =top=), =external_pnl= (=data_source_id=, =group_by=, =account_key=, =login=, =venue=, =instrument=, =source=; the period is its window), =market_deals= (=data_source_id=, =venue=, =group_key=, =category_path=, =min_value=, =max_pct=, =top=), =venue_index= (=data_source_id=, =group_key=), =watchlist= (=watchlist_id=), =arbitrage_performance= (=group_by=, =strategy=, =venture_id=), =arbitrage_scan= (the scan's options, =strategy= included) and =craft_arbitrage= (=recipe_id=, =units=, =data_source_id=, =buy_venues=, =sell_venues=, =group_key=, =sell_basis=, =max_age_hours=); all of them take =organization_id=. The market reports and the scans read the stores as they are now, so the period does not narrow them. =pnl=, =ventures= and =monthly= count the arbitrage trades a period finished (see [[file:arbitrage.org][Arbitrage]], "In the profit and loss").

#+begin_src sh
venturectl report market_deals group_key=eu min_value="10.00 GOLD" max_pct=80 top=20
venturectl report arbitrage_scan strategy=spread organization_id=2 min_roi=15
venturectl report arbitrage_performance this_month group_by=venue_pair strategy=spread
#+end_src
