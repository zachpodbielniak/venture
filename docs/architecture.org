* Architecture

** The central idea

There is no schema file, no route table, no serialiser and no form template. All of it is derived from GObject property metadata.

A record type declares its fields:

#+begin_src C
static const VentureFieldDecl venture_sale_fields[] = {
	VENTURE_FIELD_REF("venture-id", "Venture", NULL, "venture",
	                  VENTURE_COLUMN_FLAG_NOT_NULL),
	VENTURE_FIELD_MONEY("gross", "Gross", "Item total before anything else"),
	VENTURE_FIELD("occurred-at", "Sold", NULL, VENTURE_FIELD_KIND_DATETIME,
	              VENTURE_COLUMN_FLAG_INDEXED)
};

VENTURE_DEFINE_ENTITY(VentureSale, venture_sale, venture_sale_fields)
#+end_src

From that declaration alone, VENTURE produces:

| Consumer          | What it derives                                        |
|-------------------+--------------------------------------------------------|
| =src/db/schema=   | =CREATE TABLE=, column types, constraints, indexes      |
| =src/db/query=    | the filterable field vocabulary                         |
| =src/web=         | REST CRUD at =/api/v1/sale=, and a list view            |
| =VentureSerializable= | JSON and YAML that round-trip                       |
| =src/ai=          | the tool schema the model is shown                      |
| =VentureEntity=   | validation, the audit diff, the display name, search    |
| =venturectl=      | =list=, =get=, =create=, =update=, =delete= subcommands |

A plugin that registers a record type gets all of it. That is the whole extensibility story, and it is why the core has no list of record types anywhere except the registry.

** Modules

Every record type, report, page and service belongs to a module, and a module is a switch. The module registry (=src/model/venture-module.c=) holds a static table written bottom-up -- a module may only require what precedes it, which is what rules a cycle out by construction -- and resolves every module's state once from the configuration: the =modules= section, then the legacy =*.enabled= switches, then requirements. A module whose requirement is off is refused at validation, before the database is opened.

What a disabled module loses is decided there and applied to the registries the rest of the system already reads. Its types are hidden from the entity registry, so REST, the schema, the forms, the AI's tools, =venturectl= and =venturectl mcp= stop offering them without any of them knowing what a module is. Its reports are hidden from the report registry. Its pages and services ask =venture_context_module_enabled()= first. Nothing is deleted. See [[file:modules.org][Modules]].

** Links

=record_link= joins any two records by type and id with a kind that has an inverse, stored once and read from either end. The checks the schema cannot express run as a save validator inside =venture_database_save()=, which every writer goes through. See [[file:data-model.org][the data model]].

** Dashboards

A dashboard is a page of widgets and a widget is a declarative question — a count, a list, a report's figure — answered by a kind from a process-wide catalogue (=src/core/venture-dashboard.c=). Each kind produces JSON and HTML from one pass, so the browser, the API and the assistant see one answer. Both records are ordinary types; a plugin adds a kind the way it adds a report. See [[file:dashboards.org][Dashboards]].

** Layers

#+begin_src
  venture (server)            venturectl (client)
        |                            |
        +--- web/ ---+               +--- HTTP ---+
        |            |                            |
     ai/  report/  automation/  plugin/           |
        \     |         |          /              |
         +----+----+----+---------+               |
                   |                              |
                 db/  <- orm-glib -> SQLite/Postgres
                   |                              |
              model/ + boxed/ + interfaces/  <----+
                   |
              config/ + util/

=libventure-core.a= is everything from =model/= down. =libventure.a= adds the rest. =venturectl= links only the former, which is why =make venturectl= works on a machine with no libpq, no sqlite headers and no readline.

** Why a change can be proposed rather than made

The AI's tools reach the same repository the web UI and the CLI use — not a parallel, laxer path. Validation, optimistic concurrency, soft deletion and auditing all apply identically.

What differs is authority. Under the default =confirm_writes= policy, a mutating tool call does not mutate. It stages a =VentureConfirmation= holding the record with the change already applied in memory, plus a field-by-field diff, and returns a tool result telling the model plainly that nothing has happened yet. Approval applies the staged object — so approving cannot produce a different outcome from the diff that was shown.

Deletion stages even under =autonomous=. Every other AI action produces a value a person can eyeball afterwards; removing a record is the one where noticing late is materially worse.

*** The queue is not the AI's

=VentureConfirmationStore= hangs off =VentureContext=, not off =VentureAiService=, and a REST write sent with =?stage=1= mints into the same one. That is deliberate rather than incidental: an outside agent holding an API token proposes changes for the same reason the assistant does, and somebody answering "an agent wants to record a $12 expense" should have one place to look rather than one per surface. An install with AI switched off still stages.

It also means approval has exactly one implementation. Two would be two behaviours, and the behaviour in question is what gets written to the books.

Approval carries the optimistic-concurrency check that everything else here carries: the staged record holds the version it was read at, so a card approved after somebody edited the row fails with a conflict naming what moved rather than quietly restoring every field to what the agent proposed an hour ago.

** Why money is three columns

A =VentureMoney= property becomes =<name>_amount=, =<name>_currency= and =<name>_exponent=. A single text column would be tidier and would make =SELECT SUM(...)= impossible, which for a system whose purpose is totalling money is the wrong trade every time.

Reports still aggregate in C wherever currency correctness matters, because summing across currencies without a rate would produce a confidently wrong number. =venture_database_sum_money()= groups by currency and reports the majority one rather than folding them together.

** Why the query builder exists

Three of its four callers cannot be trusted with SQL text: a REST client sends query parameters, the CLI passes flags through, and the AI writes filters from a natural-language request.

So none of them contribute SQL. A filter names a field, an operator from a closed enumeration, and values. Field names are resolved against the record type's real properties and then quoted; operators map to fixed fragments; values are always bound parameters. There is no path by which caller input reaches the statement as text, which makes injection structurally impossible rather than merely unlikely.

** Concurrency

Every write, transaction and main-thread read goes through one connection behind a recursive mutex. SQLite admits one writer at a time regardless, and one writer connection leaves no interleaving to get wrong.

Record reads (=GET /api/v1/:type= and =GET /api/v1/:type/:id=) are the exception: they are answered on read worker threads (=server.read_workers=, 4 by default; 0 answers everything on the main thread), so an application using VENTURE as its backend gets several reads at once instead of one at a time.

The design avoids proving that every line a read touches is thread-safe. VENTURE's registries, configuration, automation engine and signal handlers were written for one thread, and a wrong guess is a crash under load and nowhere else. Instead the workers are fenced:

- *The gate* (=src/core/venture-parallel.c=) is a reader-writer lock the main thread holds at all times except while its outermost main loop sleeps in =poll()=. A worker holds it shared for the part of a job that reads. Jobs therefore run side by side with each other and never beside main-thread code: a write, a timer, a signal handler, or a handler waiting in a nested main loop (which does not open the gate). The lock prefers the main thread, so a stream of reads cannot starve writes: once the main thread wants the gate back, no new job enters until it is idle again.
- *Per-thread reader state.* The access policy's current reader, organization pin and list caches belong to the thread (=venture_access_policy_bind_thread()=). The main thread authenticates the request, checks the roles and builds the query, then snapshots its reader (=venture_access_policy_snapshot()=); the worker judges every row as exactly that reader.
- *Leased read connections.* =venture_database_enable_parallel_reads()= opens an =OrmConnectionPool= (orm-glib) of read-only connections (=PRAGMA query_only= on SQLite, a =READ ONLY= session on PostgreSQL). A worker leases one for the request; its reads bypass the primary connection and its lock and see committed data only. A write slipping into a worker is refused by the database itself.
- *Answers built on the main thread.* The handler returns an htmx-glib deferred response; the server pauses the message and goes on serving. The worker reads under the gate, then turns the records into JSON outside it (that touches only the records and fixed class metadata), and the response is built and written on the main thread. Middleware that reads the response afterwards (metrics) registers a completion hook.

The two paths share one body (=venture_web_api_list_fetch()= / =_render()=, =venture_web_api_get_answer()=), and =tests/test-parallel.c= holds a worker's answer to the main thread's, byte for byte, along with the gate's guarantees, isolation between concurrent readers of different businesses, reads beside writes and the read-only connections.

Hosted installs keep every request on the main thread (workspace admission and support scopes wrap the handler), and so does an in-memory SQLite database (each of its connections is a different, empty database).

What it buys depends on how long a read takes against the main thread's fixed share of each request (parsing, authentication, the query, writing the answer). Measured on a loaded 24-thread machine, 16 clients, release build: a fifty-row page of companies went from 385 to about 625 requests a second with four workers, and a two-hundred-row page from 115 to 215. More workers than four bought nothing there: the main thread's share is the limit.

Lost updates are prevented at the record level instead: every entity carries a version, an update's =WHERE= clause names the version the caller last saw, and a mismatch affects no rows and raises =VENTURE_ERROR_CONFLICT=.

** Waiting on Stripe

stripe-glib's client is synchronous: it calls its transport on the caller's stack, and between retries it sleeps there too. VENTURE's database, registries and signal handlers belong to the main thread. A Stripe call made from a request handler used to be the whole server's wait: thirty seconds for a provider that did not answer, or as long as a 429's =Retry-After= asked, with every other request held behind it.

*** The pieces

- *Fibers* (=src/core/venture-fiber.c=, private API in =venture-fiber-private.h=). A fiber is work on a stack of its own -- 8 MiB, with a 64 KiB guard below it that is never mapped readable -- still on the main thread. It runs until it yields; whoever it waits on wakes it from the main loop. One thread runs one stack at a time, so nothing ever runs beside main-thread code. The thread fibers belong to is fixed once, by =venture_fiber_init()=, which =venture_web_server_new()= calls; =venture_fiber_current()= is asked from any thread and answers =NULL= anywhere but there.
- *Deferred routes* (=src/web/venture-web-later.inc=). A route that may wait on Stripe is registered with =VENTURE_WEB_LATER_ROUTE()=. It answers with an htmx-glib deferred response, makes its fiber at once (a stack that cannot be mapped is a =503= with =Retry-After: 5=, not an abort) and starts it from a default-priority source a moment later, outside the listener's dispatch.
- *The transport* (=src/stripe/venture-stripe-transport.c=). Every Stripe client VENTURE makes comes from =venture_stripe_client_new()=: stripe-glib's own retries off (=retry_count: 0=) and =venture_stripe_transport_new()= as its transport. Called from a fiber with no transaction open, the transport sends on a pooled thread (at most eight at once) and yields until the answer is in. It also retries a 429 or a 5xx itself -- at most twice, from 200 ms doubling with jitter, never sooner than =Retry-After=, never past the request's deadline -- announcing each retry as stripe-glib did (=stripe.request.retried=), and a fiber waits out that pause yielded on a timeout source. To see a status at all it sends through its own copy of stripe-glib's soup transport (=venture-stripe-http.inc=), kept only until stripe-glib exports getters on =StripeResponse= (see [[file:stripe.org][Provider operation deadlines]]).

*** Who waits how

| Caller | What a Stripe call does |
|--------+-------------------------|
| A fiber, no transaction open | Sends on a pooled thread and yields; retry pauses yield on a timeout source |
| A fiber with a transaction open | Sends on its own stack and blocks, as before; retry pauses sleep |
| Anything else: a plain route, a timer, a sweep, another thread | Sends on its own stack and blocks, exactly as before; retry pauses sleep |

There is no nested main loop anywhere in this. A non-fiber caller that spun the default context while it waited would dispatch the next HTTP request while its own handler was still on the stack -- the re-entrancy VENTURE has already rejected (=src/automation/venture-automation.c=). Only fibers yield.

A wake does not resume a fiber inside somebody else's transaction. Some nested default-context loops exist elsewhere (the bank feed sync, the webhook test, the feeds service, the federation client) and may dispatch the source that wakes a fiber. If a transaction is open when the wake runs, it re-arms itself ten milliseconds later instead; the fiber resumes once the transaction has ended.

*** What runs as a fiber

Lightsite setup, change-card, publish, first-charge and money-back; invoice checkout (API and form); =POST /pay/:token= and the Pay now button =GET /pay/:token/checkout= (the page and the invoice email); the Stripe settings operations (configure, the statement name, the key test); Connect status and start.

Still synchronous, blocking the main loop for as long as Stripe takes: the record action route =POST /api/v1/:type/:id/actions/:action= (every Stripe action, =checkout= and =refund= among them), the customer portal's pay button, paid forms, the Stripe timers (collection, reconciliation, prepaid installments) and the Stripe webhook routes. Moving one is registering it with =VENTURE_WEB_LATER_ROUTE()= and following the rules below.

*** What a fiber carries across a yield

The main thread keeps request state in a few shared places. A fiber's swap function (=venture_web_later_swap()=) exchanges each with the fiber's own copy on every way in and every way out, so a fiber that yields leaves the loop as it found it and finds its own as it left it:

- the access policy's per-thread reader state: actor, organization pin, list caches (=venture_access_policy_exchange()=);
- the tenant service's request scope and maintenance depth (=venture_tenant_service_exchange_request()=).

It runs under the reader the request pipeline authenticated (a snapshot, the same thing the read workers judge by), a plain tenant request scope (none of these routes admits a support capability), and the pipeline's workspace admission until it is answered. Before its answer escapes, the hosted lifecycle is checked again and a browser error becomes a page, as the pipeline does for a synchronous route. =/stripe/isolation= holds an anonymous read of a signed-in route refused, and a second business's member to its own records, while one user's checkout is suspended, and that checkout's writes after the wait still carry its own audit actor.

*** One customer's Checkouts, one at a time

Fibers let a second request start while the first waits on Stripe, so two clicks of one Pay now link (or a mail scanner opening it first), or two of a new customer's invoices paid at once, would both be part-way through: the second reusing the first one's idempotency key while it is still in flight, which Stripe refuses, or linking the customer the first is still creating. The Stripe service takes a /hold/ (=venture_fiber_hold()=) on the paying party -- the invoice's company or contact -- around creating a Checkout, reading a Pay now link and creating a Stripe customer. A fiber that asks for a held key yields until the holder lets go, then takes it, in the order they asked; the second click then finds the first one's open session and answers its URL, and the second invoice finds the customer already linked. A plain stack takes a free key, and blocks while it holds it, as it always has; it never waits for a key a yielded fiber holds (that would take a nested loop) and goes on unguarded instead. No hold is taken with a transaction open, and a fiber handed one is resumed only outside a transaction, as a Stripe answer's wake is. Tests: =/stripe/payment-link/race-invoice=, =/stripe/payment-link/race-customer= (the fake Stripe also refuses a key still in flight, as Stripe does), =/fiber/hold/*=. A route whose placeholder the pipeline replaced with a refusal never runs (=/stripe/later-refused=).

*** Rules for fiber authors

Anything else of the main thread's is shared with whatever the loop runs while the fiber is suspended. So a fiber must never yield:

- inside a signal emission -- the emission's state stays on the fiber's stack while other code emits on the same object;
- while holding a mutex -- the main thread would deadlock on it the next time it takes it, with the holder suspended;
- in the middle of iterating a statement, a query result or a hash table -- whatever the loop runs meanwhile may change the database or the table underneath;
- with a transaction open -- the transport refuses to, and blocks instead, but other waits must check for themselves;
- from inside a main loop it runs itself -- =venture_fiber_current()= answers =NULL= there, and the transport then blocks.

New per-request state on the main thread needs a place in the swap function, or it leaks from one request into another across a yield.

*** Deadlines, shutdown and failure

Each Stripe call's deadline is stripe-glib's =request_timeout= (30 seconds; VENTURE does not change it). It bounds every attempt and every retry pause: a pause that cannot fit ends the call with a timeout, which keeps the operation's idempotency key for a retry. A failure is the caller's alone. A client that disconnects during the wait gets nothing written; the fiber finishes anyway, so what Stripe did is recorded (=/stripe/disconnect=).

A stop (=SIGINT= or =SIGTERM=) does not quit the loop while a fiber is suspended: the server keeps running until none is left or 35 seconds have passed, then stops as before. A second signal stops at once. =venture_fiber_count()= is what it waits on.

Under AddressSanitizer (gcc defines =__SANITIZE_ADDRESS__= for =-fsanitize=address=) every stack switch is announced with =__sanitizer_start_switch_fiber()= / =__sanitizer_finish_switch_fiber()=. Nothing is architecture-specific: =ucontext= is glibc's on x86_64 and aarch64 alike, and both grow their stacks down, which is where the guard sits.

*** Tests

The fake provider in =tests/test-stripe.c= holds a call until the test releases it, so the tests assert what was answered while a call was held, never how long anything took. =/stripe/slow=, =/stripe/payment-link/slow*=, =/stripe/binding-settings-slow=, =/stripe/connect/slow= and =/stripe/hosted-slow-provider*= answer a health check while each route is held; =/stripe/hosted-slow-provider-order= answers the first of two held pages while the second is still held; =/stripe/slow-reads= keeps the read workers answering during one. =/stripe/fiber/*= cover a 429 whose pause is yielded (=retry-after=), a pause that cannot fit (=retry-budget=), the real request deadline against a stub that never answers (=deadline=), a transaction that keeps a fiber blocking (=transaction-blocks=), a wake inside another transaction (=wake-waits-for-transaction=) and the fiber count. =/stripe/hosted-concurrent= sends publication and the first charge, and later two money-back requests, for one business at once, and Stripe is charged once and refunds once. =tests/test-venture-fiber.c= covers the fiber primitives.

** Dependencies

All are git submodules under =deps/= and are treated as the canonical copies. Several vendor each other; the build deliberately does not redirect their sub-dependency paths, because =ar t= confirms none of their archives embeds another's objects. Each archive carries unresolved references that our single canonical copy satisfies at final link time.

** Fixes made upstream

=orm_value_get_boolean()= asserted that the stored value was =ORM_VALUE_BOOLEAN=. SQLite has no boolean storage class, so every boolean column read back as an integer and tripped the assertion — no boolean field could be loaded on the default backend. It now accepts an integer, and PostgreSQL's =t=/=f= text form as well. The fix is in =deps/orm-glib=.
