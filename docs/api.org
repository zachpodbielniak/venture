* REST API

Base path =/api/v1=. Everything is JSON. The API is generated from the record
registry, so a plugin's record type is a first-class resource the moment it
registers — there is no routing to add.

* Authentication

Either a bearer token or a browser session cookie. In a hosted workspace that
trusts an identity provider (=hosted.identity_issuer=), that provider's access
token is also a bearer: it acts as the user its subject is linked to, like
their own session. See [[file:lightsite-accounts.org][Lightsite accounts]], "The owner's own sign-in".

#+begin_src sh
curl -H "Authorization: Bearer $VENTURE_TOKEN" localhost:8747/api/v1/sale
#+end_src

Mint a token in the browser at *Your account -> API tokens*
(=/account/tokens=), which is the easiest route for an administrator. The
page lists every token, mints a new one with an optional expiry, and revokes
any of them, so it is admin-only (in a hosted workspace, a tenant
administrator signed in with a session).

Or mint one over HTTP with =POST /api/v1/tokens=. Either way the plaintext is
shown exactly once; only its hash is stored. Who may call it:

- *Any signed-in user holding a browser session*, whatever their role, mints
  a token for themselves. The token belongs to them (its =user_id=), carries
  their own global role and a snapshot of their active organization
  memberships at that moment, so it can never do more than the session that
  minted it. This is how a hosted site owner -- a global editor with a tenant
  =member= row and an organization owner/admin membership -- gets the bearer
  token Lightsite uses for =GET /api/v1/account-authority=.
  The token is filed under the workspace's default organization when the
  caller belongs to it, otherwise under the first organization they are a
  member of, so the owner of a business outside the default organization can
  mint one; where it is filed grants nothing.
  Such a token always expires: the body's optional =expires_in_days= (a whole
  number) defaults to 30 and must be 1 to 90; anything else, including a
  string, a fraction or =null=, is refused with 422. A hosted tenant
  administrator is a global editor, so the same limit applies. Once expired
  the token is refused (401) everywhere, =account-authority= included; mint a
  new one from a session.
- *A global owner or admin* mints a token that never expires unless the body
  gives =expires_in_days=, which must then be 1 to 3650.
- *A bearer token* may mint another only if it carries the global admin role
  or higher. Any other token is refused with 403: a token minting its own
  successor would outlive its revocation or expiry.
- *A global owner or admin, for another account*: give =user_id= (a whole
  number) or =username= (not both) and the token is that account's. It is
  owned by them, carries *their* global role and a snapshot of *their*
  memberships, so it reaches exactly the organizations they belong to. Only
  the expiry follows the person minting: an administrator may still omit
  =expires_in_days= for one that never expires, which is what lets an agent's
  account confined to one business keep a credential without being re-minted
  every 90 days. With no =name= it is called =api token for USERNAME=, and its
  =description= records who minted it for whom. Refused: 403 below admin
  (before the account is looked up, so the answer says nothing about which
  names exist) or for an account whose role outranks the caller's (an admin
  never gets an owner's credential); 404 for an unknown or deleted account;
  422 for a deactivated one, a =user_id= that is not a positive whole number,
  an empty =username=, or both at once. Naming yourself is your own token.
  The answer adds =user_id= and =role= beside =id= and =token=, so a caller
  can see it landed on the account it meant.

Hosted host pinning, workspace lifecycle (a read-only or suspended workspace
refuses) and the second-factor requirement apply here as on any other route.
There is no API route for a member to list or revoke tokens; an administrator
revokes at =/account/tokens=, and deactivating a user rejects all of theirs.

There is no scope parameter: a token may do less only by belonging to an
account that may do less. Make that account (a global =editor= or =viewer=
with memberships in only the organizations it should reach) and either sign
in as it and mint there, or, as an administrator, mint for it with
=user_id= or =username=:

#+begin_src sh
curl -s -H "Authorization: Bearer $ADMIN_TOKEN" -H 'Content-Type: application/json' \
    -d '{"name":"books-agent","username":"books-bot","expires_in_days":365}' \
    "$VENTURE_SERVER/api/v1/tokens"
# {"id": 9, "token": "vk_...", "user_id": 12, "role": "editor", "note": "..."}
venturectl token mint name=books-agent user=books-bot expires_in_days=365
#+end_src

A membership granted after minting does not widen an existing token; mint a
new one.

=venturectl mcp= serves this API to an outside AI agent as an MCP server,
taking its token from =VENTURE_TOKEN= and generating its tool surface from
=/api/v1/schema= so a plugin's record type is offered without any change.
See [[file:mcp.org][venturectl mcp]]. The server answers the same tools itself at =POST /mcp= for a remote agent holding a token in an =Authorization: Bearer= header; see [[file:mcp.org::*Remote MCP over HTTPS: POST /mcp][Remote MCP over HTTPS]].

** Who am I

=GET /api/v1/whoami= (since 0.10.0) answers, for the credential presented,
everything a client needs to recognise its own work -- above all a client
holding one token per agent, which must tell its agent's change apart from
another's:

- =actor= -- the string every audit row, activity line, comment and webhook
  body records for it: =API token #N= for a token, the username for a
  session. It never changes, and it is what to match on. A person reading
  the history is shown the owner beside it (=erin (API token #12)=), and
  the JSON a person's tools read carries the owner in a field of its own
  (=actor_username=, a confirmation's =origin.username=); see [[*Whose token it was][Whose token it was]].
- =role= -- the global role in force (a token is held to its user's
  current role when that is lower).
- =token_id= and =expires_at= (=null= for never) for a token; =0= for a
  session.
- =user= -- =id= and =username=, or =null= for a token with no user.
- =memberships= -- the organizations this credential reaches, each
  =organization_id=, =organization= (its name), =role= (the user's current
  membership role) and, for a token, =minted_role= (the role in the
  snapshot it was minted with). A token reaches an organization only where
  both exist and both allow the action, so a membership granted after the
  token was minted is not listed: mint a new token to reach it.

Any authenticated caller may ask (viewer and up); anonymous is 401. Nothing
here is more than the caller could learn by acting.

#+begin_src sh
curl -s -H "Authorization: Bearer $VENTURE_TOKEN" "$VENTURE_SERVER/api/v1/whoami"
# {"actor":"API token #12","role":"editor","token_id":12,
#  "expires_at":"2027-01-15T10:00:00Z","user":{"id":7,"username":"scout"},
#  "memberships":[{"organization_id":1,"organization":"Acme","role":"owner",
#                  "minted_role":"owner"}]}
#+end_src

** Retrying a write: Idempotency-Key

A client whose =POST= timed out cannot tell whether the server acted. Send an =Idempotency-Key= header (1 to 255 ASCII characters of your choosing, one per intended write) on =POST /api/v1/:type=, =POST /api/v1/links= or =POST /api/v1/tickets/:id/worklog= (since 0.10.0; the =idempotency= feature), and retry with the same key:

- *The same key and the same request* -- method, path with its query, and the exact body bytes -- answers what the first one did, status and body, with =Idempotent-Replayed: true=, and writes nothing again.
- *The same key with a different request* is refused with 422: the key was reused, and neither answer would be right. Use a new key for a new write.
- *Only a success is kept* (any 2xx, a staged write's 202 included). A refused request is not, so a client that fixes it may send the same key again.
- *A key is the caller's own*: a token's keys, or a session user's, never meet another caller's.
- *Kept 24 hours, in this server process*, at most 10,000 at a time, oldest dropped first -- a restart forgets them. A client that must be safe across one dedupes on a field it owns as well, such as =ticket.external_ref= ([[file:tickets.org][Tickets]]), which refuses a second ticket with the same reference (409).
- Without the header nothing changes.

#+begin_src sh
curl -s -X POST -H "Authorization: Bearer $VENTURE_TOKEN" -H "Content-Type: application/json" \
	-H "Idempotency-Key: clawtilla-task-01m0k6-create" \
	-d '{"title":"Fix the header"}' "$VENTURE_SERVER/api/v1/ticket"
#+end_src

** Features

=GET /api/v1/health= lists =features=: what this build can do that a client
may need to know before relying on it, by name (=venture_build_features()=).
A name is added in the release that adds the ability and never removed; a
client looks for the name it needs and, on a build that does not list it,
falls back rather than guesses.

instead of making it. See [[*Staging a write][Staging a write]].

Both singular and plural type names work, so =/api/v1/sale= and =/api/v1/sales=
are the same resource. A client that presents record types to somebody should
offer one of the two spellings, not both: they are one resource, and showing
two invites a duplicate.

** Modules

=/api/v1/modules= lists every module in dependency order: name, label, description, what it requires and what requires it, the record types and reports it owns, whether it is locked, and — when it is off — why, in the words of the setting that turned it off. A type whose module is off is absent from =/api/v1/schema= and its generic routes answer 404 naming the module; a module's own routes do the same. See [[file:modules.org][Modules]].

** Links

=GET /api/v1/links/:type/:id= describes every link touching a record, read from it: the link's id, the kind from here, the other end's type, id and current label, whether the other end still exists, and the note. =POST /api/v1/links= takes ={"source_type","source_id","kind","target_type","target_id","note"}= and is the same as =POST /api/v1/record_link=, =?stage=1= included. A link is refused when either end is missing, when the ends are the same record, or when the pair is already linked in either direction — at the save, so an approved staged link is held to the same rules.

** The factory

=GET /api/v1/factory= is the loop at a glance: open milestones with their progress, the newest releases, the latest builds, each environment with the release it is running, and the incidents still open — the five questions the Factory page asks, as one object. =?organization_id=N= scopes it.

=POST /api/v1/releases/:id/changelog= drafts the release's changelog from the tickets marked as fixed in it and saves it; the body may carry ={"replace": true}= to overwrite a changelog somebody wrote, and the answer's =changed= says whether anything was; when it is false, =reason= says why (the changelog somebody wrote was kept). =POST /api/v1/releases/:id/publish= cuts the release on the forge — the tag from the record or =v= plus the version, the changelog as the body, ={"prerelease": true}= to mark it so — and answers with the release carrying the forge's id and page. Both need the editor role and the factory module; publish also needs the forge module and a repository on the release. Neither can be staged: a changelog is an ordinary field an agent can also set through =PATCH /api/v1/release/:id?stage=1=, and a publish creates a tag on another system.

The rest of what the factory works out, all needing the factory module:

|--------+-----------------------------------------+--------+-------------------------------------------------------------|
| =GET=  | =/api/v1/factory/actions=               | viewer | what needs somebody, most pressing first; =?organization_id=N= scopes it |
| =GET=  | =/api/v1/releases/:id/readiness=        | viewer | can it go out: checks that pass, warn or fail, =ready= and a =score= |
| =GET=  | =/api/v1/milestones/:id/forecast=       | viewer | when it lands at the pace it is going                       |
| =POST= | =/api/v1/releases/:id/deploy=           | editor | ={"environment_id": N, "notes": "..."}=; records the release going live, answers 201 with the deployment |
| =POST= | =/api/v1/environments/:id/rollback=     | editor | ={"reason": "..."}=; marks the current deployment rolled back and records the release before it, answers 201 with the new deployment; 409 when there is nothing to go back to |
| =POST= | =/api/v1/builds/:id/ticket=             | editor | opens the bug for a failed build, answers 201 with the ticket; 409 when the build is not failed or already has one |
| =GET=  | =/api/v1/factory/briefing=              | editor | ={"briefing": "..."}=: the status and the actions as prose, from the assistant |
| =POST= | =/api/v1/releases/:id/notes=            | editor | ={"audience": "..."}= optional; ={"notes": "..."}=, drafted by the assistant, nothing written |

The four from the assistant need the =ai= module and a configured provider, and answer with the reason when there is none. An =organization_id= that is present and unusable is a 400 rather than every organization.

Everything else about the factory is the generic routes: =/api/v1/milestone=, =release=, =build=, =environment=, =deployment=, =incident=, with =?stage=1= on every write. See [[file:factory.org][The software factory]].

** Dashboards

A widget's place on the grid is four fields, =grid_col=, =grid_row=, =grid_width= and =grid_height=, zero meaning "wherever fits"; the checked way to move one is the editor's =POST /dashboards/:slug/widgets/:id/place=, which refuses a taken cell with 409. See [[file:dashboards.org][Dashboards]].

=GET /api/v1/dashboards/:slug= returns a dashboard with every widget evaluated: each widget's settings, its resolved title, its link, an =error= when it could not be answered, and =data= in a shape its kind decides. =?data=0= lists the widgets without evaluating them; =?organization_id=N= narrows every widget to that entity and authorized descendants; membership is still required for each organization. A personal dashboard belonging to somebody else answers 404. The generic routes =/api/v1/dashboard= and =/api/v1/dashboard_widget= work like any other type's, and a widget written through them is held to the same checks as one made in the editor. See [[file:dashboards.org][Dashboards]].

** Queries: POST /api/v1/query

Runs one [[file:lql.org][LQL]] query -- =fetch=, =filter=, =fields=, =sort=, =summarize=, =limit=, =lookup= across the types the caller may read -- and answers its table. The document is modelled on libresearch's =/api/v1/query=; it is a =POST= because a query is a document of its own and outgrows a URL long before a filter does.

The request is a JSON object, and every member it may carry is listed here; any other is a =400= rather than ignored:

| Member    | Type    | Default | Means                                                                   |
|-----------+---------+---------+-------------------------------------------------------------------------|
| =query=   | string  | --      | the LQL text (required)                                                 |
| =format=  | string  | =json=  | =json= for the document, =csv= for its rows as =text/csv=; =?format=csv= does the same |
| =explain= | boolean | =false= | plan the query without running it: =explain= holds the plan, =rows= is empty |

=?organization_id=N= is the business an unqualified =fetch= reads, with everything beneath it, as =GET /api/v1/<type>?organization_id=N= is; without it the business picked in the browser, which for a token is the default one. =organization_id == N= in the query replaces that scope, as in a list.

#+begin_src sh
curl -s -H "Authorization: Bearer $VENTURE_TOKEN" -H 'Content-Type: application/json' \
     -d '{"query": "fetch ticket | summarize n = count(), by: {status}"}' \
     "$VENTURE_URL/api/v1/query" | jq '.rows'
curl -s -H "Authorization: Bearer $VENTURE_TOKEN" -H 'Content-Type: application/json' \
     -d '{"query": "fetch invoice | fields number, status, due_at | sort due_at", "format": "csv"}' \
     "$VENTURE_URL/api/v1/query" > invoices.csv
#+end_src

The answer (=venture.query/1=):

#+begin_src json
{
  "schema": "venture.query/1",
  "query": "fetch ticket | summarize n = count(), by: {status}",
  "columns": [{"name": "status", "type": "String"}, {"name": "n", "type": "Int"}],
  "rows": [{"status": "todo", "n": 4}, {"status": "done", "n": 9}],
  "row_count": 2,
  "explain": null,
  "elapsed_ms": 3
}
#+end_src

| Member       | Meaning                                                                                    |
|--------------+--------------------------------------------------------------------------------------------|
| =schema=     | always =venture.query/1=; additions are backwards compatible                               |
| =query=      | the text that ran                                                                          |
| =columns=    | the output columns in order, each =name= and its LQL =type= (=String=, =Int=, =Double=, =Boolean=, =Timestamp=, =Duration=, =Array=, =Record=, =Any=) |
| =rows=       | one object per row, every column a member, in column order; NULL is =null=, a Timestamp ISO 8601 text, a Duration its LQL literal (="1h30m"=), money ={amount, currency, exponent, formatted}= with =amount= in minor units, and =sum_money()='s per-currency totals an array of those |
| =row_count=  | how many rows                                                                              |
| =explain=    | the plan with =explain: true=, else =null=                                                 |
| =elapsed_ms= | how long the query took                                                                    |

The CSV is the document's rows: a header of every column, one CRLF line per row, text defused against spreadsheet formulas as every export is, money as =1234.56 USD= and a list of money as each total joined by =; = (=300.00 EUR; 1500.00 USD=), never one figure.

Who may ask, and what they see, is the list API's: the caller is admitted as =GET /api/v1/<type>= admits a reader (a session or a token, a viewer at least), every row is read through the access policy as that caller, and a token minted for one organization reads only it. A =fetch= of a type the list API refuses the caller -- =user=, =api_token=, =plugin_config= for a non-owner -- gets the very refusal =GET /api/v1/<type>= gives, status and message, also inside a =lookup=. LQL's file, program, SQL, git, journal and Kubernetes commands do not exist here: =read=, =sql=, =exec= and the rest are an unknown command. Nothing a query does writes.

Errors are the standard body (=error=, =message=, =code=) plus where in the query: =line= and =column= (=null= when the error has no place) and =detail=, LQL's excerpt with a caret.

| HTTP | =error=              | When                                                                            |
|------+----------------------+---------------------------------------------------------------------------------|
| 400  | =serialization=      | the body is not a JSON object                                                   |
| 400  | =invalid_argument=   | no =query=, an unknown member, a bad =format=; a query that does not parse, check or evaluate; an unknown command or source |
| 401  | =unauthenticated=    | no credential                                                                   |
| 403  | =permission_denied=  | a type the list API refuses the caller (its message)                            |
| 422  | =validation=         | over =query.max_rows= (an error, never a shorter answer) or another LQL bound    |
| 504  | =timeout=            | longer than =query.timeout_ms=, or cancelled                                    |

=venturectl query= and the MCP tool =venture_query= post here and print the answer, so the three give the same rows; =tests/test-lql-query.c= holds them equal.

The query is never evaluated on the server's main loop: the request answers from a fiber, the evaluation runs on a query worker with its fetches read back in the request's own access scope, and the deadline (=query.timeout_ms= and a second's grace) or the client going away cancels it ([[file:lql.org::*Where a query runs][LQL: where a query runs]]). Other requests are served while a query runs. The MCP tool reaches the same route over HTTP from both doors (=venturectl mcp= and =POST /mcp=), so it runs the same way.

** The workdesk

=GET /api/v1/inbox= returns ={"unread": N, "notifications": [...]}= for the caller — a token with no user has no inbox — each notification with its kind, title, body, actor, the record it is about and a =url= to it, whether it is read, and when. =POST /api/v1/inbox/read= with ={"id": N}= marks one read, or every unread one with 0; somebody else's notification is not found, never forbidden. =POST /api/v1/watch= with ={"type": "ticket", "id": 7, "watch": true}= follows a record (=false= stops); =GET /api/v1/watching/:type/:id= says whether you do and who else does.

=GET /api/v1/activity/:type/:id= is the record's timeline, newest first: each audited change with =actor=, =actor_kind=, =action=, =when= and =changes= (the diff, field to ={"from","to"}=), and for a ticket its comments (=body=, =internal=) and worklogs (=hours=, =body=) woven in. A row whose =actor= is a token also carries =actor_username=, the account that owns it, when the caller may know it (see [[*Whose token it was][Whose token it was]]); =actor= itself is always the stored =API token #N=. =GET /api/v1/tickets/:id/sla= is the ticket's clocks: whether a policy covers it, each clock's state (=none=, =ok=, =warning=, =breached=) and seconds remaining, whether it has been answered, whether it is closed.

A ticket's =assignee= (and a macro's, and a routing rule's =assignees=) must name active members of the record's organization; anything else is a =422= whose message starts with the field and quotes the value -- =assignee: "oxpeker" is not an active member of Acme; ...=. It is judged only when the value is written, so a ticket with a stale assignee still takes other changes. =GET /api/v1/organizations/:id/members?q=&limit=&offset== lists who may be assigned there -- ={"total", "count", "limit", "offset", "records": [{"username", "display_name"}]}=, =q= a case-insensitive match anywhere in either name, =limit= 1 to 500 (20 by default) -- for a caller who may read that organization, and 404 otherwise. See [[file:workdesk.org::*Assigning: who may have a ticket][Assigning]].

=POST /api/v1/tickets/:id/macro= applies a macro by name or id and answers with the ticket; =POST /api/v1/tickets/:id/worklog= logs hours and answers 201 with the worklog. =POST /api/v1/:type/bulk= takes ={"ids": [...], "changes": {"status": "done"}}= or ={"ids": [...], "delete": true}=, applies it in one transaction — one refusal and nothing changes — and answers ={"changed": N}=; at most 500 ids. =POST /api/v1/incidents/:id/ticket= opens the incident's fix ticket and answers 201 with it; an incident that already names one gets 409. =POST /api/v1/sla/sweep= marks open tickets past their resolution target and answers ={"marked": N}=.

=GET /api/v1/runs= is mission control: ={"runs": [...], "totals": {...}}=, each run with its ticket, state, runner, outcome, branch, pull request, provider, model, tokens, cost, timing and summary; =?state=running= narrows it, =?limit=N= and =?organization_id=N= as elsewhere. =GET /api/v1/budgets= lists the active budgets with =spent=, =limit=, =percent=, =runs=, =warning= and =exhausted= for the current window. None of these are stageable except the worklog, which is the record =worklog= and takes =?stage=1= through its generic route. See [[file:workdesk.org][The workdesk]].

** Webhooks and the assistant at the desk

=GET /api/v1/webhooks= lists every webhook with whether it is active and signed, its consecutive failures, when it last delivered, and its last ten deliveries; the secret itself is never in the answer, only whether there is one. =POST /api/v1/webhooks/:id/test= sends a =webhook.test= delivery, waits, and answers with the delivery record. =POST /api/v1/webhooks/:id/secret= generates one (or takes ={"secret": "..."}=) and answers with it exactly once. All three are owner-only, as is the =webhook= type itself. See [[file:webhooks.org][Webhooks out]].

=POST /api/v1/tickets/:id/triage= reads the ticket and its thread and answers ={"triage": {...}, "applied": false, "ticket": {...}}=, where the triage carries a =priority=, an =issue_type=, =tags=, a =summary=, the requester's =sentiment= and a sentence of =reasoning=. Nothing changes unless the body says ={"apply": true}=, and then only the fields the enums actually accept — an invented priority changes nothing. =GET /api/v1/tickets/:id/summary= answers ={"summary": "..."}=; =POST /api/v1/tickets/:id/draft= takes ={"instruction": "..."}= and answers ={"draft": "...", "posted": false}=. A drafted reply is never posted: add it with =POST /api/v1/ticket_comment= once somebody has read it. All three need the AI module and a configured provider.

** Settings

=/api/v1/settings= describes every setting: its section, key, resolved
value, type, the one-line explanation of what it does, and the environment
variable that overrides it. It answers "what is this server actually
using", which layered configuration otherwise makes a guessing game.

Credentials are redacted. No secret is stored in a setting — the =*_env=
settings hold a variable's name, not its value — but a database URI can
carry a password if one was spelled out, and that is masked. For settings
that name a secret's variable, a =secret_present= boolean says whether it is
set, never what it contains.

The same data renders at =/settings= in the web UI. Both are read-only:
configuration is layered, so a value written through the API could be
silently overridden by a later layer, and the page would then be showing
something the server is not using.

* Staging a write

Add =?stage=1= to a =POST=, =PUT=, =PATCH= or =DELETE= and the change is
*proposed* rather than made. The server builds and validates the record
exactly as it would for a direct write, holds it, and answers =202 Accepted=
with the confirmation somebody has to approve:

#+begin_src sh
curl -X POST -H "Authorization: Bearer $VENTURE_TOKEN" \
     -H 'Content-Type: application/json' \
     -d '{"description": "Cover art", "amount": "250.00 USD"}' \
     'localhost:8747/api/v1/expense?stage=1'
#+end_src

#+begin_src json
{
  "status": "awaiting_approval",
  "staged": true,
  "confirmation": {
    "id": "a3f9c118",
    "summary": "Create expense \"Cover art\"",
    "action": "create",
    "state": "pending",
    "type": "expense",
    "label": "Cover art",
    "origin": { "kind": "token", "name": "API token #12", "username": "erin", "via": "rest-api" },
    "diff": { "description": "Cover art", "amount": { "amount": 25000, "currency": "USD" } },
    "created_at": "2026-08-29T14:02:11Z",
    "expires_at": "2026-08-29T15:02:11Z"
  },
  "note": "Nothing has been changed. ..."
}
#+end_src

This is what an outside agent uses. Give it a token, tell it to stage, and
what it proposes lands in the same queue the in-process assistant's writes do
— answerable from the AI panel, from =GET /api/v1/confirmations=, or from a
decision inbox in another program entirely.

The card is deliberately self-contained: which record type, which record if
there is one, what would change, and who asked. Whatever renders it will not
have the request that produced it. =origin.name= is the actor string the
change will be audited under -- match on it, as clawtilla matches it against
=whoami='s =actor=. =origin.username=, when present, is the account that
owns the token, for a person deciding; it is absent for a token or owner
that has been deleted and for a reader who may not know it (see [[*Whose token it was][Whose token it was]]).

Three more members of =origin= are stable ids, so a client can tell whose
change it is without parsing =API token #N=; each is absent, never null, when
it does not apply:

- =origin.token_id= is the API token's id; present only for a change staged
  with a token. It is not secret: =origin.name= already says it.
- =origin.user_id= is the proposer's user id. For a token it follows
  =origin.username= exactly (present only when the reader may know who owns
  the token); for a person it is always present.
- =origin.organization_id= is the staged record's organization, when it has
  one.

=GET /api/v1/confirmations= lists a card only when the caller can read the
staged record, or proposed it themself and would still need approval to make
that change. The listing does not widen with a role beyond that.

The prompt behind an assistant-staged change is *not* on the card. This
endpoint is open to any viewer and a prompt is the text of somebody's private
chat thread; it goes to the audit trail instead, where "why did this change"
belongs.

** Nothing is written until it is approved

=GET /api/v1/health= reports =staged_writes: true= on a build that has this
route (and =account_logins: true= on one whose JSON-lines push reads =login=
lines and an account's =login=, which an older build refuses whole; see
[[file:plugins.org][Plugins]]). It says what the build can do and deliberately not what the install is
doing — health is the one route with no authentication, and how many changes
are waiting is business activity, behind the viewer role at
=/api/v1/confirmations=.

Ask before assuming. =?stage=1= is an unknown query parameter to an older
build, an unknown parameter on a write route is *ignored*, and the write a
client meant to hold back is applied. A value the server does not recognise —
=?stage=y= — is refused with a =400= for the same reason: read as "no", it
would apply the write.

** Approving, rejecting, and a record that moved

#+begin_src sh
curl -X POST -H "Authorization: Bearer $VENTURE_TOKEN" \
     localhost:8747/api/v1/confirmations/a3f9c118/approve
#+end_src

Approving needs the editor role, *and* the role that record type needs in its
own right for a write — a forge is read by its organization's members but
written only by the owner on the direct route, and is owner-only here.
Without that, staging would launder the authorisation.

It applies the staged object through the same repository call an ordinary
write uses, so it cannot produce a different outcome from the diff that was
shown. It also cannot overwrite work done in the meantime: the staged record
carries the version it was read at, so if somebody edited the row while the
card was waiting, the approval fails with =409= naming the fields that moved:

#+begin_src json
{ "error": "conflict",
  "message": "Update expense \"Cover art\" was not applied: memo, vendor changed since this was staged. Nothing was written -- the record was not overwritten with what was staged. Look at it as it is now and stage the change again.",
  "code": 8 }
#+end_src

The confirmation is then *dropped*. Its staged object is pinned to a version
the row has moved past, so approving it again could not succeed either, and a
card that can only ever fail is worse than none. Read the record and stage
the change afresh.

A convergent case is not a conflict: if the change was already made by
somebody else, exactly, there is nothing left to write and the approval
succeeds having done nothing.

Rejecting discards the change and records the refusal in the audit trail —
knowing what an agent proposed and was denied is as useful as knowing what it
did.

** How long a card waits, and how many

A change waits =ai.confirmation_ttl= seconds (an hour by default) and is then
dropped. It is *removed*, not marked: a server left running would otherwise
accumulate every change nobody ever answered, each holding a whole record.

At most =ai.confirmation_limit= (200 by default) may wait at once. Staging
past that is refused with a =409= naming the limit. The lifetime bounds how
long one change waits; only the cap bounds how many an agent in a retry loop
can pile up inside that window.

Both settings keep their =ai.= prefix from when the assistant was the only
thing that staged anything. They govern the whole queue.

** The audit trail says which kind of change it was

| Case                    | =actor_kind=  | =actor=        | =approved_by= | =request_id=    |
|-------------------------+---------------+----------------+---------------+-----------------|
| direct, session         | =user=        | the person     | —             | —               |
| direct, bearer token    | =token=       | =API token #N= | —             | —               |
| staged, then approved   | who asked     | who asked      | who approved  | confirmation id |
| the assistant's own     | =ai=          | the model      | who approved  | confirmation id |

=approved_by= is set only for a change that came out of the queue, so "which
of these did somebody actually approve" is a filter rather than an inference:

#+begin_src sh
venturectl list audit_entry approved_by__not_null=1 order=-occurred_at
#+end_src

A bearer token's change was recorded as =import= until =token= existed, and
those rows were not rewritten: history says what was written at the time.
So =actor_kind__eq=token= finds only the newer token changes and
=actor_kind__eq=import= still finds the older ones beside real imports. To
ask for every change any token ever made, filter on the actor string, which
has always been the same:

#+begin_src sh
venturectl list audit_entry 'actor__like=API token #%' order=-occurred_at
#+end_src

** Whose token it was

The stored actor is the key, and nothing rewrites it: not the audit row, not
the inbox, not a webhook body, not =whoami=, not a confirmation's
=origin.name=. Who the token belongs to is worked out when somebody reads it,
from the token's =user_id= to that user's =username=, once per token per page:

- A record's Activity panel, the audit log (list and entry), the dashboard's
  recent activity, a conversation's history and the inbox read
  =erin (API token #12)=. An inbox title that leads with the actor is shown
  with the owner in front; the stored title is unchanged.
- =GET /api/v1/activity/:type/:id= adds =actor_username= (and
  =approved_by_username= for an approver that was a token) to a row whose
  actor is a token; the dashboard's =activity= widget adds =actor_username=;
  a confirmation's =origin= adds =username=. Each is *absent*, never null,
  when it does not apply.
- A token that has been deleted, or whose owner has, reads =API token #12=
  exactly as before.

The owner is shown only to a reader who could already see who that person
is: a global owner or administrator, the owner themself, or somebody who is
an active member of an organization the owner is also an active member of
-- the membership records a member reads name everybody in it. Anybody else
(a customer of a hosted install, looking at a change the operator's token
made) sees =API token #12=. A request with no person behind it -- internal
work, a scheduled delivery -- is told nothing.

** What is not stageable

=POST /api/v1/:type/:id/restore= applies immediately. Un-deleting is the one
generic write whose worst case is a record being visible again, and it is not
worth an action of its own in the queue. The four verbs above are the whole
surface.

A deleted record's page says it is deleted and carries a Restore button,
which posts to =/e/:type/:id/restore= with the same checks. Deleting a
business from its page needs the form's confirmation tick (=confirm=1=),
and the last business is never deleted there. The default business is
refused for every caller: make another business the default first.

* Filtering

=field=value= is equality; =field__op=value= names an operator.

#+begin_src sh
?status__eq=active
?occurred_at__gte=2026-01-01&occurred_at__lt=2026-04-01
?status__in=active,paused
?name__ilike=%etsy%
?deleted_at__not_null=1
?period=this_quarter&period_field=occurred_at
?search=lovelace
?order=-occurred_at&limit=20&offset=40
#+end_src

Operators: =eq ne lt lte gt gte like ilike in not_in is_null not_null between=.

Periods accept the same vocabulary everywhere in VENTURE: =today=,
=yesterday=, =this_week=, =this_month=, =last_month=, =this_quarter=, =ytd=,
=mtd=, =qtd=, =fy=, =fy_2026=, =last_30_days=, =2026=, =2026-03=, =2026-Q2=,
=2026-01-01..2026-03-31=, =all=.

A field name that is not a real property of the record type is refused, with
the available fields listed. No caller-supplied string ever reaches the SQL as
text.

** =q=: an LQL filter

=q= is an [[file:lql.org][LQL]] filter over the record type, what follows =fetch TYPE | filter=:

#+begin_src sh
GET /api/v1/ticket?q=status%20not%20in%20%5B%22done%22%2C%20%22cancelled%22%5D
# q = status not in ["done", "cancelled"] and assignee == me()
#+end_src

It runs as the caller, through the same access policy and business scope as the list itself, and selects records; everything else about the request -- the other filters, =order=, =limit=, =offset=, =total= -- works as it always did on the records it selected. It is bounded like any query (=query.max_rows=, =query.timeout_ms=), and one filter may select at most 30000 records. A filter that cannot run is a 400 =invalid_argument= naming the column: ="q, column 22: unknown field 'staus' (did you mean 'status'?)"=. A field the record does not have is refused rather than matching nothing. See [[file:lql.org::*Filter bars][Filter bars]].

* Bodies

=PATCH= applies only the members present; anything omitted is left alone.
A create may name the record's =uuid= itself, and it is kept: a client that
mints the id up front can find its record again by it after a create that
timed out. A second create with a =uuid= already taken is 409
(=already_exists=), not a second record.
Money accepts several forms — ~"12.34"~, ~"$12.34"~, ~"12.34 EUR"~, or the
object form ~{"amount": 1234, "currency": "USD", "exponent": 2}~. Dates accept
ISO 8601 or =YYYY-MM-DD=. Enumerations accept their nick in any case, with
hyphens or underscores.

Responses always carry both the exact value and a formatted twin, so a
consumer that does not understand minor units still reports the right figure:

#+begin_src json
"gross": { "amount": 1499, "currency": "USD", "exponent": 2,
           "formatted": "14.99 USD" }
#+end_src

Fields flagged sensitive — password hashes, token secrets, tax identifiers —
are omitted entirely rather than nulled, so a client cannot tell "unset" from
"withheld".

* Errors

One shape for every failure:

#+begin_src json
{ "error": "validation", "message": "Code: is required", "code": 5 }
#+end_src

| Slug                       | HTTP | Meaning                              |
|----------------------------+------+--------------------------------------|
| =invalid_argument=         |  400 | unusable input                       |
| =unauthenticated=          |  401 | no valid credentials                 |
| =permission_denied=        |  403 | insufficient role                    |
| =not_found=                |  404 | no such record or route              |
| =already_exists=, =conflict= | 409 | uniqueness, or a stale version       |
| =validation=, =balance=    |  422 | semantically wrong                   |
| =ai_confirmation_required= |  202 | staged, awaiting approval            |
| =unsupported=              |  501 | not in this build                    |

A =409= from a write means someone else changed the record since you loaded
it (=conflict=), or that a value which must be unique is already taken
(=already_exists=) -- since 0.10.0 a save the database refuses for a unique
index answers =already_exists= rather than a 500. For a stale version:
reload, reapply, retry -- do not force it. For a taken value: find the record
that holds it (a filter on that field) and use it.

* Stripe payment actions

=POST /api/v1/invoices/:id/checkout= requires the editor role and the Stripe
module. It calls VentureStripeService and returns the stored Checkout record,
including =url=. Invoice eligibility is checked in that service; generic
Checkout and event writes are refused.

=POST /webhooks/stripe/<connection-id>= accepts an unauthenticated raw entity body and its
=Stripe-Signature= header. Invalid signatures and refused events receive 400;
processed, ignored and duplicate events receive 200. An unavailable provider
receives 503. Authentication is the verified signature, never a browser
session or a redirect. See [[file:stripe.org][Stripe payments]] for exact matching,
deduplication and transactional settlement.
* Fixed asset and recurring journal actions

The =assets= module adds editor-only actions:

| POST endpoint | Body |
|---------------+------|
| =/api/v1/fixed_assets/:id/place-in-service= | Optional =in_service_at= |
| =/api/v1/fixed_assets/:id/dispose= | =disposal_proceeds= and optional =disposed_at= |
| =/api/v1/fixed_assets/:id/write-off= | Optional =disposed_at=; zero proceeds |

Send a JSON object, including ={}= when no parameters are needed. Asset
actions support =?stage=1= and return a confirmation with status 202.
Direct asset actions return the resulting record; a period run returns
={"entries":N,"dry_run":false}=. The run uses one transaction for the
whole organization and month, preserves journal source links, and is
idempotent. Closed periods return the period guard's conflict.

and schedule-history writes name the required service in their refusal.

* Organization access

With =orgaccess= enabled (the default), =organization_membership=, =team=
and =team_membership= use the ordinary CRUD routes. Company, contact, deal,
ticket and venture accept =owner_user_id= and optional =team_id=. A team must
belong to the record's organization. See [[file:orgaccess.org][the role matrix]].

The server intersects requested organizations with the caller's current
memberships. Lists, searches, exports, reports and dashboard widgets return
only authorized records; a direct read outside membership returns 404.
An in-organization write refused by its role returns 403. Parent organization
filters never grant access to children without membership.

Tokens retain the minting role and a snapshot of memberships at mint time,
intersected with current roles and memberships. New grants cannot expand an
existing token. Disabling its user rejects it; demotion reduces its authority.
Legacy non-admin tokens without a snapshot must be rotated. Global owner and
admin behavior remains compatible with existing clients.

Organization viewers with a global role that permits proposals receive 202
for creates, even without =?stage=1=. An editor's
=POST /api/v1/journals/:id/post= also returns 202 and a confirmation. Approval
requires financial authority and rechecks the captured draft and lines.
Generic journal-state updates continue to be refused by the posting service.

=invoice_id=, =proration_amount=, =processed=). =?stage=1= returns 202 with a
confirmation instead. Approval uses the same transaction and checks the
pinned subscription version and fiscal guard again.

GET =/api/v1/reports/mrr=, =/churn= and =/subscriptions_due= use the report
registry, with =period=, =organization_id=, =currency=, =as_of= and (for the
due queue) =days=. Definitions are in each report's notes and
[[file:billing.org][SaaS billing]]. No endpoint sends mail or charges a card.

* Record actions

=POST /api/v1/:type/:id/actions/:action= takes a JSON object of parameters.
The registry checks the authenticated role and calls the declaring service.
Unknown actions answer 404, insufficient roles 403, state conflicts 409 and
invalid parameters 422, using the ordinary error JSON shape.

=?stage=1= returns 202 with an action confirmation. Approval checks the
current record, version, approver role and service eligibility again.

A type-level action (ID =0=) that declares no subject record -- a sweep, a
run, a batch -- is judged as belonging to the organization its
=organization_id= parameter names (a JSON integer; a string of digits is
accepted too). The organization access role matrix then applies exactly as
it does to a record there: a member of another organization is answered
404, and an organization editor is refused a financial type such as
=dunning_policy= or =invoice= with 403. A member who is not a global owner
or admin must name the organization; without =organization_id= the answer
is 422 =organization_id: ... runs in one organization=. Global owners,
admins and internal jobs without one keep running in the default
organization. The action then runs in the organization it was judged in,
never a different one.
=GET /api/v1/schema/:type= and the full schema include =actions= with
labels, descriptions, minimum roles, =stageable=, parameters and input schemas.
See [[file:actions.org][record actions]] for registration and signals.

The ledger also exposes =POST /api/v1/journals/post= (header plus =lines=),
including =?stage=1=. It dispatches the registered type-level
=create_and_post= action. See [[file:ledger.org][posting from the outside]].

** Hosted account identity

=GET /api/v1/account-identity/:id= validates a hosted organization for an
external provisioning client using existing bearer authentication and current
organization owner/admin authority. Returns canonical origin, workspace UUID,
organization ID and active lifecycle state; never grants token access to
workspace administration. See [[file:lightsite-accounts.org][Lightsite account validation]] for refusals and
consumer requirements.

=POST /api/v1/lightsite/signups= finishes a Lightsite self sign-up under a
workspace administrator's service token: it creates or links the owner and
creates their business. The body is a closed object of the seven strings
=idempotency_key=, =email=, =issuer=, =subject=, =business_name=,
=first_name= and =last_name=, plus an optional eighth, =timezone=: an IANA
zone name such as =America/New_York=, saved as the new business's time zone.
A =timezone= GLib cannot resolve, or one that is not a string, is 422 and
nothing is created; without it the zone stays blank, which Venture reads as
UTC. A repeat of a finished sign-up replays its answer and never changes the
saved zone. See [[file:lightsite-accounts.org][Lightsite accounts]], "Trusted-service self sign-up".

=POST /api/v1/lightsite/billing/subscriptions= binds a Lightsite business to a
plan in the configured billing organization (=lightsite.billing_organization_id=),
idempotently; =GET /api/v1/lightsite/billing/:organization_id= and
=GET /api/v1/lightsite/billing= read what a business, or every Lightsite
customer, is on and owes. All three take the trusted-service authority of the
sign-up and answer 404 while no billing organization is configured. See
[[file:lightsite-billing.org][Lightsite billing]].

=POST /api/v1/lightsite/bookings/:id/move= moves a confirmed booking when its
business owner reschedules it, under the same trusted-service authority.
=:id= is the booking's meeting; the body is exactly
={"organization_id": N, "starts_at": "<ISO 8601>"}=, a start the booking page
offers. It is the customer's reschedule reached by the owner: the booking
keeps its booked length and its private link is renewed. Venture sends the
customer no mail: the caller sends the letter, with the owner as the reply
address. 200 answers ={"starts_at", "ends_at", "booking"}=; a booking of
another business is 404, a taken slot or a booking that is not confirmed 409,
and a bad body or time 422. =booking= is exactly the object the signed booking
hook body carries, read after the move, so its times are the new ones:
=reservation_id=, =state=, =starts_at= and =ends_at= (ISO 8601 with the offset
of the page's zone), =time_zone=, =service= (the page title), =customer=
(={"name", "email", "phone"}=) and =note=; an unknown value is null. It is
there because the caller writes the letter and its token cannot read booking
records. The move is already made when it is read, so a failed read answers
200 with =booking= null rather than an error.

=POST /api/v1/lightsite/bookings/:id/cancel= cancels a confirmed booking when
its business owner cancels it, built the same way as the move: the same
trusted-service authority, =:id= the booking's meeting, and the body exactly
={"organization_id": N}=. It settles the same records as the customer's
cancel through the private link (the reservation is cancelled and its link
stops working, the meeting is cancelled and its capacity freed). Venture sends
the customer no mail: the caller sends the letter. 200 answers
={"booking"}=, the same object as the move's, read after the cancel, so its
=state= is =cancelled=; a failed read is =booking= null, as for the move. No
token is 401; any token but the trusted service's is 403; a booking of another
business, or none, is 404; a booking that is neither confirmed nor cancelled
(its meeting is done) is 409; and a bad body or id is 422. A cancel is safe
to retry: a booking already cancelled answers 200 with the same =booking= and
nothing changes, so after a crash the caller calls again and still has what
the letter needs. The generic
=POST /api/v1/activity/:id/actions/cancel_booking= answers 404 for a meeting
that does not exist.

=GET /api/v1/lightsite/departure/:org= reads a business's leaving state,
under the same trusted-service authority; Venture keeps it on the
organization and Lightsite only shows it. 200 answers
={"organization_id": N, "state": "active", "left_at": null, "returned_at": null, "purged_at": null}=:
=state= is =active= (the default), =closing=, =closed= or =purged=, and each
time is ISO 8601 or null. An unknown organization is 404. A generic
organization update cannot change =departure_state=, =left_at=,
=returned_at= or =purged_at=: the save refuses, naming the field. Only
these routes move them.
=POST /api/v1/lightsite/departure/:org/:action= takes no body and answers the
same object:
- =leave=: =active= to =closing=; already =closing= is 200 and nothing
  changes; =closed= or =purged= is 409.
- =close=: =closing= to =closed=, =left_at= set to now; already =closed= is
  200 and =left_at= does not move; =active= or =purged= is 409.
- =return=: =closed= to =active=, =returned_at= set to now and =left_at=
  kept; already back (=active= with =returned_at= set) is 200 and
  =returned_at= does not move; =active= and never left, or =closing=, is 409;
  =purged=, or later than =left_at= plus six calendar months, is 410.
- =purge=: =closed= to =purged=, =purged_at= set to now; already =purged= is
  200 and =purged_at= does not move; =active= or =closing= is 409.
Any other action is 404. No token is 401; any token but the trusted
service's, the business owner's own included, is 403. Lightsite calls
=leave=, cancels the plan, takes the site offline and packs the files, then
calls =close=; after a crash it calls =leave= again (200) and finishes the
steps that did not.
