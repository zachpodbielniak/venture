* REST API

Base path =/api/v1=. Everything is JSON. The API is generated from the record
registry, so a plugin's record type is a first-class resource the moment it
registers — there is no routing to add.

* Authentication

Either a bearer token or a browser session cookie.

#+begin_src sh
curl -H "Authorization: Bearer $VENTURE_TOKEN" localhost:8747/api/v1/sale
#+end_src

Mint a token in the browser at *Your account -> API tokens*
(=/account/tokens=), which is the easiest route and the only one that does
not need a token to get a token. The page lists what exists, mints a new one
with an optional expiry, and revokes any of them.

Or mint one over HTTP with =POST /api/v1/tokens= while holding a session.
Either way the plaintext is shown exactly once; only its hash is stored.

Both routes are admin-only, and a token carries the role of whoever minted
it. There is no scope parameter: for a token that may do less, sign in as a
user who may do less and mint it there.

=venturectl mcp= serves this API to an outside AI agent as an MCP server,
taking its token from =VENTURE_TOKEN= and generating its tool surface from
=/api/v1/schema= so a plugin's record type is offered without any change.
See [[file:mcp.org][venturectl mcp]].

Any of the four write verbs takes =?stage=1=, which proposes the change
instead of making it. See [[*Staging a write][Staging a write]].

Both singular and plural type names work, so =/api/v1/sale= and =/api/v1/sales=
are the same resource. A client that presents record types to somebody should
offer one of the two spellings, not both: they are one resource, and showing
two invites a duplicate.

** Modules

=/api/v1/modules= lists every module in dependency order: name, label, description, what it requires and what requires it, the record types and reports it owns, whether it is locked, and — when it is off — why, in the words of the setting that turned it off. A type whose module is off is absent from =/api/v1/schema= and its generic routes answer 404 naming the module; a module's own routes do the same. See [[file:modules.org][Modules]].

** Links

=GET /api/v1/links/:type/:id= describes every link touching a record, read from it: the link's id, the kind from here, the other end's type, id and current label, whether the other end still exists, and the note. =POST /api/v1/links= takes ={"source_type","source_id","kind","target_type","target_id","note"}= and is the same as =POST /api/v1/record_link=, =?stage=1= included. A link is refused when either end is missing, when the ends are the same record, or when the pair is already linked in either direction — at the save, so an approved staged link is held to the same rules.

** The factory

=GET /api/v1/factory= is the loop at a glance: open milestones with their progress, the newest releases, the latest builds, each environment with the release it is running, and the incidents still open — the five questions the Factory page asks, as one object. =?organization_id=N= scopes it.

=POST /api/v1/releases/:id/changelog= drafts the release's changelog from the tickets marked as fixed in it and saves it; the body may carry ={"replace": true}= to overwrite a changelog somebody wrote, and the answer's =changed= says whether anything was; when it is false, =reason= says why (the changelog somebody wrote was kept). =POST /api/v1/releases/:id/publish= cuts the release on the forge — the tag from the record or =v= plus the version, the changelog as the body, ={"prerelease": true}= to mark it so — and answers with the release carrying the forge's id and page. Both need the editor role and the factory module; publish also needs the forge module and a repository on the release. Neither can be staged: a changelog is an ordinary field an agent can also set through =PATCH /api/v1/release/:id?stage=1=, and a publish creates a tag on another system.

The rest of what the factory works out, all needing the factory module:

| Method | Path                                    | Role   | What                                                        |
|--------+-----------------------------------------+--------+-------------------------------------------------------------|
| =GET=  | =/api/v1/factory/actions=               | viewer | what needs somebody, most pressing first; =?organization_id=N= scopes it |
| =GET=  | =/api/v1/releases/:id/readiness=        | viewer | can it go out: checks that pass, warn or fail, =ready= and a =score= |
| =GET=  | =/api/v1/milestones/:id/forecast=       | viewer | when it lands at the pace it is going                       |
| =POST= | =/api/v1/releases/:id/deploy=           | editor | ={"environment_id": N, "notes": "..."}=; records the release going live, answers 201 with the deployment |
| =POST= | =/api/v1/environments/:id/rollback=     | editor | ={"reason": "..."}=; marks the current deployment rolled back and records the release before it, answers 201 with the new deployment; 409 when there is nothing to go back to |
| =POST= | =/api/v1/builds/:id/ticket=             | editor | opens the bug for a failed build, answers 201 with the ticket; 409 when the build is not failed or already has one |
| =GET=  | =/api/v1/factory/briefing=              | editor | ={"briefing": "..."}=: the status and the actions as prose, from the assistant |
| =POST= | =/api/v1/releases/:id/notes=            | editor | ={"audience": "..."}= optional; ={"notes": "..."}=, drafted by the assistant, nothing written |
| =POST= | =/api/v1/incidents/:id/postmortem=      | editor | ={"postmortem": "..."}=, a blameless draft from the records, nothing written |
| =POST= | =/api/v1/builds/:id/triage=             | editor | what a build's log is complaining about: =category=, =summary=, =cause=, =suggestion=, =retry=, =confidence= |

The four from the assistant need the =ai= module and a configured provider, and answer with the reason when there is none. An =organization_id= that is present and unusable is a 400 rather than every organization.

Everything else about the factory is the generic routes: =/api/v1/milestone=, =release=, =build=, =environment=, =deployment=, =incident=, with =?stage=1= on every write. See [[file:factory.org][The software factory]].

** Dashboards

A widget's place on the grid is four fields, =grid_col=, =grid_row=, =grid_width= and =grid_height=, zero meaning "wherever fits"; the checked way to move one is the editor's =POST /dashboards/:slug/widgets/:id/place=, which refuses a taken cell with 409. See [[file:dashboards.org][Dashboards]].

=GET /api/v1/dashboards/:slug= returns a dashboard with every widget evaluated: each widget's settings, its resolved title, its link, an =error= when it could not be answered, and =data= in a shape its kind decides. =?data=0= lists the widgets without evaluating them; =?organization_id=N= narrows every widget to that entity and authorized descendants; membership is still required for each organization. A personal dashboard belonging to somebody else answers 404. The generic routes =/api/v1/dashboard= and =/api/v1/dashboard_widget= work like any other type's, and a widget written through them is held to the same checks as one made in the editor. See [[file:dashboards.org][Dashboards]].

** The workdesk

=GET /api/v1/inbox= returns ={"unread": N, "notifications": [...]}= for the caller — a token with no user has no inbox — each notification with its kind, title, body, actor, the record it is about and a =url= to it, whether it is read, and when. =POST /api/v1/inbox/read= with ={"id": N}= marks one read, or every unread one with 0; somebody else's notification is not found, never forbidden. =POST /api/v1/watch= with ={"type": "ticket", "id": 7, "watch": true}= follows a record (=false= stops); =GET /api/v1/watching/:type/:id= says whether you do and who else does.

=GET /api/v1/activity/:type/:id= is the record's timeline, newest first: each audited change with =actor=, =actor_kind=, =action=, =when= and =changes= (the diff, field to ={"from","to"}=), and for a ticket its comments (=body=, =internal=) and worklogs (=hours=, =body=) woven in. =GET /api/v1/tickets/:id/sla= is the ticket's clocks: whether a policy covers it, each clock's state (=none=, =ok=, =warning=, =breached=) and seconds remaining, whether it has been answered, whether it is closed.

=POST /api/v1/tickets/:id/macro= applies a macro by name or id and answers with the ticket; =POST /api/v1/tickets/:id/worklog= logs hours and answers 201 with the worklog. =POST /api/v1/:type/bulk= takes ={"ids": [...], "changes": {"status": "done"}}= or ={"ids": [...], "delete": true}=, applies it in one transaction — one refusal and nothing changes — and answers ={"changed": N}=; at most 500 ids. =POST /api/v1/incidents/:id/ticket= opens the incident's fix ticket and answers 201 with it; an incident that already names one gets 409. =POST /api/v1/sla/sweep= marks open tickets past their resolution target and answers ={"marked": N}=.

=GET /api/v1/runs= is mission control: ={"runs": [...], "totals": {...}}=, each run with its ticket, state, runner, outcome, branch, pull request, provider, model, tokens, cost, timing and summary; =?state=running= narrows it, =?limit=N= and =?organization_id=N= as elsewhere. =GET /api/v1/budgets= lists the active budgets with =spent=, =limit=, =percent=, =runs=, =warning= and =exhausted= for the current window. None of these are stageable except the worklog, which is the record =worklog= and takes =?stage=1= through its generic route. See [[file:workdesk.org][The workdesk]].

** Webhooks and the assistant at the desk

=GET /api/v1/webhooks= lists every webhook with whether it is active and signed, its consecutive failures, when it last delivered, and its last ten deliveries; the secret itself is never in the answer, only whether there is one. =POST /api/v1/webhooks/:id/test= sends a =webhook.test= delivery, waits, and answers with the delivery record. =POST /api/v1/webhooks/:id/secret= generates one (or takes ={"secret": "..."}=) and answers with it exactly once. All three are owner-only, as is the =webhook= type itself. See [[file:webhooks.org][Webhooks out]].

=POST /api/v1/tickets/:id/triage= reads the ticket and its thread and answers ={"triage": {...}, "applied": false, "ticket": {...}}=, where the triage carries a =priority=, an =issue_type=, =tags=, a =summary=, the requester's =sentiment= and a sentence of =reasoning=. Nothing changes unless the body says ={"apply": true}=, and then only the fields the enums actually accept — an invented priority changes nothing. =GET /api/v1/tickets/:id/summary= answers ={"summary": "..."}=; =POST /api/v1/tickets/:id/draft= takes ={"instruction": "..."}= and answers ={"draft": "...", "posted": false}=. A drafted reply is never posted: add it with =POST /api/v1/ticket_comment= once somebody has read it. All three need the AI module and a configured provider.

** Settings

=/api/v1/settings= describes every setting: its section, key, resolved
value, type, the one-line explanation of what it does, and the environment
variable that overrides it. It answers "what is this server actually
using", which layered configuration otherwise makes a guessing game.

Credentials are redacted. No secret is stored in a setting — the =*_env=
settings hold a variable's name, not its value — but a database URI can
carry a password if one was spelled out, and that is masked. For settings
that name a secret's variable, a =secret_present= boolean says whether it is
set, never what it contains.

The same data renders at =/settings= in the web UI. Both are read-only:
configuration is layered, so a value written through the API could be
silently overridden by a later layer, and the page would then be showing
something the server is not using.

* Staging a write

Add =?stage=1= to a =POST=, =PUT=, =PATCH= or =DELETE= and the change is
*proposed* rather than made. The server builds and validates the record
exactly as it would for a direct write, holds it, and answers =202 Accepted=
with the confirmation somebody has to approve:

#+begin_src sh
curl -X POST -H "Authorization: Bearer $VENTURE_TOKEN" \
     -H 'Content-Type: application/json' \
     -d '{"description": "Cover art", "amount": "250.00 USD"}' \
     'localhost:8747/api/v1/expense?stage=1'
#+end_src

#+begin_src json
{
  "status": "awaiting_approval",
  "staged": true,
  "confirmation": {
    "id": "a3f9c118",
    "summary": "Create expense \"Cover art\"",
    "action": "create",
    "state": "pending",
    "type": "expense",
    "label": "Cover art",
    "origin": { "kind": "import", "name": "books-agent", "via": "rest-api" },
    "diff": { "description": "Cover art", "amount": { "amount": 25000, "currency": "USD" } },
    "created_at": "2026-08-29T14:02:11Z",
    "expires_at": "2026-08-29T15:02:11Z"
  },
  "note": "Nothing has been changed. ..."
}
#+end_src

This is what an outside agent uses. Give it a token, tell it to stage, and
what it proposes lands in the same queue the in-process assistant's writes do
— answerable from the AI panel, from =GET /api/v1/confirmations=, or from a
decision inbox in another program entirely.

The card is deliberately self-contained: which record type, which record if
there is one, what would change, and who asked. Whatever renders it will not
have the request that produced it.

The prompt behind an assistant-staged change is *not* on the card. This
endpoint is open to any viewer and a prompt is the text of somebody's private
chat thread; it goes to the audit trail instead, where "why did this change"
belongs.

** Nothing is written until it is approved

=GET /api/v1/health= reports =staged_writes: true= on a build that has this
route. It says what the build can do and deliberately not what the install is
doing — health is the one route with no authentication, and how many changes
are waiting is business activity, behind the viewer role at
=/api/v1/confirmations=.

Ask before assuming. =?stage=1= is an unknown query parameter to an older
build, an unknown parameter on a write route is *ignored*, and the write a
client meant to hold back is applied. A value the server does not recognise —
=?stage=y= — is refused with a =400= for the same reason: read as "no", it
would apply the write.

** Approving, rejecting, and a record that moved

#+begin_src sh
curl -X POST -H "Authorization: Bearer $VENTURE_TOKEN" \
     localhost:8747/api/v1/confirmations/a3f9c118/approve
#+end_src

Approving needs the editor role, *and* the role that record type needs in its
own right — a forge is owner-only on the direct route and is owner-only here.
Without that, staging would launder the authorisation.

It applies the staged object through the same repository call an ordinary
write uses, so it cannot produce a different outcome from the diff that was
shown. It also cannot overwrite work done in the meantime: the staged record
carries the version it was read at, so if somebody edited the row while the
card was waiting, the approval fails with =409= naming the fields that moved:

#+begin_src json
{ "error": "conflict",
  "message": "Update expense \"Cover art\" was not applied: memo, vendor changed since this was staged. Nothing was written -- the record was not overwritten with what was staged. Look at it as it is now and stage the change again.",
  "code": 8 }
#+end_src

The confirmation is then *dropped*. Its staged object is pinned to a version
the row has moved past, so approving it again could not succeed either, and a
card that can only ever fail is worse than none. Read the record and stage
the change afresh.

A convergent case is not a conflict: if the change was already made by
somebody else, exactly, there is nothing left to write and the approval
succeeds having done nothing.

Rejecting discards the change and records the refusal in the audit trail —
knowing what an agent proposed and was denied is as useful as knowing what it
did.

** How long a card waits, and how many

A change waits =ai.confirmation_ttl= seconds (an hour by default) and is then
dropped. It is *removed*, not marked: a server left running would otherwise
accumulate every change nobody ever answered, each holding a whole record.

At most =ai.confirmation_limit= (200 by default) may wait at once. Staging
past that is refused with a =409= naming the limit. The lifetime bounds how
long one change waits; only the cap bounds how many an agent in a retry loop
can pile up inside that window.

Both settings keep their =ai.= prefix from when the assistant was the only
thing that staged anything. They govern the whole queue.

** The audit trail says which kind of change it was

| Case                    | =actor_kind=  | =actor=        | =approved_by= | =request_id=    |
|-------------------------+---------------+----------------+---------------+-----------------|
| direct, session         | =user=        | the person     | —             | —               |
| direct, bearer token    | =import=      | the token      | —             | —               |
| staged, then approved   | who asked     | who asked      | who approved  | confirmation id |
| the assistant's own     | =ai=          | the model      | who approved  | confirmation id |

=approved_by= is set only for a change that came out of the queue, so "which
of these did somebody actually approve" is a filter rather than an inference:

#+begin_src sh
venturectl list audit_entry approved_by__not_null=1 order=-occurred_at
#+end_src

** What is not stageable

=POST /api/v1/:type/:id/restore= applies immediately. Un-deleting is the one
generic write whose worst case is a record being visible again, and it is not
worth an action of its own in the queue. The four verbs above are the whole
surface.

* Forge endpoints

| Method | Path                     | Role   |
|--------+--------------------------+--------|
| POST   | =/forges/:id/token=      | owner  |
| POST   | =/forges/:id/secret=     | owner  |
| POST   | =/forges/:id/verify=     | owner  |
| POST   | =/tickets/:id/link=      | editor |
| POST   | =/tickets/:id/branch=    | editor |
| POST   | =/tickets/:id/work=      | editor |
| GET    | =/tickets/:id/runs=      | viewer |
| POST   | =/runs/:id/cancel=       | editor |
| POST   | =/hooks/forge/:id=       | —      |

=/hooks/forge/:id= is the one endpoint in VENTURE that does not require a session, because the caller is a forge and has neither a cookie nor a token. It authenticates by verifying an HMAC-SHA256 over the request body against that forge's webhook secret; a forge with no secret set is refused outright. See [[file:forge.org][Git forges]].

* Filtering

=field=value= is equality; =field__op=value= names an operator.

#+begin_src sh
?status__eq=active
?occurred_at__gte=2026-01-01&occurred_at__lt=2026-04-01
?status__in=active,paused
?name__ilike=%etsy%
?deleted_at__not_null=1
?period=this_quarter&period_field=occurred_at
?search=lovelace
?order=-occurred_at&limit=20&offset=40
#+end_src

Operators: =eq ne lt lte gt gte like ilike in not_in is_null not_null between=.

Periods accept the same vocabulary everywhere in VENTURE: =today=,
=yesterday=, =this_week=, =this_month=, =last_month=, =this_quarter=, =ytd=,
=mtd=, =qtd=, =fy=, =fy_2026=, =last_30_days=, =2026=, =2026-03=, =2026-Q2=,
=2026-01-01..2026-03-31=, =all=.

A field name that is not a real property of the record type is refused, with
the available fields listed. No caller-supplied string ever reaches the SQL as
text.

* Bodies

=PATCH= applies only the members present; anything omitted is left alone.
Money accepts several forms — ~"12.34"~, ~"$12.34"~, ~"12.34 EUR"~, or the
object form ~{"amount": 1234, "currency": "USD", "exponent": 2}~. Dates accept
ISO 8601 or =YYYY-MM-DD=. Enumerations accept their nick in any case, with
hyphens or underscores.

Responses always carry both the exact value and a formatted twin, so a
consumer that does not understand minor units still reports the right figure:

#+begin_src json
"gross": { "amount": 1499, "currency": "USD", "exponent": 2,
           "formatted": "14.99 USD" }
#+end_src

Fields flagged sensitive — password hashes, token secrets, tax identifiers —
are omitted entirely rather than nulled, so a client cannot tell "unset" from
"withheld".

* Errors

One shape for every failure:

#+begin_src json
{ "error": "validation", "message": "Code: is required", "code": 5 }
#+end_src

| Slug                       | HTTP | Meaning                              |
|----------------------------+------+--------------------------------------|
| =invalid_argument=         |  400 | unusable input                       |
| =unauthenticated=          |  401 | no valid credentials                 |
| =permission_denied=        |  403 | insufficient role                    |
| =not_found=                |  404 | no such record or route              |
| =already_exists=, =conflict= | 409 | uniqueness, or a stale version       |
| =validation=, =balance=    |  422 | semantically wrong                   |
| =ai_confirmation_required= |  202 | staged, awaiting approval            |
| =unsupported=              |  501 | not in this build                    |

A =409= from a write means someone else changed the record since you loaded
it. Reload, reapply, retry — do not force it.

* Stripe payment actions

=POST /api/v1/invoices/:id/checkout= requires the editor role and the Stripe
module. It calls VentureStripeService and returns the stored Checkout record,
including =url=. Invoice eligibility is checked in that service; generic
Checkout and event writes are refused.

=POST /webhooks/stripe/<connection-id>= accepts an unauthenticated raw entity body and its
=Stripe-Signature= header. Invalid signatures and refused events receive 400;
processed, ignored and duplicate events receive 200. An unavailable provider
receives 503. Authentication is the verified signature, never a browser
session or a redirect. See [[file:stripe.org][Stripe payments]] for exact matching,
deduplication and transactional settlement.
* Fixed asset and recurring journal actions

The =assets= module adds editor-only actions:

| POST endpoint | Body |
|---------------+------|
| =/api/v1/fixed_assets/:id/place-in-service= | Optional =in_service_at= |

* Organization access

With =orgaccess= enabled (the default), =organization_membership=, =team=
and =team_membership= use the ordinary CRUD routes. Company, contact, deal,
ticket and venture accept =owner_user_id= and optional =team_id=. A team must
belong to the record's organization. See [[file:orgaccess.org][the role matrix]].

The server intersects requested organizations with the caller's current
memberships. Lists, searches, exports, reports and dashboard widgets return
only authorized records; a direct read outside membership returns 404.
An in-organization write refused by its role returns 403. Parent organization
filters never grant access to children without membership.

Tokens retain the minting role and a snapshot of memberships at mint time,
intersected with current roles and memberships. New grants cannot expand an
existing token. Disabling its user rejects it; demotion reduces its authority.
Legacy non-admin tokens without a snapshot must be rotated. Global owner and
admin behavior remains compatible with existing clients.

Organization viewers with a global role that permits proposals receive 202
for creates, even without =?stage=1=. An editor's
=POST /api/v1/journals/:id/post= also returns 202 and a confirmation. Approval
requires financial authority and rechecks the captured draft and lines.
Generic journal-state updates continue to be refused by the posting service.

* Leads

=POST /f/:token= is public capture, accepting JSON and form encoding. The
form fixes organization and venture; it controls fields and duplicate policy.
A filled honeypot silently returns 200. Rate and request-size limits apply.
See [[file:leads.org][leads]] for the embed snippet and capture responses.

Authenticated editors use =POST /api/v1/leads/:id/convert= with a JSON
object: optional =deal= boolean (default true), =company_id= and =contact_id=

roll back every new CRM record. =?stage=1= returns a 202 confirmation without

* Record actions

=POST /api/v1/:type/:id/actions/:action= takes a JSON object of parameters.
The registry checks the authenticated role and calls the declaring service.
Unknown actions answer 404, insufficient roles 403, state conflicts 409 and
invalid parameters 422, using the ordinary error JSON shape.

=?stage=1= returns 202 with an action confirmation. Approval checks the
current record, version, approver role and service eligibility again.

A type-level action (ID =0=) that declares no subject record -- a sweep, a
run, a batch -- is judged as belonging to the organization its
=organization_id= parameter names (a JSON integer; a string of digits is
accepted too). The organization access role matrix then applies exactly as
it does to a record there: a member of another organization is answered
404, and an organization editor is refused a financial type such as
=dunning_policy= or =invoice= with 403. A member who is not a global owner
or admin must name the organization; without =organization_id= the answer
is 422 =organization_id: ... runs in one organization=. Global owners,
admins and internal jobs without one keep running in the default
organization. The action then runs in the organization it was judged in,
never a different one.
=GET /api/v1/schema/:type= and the full schema include =actions= with
labels, descriptions, minimum roles, =stageable=, parameters and input schemas.
See [[file:actions.org][record actions]] for registration and signals.

The ledger also exposes =POST /api/v1/journals/post= (header plus =lines=),
including =?stage=1=. It dispatches the registered type-level
=create_and_post= action. See [[file:ledger.org][posting from the outside]].
