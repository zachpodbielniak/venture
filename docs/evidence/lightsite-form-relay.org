#+TITLE: Native Lightsite forms: definition and signed relay evidence

* Scope and reuse

Issue #173 adds authenticated discovery and a paired-daemon adapter. PR #163
already supplies published schemas, field validation, branching, response
storage and configured lead capture. PR #169 supplies durable receipts. The
new routes reuse those implementations; they do not introduce a second form
builder or a parallel lead-capture path.

* Regression evidence

Before implementation, the authenticated definition regression returned 404
instead of 200. The signed relay regression reached the old Lightsite hook,
but stored zero form responses instead of one. Both tests subsequently pass.

The expanded tests cover unpublished edits, organization isolation, bad
signatures, forged controls and origins, unknown versions, invalid choices,
retries after reopening the database, changed-answer conflicts, receipt-write
rollback and recovery, erasure, disabled sites, and a later publication adding
an unsupported upload field. The earlier ordinary version remains usable.

The authentication suite checks anonymous refusal, cross-organization refusal,
and authorized viewer access to the definition. Shared pairing regressions
continue to check the existing connection and signature boundaries.

* Built-server demonstration

On 2026-10-03, an owned SQLite instance of the actual DEBUG server was started
with authentication enabled and a synthetic owner. Through authenticated REST,
the demonstration created and published a contact/quote form, configured its
name/email lead mappings, and paired a synthetic Lightsite site. No external
provider was contacted.

Observed results:

- Anonymous definition fetch: 401.
- Authenticated definition: published name, email and message fields, labels,
  required flags, and form/version identifiers.
- Two concurrent, identically signed relay requests: two accepted replies,
  exactly one form response and one lead.
- Stored origin: the paired site's configured origin.
- Reusing the submission ID with changed answers: 409.
- Adding a browser-selected origin to the signed payload: 422.

* Integration boundary

Lightsite/libresite must render the published definition, preserve its version,
and send the documented closed envelope through the trusted daemon. The daemon
owns browser abuse controls and the stable submission ID; signing credentials
and Venture API credentials stay server-side. =relay_supported=false= directs
payments, bookings, uploads and double opt-in to the existing hosted form flow.
See [[../forms.org][the forms guide]] for the wire contract and failure semantics.
