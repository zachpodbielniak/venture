#+title: Stripe account boundary, hosted links and ACH return guards — built-artifact demonstration
#+description: Verbatim operator transcript for issue #125 (PR #130), Stripe items

This transcript runs the already-built DEBUG =venture= artifact as an operator
would: a real loopback HTTP server with a private config and state directory,
the first-run owner, two organizations, three authenticated accounts, and the
ordinary =/api/v1= and web routes. No Stripe account, bank account or live key
is involved. Every outbound destination the server could reach is pinned to a
local sink, which recorded the single attempt the server made and refused it,
so the transcript below contains proof that nothing left the machine.

* What is demonstrated

Issue #125, "Stripe account boundary — required for #124":

- "One configured Stripe account per organization. Settings show the connected
  account's safe identity, test/live environment and verification status."
  — Section A and B: each organization has its own settings page and its own
  binding; the environment/key/URL rules are enforced on the connect form.
  *Partially shown*: a connected account's displayed identity needs a verified
  account, which an offline running server cannot obtain (see LIMITATIONS).
- "Derive the Stripe account from the business record's verified organization,
  not a caller-supplied provider account or ambient default." — Sections C, E
  and F: an unverifiable account stores no binding at all; a forged
  =integration_connection= and forged =stripe_checkout= / =stripe_event= /
  =stripe_payment_link= rows are refused to generic writers; ambient
  installation =VENTURE_STRIPE_*= credentials are present in the server
  environment throughout and grant no authority anywhere.
- "Resolve webhook routing to a configured account... Shared webhook
  infrastructure must preserve this boundary." — Section F: the
  =/webhooks/stripe/:connection_id= route resolves only a configured
  connection; unknown, non-numeric and the unbound =/webhooks/stripe= endpoints
  all refuse with 503 and settle nothing. *Partially shown*: an event signed
  for organization A's connection delivered to organization B's endpoint needs
  two verified connections (see LIMITATIONS).
- "Define credential rotation, disconnect/reconnect and account replacement
  with pending payments." — *Not shown here*; see LIMITATIONS.
- "Cover two organizations with different Stripe accounts... No implicit shared
  Stripe account is supported." — Section A and D: two organizations, separate
  settings, and an administrator of the second business is refused both read
  and rotation of the first business's Stripe settings. The identical-invoice
  -number and colliding-provider-ID half needs verified connections.

Issue #125, #124 item 4 — "Specify later ACH returns/reversals and
mandate/payment-method failures, using existing refund/dispute/accounting
guards. Test closed-period and separation-of-duties behavior.":

- Section I: a settled receipt is applied, the month is closed, and a return
  dated inside the closed month is refused ("Period 'FY2026 P01' is closed for
  organization 1") with zero refund rows written. With a =pay= approval rule
  in force, the proposer's own return is refused and a pending approval is
  recorded; a distinct authenticated account repeating the exact command
  applies exactly one 30.00 USD refund and the invoice reopens as
  =partially_paid=. These are the same refund, period and whole-operation
  approval guards the Stripe return path enters; the signed
  =charge.dispute.*= entry into them is covered by the C tests named below.

Issue #125, #124 item 5 — "Define whether a hosted invoice link is a
Venture-owned resolver or a provider URL. Handle expiry/replacement, revoked
links, already-paid/deleted invoices and pending payments. Expose no arbitrary
invoice selector or sensitive data through the public link.":

- Section G: the hosted link is a Venture-owned action that refuses without
  this organization's verified account, and writes no link record.
- Section H: the public resolver =/pay/<capability>= answers a well-formed but
  unknown 101-character capability with one "Payment link is unavailable" page,
  =Cache-Control: no-store=, =Referrer-Policy: no-referrer=, and no invoice
  number or customer name; a POST carrying =invoice_id= cannot select an
  invoice, and the invoice's state is unchanged afterwards.
  *Not shown here*: creating a link and resolving it, expiry, replacement,
  revocation, already-paid/deleted invoices and a pending bank payment, all of
  which need a verified connection (see LIMITATIONS).

* Observation, not a refusal of anything the documentation promises

The two refusals in section G return HTTP 500 rather than a 4xx:
=venture_web_error_response()= maps =VENTURE_ERROR_CONFIG= to 500, which the
source already remarks on at =src/web/venture-web-server.c:17072=. The refusal
itself and its message ("Organization integration is unconfigured or
ambiguous") are correct; only the status class is coarse.

LIMITATIONS: what this transcript does NOT prove.
- No Stripe was contacted. The only outbound attempt the server made was
  captured by the local sink shown above, so no live account, bank account,
  mandate or settlement timing is exercised here.
- Venture's synthetic Stripe provider is a C StripeTransport passed to
  venture_stripe_service_new()/venture_stripe_settings_configure(); there is no
  configuration key or environment variable that injects it into a running
  server, and Venture does not expose stripe-glib's test_base_url. A running
  artifact therefore cannot hold a verified Stripe connection offline, so
  everything that needs one is shown only by the DEBUG test artifact:
  * an event signed for organization A's connection delivered to another
    endpoint, a wrong signing secret, wrong livemode, wrong account, colliding
    provider IDs across two organizations and identical local invoice numbers:
    build/debug/tests/test-stripe -p /stripe/binding-rotation,
    -p /stripe/binding-organizations, -p /stripe/binding-settings-ui,
    -p /stripe/binding-replacement, -p /stripe/binding-authorization,
    -p /stripe/binding-migration, -p /stripe/account-binding-metadata.
  * disconnect retaining historical credentials so an old connection's callbacks
    still verify while its replacement cannot borrow them:
    -p /stripe/binding-replacement.
  * rotation accepting the new signing secret and refusing the old one:
    -p /stripe/binding-rotation.
  * the hosted link lifecycle with a live capability - resolving a real token,
    the outstanding amount without the invoice number or customer, expiry,
    replacement, revocation, already-paid, deleted and changed invoices, and a
    pending bank payment that creates no second collection:
    -p /stripe/payment-link/basic, /authorization, /changed, /replacement,
    /uncertain, /deleted, /finance, /api, /paid, /processing, /form.
  * the ACH return itself arriving as a signed charge.dispute event and passing
    through the refund/dispute guards, including the closed-period and
    separation-of-duties replays:
    -p /stripe/ach/return-lost, -p /stripe/ach/return-won,
    -p /stripe/ach/return-closed-period, -p /stripe/ach/return-sod,
    -p /stripe/ach/sod, -p /stripe/ach/closed-period.
- Sections H and I demonstrate the public resolver and the refund, period and
  approval guards the Stripe return path reuses, driven through the ordinary
  HTTP API rather than through a signed provider event.
- SQLite only, one process, synthetic organizations, customers and money.
