#+title: Call logging and follow-up demonstration (#122)

* Built artifact and scope

This is a synthetic application demonstration of issue #125's =#122 — Call
logging and follow-up= checklist, run against an already-built DEBUG =venture=
binary. It builds nothing. The driver starts that artifact on an OS-chosen
loopback port with its own private YAML config, state directory and throwaway
SQLite database, bootstraps the first-run owner, and drives the documented
=log_call= surfaces — the REST record-action route, the generated =/e/= pages
and =venturectl act= — exactly as an operator would. No provider, telephony
connection, webhook or recording download exists or was contacted, and no
recording address was fetched.

* What this does not prove

The LIMITATIONS block above is part of the run's own output. In addition:

- Only the owner role in a single organization was exercised. Read-only role
  refusal, cross-organization isolation of recordings and transcripts, and the
  staged =?stage=1= confirmation and stale-approval path are covered by
  =test-activities=, not by this transcript.
- Retention is a documented policy in [[file:../activities.org][activities]] ("no automatic expiry";
  soft deletion hides but retains); nothing here exercises a retention sweep,
  because none is claimed to exist.
- The reminder sweep that delivers the follow-up's =remind_at= notification was
  not run; only the stamped reminder time is shown.
- Atomicity is observed from the outside: refused requests left no rows. The
  internal rollback after a partial write is =test-activities='s
  =call-followup-rollback= case.
- SQLite only, one process, one run. PostgreSQL and migration =000490= are
  covered by the suite when the PostgreSQL URIs are set; neither ran here.
