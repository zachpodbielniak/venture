#+title: Issue 125 — authenticated attribution and marketing walkthrough

* Scope and reproduction

This is a synthetic, local SQLite walkthrough of the actual DEBUG server,
using authenticated owner routes for configuration and CRM/accounting work and
separate anonymous clients for site capabilities and signed capture. It sends
no mail and contacts no provider or Lightsite installation. It neither provisions
Lightsite nor certifies hosted networking or a production deployment.

From the repository root:

#+begin_src sh
PKG_CONFIG_PATH=/tmp/venture-125-ocr-sdk make DEBUG=1 venture
PYTHONDONTWRITEBYTECODE=1 python3 tools/venture-attribution-server-drill.py --binary build/debug/venture
#+end_src

The SDK path above belongs to this verification environment; another developer
uses their installed build dependencies. The driver requires Python 3's standard
library. It creates an owned private directory (umask 077), synthetic credentials
and integration key, two server lifetimes, and a fresh SQLite database. It binds
loopback on an available port. Successful cleanup removes only its own directory;
failure preserves that directory and server log as private diagnostic evidence.
Credentials, visitor capabilities and HMAC values are never printed. The binary
fingerprint is checked before and after. Running with Python -O refuses before
fixture creation because acceptance assertions must remain enabled.

server stop/restart, retrying the exact original timestamp/body/signature retains
all business and submission IDs and the complete withdrawn consent/suppression
rows; it neither re-consents the address nor duplicates the receipt.

* Date defect and repair evidence

The initial ordinary-date walkthrough failed: a same-day invoice stored at UTC
midnight appeared older than its afternoon acquisition binding and was attributed
to unknown. The focused regression failed against the original implementation:

#+begin_example
/attribution/financial-calendar-dates
assertion failed (venture_money_get_amount(money) == expected): (6000 == 26000)
exit status 134
#+end_example

The repaired rule uses retained event/sale creation evidence only for exact UTC
midnight calendar dates on the acquisition day in the current configured report
timezone. Controlled Los Angeles and Tokyo boundary cases also verify that
UTC date differences cannot reject a legitimate acquisition or accept a
preexisting same-day row. It does not invent an intraday
transaction timestamp. The regression expects attributed invoices 26000 and cash
10500 cents, versus unknown invoices 12000 and cash 5500 cents. It covers a
same-day row already retained before conversion, an earlier calendar day, a
precise timestamp before conversion, and a precise timestamp after conversion.
Earlier evidence remains unknown; period dates and ledger dates do not change.
See [[file:../attribution.org][the attribution contract]].

all report call sites, and reviewed ownership, documentation and assertions. It
strengthened replay verification from identity counts to complete retained email

This walkthrough uses one synthetic touch, so first and last intentionally agree;
the separate attribution model tests cover differing touches. PostgreSQL coverage
is through schema-isolated GTests, not this SQLite server driver. Actual outbound
email delivery, provider callbacks, browser JavaScript execution and hosted
cross-origin routing are outside this demonstration. The ordinary DEBUG test
suite supplies additional subsystem regressions; this evidence does not replace
the combined PR verification or final review.
