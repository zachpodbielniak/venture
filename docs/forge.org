* What this is

VENTURE's tickets describe work. This connects that work to the code it is about: a ticket can name a repository on a git forge, carry the branch the work is on and the issue it corresponds to upstream, and — where you have opted in — be picked up by an AI agent that does the work on its own branch and opens a draft pull request.

Forgejo is the forge that is implemented. Gitea works through the same client, because their API v1 is the same interface. GitHub and GitLab are declared so the form can express what you actually have, and are refused with a clear message rather than attempted.

* The four concepts

| Record        | What it is                                                              |
|---------------+-------------------------------------------------------------------------|
| =forge=       | an organization-owned server identity; encrypted credentials live in its integration binding |
| =forge_repo=  | one repository on that server, as =owner/repo=                           |
| =forge_rule=  | what may happen automatically, per repository and per issue type         |
| =forge_run=   | one attempt by a runner at one ticket: what it did, what it cost, why it stopped |

A fifth, =ticket_link=, joins a ticket to a repository and carries the issue number, the branch and the pull request. It is one record rather than three fields on the ticket because a ticket can be worked in two repositories at once — a fix in the library and a version bump in the application — and because it is exactly the row the webhook loop guards read.

* Issue types

Tickets gained an *issue type*: =epic=, =story=, =task=, =subtask=, =research= or =bug=.

This is a different question from the ticket's *kind*, and the two are deliberately separate fields.

- *Kind* says whose problem it is — your own project work, or somebody else's support request. It is what decides who may read the replies, and it drives whether a comment is internal.
- *Issue type* says what shape the work is, and therefore how it should be approached. A bug wants a reproduction and a regression test; an epic wants breaking up and no code at all.

They are orthogonal. An external bug is both, and common. The forge rules key on the issue type.

The board at =/tickets= filters on both at once, so "external bugs" — the pair most worth looking at — is a click. Each control preserves the others, and the list view keeps whatever the board had.

Existing tickets all read as =task=, because that is what they were. The enumeration's first value is load-bearing for that reason: reordering it would silently retype every historical ticket.

* Connecting a forge

** Create the access token in Forgejo

Settings → Applications → Generate New Token. It needs:

- =read:repository= and =write:repository= — to look repositories up and create branches
- =write:issue= — to file issues, comment, and open pull requests

Give it nothing else. The token is the only credential VENTURE holds for that server, and its scope is the ceiling on what any rule can do.

** Add the forge

A forge origin is unique within its organization. Two legal organizations may
configure the same server independently. Startup reconciles the old global
constraint from field metadata, retaining forge IDs, credentials and repository
references; this schema change does not migrate credentials into the vault.


=/e/forge= → New. Name it whatever you call the server, choose Forgejo or Gitea, and give the base URL — the origin only, =https://git.example.com=, with no =/api/v1=.

*Clone base* is separate, and usually needs setting. The API and git rarely live on the same host once a reverse proxy is involved: the proxy speaks HTTP, sshd does not. A typical pair looks like

| Base URL   | =https://git.podbielniak.com=      |
| Clone base | =git@git-ssh.podbielniak.com=      |

Two shapes are accepted, and the difference matters:

- =git@host= — an account and no scheme — composes the scp-like =git@host:owner/repo.git=. The separator is a colon; =git@host/owner/repo.git= is read by git as a path, not a host.
- Anything with a scheme composes =<base>/owner/repo.git=, so =https://git.example.com= and =ssh://git@host= both work.

Leave it empty and the base URL is used, which is right when one host serves both.

A repository's page carries an *Open* panel built from these two: a link to the repository on the forge, composed from the base URL, and the =git clone= command, composed from the clone base. The command is shown as selectable text as well as offered as a copy button — the clipboard API needs a secure context, and over plain http on a LAN address it is simply not there.

A ticket with a branch gets the same treatment: the branch name links to it on the forge, and copies either as a bare name or as a =git switch= command.

A repository can also carry its own *Clone URL*, used exactly as given. That is for the one repository that does not follow its forge's pattern — a mirror, or a path a proxy rewrites — so that discovering it later does not mean a second forge record differing in one field.

On the forge's page, open *Organization forge credentials*. The settings
form derives its fields from the adapter schema and always leaves credential
inputs blank. Configure the installation's integration master key first; see
[[file:integrations.org][integration credentials]] and
[[file:integration-key-maintenance.org][offline key maintenance]]. Select an explicit organization
when creating the forge; organization zero cannot carry provider credentials.

Connect supplies an access token and a webhook secret of at least 32 bytes.
VENTURE asks the selected Forgejo/Gitea API which account the token identifies,
then encrypts both credentials under this organization's per-forge binding.
The API URL must use HTTPS; HTTP is accepted only on literal loopback for fixtures.
The secret must also be installed in that forge's webhook settings. VENTURE never
reads installation environment variables as a forge credential fallback.

The same operation contract is available through JSON on stdin:

#+begin_src sh
venturectl forge settings 1 < protected-forge-settings.json
#+end_src

The protected input file contains an operation, the exact connection ID and
version last returned, and the settings object. For a first connection:

#+begin_src json
{"operation":"configure","connection_id":0,"version":0,"settings":{"token":"SUPPLY_PRIVATELY","webhook_secret":"SUPPLY_AT_LEAST_32_RANDOM_BYTES_PRIVATELY"}}
#+end_src

The response contains only forge ID, connection ID, version and connected state.
Never put secrets in command arguments. Rotate by sending both credentials again
with the current connection ID and version. Rotation preserves the verified
account and API origin; changing either requires *Disconnect* followed by a new
connection. A stale form naming an old connection cannot rotate its replacement.
*Test account* performs an authenticated read with the exact displayed binding.
*Disconnect* disables it and revokes active credential snapshots. Retained
ciphertext remains part of the encrypted backup/key-retention contract.

For test/disconnect, send the same connection identity without a settings object:

#+begin_src json
{"operation":"test","connection_id":12,"version":1}
#+end_src

*Import legacy credentials* is explicit: it verifies the old token, creates the
encrypted binding and clears both plaintext fields in one independent audited
transaction. Any failure rolls back both parts. Existing backups may still carry
plaintext and require the operator's retention/rotation decision. Generic record
writes cannot set or clear those legacy fields. Old =forge set-token= and
=forge set-secret= endpoints authenticate then refuse with migration guidance;
there is no implicit plaintext fallback. =forge verify= uses the encrypted
binding and records the answer on the forge record as =bot-username= and
=verified-at=; those are display stamps, so verifying while a coding run is
live or a webhook is being applied does not revoke the credential lease behind
them. =forge settings= is the complete setup/rotation workflow.

Forge configuration and coding execution are host capabilities. Settings remain
platform-owner/admin operations even though credentials belong to an organization.
Organization membership alone does not authorize arbitrary network origins or a
coding runner. Hosted integration must classify these routes as PLATFORM.

** Add a repository

=/e/forge_repo= → New. The name is =owner/repo= exactly as the forge spells it — that is what a webhook payload carries and what you copy out of the address bar.

Set *Venture* to the business the code belongs to. This is what scopes a webhook-created ticket to the right organisation: a webhook carries no session, so without it a ticket would land in the default organisation and then be invisible on a board filtered to a specific entity.

Two switches decide direction:

- *File issues upstream* — linking a ticket here opens a forge issue for it.
- *Accept issues from upstream* — a webhook issue becomes a ticket.

* Rules

A rule answers: for this repository, and this kind of issue, what may happen without me?

** Resolution order

Most specific first:

1. the repository's rule for this issue type
2. the repository's catch-all (=All issue types= on)
3. the forge-wide rule for this issue type (a rule with a forge but no repository)
4. the forge-wide catch-all
5. nothing

*Nothing is a legitimate answer.* A repository nobody enrolled does not acquire an AI because a rule elsewhere was written generously.

Two things surprise people, so they are worth stating:

- A rule that is *not enabled* is skipped and the search continues past it. Switching a rule off falls through to whatever broader rule exists.
- To suppress work for one repository, create a rule that *is* enabled with the AI switched off. That stops the search at that repository.
- A rule with neither a repository nor a forge matches nothing at all. A row saved half-filled that applied everywhere is the failure that costs money.

Two rules with identical scope resolve to the lower id, every time, and log a warning naming both. Deterministic beats clever: the same ticket behaving differently on consecutive runs is far harder to diagnose than a consistent wrong answer.

** Outcomes

| Outcome        | What happens                                    |
|----------------+-------------------------------------------------|
| =draft_pr=     | commit, push the branch, open a *draft* pull request |
| =push_branch=  | commit and push the branch, and stop            |
| =local_branch= | commit in the checkout and stop                 |
| =none=         | change nothing anywhere                         |

Nothing here ever merges. A draft pull request is a place to look at the work, which is the point.

** Runners

| Runner  | Can edit | Can run your tests | Needs                        |
|---------+----------+--------------------+------------------------------|
| =agent= | yes      | *no*               | nothing beyond a model key   |
| =cli=   | yes      | yes                | =claude-code=, =opencode= or =grok-build= on the host |

The in-process =agent= runner uses file tools VENTURE wrote, confined to the run's checkout: every path is canonicalised and anything resolving outside is refused. It has *no shell*, and that is the honest cost of running inside the server's own process — ai-glib's built-in tools accept absolute paths unchanged and its =bash= tool is a shell with the server's uid and the server's environment, which is one =env= away from every provider key and the session secret.

The =cli= runner spawns a coding CLI in the checkout. It can do both because it is a separate process with its own permission model, and the command it may spawn has to appear in =forge.cli_allowed_commands=. That list is not optional: a rule names its command, a rule is editable by anybody who can edit rules, and without the list that is arbitrary command execution with a longer fuse than the shell tool the assistant is denied.

* The webhook

=POST /hooks/forge/<id>= intentionally does not require a session. It authenticates by verifying an HMAC-SHA256 over the request body against the exact active encrypted binding's webhook secret.

Three things about it are deliberate:

- A forge with *no secret set is refused outright*, not trusted. An unconfigured forge would otherwise be an unauthenticated endpoint that creates records and can start an AI run.
- An absent signature is a rejection, not "nothing to check".
- The comparison is constant time. A check that returns as soon as two bytes differ leaks the digest to anybody who can measure the reply, and this endpoint is by definition reachable by whoever is guessing.

** Setting it up in Forgejo

Repository → Settings → Webhooks → Add Webhook → Forgejo.

- *Target URL*: the address shown on the forge's page in VENTURE.
- *Secret*: the one you set or generated.
- *Trigger*: Issues, and Issue Comment if you want comments to come across. With the [[file:factory.org][factory]] module on, add Workflow Run to record every CI run as a build, and Release to record releases cut on the forge.

Anything else you send is acknowledged and ignored rather than rejected, because a forge disables a webhook that keeps erroring.

** Loops

VENTURE files an issue; the forge delivers a webhook for it; without care that becomes a second ticket for the issue VENTURE just created. Three guards:

1. *The sender is VENTURE's own account.* The account is the login the forge answered with when the binding was configured, stored as the binding's verified =account-id= and read from there on every delivery; it is not the forge record's =bot-username=. Exact, needs no stored state on the ticket side, and works in the window before the link row has the issue number written back.
2. *The delivery has already been applied.* A forge retries a delivery it thinks failed, and a retry that re-applied its payload would reopen a ticket somebody had just closed.
3. *The edit changes nothing.* Compared before the write, not after — a save with an empty diff reports success without writing, so "did anything change" is not available as a signal afterwards.

A closed issue closes the ticket. An open one does *not* reopen it: somebody moved that ticket into review deliberately, and the forge does not get to move it back.

* Three worked configurations

** 1. Link only

The safe starting point. Repositories and branches tracked by hand, no AI, no webhook.

#+begin_src yaml
forge:
  enabled: true
  webhooks_enabled: false
  runs_enabled: false
#+end_src

Add a forge and a repository, set =File issues upstream= on, leave =Accept issues from upstream= off, and create no rules. Ticket pages gain a Code panel with *File upstream* and *Create the branch*.

From the command line:

#+begin_src bash
venturectl create forge name="Home" kind=forgejo \
    base_url=https://git.example.com \
    clone_base_url=git@git-ssh.example.com
venturectl create forge_repo name=zach/venture forge_id=1 default_branch=master \
    branch_prefix=venture/ push_issues=true active=true
#+end_src

Connect encrypted credentials through the forge settings page or =venturectl forge settings=. Generic record CRUD never accepts secrets.

** 2. Bugs worked automatically

One forge-wide rule. Every bug on every repository of that forge gets an agent and a draft pull request; everything else is untouched.

#+begin_src yaml
forge:
  enabled: true
  webhooks_enabled: true
  runs_enabled: true
  run_concurrency: 1
  run_timeout: 1800
#+end_src

#+begin_src bash
venturectl create forge_rule name="Bugs, anywhere" forge_id=1 \
    issue_type=bug all_issue_types=false enabled=true \
    runner=agent outcome=draft_pr trigger=on_create \
    max_turns=30 max_runs_per_day=10 \
    prompt="Reproduce the bug first, then fix it. Add the test that would have caught it."
#+end_src

=max_runs_per_day= is the runaway guard. A webhook that fires on every comment, a rule that opens a draft pull request each time, and a model that comments back is a loop with a monthly invoice attached.

** 3. One repository held to a stricter standard

The forge-wide rule above, plus a narrower one on the repository that matters, showing precedence at work.

#+begin_src bash
venturectl create forge_rule name="Bugs in venture itself" repo_id=1 \
    issue_type=bug all_issue_types=false enabled=true \
    runner=cli runner_command=claude outcome=push_branch \
    require_approval=true max_turns=60
#+end_src

A bug on repository 1 now resolves to this rule — CLI runner, no pull request, and a person has to start it. A bug anywhere else on the forge still gets rule 2.

#+begin_src yaml
forge:
  cli_allowed_commands:
    - "claude"
#+end_src

Without that list entry the rule refuses to run, which is the intended behaviour rather than an obstacle.

* What the assistant can and cannot reach

The chat assistant cannot see =forge= records at all. Its own tools refuse the type: a forge row exists to hold a credential and to name the host that credential is sent to, and listing them would tell it exactly where this install's code lives.

It also cannot write =forge_rule= or =forge_run=. A model able to edit the rule governing it can widen its own authority, and unlike a staged record change that widening applies to every future run rather than to one row. Run records are refused writes for everybody, like the audit log: a run record is evidence.

A coding agent is a separate thing from the chat assistant, on a separate executor, in a separate directory, with no access to the database at all.

* Troubleshooting

- *"That forge rejected this install's access token"* — the token is wrong, expired, or was revoked. Rotate both credentials in the forge settings page.
- *"The access token is not allowed to …"* — the token exists but lacks a scope. Check =write:issue= for filing and commenting, =write:repository= for branches.
- *A webhook does nothing.* Check the secret matches, that the repository has =Accept issues from upstream= on, and that the repository's name in VENTURE matches =owner/repo= exactly. Forgejo's own delivery log shows the response VENTURE gave.
- *A webhook creates nothing and the delivery shows 401.* The exact active binding is missing, inactive, revoked or signed with a different secret. Configure or rotate explicitly; plaintext is never a fallback.
- *Tickets appear but not on the board.* The repository has no Venture set, so its tickets landed in the default organisation. Set it and move them.
- *"Coding runs are turned off in settings"* — =forge.runs_enabled= is false, which is the default.
- *A run fails immediately with a git error* — =git= is missing from the runtime image, or the clone URL is not reachable from the server. Check the clone base: cloning from the API host is the usual mistake, and it fails minutes into a run rather than when you saved the forge.
- *An SSH clone hangs or is refused* — the server needs a key the forge accepts, and =GIT_TERMINAL_PROMPT= is off so git fails rather than waiting for a passphrase. In a container that means mounting a key and a =known_hosts=. An HTTPS clone base on the approved forge authority uses the bound access token, passed to git through an askpass helper so it never reaches the command line or =.git/config=.
- *A CLI run refuses to start* — the command is not in =forge.cli_allowed_commands=, or the binary is not in the image. See [[file:containers.org][Containers]].
- *A run says =interrupted=* — the server stopped while it was going. Nothing is resumed automatically, because nobody observed how far it got. Start a new one when you have looked at the branch.

* Where things run

A coding run takes minutes. Everything else in VENTURE takes milliseconds on one main loop, so runs get the only background thread in the program — with its own main context, and a rule that it never touches the database. Progress crosses back as plain data and is written to the run record on the main thread.

Forge API calls are *not* on that thread: they happen inside the request that asked for them, bounded by =forge.request_timeout=. That is the same shape as the AI chat route and the invoice actions, and it is why the timeout is worth keeping short.

* Credential lifetime, cloning and uncertain outcomes

Provider clients resolve their organization, forge origin/kind, account and binding
version on the main thread. They retain immutable credential snapshots with a
thread-safe cancellable. Main-thread changes to the binding, forge or organization
revoke the snapshot, conservatively even if a surrounding transaction rolls back.
An authenticated operation also snapshots its initiating user/token identity.
Changes or removal of that user's identity, token or organization membership
revoke its in-flight credential capability before another worker git operation;
a running subprocess receives cancellation. Membership reassignment checks both
old and new subjects. Login and token activity timestamps alone do not revoke.
Other edits conservatively require starting a new operation, including edits
that later roll back. This protects clone/push as well as the separate AI
provider's request checks; it does not undo an external operation already accepted.
A worker never reads the database. New run records retain the exact connection
ID and credential version; historical runs remain explicitly unknown (zero),
without invented credential backfills. Callbacks and publishing revalidate retained
versions on the main thread before applying results; webhook record application
runs inside a transaction and rolls back if its credential identity changed.
Disconnect/rotation do not make an already transmitted remote effect disappear;
an interrupted external outcome requires reconciliation rather than blind retry.

HTTPS cloning may send credentials only to the configured forge authority. Other
clone hosts require explicit SSH/key-agent transport, which receives no token.
The owned git launcher refuses redirects and recursive submodules, disables
credential helpers and repository hooks, and limits askpass answers to the
approved HTTPS authority. Tokens are present only in the environment of an owned
network git operation, never its arguments, remote URL or checkout files.
Cancellation terminates that git process group. The runner is still a trusted
host capability: these controls do not sandbox an arbitrary coding CLI or isolate
same-user processes from each other's memory/environment.

Low-level =venture_forgejo_client_new()= retains explicit-token construction for
transport fixtures and trusted adapters. The old record-only
=venture_forge_client_for_forge()= always refuses. Application callers must use
=venture_forge_client_for_database()= and retain its credential identity through
completion. This follows the installation's single-process workspace lease;
external SQL writes are maintenance, not a live credential-control channel.

The credential helper is created beside the checkout, never inside it: git
refuses to clone into a nonempty directory. It is removed after every run,
including failed runs whose checkout is retained. Worker completion is applied
on the main context only after cleanup, so the final service release cannot
join its own worker or race fixture/workspace teardown.
