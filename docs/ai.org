* AI

The AI is a participant, not a bolt-on. It reads the same repository the web
UI and the CLI use — same validation, same concurrency checks, same soft
deletion, same audit trail. What differs is authority.

* Setup

#+begin_src yaml
ai:
  enabled: true
  provider: "claude"          # claude openai gemini grok ollama claude-code opencode
  model: "claude-sonnet-5"
  policy: "confirm_writes"    # read_only | confirm_writes | autonomous
#+end_src

The key comes from the provider's conventional environment variable
(=ANTHROPIC_API_KEY=, =OPENAI_API_KEY=, ...) or from whichever variable
=ai.api_key_env= names. It never lives in the configuration file.

With no key the server still runs; the AI panel says AI is not configured
rather than silently doing nothing.

* The panel

The assistant lives in a floating launcher at the bottom right of every
page. Clicking it — or =Ctrl+/= — slides a panel in from the right; =Esc= or
its close button hides it again. The panel overlays the page rather than
reflowing it, so opening the assistant never disturbs the table you were
reading.

** It knows what you are looking at

Every question carries the page it was asked from. On a record page the model is told the record — its type, id, name and the fields a person would read — ahead of the question, so "summarise this", "draft a reply" and "what should happen next" mean the thing on the screen. On any other page it is told the page: the inbox, the ticket board, a dashboard, a report. The same permission check the page itself made is made again, since the path arrives from the browser.

This rides on the turn only. The stored transcript keeps one line, =[While viewing /e/ticket/12]=, when the question was asked from a record page, so it still makes sense read back a month later; a list or a dashboard leaves no trace.

** Starters

While a conversation is empty the panel offers a few questions for the page: a ticket wants summarising and answering, the inbox wants triage, the home page wants "what needs my attention today", and every page offers "what can you do, and what needs my approval". Clicking one sends it, with the page as context. They make way for the conversation once there is one.

** The harness

The composer is a harness in ai-glib's sense, the same one =ai-tui= drives in a terminal: a resource registry that finds command files, a command set that resolves a typed line against them, and a completion context that answers "what could this be" for the text at the cursor. What differs here is the front end — a panel rather than a terminal — and what an =@= names.

Three sigils, each answering a different question you have mid-sentence:

| =/command= | what can I ask for?  | commands, from here and from disk |
| =@record=  | which one do I mean? | a ticket, a release, an incident  |
| =#base=    | what should it read? | a knowledge base                  |

A menu opens as you type. Arrows move, =Enter= or =Tab= picks, =Escape= closes. The *Harness* page in the sidebar lists everything the composer knows and where each piece came from, which is how you answer "why does =/release= do that" — the answer is nearly always two files of the same name, one shadowing the other.

*** Commands

Eight are built in: =/summarise=, =/reply=, =/triage=, =/next=, =/standup=, =/weekly=, =/explain=, =/chase=. They lean on the page context every question carries, so =/summarise= on a ticket means that ticket.

Your own are =ai_skill= records — name, trigger, one-line description, prompt, enabled — reachable from the *Harness* page, the API and =venturectl=. In a prompt, ={input}= is replaced by whatever follows the trigger; without it the input is appended as instructions. A record whose trigger matches a built-in replaces it, which is how a house style overrides the stock wording. A disabled record is invisible.

Beyond those, the harness reads the directories every other agent tool already uses: =~/.claude/commands=, =~/.config/ai-glib/commands=, =.agents/skills= and their project-local equivalents. A markdown file with a =description= in its frontmatter is a slash command; =$ARGUMENTS= in the body takes what follows the trigger, and a body without it still takes them, appended as instructions. Commands an operator wrote for a terminal agent are not written again here. Precedence is: this install's skills, then project files, then your home directory.

A command body's =!`cmd`= shell escape is *never* run. ai-glib requires a file to opt in with =shell: true=; this turns it off outright, because those directories are shared with every other tool on the machine and this process answers a network port.

The menu also lists the panel's own commands — =/new=, =/threads=, =/export=, =/close=, =/help= — which run at once and never reach the model.

*** Naming a record

Type =@= and the menu offers the record types you may read; type past the slash and it searches that type. =@ticket/12=, =@release/4=, =@incident/2=. The record's fields go to the model ahead of the question, the same rendering the page context uses, so a conversation about the software factory can name what it is about instead of describing it.

The text is left alone: you wrote =@ticket/12= and the transcript says so a month later. Naming the same record twice in one question reads it once. A type you may not open is not offered and not read — the harness asks the web layer, which is where that policy lives.

*** Naming a knowledge base

Type =#= and the menu lists the knowledge bases you may read, by slug. The passages retrieved from that base ride ahead of the question. The menu opens for a =#= at the start of a word only, so "C#" and "issue#3" leave it shut — and a =/= opens the command menu only at the very start of the composer, so a date or a path does not.

** The composer

- =Enter= sends; =Shift+Enter= is a new line.
- =Up= in an empty box recalls the last question, to fix a word and send it again.
- A half-typed question survives a click on a link: the draft is kept in the browser until it is sent.
- One question at a time. While an answer is on its way a second send is held with a note rather than interleaving two replies; a reply that never arrives releases the box after three minutes.
- Slash commands, none of which reach the model: =/new=, =/threads=, =/export=, =/close=, =/help=.

** Replies arrive as they are written

An answer is streamed. The panel shows an empty bubble the moment you send, and the model's prose fills it in a word at a time, with a caret at the end so a pause reads as thinking rather than as a hang. While the model is off calling a tool — reading a record, running a report — the bubble says which one instead of sitting silent, which is the difference between a slow answer and an interface that looks stuck.

It is two requests. The =POST= stores the question, works out what the model will be shown — the replayed history, the attachments, the page you are on — and parks it behind a one-shot token; a =GET= on =/ui/chat/stream/<token>= holds a connection open and answers it. The token is spent on use, expires after two minutes, and belongs to the person who asked: anyone else's is indistinguishable from one that never existed. Nothing about the conversation travels in the URL.

When the turn finishes, the whole reply — rendered the way a stored one is, with its markdown, its links and its approval cards — replaces everything the deltas painted. That is deliberate rather than wasteful: markdown cannot be formatted a fragment at a time, and a turn that called a tool halfway through says things before it that are not part of the answer.

Closing the tab does not cancel the turn. The model is already working and the answer is stored either way, so reopening the conversation finds it.

*One at a time.* A turn holds the executor, the streaming flag and the prompt that an audit entry will be stamped with, all of which are single slots. A second question while one is in flight is refused with "the assistant is answering another question" and the *Try again* button, rather than queued behind a wait with nothing to show or — worse — interleaved into the same transcript. The composer already holds one send at a time per browser, so this is only reachable from two tabs or two people.

*Degrading.* A provider that cannot stream still answers; it simply says nothing until the answer is whole. A browser without =EventSource=, or a form posted with scripting off, takes the blocking path instead — the same one the CLI and the API take — and the reply arrives in one piece. The client asks for a stream per send rather than once, so a page rendered before the script ran never claims a capability the browser lacks.

** Replies

The model's markdown is rendered — paragraphs, lists, bold, inline code — and never interpreted: everything it says is escaped first and formatted after, so a reply cannot carry markup into the page. Fenced code blocks come through whole, with nothing inside them treated as formatting. A markdown link becomes a link only to an =http(s)= URL or a local path; anything else stays text. A =>= line is a quote.

Every reply has a *Copy* button on hover, which copies the text as shown. A provider failure is shown as a notice with a *Try again* button: the question was stored, and a retry sends it once more. When a reply lands while the panel is closed, the launcher lights up and a toast says so.

** Conversations persist

Every exchange is stored as ordinary records — a =chat_thread= and its
=chat_message= rows — through the same repository as everything else. That
buys three things at once:

- *Resume.* The panel remembers which conversation was active (the thread id
  lives in =localStorage=; the transcript lives on the server) and replays it
  on the next page load, the next day, or another machine.
- *History.* When a thread continues, the model is shown the whole stored
  transcript before the new question, so "and the fees on that?" means
  something. Earlier tool exchanges are deliberately not replayed — a tool
  result is a snapshot, and the model re-reads rather than trusting one.
- *A record.* What you asked the thing with write access to your books is
  itself worth keeping.

The ☰ button lists previous conversations, newest activity first; =+= starts a fresh one; each row has a rename (✎) and a delete button, and deletion is soft like every other delete here. Past a handful of conversations the list gets a filter box. The ⤓ button — or =/export= — downloads the active conversation as an org file: the title, when it started, and each turn as a heading, the bodies verbatim.

A long conversation is replayed to the model from its tail: the newest messages up to about forty thousand characters and never more than sixty. The stored transcript keeps everything; what the model is shown is the part that costs and can overflow a context window, and cutting it at a message boundary beats the provider refusing the one question that happened to be too many.

** Attachments

The paperclip attaches files to a message — PDFs, plain text, CSV, JSON,
YAML, org. Each upload immediately becomes an ordinary =document= record:
the file itself lands under the state directory, and its text — extracted
by poppler for PDFs, taken verbatim for text — is stored on the record's
=extracted-text= field, which also makes every filed invoice full-text
searchable.

The model sees the extracted text inline in the message it arrives with;
the stored transcript keeps only a one-line reference naming the document.
A resumed conversation does not replay kilobytes of invoice into every
turn — the model re-reads the document with =venture_get= when it needs
it.

The intended loop: attach an invoice, say "book this". The system prompt
tells the model to pull the date, amount, currency and counterparty out of
the attachment and stage the matching expense with the document id in the
memo — staged, so the figures it read are shown to you as a diff before
anything is written.

A chip marked /no text/ means extraction found nothing (a scanned image
PDF, a binary format): the file is stored all the same, but the model
cannot read its contents. There is no OCR.

** Screenshots

PNG, JPEG, WebP and GIF attachments are handed to the model *as images*,
not as extracted text — so a vision-capable model reads the picture. Paste
one straight into the composer: a screen capture lands on the clipboard,
and making you save it to a file first was a step worth deleting. Chips for
images show a thumbnail rather than a /no text/ warning.

The use this was built for: screenshot an advertising dashboard — Amazon
Ads, Etsy, Meta — say "file this", and the campaign is staged with the
figures read off the image. The system prompt tells the model to read every
value it can (name, status, budget, spend, impressions, clicks,
conversions, dates), stage *one record per campaign shown*, and search
first so re-uploading next week's screenshot updates the campaign rather
than duplicating it. It is also told never to guess a figure it cannot
read: a blank spend column is recoverable, an invented one is not.

Whether a model reads every field is a property of the model, not of
VENTURE. Check the staged values before approving — that is what the card
is for.

Images ride on the turn they are attached to. The stored transcript names
the documents instead, so a long conversation does not re-send every
screenshot with every later question.

Providers: images reach Claude as Anthropic image blocks and OpenAI, Grok
and other Chat Completions providers as =image_url= parts. Ollama has no
image path in ai-glib yet, so a local model will not see attachments.

* Approving a staged change

Staged writes appear in the panel as a card: what will change, field by
field, with *Apply* and *Discard*. Money renders as money and the identity
spine is left out, because an approval nobody reads is the same as no
approval at all.

Cards for changes still waiting reappear when the conversation is resumed,
so a staged change is never stranded by closing the panel. Restaging an
identical change — models do retry when a tool answers /awaiting_approval/
rather than /ok/ — updates the existing card instead of adding a second:
three cards for one campaign would mean approving all three creates three
records.

Uploads require the editor role, are capped at 15 MB, and the attachment
text offered to the model is capped per file — the tail of a very long
document is a =venture_get= away rather than silently absent.

** Who can read a conversation

The thread's owner, and nobody else. The chat routes refuse to serve a
thread whose =user-id= is not the caller's — reporting /not found/ rather
than /forbidden/, so sequential thread ids confirm nothing. The generic
=/e/chat_thread= and =/api/v1/chat_message= surfaces are owner-only: an
editor must not be able to read what a colleague has been asking about the
books by walking around the chat routes. =tests/test-auth.c= pins both
properties.

* Tools

| Tool                  | Authority                                    |
|-----------------------+----------------------------------------------|
| =venture_list_types=  | read — the record types and their fields     |
| =venture_query=       | read — filtered records                      |
| =venture_get=         | read — one record, whole                     |
| =venture_count=       | read — exact counts, uncapped                |
| =venture_search=      | read — free text across every type at once   |
| =venture_fetch_url=   | read — a public web page, as text            |
| =venture_report=      | read — any report                            |
| =venture_links=       | read — every link touching a record          |
| =venture_dashboard=   | read — a dashboard, every widget evaluated; or the list of them |
| =venture_factory=     | read for status; changelog staged unless autonomous; publish only when autonomous |
| =venture_inbox=       | read — the operator's own inbox; marking read is theirs to do |
| =venture_runs=        | read — the coding runs with cost, and the agent budgets |
| =venture_desk= (triage, summarise, draft) | read — judgements about a ticket's text, on the toolless path |
| =venture_desk=        | read for sla, activity, sprints; worklog staged unless autonomous; macro, fix_ticket and bulk only when autonomous |
| =venture_dashboard_build= | only when autonomous — a whole page cannot be staged   |
| =venture_link=        | staged unless the policy is autonomous       |
| =venture_create=      | staged unless the policy is autonomous       |
| =venture_update=      | staged unless the policy is autonomous       |
| =venture_delete=      | always staged, whatever the policy           |

Under =read_only= the mutating tools are not registered at all, rather than
registered and refused. A model cannot misuse a capability it was never told
about, and refusing calls it believes it has just wastes turns.

** Filling a record from a link

Give the assistant a URL — a product listing, a marketplace page — and
=venture_fetch_url= returns its readable text for the same
read-then-stage treatment a screenshot gets. Naming another record works
too: "add it under my Wrenmouth Press venture" makes the model resolve the
name with =venture_search= and set =venture_id=, because an unattached
record is missing from every report that groups by venture.

The fetcher is deliberately narrow, because the model picks the address
and the pages it reads can suggest the next one:

- http and https only — =file://= would read the server's own disk
- the host is resolved first and refused if *any* of its addresses is
  loopback, link-local, site-local, multicast or carrier-grade NAT, so a
  fetch cannot reach the cloud metadata endpoint, the database port on the
  container network, or a router's admin page
- capped in size and time, and non-text content types are refused
- the result is labelled untrusted, and the model is told to take field
  values from it and never instructions

=tests/test-plugin.c= pins the refusals directly rather than through a
conversation: a model may decline such a URL on its own, which looks like
the check working and proves nothing about the check.

** What no tool reaches

Accounts, API tokens and chat history are invisible to the model: absent
from =venture_list_types=, refused by every read tool, refused by every
write tool. The sensitive-field mechanism is not enough there — it hides
the password hash, not the fact that an account named alice exists or what
she has been asking the assistant about the books.

There is no shell, no filesystem and no code execution. ai-glib's tool
executor ships with =bash=, =read=, =write= and =edit= pre-registered, and
its =unregister= does not remove built-ins; VENTURE therefore builds its
executor with =ai_tool_executor_new_empty()= and registers only the tools
above. A =bash= tool would walk around every guarantee on this page — the
staged confirmations, the audit trail, the sensitive-field rules — in one
call.

The audit log is readable — "why did this number change" is a fair
question — but no tool can write it, whatever the policy. The trail is the
record of what the AI did; a model able to write it, even through an
approval, could launder its own history. The same refusal holds for every
human caller of the generic API: the audit system is the only writer.

Forge records are deliberately *not* on that list. The assistant can read and propose changes to forges, repositories and rules, because helping set the integration up is most of the work of using it — "add my Forgejo, point it at these three repositories, and run on bugs only" is a reasonable thing to ask for.

Three things make that safe rather than reckless:

- *Credentials cannot be written at all.* Sensitive fields are refused from any payload, so a token or webhook secret named in a tool call is ignored no matter who made the call. Setting one is a human in a browser, on the forge's own page.
- *Changes are staged.* Under the default =confirm_writes= policy a person approves each one, which is exactly the review a change to where this install sends its token deserves.
- *Approving respects the record's own role.* A forge is owner-only and a rule is admin-only on the REST API; approving a staged change to one requires the same. Without that, staging would launder the authorisation — an editor could ask for a change the API refuses them and then approve it.

An install running =policy: autonomous= has given the second of those away, for every type. That is the setting to weigh, not the type list.

Run records stay unwritable, like the audit log: nobody fills one out, and it is the record of what a runner did.

A coding agent is not the assistant. It runs on its own executor, in its own checkout, with no database tools at all. The in-process runner gets file tools VENTURE wrote that refuse any path resolving outside the checkout, and no shell; the CLI runner gets an empty executor and brings its own tools in a separate process. See [[file:forge.org][Git forges]].

* Why writes are staged

The default is =confirm_writes= because the failure mode it prevents is not a
UI annoyance. A model that misreads "the etsy fees were wrong last month" and
rewrites forty expense records has created a tax problem, and nothing
downstream would notice.

A mutating tool call therefore does not mutate. It builds the record with the
change already applied *in memory*, computes a field-by-field diff, and
returns a tool result that says plainly:

#+begin_src json
{
  "status": "awaiting_approval",
  "confirmation_id": "a3f9c118",
  "summary": "Update expense \"Cover art\"",
  "diff": { "amount": { "from": "250.00 USD", "to": "260.00 USD" } },
  "note": "Nothing has been changed yet. ..."
}
#+end_src

Approval applies the staged object, so approving cannot produce a different
outcome from the diff that was shown. The system prompt tells the model the
policy explicitly — a model that knows writes are staged behaves far better
than one that discovers it by having a call refused.

Deletion stages even under =autonomous=. Every other AI action produces a
value a person can eyeball afterwards; removing a record is the one where
noticing late is materially worse.

Staged changes expire after =ai.confirmation_ttl= seconds. One that has sat
unapproved for an hour almost certainly refers to a conversation the operator
has moved on from. An expired change is *removed* rather than marked: nothing
can be done with one, and a server left running would otherwise accumulate
every change nobody ever answered. At most =ai.confirmation_limit= may wait at
once; staging past that is refused.

** The queue is not the assistant's alone

A staged change lives in a queue on the context rather than inside the AI
service, and the REST API stages into the same one: =POST /api/v1/expense?stage=1=
mints a confirmation exactly as a tool call does. See
[[file:api.org][Staging a write]].

That is why the two settings above keep their =ai.= prefix while governing
changes the assistant had nothing to do with — they predate the sharing, and
renaming a configuration key to tidy up a prefix is not worth the install that
silently reverts to a default.

It also means an install running =ai.enabled: false= still has a working
confirmation queue, and =/api/v1/confirmations= answers rather than returning
an empty array. What is absent without AI is the assistant, not staging.

Approving applies the staged object through the same repository call an
ordinary write uses, so a stale approval is a =409= naming what changed
underneath rather than a silent overwrite. The rules are the same whoever
proposed the change, which is the point of there being one queue.

* Approving

In the AI panel, or over the API:

#+begin_src sh
curl -H "Authorization: Bearer $VENTURE_TOKEN" \
     localhost:8747/api/v1/confirmations

curl -X POST -H "Authorization: Bearer $VENTURE_TOKEN" \
     localhost:8747/api/v1/confirmations/a3f9c118/approve
#+end_src

Approving requires the editor role — exactly the authority an editor has, and
exactly what a viewer must not have.

* The audit trail

Every AI-originated mutation records the actor kind =ai=, the model, the diff,
and *the prompt that caused it*. That last field is why "why did this number
change" is answerable months later.

#+begin_src sh
venturectl list audit_entry actor_kind__eq=ai order=-occurred_at
#+end_src

A change that came out of the confirmation queue additionally records
=approved_by=, the person who let it through, and =request_id=, the
confirmation's own identifier. A direct write sets neither, so the three cases
are three different rows rather than three readings of one:

#+begin_src sh
# everything somebody approved, whoever proposed it
venturectl list audit_entry approved_by__not_null=1 order=-occurred_at
#+end_src

=actor= stays whoever *asked* — the model for an assistant change, the token's
account for an agent's. Collapsing the two parties into one field would lose
exactly the distinction the trail is for.

A rejection is audited too: knowing what the AI proposed and was denied is as
useful as knowing what it did.

* What the model is protected from

- Sensitive fields are withheld from tool results exactly as from an API
  response, so a password hash or tax identifier never enters its context.
- Query results are capped regardless of the requested limit; a model that
  asks for every row would blow its own context and learn nothing.
- Filters go through the same closed operator set as every other caller, so a
  hallucinated filter is an error message rather than SQL.
- An unknown record type or report returns the list of valid ones, turning a
  dead end into a usable next step.

* House rules

=ai.system_prompt_extra= is appended to the system prompt and is the cheapest
place to teach it your conventions:

#+begin_src yaml
ai:
  system_prompt_extra: >
    Amounts are US dollars unless stated otherwise. When asked about "the
    business", assume the default organization. Never modify an expense that
    has already been included in a filed tax report.
#+end_src

* Reconciliation

=venture_reconcile_suggest= takes =type=, =id=, optional =matcher= and
=threshold=. It ranks book matches and stages confirmations above the
threshold when =bank_match= exists. It never applies a match, even with
=autonomous= policy; under =read_only= it is not offered. The =ai= matcher
uses the separate tool-free completion path. See
[[file:reconciliation.org][reconciliation suggestions]].
