* What this is

The =dashboards= module lets you build pages. A dashboard is a named page with a grid of widgets; a widget is a small declarative question — "how many incidents are open", "the newest eight builds", "this month's profit and loss", "what is due in the next fortnight", "a note about how this team works" — answered from whatever record type or report it names. You can have as many dashboards as you like, one of them can be the home page, and each can be shared with everyone or kept to yourself.

Both the dashboard and its widgets are ordinary record types, so they get what every record type gets: a table, REST CRUD, an audit trail, =venturectl=, and the assistant's tools. What this module adds is the meaning of a widget: the catalogue of kinds, what each kind reads from a widget's settings, and one function that turns a widget into something to show — as HTML for the browser and as JSON for the API, from the same pass over the data, so the two cannot disagree.

The module requires only =core=. A widget can point at any module's records or reports; when that module is off the widget says so in its place and the rest of the page still works, and when it comes back on the widget answers again. Nothing about a dashboard needs to change when a module is switched.

* The pages

| Path                            | What it is                                                     |
|---------------------------------+----------------------------------------------------------------|
| =/dashboards=                   | every dashboard you may see, the templates, and the import box |

| =/dashboards/:slug/edit=        | the same page with its controls out, and the dashboard's settings |
| =/dashboards/:slug/widgets/new= | add a widget                                                   |
| =/dashboards/:slug/widgets/:id/edit= | change one                                                 |

| =/=                             | the dashboard marked as home, else the headline cards, else the built-in overview |

Every dashboard you may see is listed in the sidebar under *Views*, so a page you built is one click from anywhere.

A dashboard's slug is its address, made from the name when you leave it blank and normalised when you type one; two living dashboards cannot share one.

* Making one

Three ways, all on =/dashboards=.

*From a template.* Four ship: =factory= (the software factory at a glance — what is planned, building, shipping and running, the incidents open, the coding runs in flight, the knowledge and the actions beside them), =reporting= (month end: the P&L figures, revenue by venture, receivables, the pipeline, profit by month), =work= (your tickets, what is due, what is waiting for a decision), and =overview= (the built-in home page as widgets you can rearrange). A template is a definition in the export format, so what you get is exactly what an export of it would be, and you can change every widget afterwards.

*Empty*, with a name and a purpose, then add widgets.

*Imported*, from a definition somebody exported — pasted into the box, or with =venturectl dashboard import FILE=.

A dashboard has a *purpose* — overview, reporting or work — which changes nothing about what it may hold and is there so twenty views sort sensibly. It has a *layout* of one to four columns; narrow screens collapse every layout to one. *Home* puts it at =/=; only one dashboard is home, and marking one unmarks the rest. *Personal* keeps it to its owner: nobody else sees it in the list, the sidebar, or the API, and the page answers 404 rather than 403, so whether somebody else's page exists is not something a stranger can learn. A *venture* narrows every widget that can be narrowed to one venture — every list, count and breakdown on a type with a =venture_id= field.

* Widgets

Every widget has a kind, a title (or the kind supplies one), a width — one column, two, or the whole row — a position, and an optional refresh interval in seconds, on which the card reloads itself without the page. The rest of its settings are read by the kind, and the editor shows only the ones the chosen kind reads.

| Kind             | Shows                                                                          | Reads                                         |
|------------------+--------------------------------------------------------------------------------+-----------------------------------------------|
| =count=          | one figure: how many records of a type match a filter, optionally within a period on a date field | =entity_type=, =filter=, =period=, =field=    |
| =list=           | the newest few records of a type matching a filter, with the columns you choose, each linking to its page | =entity_type=, =filter=, =order=, =limit=, =columns= |
| =breakdown=      | counts per value of a field with a fixed set of values — tickets by status, deals by stage — as bars linking to their rows | =entity_type=, =field=, =filter=              |
| =upcoming=       | what is due within the next so many days on a date field, overdue first        | =entity_type=, =field=, =filter=, =limit=, =options= (={"days": 14}=) |
| =record=         | one record's fields                                                            | =entity_type=, =record_id=, =columns=         |
| =links=          | everything linked to one record, read from it                                  | =entity_type=, =record_id=                    |
| =metric=         | one headline figure from a report, with its change against the previous period | =report_name=, =period=, =field= (the metric's key; the first when blank) |
| =report=         | a whole report for a period: the tiles, the table, or both                     | =report_name=, =period=, =limit=, =options= (={"tiles": false}=, ={"table": false}=) |
| =chart=          | a report's rows as bars: one column for the labels, one for the lengths        | =report_name=, =period=, =field= (value column), =columns= (label column), =limit= |
| =activity=       | the latest changes from the audit trail, optionally for one record type        | =entity_type=, =limit=                        |
| =confirmations=  | staged changes waiting for a person                                            | =limit=                                       |
| =note=           | words: lines starting with =-= are bullets; paths and URLs become links        | =body=                                        |
| =actions=        | buttons, one per line as =Label | /path=                                       | =body=                                        |
| =search=         | a search box, for everything or for one type                                   | =entity_type=                                 |
| =environments=   | each environment and the release it is running now (needs =factory=)           | =filter=, =order=, =limit=                    |
| =milestone=      | one milestone's tickets done over planned; the soonest-due open one when no id is given (needs =factory=) | =record_id=                                   |

A *filter* is written exactly as on a list page's URL: =status=open&priority__in=high,urgent=. The same parser reads both, so what a widget shows is what that URL shows, and every count and list carries a link to its rows. Two placeholders are substituted for whoever is looking: ={me}= is their username and ={user_id}= their id, so a work dashboard's "my tickets" is =assignee={me}= and the same page answers for everyone who opens it. ={venture_id}= is the dashboard's venture.

An *order* is a field name, with a leading =-= for descending. A *period* is anything a report accepts: =this_month=, =last_30_days=, =ytd=, =2026-Q2=, =all_time=. *Columns* are field names in the wire spelling, comma separated; sensitive fields are never shown whatever was asked. *Options* are a JSON object, for the few settings a kind needs beyond these.

A widget's *scope* is the viewer's: the entity picked in the sidebar and everything beneath it, the same as every list and report. A widget never scopes itself, so the same widget on a page and in an API call answers about the same rows.

Every widget is checked at the save, whichever door it came through: the kind must exist, the record type must exist (even one whose module is off — the widget outlives the switch), the report must exist, the options must be a JSON object. A widget that cannot be answered when the page renders — a report that errored, a module that is off, a record that was deleted — says so in its place. One bad widget never takes the page down.

* The grid

A dashboard is a grid of one to four columns, and every widget sits on it at a column, a row, a width in columns and a height in rows. The four are the widget's =grid_col=, =grid_row=, =grid_width= and =grid_height=; zero means "wherever fits", which is how a template lays out without knowing the layout: a widget with no placement flows into the first free cells after the placed ones, in page order, wide ones taking the room their =span= asks for.

The layout is resolved on every render, and it is always a valid tiling whatever the rows say. A placed widget keeps its cells when they fit the layout and touch nothing placed before it; one that overlaps, or falls off the edge after the layout lost a column, is treated as unplaced and flows — nothing is ever drawn on top of anything, and nothing is ever lost.

*In the editor the grid is a canvas.* Pick a card up anywhere on it and it follows the pointer; a rectangle shows where it will land before you let go — blue where it will go, amber where it will trade places with the card already there, red where it will not fit. Drag the corner to resize, and the card grows as you drag rather than after. Let go and it stays; the page does not reload. Escape cancels a drag in flight and puts the card back.

Two cards of the same size trade places when you drop one on the other, which is the only way to rearrange a full page: a placement refuses a taken cell, and a tidy grid has no spare cell to move a card through. Different sizes are refused rather than guessed at — one of them would have to end up somewhere neither card asked for — so move the other card out of the way first.

This is a nicer way to reach the same endpoints, not a second set of rules. Every gesture ends in the POST a button sends, and the server has the last word: a drop onto cells another placed widget holds is refused with that widget named, never overlapped, and the card goes back where it was. Each card still has arrows to move it a cell at a time and =W±= / =H±= to resize it, revealed when the card is hovered or something in it has focus — plain forms, so the grid is editable from the keyboard and with scripting off. *Tidy* closes the gaps: every widget to the first free cell in page order, written down.

The rows are sized to their contents, so a row holding a list is taller than one holding a count. The editor measures where the columns and rows actually are rather than assuming they are all one size — assuming cost a card that landed in row 15 of a nine-row page.

Over the API the same rules hold. =PATCH /api/v1/dashboard_widget/:id= with the four fields sets a placement — the save checks the numbers are in range; whether it fits is decided when the page renders, because the layout can change afterwards. =POST /dashboards/:slug/widgets/:id/place= (=col=, =row=, and optionally =width=, =height=) is the checked version the editor uses: it answers 409 naming the widget in the way, or 422 when the block would not fit. =POST /dashboards/:slug/widgets/:id/move= with =direction= up, down, left, right, wider, narrower, taller or shorter nudges by one; =POST /dashboards/:slug/widgets/:id/swap= with =with== another widget's id exchanges their places in one transaction, refusing two of different sizes; =POST /dashboards/:slug/arrange= tidies. Every evaluated widget in =GET /api/v1/dashboards/:slug= carries its resolved place too.

On a narrow screen placement is set aside and the cards stack in layout order — and the editor will not start a drag there, because a position on a grid that has collapsed to one column means nothing.

* Export and import

=/dashboards/:slug/export= and =GET /api/v1/dashboards/:slug/export= write a definition: the dashboard's settings and each widget's, in the wire spelling, with no ids, owners or timestamps.

#+begin_src json
{
  "name": "Factory",
  "slug": "factory",
  "description": "From a ticket to a running release, and back.",
  "purpose": "work",
  "layout": "three_columns",
  "home": false,
  "personal": false,
  "position": 0,
  "widgets": [
    {"kind": "count", "title": "Open incidents", "entity_type": "incident",
     "filter": "status__in=open,mitigated", "span": "normal", ...},
    ...
  ]
}
#+end_src

It imports on any install through the box on =/dashboards=, =POST /api/v1/dashboards/import=, or =venturectl dashboard import FILE=. A taken slug gets a number suffixed, so importing the same file twice gives two dashboards rather than a refusal. Every widget is built and checked before anything is written, so a definition with one bad widget — an unknown kind, a misspelt setting, a type that does not exist — is refused as a whole and leaves nothing behind. Positions follow the file's order unless the file says otherwise.

Definitions are plain JSON, so they belong in git. A team's factory dashboard can live beside the code it watches.

* The API, the CLI, the assistant

| Method | Path                                   | Purpose                                              |
|--------+----------------------------------------+------------------------------------------------------|
| =GET=  | =/api/v1/dashboards=                   | every dashboard the caller may see, widgets unevaluated |
| =GET=  | =/api/v1/dashboards/:slug=             | one, every widget evaluated; =?data=0= to skip that; =?organization_id=N= to scope |
| =GET=  | =/api/v1/dashboards/:slug/export=      | the definition                                       |
| =POST= | =/api/v1/dashboards/import=            | a definition in the body                             |
| =POST= | =/api/v1/dashboards/from-template=     | ={"template": "factory"}=                            |
| =GET=  | =/api/v1/widget-kinds=                 | the catalogue: name, label, what it reads, whether its module is on |
| =GET=  | =/api/v1/dashboard-templates=          | the templates, definitions included                  |
| =*=    | =/api/v1/dashboard=, =/api/v1/dashboard_widget= | the generic record routes, like any type   |

Each evaluated widget carries its settings, its resolved title, its link, an =error= when it could not be answered, and =data= in a shape the kind decides — a count's ={"count": 3}=, a list's rows, a metric's figure and change, a breakdown's groups, a report's whole result.

#+begin_src sh
venturectl dashboards                    # what exists
venturectl dashboard factory             # every widget, evaluated, as a table
venturectl -f json dashboard factory     # the whole answer
venturectl dashboard export factory > factory.json
venturectl dashboard import factory.json
venturectl dashboard create work         # from a template
venturectl dashboard templates
venturectl dashboard kinds
#+end_src

Through =venturectl mcp=, an outside agent has =venture_dashboards= (=what=: =list=, =kinds= or =templates=), =venture_dashboard= (=mode=: =data=, =settings= or =definition=) and =venture_dashboard_build= (a template name or a definition). Building is refused while the MCP server stages writes — a whole page cannot wait in the queue — and the refusal says to start it with =--apply-writes= or to create the =dashboard= and each =dashboard_widget= with =venture_create=, which stage like any record. See [[file:mcp.org][venturectl mcp]].

The assistant has =venture_dashboard=: with a slug, every widget on that dashboard with what it shows right now; without one, the dashboards that exist. It reads shared dashboards only — a personal one belongs to a person — and reads them across every entity, as the assistant does everything. Ask it "what does the factory dashboard say" and it reads the page you built rather than guessing which queries you meant. Under the autonomous policy it also has =venture_dashboard_build=; under the default policy it builds a page record by record with =venture_create=, each staged for approval.

* Adding a widget kind

A plugin registers a kind the way it registers a report:

#+begin_src c
static VentureWidgetResult *
my_kind(VentureContext *context, VentureDashboardWidget *widget,
        const VentureWidgetScope *scope, gpointer user_data, GError **error)
{
	VentureWidgetResult *result;

	result = venture_widget_result_new();
	result->title = g_strdup("Weather");
	result->html = g_strdup("<p>Sunny</p>");
	result->data = json_node_new(JSON_NODE_NULL);
	result->link = g_strdup("/e/venture");
	return result;
}

static const gchar *const my_kind_uses[] = { "entity_type", "limit", NULL };

static const VentureWidgetKindInfo my_kind_info = {
	"weather", "Weather", "What the sky is doing over a venture",
	NULL, my_kind_uses, my_kind
};

venture_widget_kind_registry_add(venture_widget_kind_registry_get_default(),
                                 &my_kind_info, NULL, NULL, &error);
#+end_src

The registry is process-wide, like the entity registry, so a kind registered once is offered by every context. =uses= lists the widget fields the kind reads, in the wire spelling; the editor shows only those. A =module= makes the kind say "off" instead of rendering when that module is. The function reads what it needs from the widget, answers within the scope — the entities in =organization_ids=, the viewer's =username= for ={me}= — and fills both =html= and =data=; returning =NULL= with an error is a failure the page renders in place.

* Why it is shaped this way

*Settings are columns, not a blob.* A widget's record type, report, filter, order, limit and so on are plain fields on =dashboard_widget=. A column has a label, a help line and a form box for free; a JSON blob would need a hand-written form, which is the thing this codebase exists to avoid. The kind decides which columns mean something, and =options= exists for the two or three settings that do not deserve a column.

*The kind is a string, not an enum.* A plugin can add one without a change to the core, and the save validator refuses a kind nobody registered, so the freedom costs nothing.

*One function produces both renderings.* Every kind writes its JSON and its HTML from the same loop. Two implementations would be two answers, and the assistant reading one while the operator looks at the other is exactly the disagreement a dashboard exists to prevent.

*Rendering never fails.* =venture_dashboard_render_widget()= returns a result with an error in it rather than nothing. A page is a set of independent questions; a report that started failing yesterday should be a red card, not a blank page.

*The layout never fails.* A placement is a hint the editor keeps consistent, not an invariant the schema enforces: the resolver treats an impossible one as unplaced and flows it. A page that stopped rendering because someone shrank the layout from four columns to two, or PATCHed two widgets onto one cell, would be the wrong trade.

*A widget outlives a module switch.* The validator accepts a record type that exists but is hidden, so a factory dashboard built while the factory is on survives it being turned off and is whole again when it comes back. Refusing would mean a configuration change deleted somebody's page.

*One home, at the save.* "Only one dashboard is home" is enforced by the dashboard's save validator, which unmarks the others — a write from inside a validator, allowed because the lock is recursive. It is there rather than in the web handler so the API and an import behave the same.

* Planned activity sources

Use =entity_type=activity= with =list= or =count= and
=filter=status=planned&owner={me}=. The =upcoming= kind takes the same source
with =field=due_at= and =options={"days":14}=.
For current UTC day counts, use =kind=metric=, =report_name=worklist= and
=field=activities_overdue= or =field=activities_today=. A =report= widget
with =report_name=worklist= shows overdue, due today, due this week and
done this week per owner. These sources require the activities module.

* The headline cards

With the =headline= module on, =/= is the headline cards by default, one
per question in issue #75. A dashboard you have marked as *home* still wins,
as the table above says; the cards are what you get when you have not chosen
one. Each card is a number for the period, an arrow against the comparison
period, two to four lines of detail, the card's definition, and a link to
the report it was read from.

| Card          | Number                  | Beside it                                   | Report                     |
|---------------+-------------------------+---------------------------------------------+----------------------------|
| P&L           | profit                  | revenue, expenses, cash in the bank         | =pnl=                      |
| Recurring revenue | MRR (billing in use only) | ARR, quick ratio, net revenue retention | =mrr=                  |
| CAC           | cost per new customer   | acquisition spend, new customers            | =cac=                      |
| Churn         | logo churn (billing in use), else monthly activity churn | revenue churn and activity churn, or recurring churn, customers gone quiet and at risk | =churn= or =customer_churn= |
| LTV:CAC       | the ratio               | projected LTV, CAC, ARPA, CAC payback       | =ltv_cac=                  |
| Support       | support cost            | tickets open now, service levels missed, raised in period | =support_rollup=  |

Every number is defined exactly in [[file:reporting.org][Reporting]] and
[[file:billing.org][SaaS billing]]; each card carries a one-paragraph
version of its definition. In brief:

- *Profit* is the =pnl= report's net revenue (sales less refunds, platform
  fees and shipping cost) minus every expense dated in the period. *Cash in
  the bank* is the sum of every bank account's last statement balance ---
  what is actually in the account, beside what the books say was earned. It
  says =no statements= until one has been imported.
- *Billing in use* means the =billing= module is on and the organisation has
  at least one subscription event. Only then is there a recurring revenue
  card, and only then is churn read from subscriptions: an install with
  billing switched on but unused keeps activity churn rather than showing a
  subscription churn of nobody.
- *Recurring revenue* is contracted MRR at the period's end; ARR is twelve
  times MRR; the quick ratio is MRR gained (new, expansion, reactivation)
  over MRR lost (contraction, churn) in the period; net revenue retention is
  what the period's opening subscribers pay at its end, their expansion
  included, over what they paid at its start.
- *CAC* is acquisition spend (acquisition-flagged expenses and bill lines,
  and campaign spend pro-rated over each campaign) over new customers:
  companies whose first cash receipt fell in the period.
- *Churn*, with billing in use, is logo churn: companies paying for a
  subscription when the period opened and for none at its end, over those
  paying at its start; revenue churn is the MRR they lost, contraction
  included, over their opening MRR. Otherwise it is monthly activity churn:
  churn events in the trailing twelve months over customer-months at risk.
- *LTV:CAC* is projected LTV over CAC; *ARPA* is billing MRR per paying
  company, else cash per customer-month; *CAC payback* is CAC over ARPA times
  gross margin, in months.
- *Support* is what supporting customers cost in the period: the
  =support_rollup= report's total, agent minutes on the tickets raised in
  the period at the support hourly rate plus the per-ticket rate for
  tickets with no minutes, and =n/a= until a rate is set. Beneath it,
  tickets open now, those past a service level, and tickets raised in the
  period. With the tickets module off every figure is =n/a=: nobody
  counted, which is not the same as zero.

*The P&L card's cuts.* Beside its *Report* button the P&L card links to
the four cuts the =pnl_cuts= module adds --- revenue by customer, spend
by vendor, recurring costs and the cash outlook --- each with the card's
own period and scope, carried in the card's JSON as =links=, an array of
=label=/=href= pairs. With =pnl_cuts= off there are no links, since the
reports they would open are not there. They are described in
[[file:reporting.org][Reporting]].

*The period.* =?period== takes anything a report accepts, =this_month= by
default; the page offers the same period buttons as a report page. A period
that does not parse is shown as a notice above this month's cards rather
than dropping back to the old dashboard; the API refuses it.

*The arrow* compares the card's number with the same number for the
comparison period (=venture_date_range_comparison_period()=): up, down or
flat, coloured for whether up is good (profit, MRR, LTV:CAC) or bad (CAC,
churn, open tickets). A number that is =n/a= on either side has no arrow.

- A range of whole calendar months --- a month, a quarter, a year, a fiscal
  year --- is compared with the same number of months immediately before it,
  on the calendar and in the configured timezone: September with August,
  March with February, whatever their lengths and whether or not a
  daylight-saving change falls inside. Subtracting a length compared
  September with 2 August to 1 September.
- A range of whole days is compared with the same number of days before it.
- A range containing today is compared with the same elapsed part of the
  previous one, to the hour: on 3 September at ten, the first two days and
  ten hours of September against the first two days and ten hours of
  August. Comparing two days with a whole month put a red arrow on every
  card at the start of every month. The elapsed part is capped at the
  period's start, so 31 March compares with all of February.
- Month, quarter and year to date end tomorrow; they are compared with the
  smallest calendar unit that starts where they start and contains them.

The support card's arrow compares the period's support cost with the
comparison period's, and down is good. The queue --- tickets open now ---
is a line under it rather than the number, because "what is waiting" is a
live question and "what did March cost" is the one the card answers.

*Who sees the numbers.* The cards are organisation totals, so they are
computed only for a global owner or administrator, or a member holding the
owner, admin or finance role in the organisation
(=venture_access_policy_has_organization_role()=), and then computed over
every row of the organisation. Anybody else gets the same cards in a
=restricted= state with no figures: a total of only the rows a viewer's
record policy lets them read, presented as the organisation's, is a smaller
and wrong number that looks exactly like the right one.

*A card that fails* is an error card --- =n/a=, the message in its place,
and a warning in the log --- and every other card still renders. A page is
a set of independent questions.

*One pass.* =venture_headline_home_render()= writes every card as JSON, HTML
and CSV in the loop that computes it, so the page, the API and an export
cannot disagree. =GET /api/v1/headline?period=this_month= is the JSON; add
=format=csv= for one row per figure and per line (=card,metric,value,trend,state=);
=organization_id=, =venture_id= and =as_of= narrow it. Each card carries
=key=, =label=, =value=, =trend= (-1, 0, 1), =higher_is_better=, =link=,
=definition=, =state= (=ok=, =error= or =restricted=), =error= and =lines=.
Each card's =link= opens its report with the same =period=,
=organization_id= and, when given, =venture_id= and =as_of=. A line may
carry a =link= of its own, and the page renders its value as one.

*At risk.* With the =customer_health= module on, the churn card's last
line is *At risk: N* --- the number of customers banded red as of the
period's end, linking to the =customer_health= report for the same
period and organisation with =band=red=, the list of who they are and
why. With the module off the line is absent and the card is exactly as
before; a health report that fails costs the line (=n/a=), not the card.
See [[file:reporting.org][the customer health report]].

*Back to the old dashboard.* Save a =headline_setting= for the
organisation with =classic_home=true= (=venturectl create headline_setting
organization_id=1 classic_home=true=) and =/= is the built-in overview,
exactly as before. The cards are still at =/api/v1/headline= and the
reports on =/reports=. One living settings row per organisation; a second
is refused.
